SQL — Querying Data

Learn the language every relational database speaks — from simple reads to complex joins and aggregations.

What You Will Learn

  • SELECT basics — reading data from tables
  • Filtering with WHERE, AND, OR, NOT, LIKE, and ILIKE
  • INSERT, UPDATE, and DELETE — writing and modifying data
  • Sorting with ORDER BY and paginating with LIMIT/OFFSET
  • Aggregate functions: COUNT, SUM, AVG, MIN, MAX
  • GROUP BY and HAVING for summarizing data
  • JOINs — combining data from multiple tables
  • Subqueries for complex logic
  • CREATE TABLE and ALTER TABLE for schema management
  • NULL handling, soft deletes, and upsert patterns

SELECT — Reading Data

The SELECT statement is the most fundamental SQL command. It reads data from one or more tables.

Select All Columns

-- Get everything from the customers table
SELECT * FROM customers;

The * means "all columns." This is handy for exploration but in production code, you should list specific columns to avoid fetching data you do not need.

Select Specific Columns

-- Only get name and email
SELECT name, email FROM customers;

Column Aliases

-- Rename columns in the output
SELECT
  name AS customer_name,
  email AS contact_email
FROM customers;

WHERE — Filtering Results

The WHERE clause filters which rows are returned. Only rows that match the condition appear in the results.

Comparison Operators

OperatorMeaningExample
=Equal toWHERE status = 'published'
!= or <>Not equal toWHERE status != 'draft'
>Greater thanWHERE price > 100
>=Greater than or equalWHERE price >= 50
<Less thanWHERE quantity < 10
<=Less than or equalWHERE quantity <= 0
 
-- Find all published blog posts
SELECT title, published_at
FROM blog_posts
WHERE status = 'published';

-- Find computers priced over $500
SELECT name, price
FROM gallery_computers
WHERE price > 500;

AND, OR, NOT

-- Multiple conditions must ALL be true
SELECT * FROM blog_posts
WHERE status = 'published'
  AND category_id IS NOT NULL;

-- At least ONE condition must be true
SELECT * FROM tickets
WHERE status = 'new'
   OR status = 'in_progress';

-- Negate a condition
SELECT * FROM customers
WHERE NOT is_active;

IN — Multiple Values

-- Shorthand for multiple OR conditions
SELECT * FROM tickets
WHERE status IN ('new', 'in_progress', 'waiting_for_parts');

-- Equivalent to:
-- WHERE status = 'new' OR status = 'in_progress' OR status = 'waiting_for_parts'

BETWEEN

-- Range check (inclusive on both ends)
SELECT * FROM invoices
WHERE amount BETWEEN 50 AND 500;

-- Date ranges
SELECT * FROM blog_posts
WHERE published_at BETWEEN '2026-01-01' AND '2026-01-31';

String Matching: LIKE and ILIKE

LIKE performs pattern matching. ILIKE is the case-insensitive version (PostgreSQL-specific).

PatternMatches
%Any number of characters (including zero)
_Exactly one character
 
-- Names starting with "J"
SELECT * FROM customers
WHERE name LIKE 'J%';

-- Emails containing "gmail" (case-insensitive)
SELECT * FROM customers
WHERE email ILIKE '%gmail%';

-- Names that are exactly 4 characters
SELECT * FROM customers
WHERE name LIKE '____';

INSERT — Adding Data

-- Insert a single row
INSERT INTO customers (name, email)
VALUES ('Jane Smith', 'jane@example.com');

-- Insert multiple rows at once
INSERT INTO blog_tags (name, slug)
VALUES
  ('Windows', 'windows'),
  ('Linux', 'linux'),
  ('Hardware', 'hardware');

-- Insert and return the created row
INSERT INTO blog_posts (title, slug, content, author_name, status)
VALUES ('My First Post', 'my-first-post', 'Hello world!', 'Matthew', 'draft')
RETURNING *;

The RETURNING * clause is a PostgreSQL feature that returns the inserted row, including any auto-generated values like id and created_at. Very useful in application code.

UPDATE — Modifying Data

-- Update a specific row
UPDATE blog_posts
SET status = 'published',
    published_at = NOW()
WHERE id = 'abc123-...';

-- Update multiple rows
UPDATE tickets
SET status = 'resolved'
WHERE status = 'ready_for_pickup'
  AND created_at < '2026-01-01';
Always include a WHERE clause with UPDATE! Running UPDATE customers SET is_active = false; without a WHERE will set every single customer to inactive. This is one of the most common and devastating SQL mistakes. Always double-check your WHERE clause before running an UPDATE or DELETE.

DELETE — Removing Data

-- Delete a specific row
DELETE FROM blog_post_tags
WHERE post_id = 'abc123-...' AND tag_id = 'def456-...';

-- Delete all expired sessions
DELETE FROM sessions
WHERE expires_at < NOW();

Why Soft Deletes Are Better

In most production applications, you never truly delete data. Instead, you mark it as inactive or archived. This is called a soft delete.

Analogy: When you "delete" an email, it goes to the Trash folder first. You can recover it. Only when you empty the Trash is it truly gone. Soft deletes work the same way — data is marked as removed but can be recovered.

There are two common patterns:

-- Pattern 1: Boolean flag
-- Add an is_active column (default true)
UPDATE gallery_computers
SET is_active = false,
    archived_at = NOW()
WHERE id = 'abc123-...';

-- Only show active items
SELECT * FROM gallery_computers WHERE is_active = true;

-- Pattern 2: Timestamp
-- NULL means active, a date means "deleted at this time"
UPDATE tickets
SET archived_at = NOW()
WHERE id = 'abc123-...';

-- Only show non-archived
SELECT * FROM tickets WHERE archived_at IS NULL;
CSK Connection CSK uses soft deletes for gallery computers. The deleteComputer() function in src/lib/supabase.ts does not actually DELETE the row — it sets is_active = false and records an archived_at timestamp. There is a separate hardDeleteComputer() for permanent removal and a restoreComputer() to undo a soft delete.

ORDER BY, LIMIT, and OFFSET

Sorting Results

-- Sort alphabetically by name (ascending is default)
SELECT * FROM customers ORDER BY name;

-- Sort by newest first (descending)
SELECT * FROM blog_posts ORDER BY published_at DESC;

-- Sort by multiple columns
SELECT * FROM tickets
ORDER BY status ASC, created_at DESC;

Pagination with LIMIT and OFFSET

When you have thousands of rows, you do not want to return them all at once. LIMIT restricts how many rows are returned. OFFSET skips a number of rows before starting to return results.

-- First page: 10 items
SELECT * FROM blog_posts
WHERE status = 'published'
ORDER BY published_at DESC
LIMIT 10;

-- Second page: skip the first 10, get the next 10
SELECT * FROM blog_posts
WHERE status = 'published'
ORDER BY published_at DESC
LIMIT 10 OFFSET 10;

-- Third page
LIMIT 10 OFFSET 20;

Formula: OFFSET = (page_number - 1) * page_size

OFFSET Performance Warning Large OFFSET values are slow because the database still reads and skips all those rows. For high-performance pagination on large tables, consider cursor-based pagination (using WHERE clauses with the last seen value) instead of OFFSET.

Aggregate Functions

Aggregate functions calculate a single result from multiple rows.

FunctionWhat It DoesExample
COUNT(*)Counts rowsSELECT COUNT(*) FROM customers;
COUNT(column)Counts non-NULL valuesSELECT COUNT(email) FROM customers;
SUM(column)Adds up all valuesSELECT SUM(amount) FROM invoices;
AVG(column)Calculates the averageSELECT AVG(price) FROM gallery_computers;
MIN(column)Finds the smallest valueSELECT MIN(price) FROM gallery_computers;
MAX(column)Finds the largest valueSELECT MAX(price) FROM gallery_computers;
 
-- How many published posts?
SELECT COUNT(*) FROM blog_posts WHERE status = 'published';

-- Total revenue from paid invoices
SELECT SUM(amount) AS total_revenue
FROM invoices
WHERE paid_at IS NOT NULL;

-- Average computer price
SELECT AVG(price) AS avg_price FROM gallery_computers WHERE is_active = true;

-- Price range
SELECT
  MIN(price) AS cheapest,
  MAX(price) AS most_expensive,
  AVG(price) AS average_price
FROM gallery_computers
WHERE is_active = true;

GROUP BY and HAVING

GROUP BY splits rows into groups based on column values, then lets you run aggregate functions on each group.

-- How many tickets does each customer have?
SELECT
  customer_id,
  COUNT(*) AS ticket_count
FROM tickets
GROUP BY customer_id;

-- How many posts in each category?
SELECT
  c.name AS category_name,
  COUNT(p.id) AS post_count
FROM blog_categories c
LEFT JOIN blog_posts p ON p.category_id = c.id
GROUP BY c.name
ORDER BY post_count DESC;

HAVING — Filtering Groups

WHERE filters individual rows before grouping. HAVING filters groups after grouping.

-- Find customers with more than 5 tickets
SELECT
  customer_id,
  COUNT(*) AS ticket_count
FROM tickets
GROUP BY customer_id
HAVING COUNT(*) > 5;

-- Find categories with at least 3 published posts
SELECT
  c.name,
  COUNT(p.id) AS post_count
FROM blog_categories c
JOIN blog_posts p ON p.category_id = c.id
WHERE p.status = 'published'      -- WHERE filters rows BEFORE grouping
GROUP BY c.name
HAVING COUNT(p.id) >= 3           -- HAVING filters groups AFTER grouping
ORDER BY post_count DESC;

JOINs — Combining Tables

JOINs are how you combine data from two or more related tables in a single query. This is the real power of relational databases.

INNER JOIN

Returns only rows where there is a match in both tables. If a row in either table has no match, it is excluded.

INNER JOIN: Only matching rows from both sides customers tickets +-------+--------+ +-------+---------+-------------+ | id | name | | id | subject | customer_id | +-------+--------+ +-------+---------+-------------+ | uuid1 | Jane | --- | tkt-1 | Screen | uuid1 | Match! | uuid2 | Bob | --- | tkt-2 | Virus | uuid2 | Match! | uuid3 | Sue | | tkt-3 | Slow PC | uuid1 | Match! +-------+--------+ +-------+---------+-------------+ Result: Jane + Screen, Bob + Virus, Jane + Slow PC Sue is EXCLUDED (no tickets) 
SELECT
  c.name AS customer_name,
  t.subject AS ticket_subject,
  t.status
FROM customers c
INNER JOIN tickets t ON t.customer_id = c.id;

LEFT JOIN (LEFT OUTER JOIN)

Returns all rows from the left table, and matching rows from the right table. If there is no match, the right side columns are NULL.

LEFT JOIN: All rows from left, matching from right customers (LEFT) tickets (RIGHT) +-------+--------+ +-------+---------+-------------+ | id | name | | id | subject | customer_id | +-------+--------+ +-------+---------+-------------+ | uuid1 | Jane | --- | tkt-1 | Screen | uuid1 | Match! | uuid2 | Bob | --- | tkt-2 | Virus | uuid2 | Match! | uuid3 | Sue | | | No match +-------+--------+ +-------+---------+-------------+ Result: Jane + Screen, Bob + Virus, Jane + Slow PC, Sue + NULL Sue is INCLUDED (with NULL ticket data) 
-- Show ALL customers and their tickets (even if they have none)
SELECT
  c.name AS customer_name,
  t.subject AS ticket_subject
FROM customers c
LEFT JOIN tickets t ON t.customer_id = c.id;

-- Find customers with NO tickets
SELECT c.name
FROM customers c
LEFT JOIN tickets t ON t.customer_id = c.id
WHERE t.id IS NULL;

RIGHT JOIN (RIGHT OUTER JOIN)

The mirror of LEFT JOIN: returns all rows from the right table and matching rows from the left. In practice, you can always rewrite a RIGHT JOIN as a LEFT JOIN by swapping the table order, so RIGHT JOINs are rarely used.

Joining Multiple Tables

-- Get blog posts with their category name and all tag names
SELECT
  p.title,
  c.name AS category,
  t.name AS tag
FROM blog_posts p
LEFT JOIN blog_categories c ON c.id = p.category_id
LEFT JOIN blog_post_tags pt ON pt.post_id = p.id
LEFT JOIN blog_tags t ON t.id = pt.tag_id
WHERE p.status = 'published'
ORDER BY p.published_at DESC;
CSK Connection In src/lib/supabase.ts, the getPublishedPosts() function uses Supabase's .select('*, category:blog_categories(*)') which generates a LEFT JOIN behind the scenes. Tags are fetched separately via the blog_post_tags junction table. Understanding JOINs helps you know what Supabase is doing for you under the hood.

Subqueries

A subquery is a query nested inside another query. It runs first, and its result is used by the outer query.

-- Find posts that have the tag "Linux"
SELECT * FROM blog_posts
WHERE id IN (
  SELECT post_id FROM blog_post_tags
  WHERE tag_id = (
    SELECT id FROM blog_tags WHERE slug = 'linux'
  )
);

-- Find customers who have spent more than the average
SELECT name, email FROM customers
WHERE id IN (
  SELECT customer_id FROM invoices
  GROUP BY customer_id
  HAVING SUM(amount) > (SELECT AVG(amount) FROM invoices)
);

While powerful, subqueries can sometimes be rewritten as JOINs for better readability and performance. Use whichever is clearer.

CREATE TABLE and ALTER TABLE

Creating Tables

We covered the basics in Lesson 23, but here is the full syntax with all common options:

CREATE TABLE IF NOT EXISTS blog_categories (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  name VARCHAR(100) NOT NULL UNIQUE,
  slug VARCHAR(100) NOT NULL UNIQUE,
  description TEXT,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

IF NOT EXISTS prevents errors if the table already exists — useful in migration scripts that might run multiple times.

Altering Tables

As your application evolves, you will need to modify existing tables.

-- Add a new column
ALTER TABLE rs_customers
  ADD COLUMN IF NOT EXISTS business_id INTEGER REFERENCES businesses(id);

-- Change a column's type
ALTER TABLE products
  ALTER COLUMN price TYPE NUMERIC(10, 2);

-- Add a constraint after the fact
ALTER TABLE blog_posts
  ADD CONSTRAINT check_status
  CHECK (status IN ('draft', 'published', 'archived'));

-- Rename a column
ALTER TABLE customers
  RENAME COLUMN phone TO phone_number;

-- Drop a column (careful!)
ALTER TABLE customers
  DROP COLUMN IF EXISTS legacy_field;
CSK Connection CSK's migration files in docs/database/ are full of real ALTER TABLE statements. For example, businesses-table-migration.sql adds a business_id column to the existing rs_customers table. assets-updated-migration.sql adds the assets_updated boolean flag. These are raw SQL scripts that show how production schemas evolve over time.

NULL Handling

NULL in SQL means "unknown" or "no value." It is not the same as zero, empty string, or false. NULL requires special handling because any comparison with NULL returns NULL (not true or false).

-- WRONG: This will NOT find null values!
SELECT * FROM blog_posts WHERE published_at = NULL;  -- Always returns 0 rows!

-- CORRECT: Use IS NULL / IS NOT NULL
SELECT * FROM blog_posts WHERE published_at IS NULL;      -- Drafts (never published)
SELECT * FROM blog_posts WHERE published_at IS NOT NULL;  -- Published posts

COALESCE — Default for NULL

COALESCE returns the first non-NULL value from its arguments. Use it to provide fallback values.

-- If excerpt is NULL, use the first 100 characters of content
SELECT
  title,
  COALESCE(excerpt, LEFT(content, 100)) AS preview
FROM blog_posts;

-- If category name is NULL (no category), show "Uncategorized"
SELECT
  p.title,
  COALESCE(c.name, 'Uncategorized') AS category
FROM blog_posts p
LEFT JOIN blog_categories c ON c.id = p.category_id;

Common SQL Patterns

Upsert: INSERT ON CONFLICT

An "upsert" inserts a row if it does not exist, or updates it if it does. This is extremely useful for syncing data.

-- Insert a tag, or do nothing if the slug already exists
INSERT INTO blog_tags (name, slug)
VALUES ('Windows', 'windows')
ON CONFLICT (slug) DO NOTHING;

-- Insert or update a ticket status override
INSERT INTO ticket_status_overrides (repairshopr_ticket_id, custom_status, updated_at)
VALUES (12345, 'diagnosing', NOW())
ON CONFLICT (repairshopr_ticket_id)
DO UPDATE SET
  custom_status = EXCLUDED.custom_status,
  updated_at = EXCLUDED.updated_at;

EXCLUDED refers to the row that was attempted to be inserted. This pattern is used extensively in data synchronization.

CSK Connection CSK uses upserts throughout. The setTicketStatusOverride() function uses Supabase's .upsert() method (which generates INSERT ON CONFLICT). The blog schema seeds default categories and tags with ON CONFLICT (slug) DO NOTHING to safely re-run the migration.

Counting with Conditions

-- Count different statuses in one query
SELECT
  COUNT(*) AS total,
  COUNT(*) FILTER (WHERE status = 'published') AS published,
  COUNT(*) FILTER (WHERE status = 'draft') AS drafts,
  COUNT(*) FILTER (WHERE status = 'archived') AS archived
FROM blog_posts;

Checking Existence

-- Does this slug already exist?
SELECT EXISTS (
  SELECT 1 FROM blog_posts WHERE slug = 'my-first-post'
) AS slug_taken;

Complete Query Examples

Here are some realistic queries that combine multiple concepts:

-- 1. Published blog posts with categories, sorted by date, paginated
SELECT
  p.id,
  p.title,
  p.slug,
  p.excerpt,
  p.published_at,
  c.name AS category_name
FROM blog_posts p
LEFT JOIN blog_categories c ON c.id = p.category_id
WHERE p.status = 'published'
ORDER BY p.published_at DESC
LIMIT 10 OFFSET 0;

-- 2. Customer summary: name, total tickets, total spent
SELECT
  c.name,
  c.email,
  COUNT(DISTINCT t.id) AS ticket_count,
  COALESCE(SUM(i.amount), 0) AS total_spent
FROM customers c
LEFT JOIN tickets t ON t.customer_id = c.id
LEFT JOIN invoices i ON i.customer_id = c.id AND i.paid_at IS NOT NULL
GROUP BY c.id, c.name, c.email
ORDER BY total_spent DESC
LIMIT 20;

-- 3. Find all posts tagged with either "linux" or "hardware"
SELECT DISTINCT p.title, p.slug
FROM blog_posts p
JOIN blog_post_tags pt ON pt.post_id = p.id
JOIN blog_tags t ON t.id = pt.tag_id
WHERE t.slug IN ('linux', 'hardware')
  AND p.status = 'published'
ORDER BY p.published_at DESC;

Hands-On Exercises

  1. Basic SELECT: Write a query to get the title and status of all blog posts, sorted by created_at (newest first).
  2. Filtering: Write a query to find all customers whose email ends with @gmail.com (case-insensitive) and who are active.
  3. INSERT and RETURNING: Write an INSERT statement to add a new blog category called "Tutorials" with slug "tutorials" and description "Step-by-step guides for common tasks." Return the created row.
  4. Safe UPDATE: Write an UPDATE that publishes a blog post (sets status to 'published' and published_at to NOW()) but ONLY if the post is currently in 'draft' status. Target a specific post by its slug.
  5. Aggregation: Write a query that shows each ticket status and how many tickets have that status, sorted by count descending.
  6. JOIN Challenge: Write a query that shows all blog categories and the number of published posts in each category. Include categories that have zero published posts. Sort by post count descending.
  7. Upsert: Write an INSERT ON CONFLICT statement that inserts a customer protection plan record. If the customer already has a record, update the plan_tier and updated_at instead.
  8. Soft Delete: Design a soft delete mechanism for a products table. Write the ALTER TABLE to add the necessary columns, the "delete" UPDATE statement, and a SELECT that only shows non-deleted products.

Key Takeaways

  • SELECT reads data; always specify columns in production code instead of using *.
  • WHERE filters rows with comparison operators, AND/OR/NOT, IN, BETWEEN, LIKE/ILIKE.
  • INSERT adds rows; UPDATE modifies them; DELETE removes them — always use WHERE with UPDATE and DELETE.
  • ORDER BY sorts results; LIMIT/OFFSET handles pagination.
  • Aggregate functions (COUNT, SUM, AVG, MIN, MAX) summarize data across rows.
  • GROUP BY creates groups for aggregation; HAVING filters groups after aggregation.
  • INNER JOIN returns only matching rows; LEFT JOIN returns all left rows plus matches.
  • Use IS NULL / IS NOT NULL (never = NULL); use COALESCE for fallback values.
  • Soft deletes (boolean flag or timestamp) are safer than hard deletes in production.
  • Upserts (INSERT ON CONFLICT) insert or update in a single atomic operation.
