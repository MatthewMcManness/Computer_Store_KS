Development Mode vs. Production Mode

Throughout this curriculum, you have been running your Next.js application with npm run dev. That command starts the application in development mode, which is optimized for the developer experience. Production mode is a completely different beast, optimized for the user experience.

Feature Development (npm run dev) Production (npm run build + npm run start)
Speed priority Fast refresh (instant code changes) Fast page loads for users
Error messages Detailed, with source maps and stack traces Generic (no internal details exposed)
Code optimization None (unminified, uncompressed) Full (minified, tree-shaken, compressed)
Caching Disabled (every refresh shows latest code) Aggressive (pages cached for performance)
Bundle size Large (includes dev tools, source maps) Small (stripped to essentials)
TypeScript Loose checking (does not block page loads) Strict checking (errors can block the build)
Hot Module Replacement Yes (code updates without full refresh) No (not needed in production)
Analogy: Development mode is like rehearsing a play. The lights are on, the director is shouting notes, actors can stop and restart scenes, and the script is still being revised. Production mode is opening night: the house lights are off, the audience is watching, and everything must run smoothly from start to finish. The same play, but the experience is completely different.

You would never deploy development mode to production. The JavaScript bundles are 5-10x larger, error messages leak internal implementation details, and there is zero optimization. The build process transforms your development code into a production-ready application.

What npm run build Does

When you run npm run build, Next.js performs a multi-step compilation process. Understanding each step helps you diagnose problems when builds fail.

Step 1: TypeScript Compilation

Next.js reads your tsconfig.json and compiles all .ts and .tsx files to JavaScript. If your TypeScript has errors (missing types, incorrect assignments, unused variables with strict mode enabled), the build will fail here.

# TypeScript build error example:
Type error: Property 'name' does not exist on type '{}'.

  12 |   const user = {};
  13 |   return (
> 14 |     <h1>{user.name}</h1>
     |               ^
  15 |   );
  16 | }

Step 2: ESLint Validation

Next.js runs ESLint on your code to catch potential bugs and enforce code quality rules. Lint errors can block the build depending on your configuration.

Step 3: Route Analysis and Page Rendering

Next.js analyzes every route in your src/app/ directory and determines how each page should be rendered. It categorizes pages as either static or dynamic:

Type Symbol in Build Output When Rendered Use Case
Static ○ (circle) At build time (HTML generated once) About page, landing pages, blog posts
Dynamic λ (lambda) At request time (HTML generated per request) Dashboard, search results, user-specific pages

Static pages are pre-rendered into HTML files during the build. They load instantly because the server just sends a file. Dynamic pages run server-side code on every request, which is slower but necessary for personalized or real-time content.

Step 4: JavaScript Bundling and Optimization

Next.js uses webpack (a JavaScript bundler) to combine, optimize, and split your JavaScript code:

  • Minification: Variable names are shortened (userAuthenticationStatus becomes a), whitespace is removed, and comments are stripped. This reduces file size dramatically.
  • Tree shaking: Unused code is removed. If you import a utility library but only use one function, the rest of the library is excluded from the bundle.
  • Code splitting: Instead of one massive JavaScript file, Next.js creates separate bundles for each route. When a user visits /about, they only download the JavaScript for the About page, not the entire application.
  • Compression: Files are compressed with gzip or Brotli, reducing download size by 60-80%.

Step 5: Asset Optimization

Images referenced via the next/image component are optimized for different screen sizes. CSS is extracted and optimized. Fonts loaded via next/font are self-hosted and preloaded.

The .next/ Build Output Directory

Everything the build produces goes into the .next/ directory at the root of your project. This directory is created fresh on every build. It is listed in .gitignore and should never be committed to Git.

.next/
├── cache/                 # Build cache for faster subsequent builds
├── server/                # Server-side rendered pages and API routes
│   ├── app/              # Compiled app router pages
│   ├── chunks/           # Server-side code chunks
│   └── pages/            # Compiled pages router (if used)
├── static/                # Client-side static assets
│   ├── chunks/           # JavaScript bundles for the browser
│   ├── css/              # Compiled CSS files
│   └── media/            # Optimized images and fonts
├── standalone/            # Self-contained server (if output: 'standalone')
│   ├── server.js         # Minimal Node.js server
│   ├── node_modules/     # Only the dependencies needed to run
│   └── .next/            # Nested build output
├── BUILD_ID              # Unique identifier for this build
├── build-manifest.json   # Maps routes to their JavaScript bundles
└── routes-manifest.json  # All routes and their configurations
Build Cache The .next/cache/ directory stores results from previous builds. On subsequent builds, Next.js can skip work that has not changed, making builds significantly faster. If you are experiencing strange build issues, deleting the .next/ directory forces a completely fresh build.

Static vs. Dynamic Pages in Build Output

Understanding the difference between static and dynamic pages is crucial for performance optimization and deployment.

Static Pages

A page is statically generated when Next.js can render it completely at build time. The resulting HTML is saved as a file and served directly -- no server-side computation needed on each request.

Pages are static when they:

  • Do not use cookies(), headers(), or searchParams
  • Do not make uncached fetch() calls
  • Do not use export const dynamic = 'force-dynamic'
  • Only depend on data available at build time
// This page is STATIC -- it can be fully rendered at build time
export default function AboutPage() {
  return (
    <main>
      <h1>About Us</h1>
      <p>We have been repairing computers since 2010.</p>
    </main>
  );
}

Dynamic Pages

A page is dynamically rendered when it depends on information that is only available at request time -- like cookies (for authentication), URL search parameters, or real-time database queries.

// This page is DYNAMIC -- it reads cookies at request time
import { cookies } from 'next/headers';

export default async function AdminDashboard() {
  const cookieStore = cookies();
  const session = cookieStore.get('session');

  // This data changes per request
  const tickets = await getTicketsByUser(session?.value);

  return (
    <main>
      <h1>Dashboard</h1>
      <p>You have {tickets.length} open tickets.</p>
    </main>
  );
}

Static pages are faster and cheaper to serve. Dynamic pages are more flexible. The goal is to make as many pages static as possible and only use dynamic rendering when truly necessary.

Standalone Output Mode

By default, a Next.js build produces output that depends on the entire node_modules/ directory (which can be hundreds of megabytes). This is impractical for deployment because you would need to upload all those dependencies alongside your application.

Standalone output mode solves this by creating a self-contained server that includes only the files and dependencies needed to run. Instead of a 500 MB node_modules/ directory, you get a lean package that can be started with a single command.

Enabling Standalone Mode

// next.config.mjs
/** @type {import('next').NextConfig} */
const nextConfig = {
  output: 'standalone',
};

export default nextConfig;

With this setting, npm run build creates a .next/standalone/ directory containing:

.next/standalone/
├── server.js              # Minimal Node.js server (start with: node server.js)
├── node_modules/          # Only required runtime dependencies
├── package.json           # Minimal package.json
└── .next/                 # Build output (server pages, etc.)
    └── ...

Why Standalone Matters for Deployment

Aspect Default Output Standalone Output
Size Entire node_modules/ (200-500 MB) Only needed deps (20-50 MB)
Start command npm run start (needs package.json scripts) node server.js (self-contained)
Deployment Must install all dependencies on server Copy directory and run
Docker image Large image Minimal image
Important: Static Files Are Not Included The standalone output does not include the public/ directory or the .next/static/ directory. You need to copy these manually after the build. This is why the CSK build command includes extra copy steps.
CSK Connection The CSK next.config.mjs sets output: 'standalone'. The Render build command then copies the required files into the standalone directory: npm install && npm run build && cp -r .next/static .next/standalone/.next/static && rm -rf .next/standalone/public && cp -R public .next/standalone/ && cp -r node_modules .next/standalone/ && cp package.json .next/standalone/. The start command runs the standalone server: cd .next/standalone && node server.js.

Configuring next.config.mjs

The next.config.mjs file (or next.config.js) is where you configure how Next.js builds and runs your application. The .mjs extension means it uses ES module syntax (import/export).

Key Configuration Options

// next.config.mjs
import path from 'path';
import { fileURLToPath } from 'url';

const __filename = fileURLToPath(import.meta.url);
const __dirname = path.dirname(__filename);

/** @type {import('next').NextConfig} */
const nextConfig = {
  // ---- DEPLOYMENT ----
  output: 'standalone',           // Self-contained server for deployment

  // ---- TYPESCRIPT ----
  typescript: {
    ignoreBuildErrors: true,      // Don't block builds on TS errors
  },

  // ---- ESLINT ----
  eslint: {
    ignoreDuringBuilds: true,     // Don't block builds on lint errors
  },

  // ---- WEBPACK CUSTOMIZATION ----
  webpack: (config, { isServer }) => {
    // Add @ path alias (import from '@/components/...')
    config.resolve.alias = {
      ...config.resolve.alias,
      '@': path.resolve(__dirname, './src'),
    };

    // Ensure TypeScript extensions are resolved
    const extensions = ['.tsx', '.ts', '.jsx', '.js', '.json'];
    extensions.forEach(ext => {
      if (!config.resolve.extensions.includes(ext)) {
        config.resolve.extensions.push(ext);
      }
    });

    return config;
  },

  // ---- IMAGE OPTIMIZATION ----
  images: {
    remotePatterns: [
      {
        protocol: 'https',
        hostname: '**',           // Allow images from any HTTPS source
      },
    ],
  },

  // ---- EXPERIMENTAL FEATURES ----
  experimental: {
    optimizePackageImports: ['lucide-react'],  // Tree-shake icon library
    serverActions: {
      bodySizeLimit: '100mb',     // Allow large file uploads
    },
  },

  // ---- SECURITY HEADERS ----
  async headers() {
    return [
      {
        source: '/(.*)',
        headers: [
          { key: 'X-Content-Type-Options', value: 'nosniff' },
          { key: 'X-Frame-Options', value: 'DENY' },
          { key: 'Referrer-Policy', value: 'origin-when-cross-origin' },
        ],
      },
    ];
  },
};

export default nextConfig;

Understanding the Webpack Configuration

Webpack is the module bundler that Next.js uses internally. It takes your many source files and combines them into optimized bundles for the browser. Most of the time, you do not need to configure webpack directly because Next.js handles it automatically. But there are cases where custom configuration is necessary:

  • Path aliases: The @ alias lets you write import { Button } from '@/components/ui/button' instead of import { Button } from '../../../components/ui/button'. The webpack alias configuration makes this work at build time.
  • Extension resolution: Telling webpack which file extensions to look for means you can write import { utils } from '@/lib/utils' without specifying .ts.
  • Custom loaders: If you need to import file types that webpack does not handle by default (like SVGs as React components or markdown files).

TypeScript and ESLint Build Behavior

The ignoreBuildErrors and ignoreDuringBuilds options are controversial. In a perfect world, you would want builds to fail on TypeScript and ESLint errors so that broken code never reaches production. However, in practice, especially during active development:

  • Some TypeScript errors are in code that does not affect functionality
  • Strict lint rules can block deployments for cosmetic issues
  • You may want to run type checking and linting as separate CI steps
CSK Connection The CSK next.config.mjs sets both ignoreBuildErrors and ignoreDuringBuilds to true. TypeScript and ESLint checks are handled separately in the development workflow rather than blocking production builds. The webpack configuration adds the @/ path alias and ensures proper TypeScript extension resolution, which is critical for the Render build environment.

Common Build Errors and How to Fix Them

Build failures are one of the most common frustrations in web development. Here are the errors you will encounter most often and how to resolve them.

TypeScript Errors

# Error:
Type error: Argument of type 'string | undefined' is not assignable
to parameter of type 'string'.

# Fix: Add a null check or non-null assertion
const value = process.env.API_KEY!;     // assertion
const value = process.env.API_KEY ?? ''; // fallback

Missing Imports

# Error:
Module not found: Can't resolve '@/components/Header'

# Fix: Check the file exists and the path is correct
# Verify the @ alias is configured in next.config.mjs and tsconfig.json

Client/Server Mismatch

# Error:
You're importing a component that needs useState. It only works in a
Client Component but none of its parents are marked with "use client".

# Fix: Add 'use client' directive at the top of the file
'use client';
import { useState } from 'react';

Build Error Debugging Checklist

Error Type Common Cause Fix
Type error TypeScript type mismatch Fix the type or add assertion
Module not found Missing dependency or wrong path Run npm install or fix import path
ESLint error Code quality rule violation Fix the code or configure the rule
Hydration mismatch Server and client HTML differ Ensure consistent rendering
Out of memory Large project, limited RAM Increase Node memory: NODE_OPTIONS=--max-old-space-size=4096
Dynamic server usage Using cookies/headers in static page Mark page as dynamic or restructure
The Nuclear Option: Clean Build If you are stuck with a mysterious build error, delete the build cache and dependencies and start fresh: rm -rf .next node_modules && npm install && npm run build. This solves a surprising number of problems caused by stale caches or corrupted dependencies.

Build Optimization Techniques

Tree Shaking

Tree shaking is the process of removing unused code from your bundles. The name comes from imagining a tree of code dependencies -- if you shake the tree, the dead branches (unused code) fall off.

// utils.ts exports 10 functions
export function formatDate() { /* ... */ }
export function formatCurrency() { /* ... */ }
export function formatPhone() { /* ... */ }
// ... 7 more functions

// Your component only uses one:
import { formatDate } from '@/lib/utils';

// Tree shaking removes the other 9 functions from the bundle
// Result: smaller JavaScript, faster page loads

Tree shaking works automatically with ES modules (import/export). It does not work with CommonJS (require/module.exports), which is one reason the industry has moved to ES modules.

Code Splitting

Next.js automatically splits your code by route. Each page gets its own JavaScript bundle. But you can also manually split code within a page using dynamic imports:

// Instead of importing a heavy component at the top:
// import HeavyChart from '@/components/HeavyChart';

// Dynamically import it -- it loads only when needed:
import dynamic from 'next/dynamic';

const HeavyChart = dynamic(() => import('@/components/HeavyChart'), {
  loading: () => <p>Loading chart...</p>,
});

export default function DashboardPage() {
  return (
    <main>
      <h1>Dashboard</h1>
      <HeavyChart /> {/* Loaded separately, not in initial bundle */}
    </main>
  );
}

Dynamic imports are especially valuable for:

  • Large third-party libraries (chart libraries, rich text editors, PDF generators)
  • Components that appear below the fold (users might not scroll down)
  • Features behind modals or tabs (only load when opened)

Analyzing Bundle Size

You can visualize what is inside your bundles using the @next/bundle-analyzer package. It generates an interactive treemap showing every module and its size, making it easy to spot unexpectedly large dependencies.

# Install the analyzer
$ npm install @next/bundle-analyzer

# Add to next.config.mjs
import bundleAnalyzer from '@next/bundle-analyzer';
const withBundleAnalyzer = bundleAnalyzer({
  enabled: process.env.ANALYZE === 'true',
});
export default withBundleAnalyzer(nextConfig);

# Run the analysis
$ ANALYZE=true npm run build

Testing Production Locally

Before deploying, you should always test the production build on your local machine. This catches errors that only appear in production mode.

# Step 1: Build the production version
$ npm run build

# Step 2: Start the production server
$ npm run start

# Step 3: Open http://localhost:3000 and test everything
# - Check that all pages load
# - Test forms and API routes
# - Verify images and styles
# - Check the browser console for errors

The production server (npm run start) behaves very differently from the development server (npm run dev). Pages that worked in dev might fail in production due to missing environment variables, incorrect NEXT_PUBLIC_ usage, or dynamic import issues. Always test before deploying.

Build Time vs. Runtime

Understanding when things happen is crucial for debugging production issues.

Aspect Build Time (during npm run build) Runtime (when users visit)
When it happens Once, during deployment On every request
Environment Build server (CI/CD, Render) Production server
NEXT_PUBLIC_ vars Baked into JavaScript bundles Already embedded, cannot change
Server-only vars Available via process.env Available via process.env
Static pages HTML generated and saved Served as static files
Dynamic pages Not generated Generated on each request

This distinction explains a common gotcha: if you change a NEXT_PUBLIC_ variable, the change will not take effect until you rebuild. The value was embedded in the JavaScript at build time. Server-only variables, by contrast, are read fresh on every request and take effect immediately after a server restart.

npm ci vs. npm install

In deployment environments, you will see npm ci used instead of npm install. The difference matters:

Feature npm install npm ci
Lock file May update package-lock.json Never modifies lock file
Versions May resolve to newer compatible versions Installs exact versions from lock file
Speed Slower (resolves dependency tree) Faster (skips resolution, trusts lock file)
node_modules Updates existing node_modules/ Deletes and recreates from scratch
Use case Local development (adding packages) CI/CD, builds, deployments

npm ci guarantees that everyone (your laptop, your teammate's laptop, and the Render build server) installs exactly the same versions of every dependency. This eliminates "works on my machine" bugs caused by subtly different dependency versions.

# Local development: use npm install
$ npm install

# Build/deploy: use npm ci
$ npm ci && npm run build
Requirement for npm ci npm ci requires a package-lock.json file. If the lock file does not exist or is out of sync with package.json, npm ci will fail. Always commit your package-lock.json to Git.

Exercises

  1. Run a production build: In any Next.js project, run npm run build and read the output carefully. Identify which routes are static (circle) and which are dynamic (lambda). Count the total number of each type.
  2. Explore the .next directory: After building, use ls -la .next/ and explore the directory structure. Find the BUILD_ID file and read its contents. Look at .next/server/app/ and identify the compiled pages.
  3. Enable standalone mode: Add output: 'standalone' to your next.config.mjs and rebuild. Explore .next/standalone/. Try starting the server with node .next/standalone/server.js and see what happens (you will need to copy static files first).
  4. Test production locally: Run npm run build followed by npm run start. Visit the site at http://localhost:3000. Compare the experience to npm run dev -- look at page load speed, JavaScript bundle sizes in DevTools Network tab, and error messages.
  5. Intentionally break the build: Introduce a TypeScript error (like assigning a number to a string variable) and run npm run build. Read the error message. Then fix it and add typescript: { ignoreBuildErrors: true } to next.config.mjs. Rebuild and notice the error is now a warning, not a failure.
  6. Dynamic import practice: Take a component in your project and convert it to use dynamic() from next/dynamic. Add a loading fallback. Build and check the bundle output -- the dynamically imported component should appear as a separate chunk.

Key Takeaways

  • Development mode prioritizes developer experience (fast refresh, detailed errors). Production mode prioritizes user experience (optimized bundles, aggressive caching).
  • npm run build compiles TypeScript, runs ESLint, analyzes routes, bundles JavaScript, and optimizes assets into the .next/ directory.
  • Pages are either static (rendered once at build time) or dynamic (rendered on every request). Static is faster; dynamic is more flexible.
  • output: 'standalone' in next.config.mjs creates a self-contained server with only the dependencies needed to run, making deployment significantly easier.
  • Webpack handles bundling, path aliases (@/), and extension resolution. Most configuration is automatic, but custom settings go in next.config.mjs.
  • Tree shaking removes unused code. Code splitting creates per-route bundles. Dynamic imports load heavy components on demand.
  • Always test production builds locally with npm run build && npm run start before deploying.
  • NEXT_PUBLIC_ variables are baked in at build time and cannot change without a rebuild. Server-only variables are read at runtime.
  • Use npm ci (not npm install) in CI/CD and deployment to guarantee exact dependency versions from the lock file.
