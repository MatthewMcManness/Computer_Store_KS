Phase 3: React

React State & Hooks

Make your components interactive with state, side effects, DOM references, and controlled forms.

What You Will Learn

  • Understand what state is and why it exists separately from props
  • Use useState to declare, read, and update state
  • Update objects and arrays in state without mutating them
  • Use useEffect for side effects like data fetching, timers, and event listeners
  • Understand the dependency array and cleanup functions
  • Use useRef for DOM references and mutable values
  • Build controlled forms with input state and onChange handlers
  • Implement loading, error, and success states
  • Lift state up when sibling components need the same data
  • Follow the rules of hooks

What Is State?

In the previous lesson, you learned that props are data passed into a component from its parent. Props are read-only — a child component cannot change its own props. But what about data that changes over time in response to user interaction?

  • A search box needs to track what the user has typed
  • A filter needs to track which option is selected
  • A counter needs to track the current number
  • A form needs to track every field's value
  • A data-fetching component needs to track loading, error, and success conditions

This is state — data that is owned and managed by a component, that can change over time, and whose changes cause the component to re-render with the new values.

Analogy: Think of a whiteboard in a meeting room. The props are like printed handouts given to attendees — fixed information provided from the outside. The state is what is written on the whiteboard — it changes during the meeting as people add and erase content. When the whiteboard changes, everyone in the room (the UI) sees the updated version.
Characteristic Props State
Owned by Parent component The component itself
Can be changed by component? No (read-only) Yes (via setter function)
Causes re-render on change? Yes (when parent re-renders) Yes (when setter is called)
Passed down to children? Yes, as their props Yes, as their props

useState: Declaring and Updating State

useState is a hook — a special function provided by React that lets you "hook into" React features from function components. It is the most fundamental hook and the one you will use the most.

import { useState } from 'react';

function Counter() {
  //          current value   setter function     initial value
  //               |                |                  |
  const [count,         setCount]     = useState(0);

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(count + 1)}>
        Increment
      </button>
    </div>
  );
}

Let us break down what is happening:

  1. useState(0) tells React "I want a piece of state that starts at 0."
  2. It returns an array with exactly two elements: the current value (count) and a setter function (setCount).
  3. We use array destructuring to give them names. By convention, the setter is named set + the state variable name.
  4. When the button is clicked, setCount(count + 1) tells React "the new value should be the old value plus 1."
  5. React updates the state and re-renders the component with the new value. The function runs again, count is now 1, and the UI shows "Count: 1".

TypeScript with useState

TypeScript usually infers the type from the initial value, but you can be explicit when needed:

// Type is inferred as number
const [count, setCount] = useState(0);

// Type is inferred as string
const [name, setName] = useState('');

// Explicit type needed when initial value doesn't tell the whole story
const [user, setUser] = useState<User | null>(null);
// null alone would be inferred as "always null" - we need to tell TS it can be User too

const [tickets, setTickets] = useState<Ticket[]>([]);
// Empty array alone would be inferred as never[] - specify the element type

const [status, setStatus] = useState<'idle' | 'loading' | 'success' | 'error'>('idle');
// Union type for a finite set of possible values

State Is Immutable (Why You Cannot Mutate Directly)

This is one of the most critical concepts in React. You must never modify state directly. Always use the setter function to create a new value.

const [count, setCount] = useState(0);

// WRONG - mutating state directly
count = count + 1;          // This won't work (const can't be reassigned)
count++;                   // This won't work either

// CORRECT - using the setter
setCount(count + 1);        // Creates a new value, triggers re-render

Why? Because React uses the setter call as a signal to re-render. If you mutate the value directly, React has no way of knowing something changed, so the UI will not update. The setter function is like pressing a doorbell — it tells React "something changed, please re-render."

Updating Objects in State

When state is an object, you must create a new object with the changes, not mutate the existing one. Use the spread operator (...) to copy existing properties and override specific ones:

interface Customer {
  name: string;
  email: string;
  phone: string;
}

const [customer, setCustomer] = useState<Customer>({
  name: 'John Smith',
  email: 'john@example.com',
  phone: '555-0123',
});

// WRONG - mutating the existing object
customer.email = 'newemail@example.com';  // UI won't update!

// CORRECT - creating a new object with the spread operator
setCustomer({
  ...customer,                            // Copy all existing properties
  email: 'newemail@example.com',          // Override just the email
});

The spread operator ...customer copies name, email, and phone from the old object. Then email: 'newemail@example.com' overrides just the email. The result is a brand new object. React sees a new object reference and re-renders.

Updating Arrays in State

The same principle applies to arrays. Never use mutating methods like .push(), .pop(), .splice(), or .sort() directly on state. Instead, create new arrays:

const [tickets, setTickets] = useState<string[]>(['Ticket A', 'Ticket B']);

// Adding an item (spread + new item)
setTickets([...tickets, 'Ticket C']);
// Result: ['Ticket A', 'Ticket B', 'Ticket C']

// Removing an item (filter creates a new array)
setTickets(tickets.filter(t => t !== 'Ticket A'));
// Result: ['Ticket B']

// Updating an item (map creates a new array)
setTickets(tickets.map(t =>
  t === 'Ticket A' ? 'Ticket A (Updated)' : t
));
// Result: ['Ticket A (Updated)', 'Ticket B']

// Sorting (copy first, then sort the copy)
setTickets([...tickets].sort());
// [...tickets] creates a copy, .sort() mutates the copy (not the original)
Operation Mutating (avoid) Non-Mutating (use this)
Add item arr.push(item) [...arr, item]
Remove item arr.splice(i, 1) arr.filter(x => x.id !== id)
Update item arr[i] = newVal arr.map(x => x.id === id ? newVal : x)
Sort arr.sort() [...arr].sort()
Reverse arr.reverse() [...arr].reverse()

Functional Updates

When your new state depends on the previous state, use the functional form of the setter. Instead of passing a value, pass a function that receives the previous state:

// Simple form - fine for most cases
setCount(count + 1);

// Functional form - safer when multiple updates could happen
setCount(prev => prev + 1);

// Why does it matter? Imagine this:
function handleTripleClick() {
  setCount(count + 1);  // count is 0, sets to 1
  setCount(count + 1);  // count is STILL 0 (stale closure), sets to 1
  setCount(count + 1);  // count is STILL 0, sets to 1
  // Result: 1, not 3!
}

function handleTripleClickCorrect() {
  setCount(prev => prev + 1);  // prev is 0, returns 1
  setCount(prev => prev + 1);  // prev is 1, returns 2
  setCount(prev => prev + 1);  // prev is 2, returns 3
  // Result: 3!
}

The functional form always receives the most up-to-date value, avoiding stale closure problems. Use it whenever you are updating based on the previous state.

useEffect: Side Effects

Components in React should be "pure" when it comes to rendering — given the same props and state, they should produce the same JSX. But real applications need to do things outside of rendering:

  • Fetch data from an API
  • Set up a timer or interval
  • Add event listeners to the window
  • Update the document title
  • Write to localStorage

These are called side effects, and useEffect is the hook that lets you perform them.

import { useState, useEffect } from 'react';

function PageTitle({ title }: { title: string }) {
  useEffect(() => {
    document.title = title;  // Side effect: update the browser tab title
  }, [title]);               // Only run when title changes

  return <h1>{title}</h1>;
}

useEffect takes two arguments:

  1. A function containing the side effect code (called the "effect")
  2. An optional dependency array that controls when the effect runs

The Dependency Array

The dependency array is the most important (and most misunderstood) part of useEffect. It tells React when to re-run the effect:

// 1. Empty array: Run ONCE after the first render (on "mount")
useEffect(() => {
  console.log('Component mounted!');
  fetchInitialData();
}, []);  // <-- empty array = run once


// 2. With dependencies: Run on mount AND whenever listed values change
useEffect(() => {
  console.log(`Search changed to: ${searchTerm}`);
  fetchResults(searchTerm);
}, [searchTerm]);  // <-- runs whenever searchTerm changes


// 3. No array at all: Run after EVERY render (rarely wanted)
useEffect(() => {
  console.log('This runs after every single render');
});  // <-- no array = runs every time (usually a bug)
Common Mistake: Forgetting the dependency array causes the effect to run after every render. For data fetching, this creates an infinite loop: render -> effect fetches data -> state updates -> re-render -> effect fetches data -> repeat forever. Always include a dependency array.

Cleanup Functions

Some side effects need to be "cleaned up" when the component is removed from the page or before the effect runs again. For example, if you set up a timer, you need to clear it. If you add an event listener, you need to remove it. The effect function can return a cleanup function:

function WindowSize() {
  const [width, setWidth] = useState(window.innerWidth);

  useEffect(() => {
    // Setup: add event listener
    const handleResize = () => setWidth(window.innerWidth);
    window.addEventListener('resize', handleResize);

    // Cleanup: remove event listener when component unmounts
    return () => {
      window.removeEventListener('resize', handleResize);
    };
  }, []); // Empty array: set up once, clean up on unmount

  return <p>Window width: {width}px</p>;
}

The cleanup function runs:

  • Before the effect runs again (if dependencies changed)
  • When the component is removed from the DOM (unmounts)

Common useEffect Patterns

Pattern 1: Fetching Data

interface Ticket {
  id: number;
  subject: string;
  status: string;
}

function TicketList() {
  const [tickets, setTickets] = useState<Ticket[]>([]);
  const [isLoading, setIsLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    async function fetchTickets() {
      try {
        setIsLoading(true);
        const response = await fetch('/api/tickets');
        if (!response.ok) throw new Error('Failed to fetch tickets');
        const data = await response.json();
        setTickets(data);
      } catch (err) {
        setError(err instanceof Error ? err.message : 'Unknown error');
      } finally {
        setIsLoading(false);
      }
    }

    fetchTickets();
  }, []); // Empty array: fetch once on mount

  if (isLoading) return <p>Loading tickets...</p>;
  if (error) return <p className="error">Error: {error}</p>;

  return (
    <ul>
      {tickets.map(ticket => (
        <li key={ticket.id}>{ticket.subject} ({ticket.status})</li>
      ))}
    </ul>
  );
}
Why is the async function inside useEffect? The effect callback itself cannot be async (React expects it to return either nothing or a cleanup function, not a Promise). So we define an async function inside and immediately call it. This is the standard pattern.

Pattern 2: Setting Up an Interval (Polling)

function CallCustomerWidget() {
  const [tickets, setTickets] = useState<Ticket[]>([]);

  useEffect(() => {
    // Fetch immediately on mount
    fetchCallCustomerTickets();

    // Then fetch every 30 seconds
    const intervalId = setInterval(() => {
      fetchCallCustomerTickets();
    }, 30000); // 30,000 ms = 30 seconds

    // Cleanup: clear the interval when component unmounts
    return () => clearInterval(intervalId);
  }, []);

  async function fetchCallCustomerTickets() {
    try {
      const res = await fetch('/api/tickets?status=call_customer');
      const data = await res.json();
      setTickets(data);
    } catch (err) {
      console.error('Failed to fetch call-customer tickets', err);
    }
  }

  return (
    <div className="call-widget">
      <h3>Customers to Call ({tickets.length})</h3>
      {tickets.map(t => <p key={t.id}>{t.subject}</p>)}
    </div>
  );
}
CSK Connection The admin dashboard's "Call Customer" widget works exactly like this. It uses useEffect with setInterval to poll the tickets API every 30 seconds, showing employees which customers need a phone call. The cleanup function clears the interval when navigating away from the dashboard.

Pattern 3: Effect with Changing Dependencies

function SearchableTickets() {
  const [searchTerm, setSearchTerm] = useState('');
  const [results, setResults] = useState<Ticket[]>([]);

  useEffect(() => {
    if (searchTerm.length < 2) {
      setResults([]);
      return;  // Don't search for very short strings
    }

    async function search() {
      const res = await fetch(`/api/tickets?q=${encodeURIComponent(searchTerm)}`);
      const data = await res.json();
      setResults(data);
    }

    search();
  }, [searchTerm]);  // Re-run whenever searchTerm changes

  return (
    <div>
      <input
        value={searchTerm}
        onChange={e => setSearchTerm(e.target.value)}
        placeholder="Search tickets..."
      />
      {results.map(t => <div key={t.id}>{t.subject}</div>)}
    </div>
  );
}

useRef: DOM References and Mutable Values

useRef gives you a way to hold a mutable value that persists across re-renders without causing a re-render when it changes. It has two main uses:

Use 1: Referencing DOM Elements

import { useRef, useEffect } from 'react';

function SearchBar() {
  const inputRef = useRef<HTMLInputElement>(null);

  useEffect(() => {
    // Focus the input when the component mounts
    inputRef.current?.focus();
  }, []);

  return (
    <input
      ref={inputRef}
      type="text"
      placeholder="Search..."
    />
  );
}

The ref attribute connects the ref object to the actual DOM element. After rendering, inputRef.current points to the real <input> DOM node, and you can call methods like .focus() on it.

Use 2: Storing Mutable Values Without Re-Rendering

function StopWatch() {
  const [seconds, setSeconds] = useState(0);
  const intervalRef = useRef<ReturnType<typeof setInterval> | null>(null);

  function start() {
    intervalRef.current = setInterval(() => {
      setSeconds(prev => prev + 1);
    }, 1000);
  }

  function stop() {
    if (intervalRef.current) {
      clearInterval(intervalRef.current);
    }
  }

  return (
    <div>
      <p>{seconds} seconds</p>
      <button onClick={start}>Start</button>
      <button onClick={stop}>Stop</button>
    </div>
  );
}

We store the interval ID in a ref because we need to remember it (to clear it later) but changing it should NOT cause a re-render. If we used state for the interval ID, every time we set it, the component would re-render unnecessarily.

Feature useState useRef
Persists across renders? Yes Yes
Triggers re-render on change? Yes No
Accessed via The value directly .current property
Best for Data displayed in UI DOM refs, timer IDs, previous values

Controlled Forms

In HTML, form inputs (<input>, <textarea>, <select>) maintain their own internal state. When a user types into an input, the input updates itself. In React, we prefer controlled components, where React state is the "single source of truth" for the input's value.

Single Input

function SearchBox() {
  const [query, setQuery] = useState('');

  return (
    <input
      type="text"
      value={query}                         // Input displays the state value
      onChange={e => setQuery(e.target.value)}  // Every keystroke updates state
      placeholder="Search tickets..."
    />
  );
}

The flow is: user types -> onChange fires -> setQuery updates state -> component re-renders -> input shows new value. React is always in control of what the input displays.

Multiple Form Fields

For forms with many fields, use an object for state instead of separate useState calls for each field:

interface ContactFormData {
  name: string;
  email: string;
  message: string;
  priority: 'low' | 'medium' | 'high';
}

function ContactForm() {
  const [formData, setFormData] = useState<ContactFormData>({
    name: '',
    email: '',
    message: '',
    priority: 'medium',
  });

  // Generic handler that works for any field
  function handleChange(e: React.ChangeEvent<HTMLInputElement | HTMLTextAreaElement | HTMLSelectElement>) {
    const { name, value } = e.target;
    setFormData(prev => ({
      ...prev,
      [name]: value,  // Computed property name: uses the input's name attribute
    }));
  }

  function handleSubmit(e: React.FormEvent) {
    e.preventDefault();  // Prevent page reload
    console.log('Submitting:', formData);
    // Send to API...
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        name="name"
        value={formData.name}
        onChange={handleChange}
        placeholder="Your name"
      />

      <input
        name="email"
        type="email"
        value={formData.email}
        onChange={handleChange}
        placeholder="Your email"
      />

      <select name="priority" value={formData.priority} onChange={handleChange}>
        <option value="low">Low</option>
        <option value="medium">Medium</option>
        <option value="high">High</option>
      </select>

      <textarea
        name="message"
        value={formData.message}
        onChange={handleChange}
        placeholder="Describe the issue..."
      />

      <button type="submit">Submit</button>
    </form>
  );
}

The key trick is using [name]: value in the state update, where name matches the HTML name attribute on each input. This lets one handler work for all fields.

Loading, Error, and Success States

Any component that fetches data or submits forms needs to handle three states beyond the "happy path." This is a pattern you will use constantly in production code:

function ContactFormComplete() {
  const [formData, setFormData] = useState({ name: '', email: '', message: '' });
  const [status, setStatus] = useState<'idle' | 'loading' | 'success' | 'error'>('idle');
  const [errorMessage, setErrorMessage] = useState('');

  async function handleSubmit(e: React.FormEvent) {
    e.preventDefault();
    setStatus('loading');

    try {
      const res = await fetch('/api/contact', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(formData),
      });

      if (!res.ok) throw new Error('Failed to send message');
      setStatus('success');
    } catch (err) {
      setStatus('error');
      setErrorMessage(err instanceof Error ? err.message : 'Something went wrong');
    }
  }

  // Show success message after submission
  if (status === 'success') {
    return (
      <div className="success-message">
        <h3>Message Sent!</h3>
        <p>We will get back to you soon.</p>
      </div>
    );
  }

  return (
    <form onSubmit={handleSubmit}>
      {status === 'error' && (
        <div className="error-banner">{errorMessage}</div>
      )}

      {/* ... form fields ... */}

      <button type="submit" disabled={status === 'loading'}>
        {status === 'loading' ? 'Sending...' : 'Send Message'}
      </button>
    </form>
  );
}
CSK Connection The CSK admin ticket page uses exactly these patterns: useState for search text and active status filter, useEffect for 30-second polling to keep the ticket list fresh, useRef for form input references in the note entry field. The contact form on the public site implements loading/error/success states when sending customer inquiries via Resend.

Lifting State Up

Sometimes two sibling components need to share the same data. Since props only flow downward (from parent to child), the solution is to "lift" the state up to the nearest common parent.

Before (broken - siblings can't share state): <App> <SearchBar /> <TicketList /> [has searchTerm] [needs searchTerm... but how?] After (working - state lifted to parent): <App> [searchTerm state lives here] | | v v <SearchBar <TicketList searchTerm={...} searchTerm={...} onSearch={...} /> tickets={...} />
function App() {
  // State lives in the common parent
  const [searchTerm, setSearchTerm] = useState('');
  const [tickets, setTickets] = useState<Ticket[]>([]);

  // Filter tickets based on search term
  const filteredTickets = tickets.filter(t =>
    t.subject.toLowerCase().includes(searchTerm.toLowerCase())
  );

  return (
    <div>
      {/* Pass state down as props */}
      <SearchBar
        value={searchTerm}
        onChange={setSearchTerm}
      />
      <TicketList tickets={filteredTickets} />
    </div>
  );
}

function SearchBar({ value, onChange }: { value: string; onChange: (v: string) => void }) {
  return (
    <input
      value={value}
      onChange={e => onChange(e.target.value)}
      placeholder="Search..."
    />
  );
}

function TicketList({ tickets }: { tickets: Ticket[] }) {
  return (
    <ul>
      {tickets.map(t => <li key={t.id}>{t.subject}</li>)}
    </ul>
  );
}

The parent owns the state and passes it down as props. The SearchBar receives both the current value and a callback to change it. The TicketList receives the filtered results. Neither sibling knows about the other — they only know about their props.

Rules of Hooks

Hooks have two strict rules that must be followed. Breaking them causes bugs that are extremely difficult to track down.

Rule 1: Only Call Hooks at the Top Level

Never call hooks inside conditions, loops, or nested functions. Hooks must be called in the same order every time the component renders.

// WRONG - hook inside a condition
function BadComponent({ isAdmin }: { isAdmin: boolean }) {
  if (isAdmin) {
    const [users, setUsers] = useState([]);  // DON'T DO THIS
  }
}

// CORRECT - hook at top level, condition in the JSX
function GoodComponent({ isAdmin }: { isAdmin: boolean }) {
  const [users, setUsers] = useState([]);  // Always called

  if (!isAdmin) return null;  // Condition after all hooks

  return <UserList users={users} />;
}

Rule 2: Only Call Hooks in React Functions

Hooks can only be called inside React function components or custom hooks (covered in Lesson 14). Never call them in regular JavaScript functions, class methods, or event handlers.

// WRONG - hook in a regular function
function calculateTotal() {
  const [total, setTotal] = useState(0);  // DON'T DO THIS
}

// CORRECT - hook in a component (starts with capital letter)
function TotalDisplay() {
  const [total, setTotal] = useState(0);  // This is fine
  return <p>Total: ${total}</p>;
}
Why these rules? React tracks hooks by their call order. The first useState call is always hook #1, the second is hook #2, and so on. If a hook is inside a condition, the call order changes between renders, and React assigns the wrong state to the wrong hook. The ESLint plugin eslint-plugin-react-hooks catches these violations automatically.

Hands-On Exercises

  1. Build a counter with controls: Create a component with increment, decrement, and reset buttons. Display the count. Prevent the count from going below 0 (disable the decrement button or guard with a condition).
  2. Build a to-do list: Create a component that lets users type a task and add it to a list. Each task should have a "Remove" button. Use an array of objects in state with unique IDs. Apply all the non-mutating array patterns (spread to add, filter to remove).
  3. Data fetching with states: Create a component that fetches data from a free public API (like https://jsonplaceholder.typicode.com/posts) on mount. Implement loading, error, and empty states using the patterns from this lesson.
  4. Polling timer: Create a component that displays the current time, updating every second using useEffect with setInterval. Include a cleanup function. Add a "Pause" and "Resume" button.
  5. Contact form: Build a complete form with name, email, phone, and message fields. Use an object in state with a single handleChange function. Add a handleSubmit that prevents default and logs the form data. Implement a "loading" state on the submit button.
  6. Search filter: Create a parent component that holds an array of items and a search term. Render a search input and a filtered list. Lift the state so both children use data from the parent. Highlight matching text in the results.

Key Takeaways

  • State is data owned by a component that changes over time. Use useState to declare it. State changes trigger re-renders.
  • Never mutate state directly. Always use the setter function. For objects, use {...obj, key: newValue}. For arrays, use .map(), .filter(), and spread.
  • Use the functional updater setState(prev => ...) when the new value depends on the previous one.
  • useEffect runs side effects. The dependency array controls when: [] = mount only, [dep] = when dep changes, no array = every render. Return a cleanup function for timers and event listeners.
  • useRef holds a mutable value that persists across renders without triggering re-renders. Use it for DOM references and timer IDs.
  • In controlled forms, React state drives input values. The onChange handler updates state, state drives the value prop.
  • Always handle loading, error, and success states in components that fetch data or submit forms.
  • Lift state up to the nearest common parent when sibling components need to share data.
  • Hooks must be called at the top level (not inside conditions/loops) and only inside React components or custom hooks.
