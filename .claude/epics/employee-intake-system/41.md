# Task: Supabase Schema & Auth Update

## Description
Create the `customer_accounts` table in Supabase for customer portal authentication and update the existing auth flow to support cascading authentication (RepairShopr for employees first, then Supabase for customers).

## Acceptance Criteria
- [ ] `customer_accounts` table created in Supabase with proper schema
- [ ] Table includes: id, email, password_hash, repairshopr_customer_id, created_at, updated_at
- [ ] Unique constraint on email
- [ ] Index on repairshopr_customer_id for fast lookups
- [ ] Auth flow updated: tries RepairShopr API first, then Supabase customer_accounts
- [ ] Employee login still works via RepairShopr
- [ ] Customer login works via Supabase (for future customer portal)
- [ ] Session correctly identifies user type (employee vs customer)

## Technical Details
- **Database**: Supabase PostgreSQL
- **Schema file**: `docs/database/customer-accounts-schema.sql`
- **Auth file**: `src/lib/auth.ts`
- **Login API**: `src/app/api/auth/login/route.ts`

### Schema Design
```sql
CREATE TABLE customer_accounts (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email VARCHAR(255) NOT NULL UNIQUE,
  password_hash VARCHAR(255) NOT NULL,
  repairshopr_customer_id INTEGER NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_customer_accounts_repairshopr_id
  ON customer_accounts(repairshopr_customer_id);
```

### Auth Flow Changes
1. Receive login request (email, password)
2. Try RepairShopr `/sign_in` endpoint
3. If success → employee session (admin access)
4. If fail → check Supabase customer_accounts
5. If found → verify password hash → customer session (portal access)
6. If both fail → return authentication error
