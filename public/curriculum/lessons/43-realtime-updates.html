Why Real-Time Data Matters

Most of the web applications you have built so far follow a simple pattern: the user opens the page, data loads once, and the page stays the same until the user navigates away or manually refreshes. This works fine for static content like blog posts or product listings. But some applications need to show data that changes constantly, and users expect to see those changes without lifting a finger.

Think about these scenarios:

  • A repair shop dashboard — When a technician changes a ticket's status from "diagnosing" to "repairing," the receptionist's screen should update within seconds so they can inform the customer
  • A notification system — When a new message arrives, the notification badge should appear without the user refreshing
  • A collaborative document — Multiple people editing the same document need to see each other's changes in real time
  • A stock ticker or sports scoreboard — Data changes every few seconds, and stale data is useless
  • An admin panel showing system status — Server health, queue lengths, and active users need to stay current

There are several techniques to keep a UI current, ranging from simple to complex. In this lesson, we will focus on the most practical approach for most applications: polling. We will also explore when and why you might choose more advanced alternatives.

Analogy: Imagine you are waiting for a package delivery. Polling is like checking your front porch every 5 minutes to see if the package arrived. WebSockets are like having a doorbell that rings when the delivery person arrives. Server-Sent Events are like having a delivery tracker that pushes updates to your phone. All three get you the package, but they use different amounts of effort.
CSK Connection The Computer Store KS admin dashboard uses polling in several places. The "Call Customer" widget auto-refreshes every 30 seconds using useEffect + setInterval. The ticket list refreshes to pick up status changes made by other employees. These auto-refreshes keep the receptionist's screen current without requiring manual page refreshes.

Polling: Fetching Data on a Timer

Polling is the simplest real-time technique. You fetch data from the server, wait a set amount of time, then fetch it again. Repeat forever (or until the component unmounts). It is not truly "real-time" in the strictest sense — there is always a delay equal to your polling interval — but for most applications, refreshing every 10–30 seconds is perfectly adequate.

The Basic Pattern

function TicketList() {
  const [tickets, setTickets] = useState([]);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    // Fetch immediately on mount
    fetchTickets();

    // Then fetch again every 30 seconds
    const intervalId = setInterval(fetchTickets, 30000);

    // Clean up: stop polling when component unmounts
    return () => clearInterval(intervalId);
  }, []);

  async function fetchTickets() {
    try {
      const response = await fetch('/api/tickets');
      const data = await response.json();
      setTickets(data);
    } catch (error) {
      console.error('Failed to fetch tickets:', error);
    } finally {
      setLoading(false);
    }
  }

  if (loading) return <p>Loading tickets...</p>;

  return (
    <ul>
      {tickets.map(ticket => (
        <li key={ticket.id}>{ticket.subject} - {ticket.status}</li>
      ))}
    </ul>
  );
}

Let us break this down step by step:

  1. fetchTickets() is called immediately — The user sees data as soon as the component mounts, without waiting for the first interval to fire
  2. setInterval(fetchTickets, 30000) — Schedules the function to run every 30,000 milliseconds (30 seconds)
  3. The cleanup function clearInterval(intervalId) — This is critical. When the component unmounts (the user navigates away), the interval is stopped. Without this, the interval would keep running in the background, making API calls to nowhere and potentially causing errors
Always Clean Up Intervals If you forget the return () => clearInterval(intervalId) line, you create a memory leak. The interval keeps running even after the component is gone. Each time the user navigates to and from the page, another interval starts. After 10 visits, you have 10 intervals all firing simultaneously. Always return a cleanup function from useEffect when using setInterval or setTimeout.

Building a Reusable usePolling Hook

The polling pattern is so common that it deserves its own custom hook. A reusable hook lets you add polling to any component with a single line of code instead of repeating the useEffect + setInterval + cleanup boilerplate every time.

import { useEffect, useRef, useCallback } from 'react';

/**
 * Custom hook that repeatedly calls a function at a set interval.
 *
 * @param callback - The function to call on each interval tick
 * @param intervalMs - Time between calls in milliseconds
 * @param enabled - Whether polling is active (default: true)
 */
function usePolling(
  callback: () => void | Promise<void>,
  intervalMs: number,
  enabled: boolean = true
) {
  // Store the latest callback in a ref so the interval
  // always calls the most current version
  const savedCallback = useRef(callback);

  // Update the ref when callback changes
  useEffect(() => {
    savedCallback.current = callback;
  }, [callback]);

  useEffect(() => {
    if (!enabled) return;

    // Call immediately on start
    savedCallback.current();

    // Then set up the interval
    const id = setInterval(() => {
      savedCallback.current();
    }, intervalMs);

    return () => clearInterval(id);
  }, [intervalMs, enabled]);
}

Using the Hook

function TicketDashboard() {
  const [tickets, setTickets] = useState([]);

  const fetchTickets = useCallback(async () => {
    const response = await fetch('/api/tickets');
    const data = await response.json();
    setTickets(data);
  }, []);

  // Poll every 30 seconds
  usePolling(fetchTickets, 30000);

  return (
    <ul>
      {tickets.map(ticket => (
        <li key={ticket.id}>{ticket.subject}</li>
      ))}
    </ul>
  );
}

Now adding polling to any component is a single line: usePolling(fetchFunction, interval). The hook handles the setup, cleanup, and stale callback issues internally.

Conditional Polling

The enabled parameter lets you pause and resume polling:

function Dashboard() {
  const [isVisible, setIsVisible] = useState(true);

  // Only poll when the tab is visible
  useEffect(() => {
    function handleVisibility() {
      setIsVisible(!document.hidden);
    }
    document.addEventListener('visibilitychange', handleVisibility);
    return () => document.removeEventListener('visibilitychange', handleVisibility);
  }, []);

  // Polling pauses when the user switches to another tab
  usePolling(fetchData, 15000, isVisible);
}

This is a smart optimization. If the user switches to a different browser tab, there is no point in continuing to poll your API. The visibilitychange event lets you detect this and pause polling until the user returns.

The Stale State Pitfall

One of the most common bugs in React polling code involves stale closures. This happens when an interval callback captures an old version of a state variable. Let us see the problem and its solutions.

The Problem

// BUG: This has a stale closure problem
function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      // This 'count' is always 0 because the closure
      // captured the initial value and never updates
      setCount(count + 1);
    }, 1000);

    return () => clearInterval(id);
  }, []); // Empty dependency array means this effect runs once

  return <p>Count: {count}</p>; // Always shows 1
}

The interval callback is created once (when the effect runs). At that moment, count is 0. The callback permanently captures count = 0 in its closure. Every second it runs setCount(0 + 1), which sets count to 1, over and over. The counter never goes past 1.

Solution 1: Functional State Updates

// FIXED: Use the functional form of setState
useEffect(() => {
  const id = setInterval(() => {
    // prev is always the latest value
    setCount(prev => prev + 1);
  }, 1000);

  return () => clearInterval(id);
}, []);

When you pass a function to setCount, React calls that function with the current state value as the argument. The closure no longer needs to capture the state variable because the latest value is provided by React each time. This is the preferred solution for state updates inside intervals.

Solution 2: Using a Ref

// FIXED: Store the latest value in a ref
function Counter() {
  const [count, setCount] = useState(0);
  const countRef = useRef(count);

  // Keep the ref in sync with state
  useEffect(() => {
    countRef.current = count;
  }, [count]);

  useEffect(() => {
    const id = setInterval(() => {
      // Read the latest value from the ref
      setCount(countRef.current + 1);
    }, 1000);

    return () => clearInterval(id);
  }, []);

  return <p>Count: {count}</p>;
}

A ref is a mutable container whose .current property persists across renders. Unlike state, reading countRef.current inside the interval always gives you the latest value. This approach is especially useful when you need to read (but not update) state inside an interval — for example, checking whether a flag is set.

When to Use Which Solution Use functional updates (setState(prev => ...)) when the interval needs to update state based on its previous value. Use refs when the interval needs to read a value without updating it, like checking a condition or reading a prop. Our usePolling hook uses the ref approach for the callback itself, which is why it always calls the latest version of the callback.

Optimistic Updates

Polling keeps your UI current with server state, but there is a delay: when the user performs an action, they have to wait for the next poll cycle to see the result. Optimistic updates solve this by updating the UI immediately, assuming the server will confirm the change.

The Pattern

async function markTicketComplete(ticketId) {
  // Step 1: Optimistically update the UI immediately
  setTickets(prev =>
    prev.map(ticket =>
      ticket.id === ticketId
        ? { ...ticket, status: 'completed' }
        : ticket
    )
  );

  try {
    // Step 2: Send the change to the server
    const response = await fetch(`/api/tickets/${ticketId}`, {
      method: 'PATCH',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ status: 'completed' }),
    });

    if (!response.ok) {
      throw new Error('Failed to update ticket');
    }

    // Step 3: Success! The next poll will confirm the data
  } catch (error) {
    // Step 4: Rollback - revert the optimistic update
    setTickets(prev =>
      prev.map(ticket =>
        ticket.id === ticketId
          ? { ...ticket, status: 'open' }  // Revert to previous status
          : ticket
      )
    );

    alert('Failed to update ticket. Please try again.');
  }
}

The user clicks a button, and the ticket instantly changes to "completed" in the UI. Behind the scenes, the request goes to the server. If it succeeds, everything is consistent. If it fails, the UI reverts to the previous state and the user sees an error message. This feels much snappier than waiting for the server response before updating the UI.

Analogy: Optimistic updates are like crossing off an item on your to-do list right after you start working on it, confident you will finish. If something goes wrong and you cannot complete the task, you erase the checkmark and put the item back on the list. Most of the time, you finish the task and the crossed-off item was correct all along.

Subtle Loading States During Refresh

When data loads for the first time, a full-page loading spinner is appropriate. But when data is refreshing (loading again after the initial load), a full-page spinner is disruptive. The user is reading the current data, and suddenly everything disappears behind a spinner. Instead, use subtle indicators that data is refreshing.

The isRefreshing Pattern

function TicketDashboard() {
  const [tickets, setTickets] = useState([]);
  const [isLoading, setIsLoading] = useState(true);      // First load
  const [isRefreshing, setIsRefreshing] = useState(false); // Subsequent loads

  async function fetchTickets() {
    // Only show full loading state on first load
    if (tickets.length === 0) {
      setIsLoading(true);
    } else {
      setIsRefreshing(true);
    }

    try {
      const response = await fetch('/api/tickets');
      const data = await response.json();
      setTickets(data);
    } catch (error) {
      console.error('Fetch failed:', error);
    } finally {
      setIsLoading(false);
      setIsRefreshing(false);
    }
  }

  usePolling(fetchTickets, 30000);

  // First load: show full spinner
  if (isLoading) {
    return <div className="loading-spinner">Loading tickets...</div>;
  }

  return (
    <div>
      {/* Subtle refresh indicator */}
      <div className="dashboard-header">
        <h2>Tickets</h2>
        {isRefreshing && (
          <span className="refresh-indicator">
            Updating...
          </span>
        )}
      </div>

      <ul>
        {tickets.map(ticket => (
          <li key={ticket.id}>{ticket.subject} - {ticket.status}</li>
        ))}
      </ul>
    </div>
  );
}

Polling vs. WebSockets vs. Server-Sent Events

Polling is not the only way to keep data current. Here are the three main approaches, with their trade-offs:

Feature Polling WebSockets Server-Sent Events (SSE)
How it works Client fetches on a timer Persistent two-way connection Persistent one-way (server to client)
Latency Up to 1 full interval behind Near-instant Near-instant
Server load One request per interval per client One persistent connection per client One persistent connection per client
Complexity Low (just fetch + setInterval) High (connection management, reconnection, message protocols) Medium (simpler than WebSockets, auto-reconnect built in)
Direction Client pulls from server Both directions (client and server) Server pushes to client only
Best for Dashboards, status pages, infrequent updates Chat apps, multiplayer games, collaborative editing Notifications, live feeds, progress updates
Browser support Universal Universal Universal (except IE11)
Works with REST APIs Yes (it IS REST) No (separate protocol) Partially (separate endpoint)

When to Choose Each

Use polling when:

  • Data updates are not time-critical (seconds of delay are acceptable)
  • You already have REST API endpoints and do not want to add infrastructure
  • The number of clients is small to moderate (under a few hundred concurrent)
  • You want the simplest possible implementation

Use WebSockets when:

  • You need true real-time with sub-second latency
  • Communication needs to flow both ways (client to server AND server to client)
  • You are building chat, multiplayer, or collaborative features
  • You can invest in the connection management complexity

Use Server-Sent Events when:

  • You only need one-way updates (server to client)
  • You want automatic reconnection (built into the SSE spec)
  • You want something simpler than WebSockets but faster than polling
  • You are building notification feeds or live dashboards
Start with Polling, Upgrade Later For most applications, polling is the right starting point. It is simple, it uses your existing API endpoints, and it has zero infrastructure requirements. If you later find that polling is not fast enough or creates too much server load, you can upgrade to WebSockets or SSE without rewriting your entire application. The UI components stay the same — you just change how data arrives.

Supabase Realtime: Database Change Subscriptions

Supabase includes a built-in realtime engine that lets you subscribe to database changes. When a row is inserted, updated, or deleted, Supabase pushes the change to all subscribed clients. This gives you WebSocket-level real-time updates without managing any WebSocket infrastructure yourself.

Basic Subscription

import { createClient } from '@supabase/supabase-js';

const supabase = createClient(
  process.env.NEXT_PUBLIC_SUPABASE_URL,
  process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY
);

function TicketList() {
  const [tickets, setTickets] = useState([]);

  useEffect(() => {
    // Initial fetch
    fetchTickets();

    // Subscribe to changes on the tickets table
    const channel = supabase
      .channel('ticket-changes')
      .on(
        'postgres_changes',
        {
          event: '*',          // Listen for INSERT, UPDATE, DELETE
          schema: 'public',
          table: 'rs_tickets',
        },
        (payload) => {
          console.log('Change received:', payload);

          if (payload.eventType === 'INSERT') {
            setTickets(prev => [payload.new, ...prev]);
          }

          if (payload.eventType === 'UPDATE') {
            setTickets(prev =>
              prev.map(t => t.id === payload.new.id ? payload.new : t)
            );
          }

          if (payload.eventType === 'DELETE') {
            setTickets(prev =>
              prev.filter(t => t.id !== payload.old.id)
            );
          }
        }
      )
      .subscribe();

    // Cleanup: unsubscribe when component unmounts
    return () => {
      supabase.removeChannel(channel);
    };
  }, []);

  async function fetchTickets() {
    const { data } = await supabase
      .from('rs_tickets')
      .select('*')
      .order('created_at', { ascending: false });
    setTickets(data || []);
  }

  return (
    <ul>
      {tickets.map(ticket => (
        <li key={ticket.id}>{ticket.subject}</li>
      ))}
    </ul>
  );
}

The subscription listens for all events (*) on the rs_tickets table. When any row changes, the callback receives a payload containing the event type and the new/old row data. The component updates its local state accordingly, and the UI re-renders to show the change.

Supabase Realtime Requires RLS Supabase Realtime respects Row-Level Security (RLS) policies. If your table has RLS enabled (which it should), only changes visible to the current user will be delivered. Make sure your RLS policies allow the reads you need. Also, Realtime must be enabled on the table in the Supabase dashboard (Database > Replication).

Building a Notification System with Polling

A notification system is one of the most common uses for polling. The idea is simple: periodically check for new notifications and display them. Let us build one.

function NotificationBell() {
  const [notifications, setNotifications] = useState([]);
  const [unreadCount, setUnreadCount] = useState(0);
  const [isOpen, setIsOpen] = useState(false);

  // Poll for new notifications every 15 seconds
  const fetchNotifications = useCallback(async () => {
    try {
      const response = await fetch('/api/notifications');
      const data = await response.json();
      setNotifications(data);
      setUnreadCount(data.filter(n => !n.read).length);
    } catch (error) {
      // Silently fail - notifications are not critical
      console.error('Notification fetch failed:', error);
    }
  }, []);

  usePolling(fetchNotifications, 15000);

  async function markAsRead(notificationId) {
    // Optimistic update
    setNotifications(prev =>
      prev.map(n =>
        n.id === notificationId ? { ...n, read: true } : n
      )
    );
    setUnreadCount(prev => Math.max(0, prev - 1));

    // Sync with server
    await fetch(`/api/notifications/${notificationId}/read`, {
      method: 'POST',
    });
  }

  return (
    <div className="notification-bell">
      <button
        onClick={() => setIsOpen(!isOpen)}
        aria-label={`Notifications (${unreadCount} unread)`}
      >
        Bell Icon
        {unreadCount > 0 && (
          <span className="badge">{unreadCount}</span>
        )}
      </button>

      {isOpen && (
        <div className="notification-dropdown">
          {notifications.length === 0 ? (
            <p>No notifications</p>
          ) : (
            notifications.map(n => (
              <div
                key={n.id}
                className={`notification ${n.read ? '' : 'unread'}`}
                onClick={() => markAsRead(n.id)}
              >
                <p>{n.message}</p>
                <span>{new Date(n.created_at).toLocaleString()}</span>
              </div>
            ))
          )}
        </div>
      )}
    </div>
  );
}

This notification bell polls every 15 seconds. The unread count badge updates automatically. When the user clicks a notification, it is optimistically marked as read in the UI and synced to the server. The error handling is intentionally lenient: if a notification fetch fails, the user just does not see new notifications for another 15 seconds. This is acceptable because notifications are not mission-critical.

Debouncing and Throttling API Calls

When building features that trigger API calls based on user input (like search-as-you-type or auto-save), you need to limit how often those calls happen. Without limits, a user typing "repair" would trigger 6 separate API calls: "r", "re", "rep", "repa", "repai", "repair". Debouncing and throttling solve this.

Debouncing

Debouncing waits until the user stops doing something for a specified duration before executing the callback. If the user types another character before the timer expires, the timer resets.

import { useState, useEffect, useCallback, useRef } from 'react';

function useDebounce(value, delayMs) {
  const [debouncedValue, setDebouncedValue] = useState(value);

  useEffect(() => {
    const timer = setTimeout(() => {
      setDebouncedValue(value);
    }, delayMs);

    // If value changes before delay expires, cancel and restart
    return () => clearTimeout(timer);
  }, [value, delayMs]);

  return debouncedValue;
}

// Usage: Search input
function SearchBar() {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState([]);

  // Only update debouncedQuery after 300ms of no typing
  const debouncedQuery = useDebounce(query, 300);

  useEffect(() => {
    if (!debouncedQuery) {
      setResults([]);
      return;
    }

    async function search() {
      const response = await fetch(`/api/search?q=${debouncedQuery}`);
      const data = await response.json();
      setResults(data);
    }
    search();
  }, [debouncedQuery]); // Only fires when debounced value changes

  return (
    <div>
      <input
        type="text"
        value={query}
        onChange={e => setQuery(e.target.value)}
        placeholder="Search tickets..."
      />
      {results.map(r => (
        <div key={r.id}>{r.title}</div>
      ))}
    </div>
  );
}

The user types "repair" and the input updates instantly on every keystroke (good responsiveness). But the API call only happens once, 300ms after the user stops typing. This reduces 6 API calls down to 1.

Throttling

Throttling limits execution to at most once per specified duration. Unlike debouncing, throttling does not wait for the user to stop — it fires at regular intervals regardless.

function useThrottle(value, limitMs) {
  const [throttledValue, setThrottledValue] = useState(value);
  const lastRan = useRef(Date.now());

  useEffect(() => {
    const handler = setTimeout(() => {
      if (Date.now() - lastRan.current >= limitMs) {
        setThrottledValue(value);
        lastRan.current = Date.now();
      }
    }, limitMs - (Date.now() - lastRan.current));

    return () => clearTimeout(handler);
  }, [value, limitMs]);

  return throttledValue;
}
Technique Behavior Best For
Debounce Wait until input stops, then fire Search inputs, auto-save, form validation
Throttle Fire at most once per interval Scroll handlers, resize events, analytics

Complete Example: Auto-Refreshing Ticket Dashboard

Here is a comprehensive example combining polling, optimistic updates, subtle loading states, and the visibility API:

'use client';

import { useState, useEffect, useRef, useCallback } from 'react';

// ── Reusable polling hook ──
function usePolling(callback, intervalMs, enabled = true) {
  const savedCallback = useRef(callback);
  useEffect(() => { savedCallback.current = callback; }, [callback]);

  useEffect(() => {
    if (!enabled) return;
    savedCallback.current();
    const id = setInterval(() => savedCallback.current(), intervalMs);
    return () => clearInterval(id);
  }, [intervalMs, enabled]);
}

// ── Dashboard Component ──
export default function TicketDashboard() {
  const [tickets, setTickets] = useState([]);
  const [isLoading, setIsLoading] = useState(true);
  const [isRefreshing, setIsRefreshing] = useState(false);
  const [lastUpdated, setLastUpdated] = useState(null);
  const [isTabVisible, setIsTabVisible] = useState(true);

  // Pause polling when tab is hidden
  useEffect(() => {
    const handler = () => setIsTabVisible(!document.hidden);
    document.addEventListener('visibilitychange', handler);
    return () => document.removeEventListener('visibilitychange', handler);
  }, []);

  // Fetch function
  const fetchTickets = useCallback(async () => {
    if (tickets.length > 0) {
      setIsRefreshing(true);
    }

    try {
      const response = await fetch('/api/repairshopr/tickets');
      if (!response.ok) throw new Error('Fetch failed');
      const data = await response.json();
      setTickets(data.tickets || []);
      setLastUpdated(new Date());
    } catch (error) {
      console.error('Failed to refresh tickets:', error);
    } finally {
      setIsLoading(false);
      setIsRefreshing(false);
    }
  }, [tickets.length]);

  // Poll every 30 seconds when tab is visible
  usePolling(fetchTickets, 30000, isTabVisible);

  // Optimistic status update
  async function updateStatus(ticketId, newStatus) {
    const previousTickets = [...tickets];

    // Optimistic update
    setTickets(prev =>
      prev.map(t =>
        t.id === ticketId ? { ...t, status: newStatus } : t
      )
    );

    try {
      const response = await fetch(`/api/repairshopr/tickets/status/${ticketId}`, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ custom_status: newStatus }),
      });
      if (!response.ok) throw new Error('Update failed');
    } catch {
      // Rollback on failure
      setTickets(previousTickets);
    }
  }

  if (isLoading) {
    return <div>Loading tickets...</div>;
  }

  return (
    <div>
      <div style={{ display: 'flex', justifyContent: 'space-between', alignItems: 'center' }}>
        <h1>Tickets ({tickets.length})</h1>
        <div>
          {isRefreshing && <span>Refreshing...</span>}
          {lastUpdated && (
            <span>Last updated: {lastUpdated.toLocaleTimeString()}</span>
          )}
        </div>
      </div>

      <table>
        <thead>
          <tr>
            <th>ID</th>
            <th>Subject</th>
            <th>Status</th>
            <th>Actions</th>
          </tr>
        </thead>
        <tbody>
          {tickets.map(ticket => (
            <tr key={ticket.id}>
              <td>{ticket.id}</td>
              <td>{ticket.subject}</td>
              <td>{ticket.status}</td>
              <td>
                <button onClick={() => updateStatus(ticket.id, 'completed')}>
                  Complete
                </button>
              </td>
            </tr>
          ))}
        </tbody>
      </table>
    </div>
  );
}

Hands-On Exercises

  1. Basic polling: Create a component that displays the current time from a mock API endpoint. Use useEffect and setInterval to poll every 5 seconds. Verify the cleanup by checking the browser console for continued fetches after unmounting.
  2. usePolling hook: Extract the polling logic from Exercise 1 into a reusable usePolling hook. Use the hook in two separate components with different intervals.
  3. Stale state fix: Create a counter that increments by 1 every second using setInterval. First, write the buggy version (stale closure). Then fix it using the functional updater pattern setCount(prev => prev + 1).
  4. Subtle refresh indicator: Build a list component that shows a "Loading..." state on first load, then a small "Refreshing..." badge on subsequent loads. The list content should stay visible during refreshes.
  5. Debounced search: Build a search input that calls a mock search function. Without debouncing, log how many times the function is called while typing "hello." Then add the useDebounce hook and compare the call count.
  6. Optimistic update: Build a simple to-do list with a "Complete" button on each item. Implement optimistic updates: the item should visually change immediately when clicked, then sync with a mock API. Add a random 20% failure rate to the mock API and verify that the UI rolls back on failure.

Key Takeaways

  • Polling is the simplest way to keep data fresh: fetch on a timer with setInterval inside useEffect.
  • Always clean up intervals by returning clearInterval from useEffect to prevent memory leaks.
  • The stale closure pitfall is the most common polling bug — fix it with functional state updates or refs.
  • A reusable usePolling hook eliminates boilerplate and encapsulates the callback-ref pattern.
  • Optimistic updates make the UI feel instant: update first, sync with the server second, roll back on failure.
  • Use subtle refresh indicators (small badges, not full-page spinners) during background data refreshes.
  • Polling is best for low-frequency updates. Use WebSockets for real-time chat or collaboration, and SSE for server-pushed notifications.
  • Supabase Realtime gives you WebSocket-level updates with minimal setup by subscribing to database changes.
  • Debounce user input (like search) to reduce unnecessary API calls; throttle continuous events (like scroll).
