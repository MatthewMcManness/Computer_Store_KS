TypeScript

Catch bugs before your users do — TypeScript adds a powerful type system to JavaScript that makes your code safer, clearer, and easier to maintain.

Why TypeScript Exists

JavaScript is an incredibly flexible language, and that flexibility is both its greatest strength and its most dangerous weakness. JavaScript lets you pass any value to any function, access any property on any object, and perform operations between any types—all without complaint. The problem is that many of these operations are wrong, and you only find out when the code runs and crashes.

Consider this JavaScript code:

function calculateTotal(price, quantity) {
  return price * quantity;
}

// This works perfectly
calculateTotal(19.99, 3);  // 59.97

// This also "works" but gives nonsense
calculateTotal("nineteen", 3);  // NaN

// This is clearly wrong but JavaScript does not complain
calculateTotal();  // NaN

JavaScript happily multiplies a string by a number, producing NaN (Not a Number). It lets you call a function with no arguments even though it clearly expects two. These are bugs, but JavaScript does not tell you about them until the program is running and a user encounters the broken behavior.

TypeScript was created by Microsoft in 2012 to solve this exact problem. It adds a type system on top of JavaScript that catches these errors at development time—before the code ever runs. The same function in TypeScript:

function calculateTotal(price: number, quantity: number): number {
  return price * quantity;
}

calculateTotal(19.99, 3);        // OK: 59.97
calculateTotal("nineteen", 3);   // ERROR: Argument of type 'string' is not
                                 //   assignable to parameter of type 'number'
calculateTotal();                // ERROR: Expected 2 arguments, but got 0

The errors appear immediately in your editor, with red underlines and clear messages, before you even save the file. You fix the bug in seconds instead of discovering it days later in production.

Analogy: JavaScript is like building with unlabeled boxes. You stack them up and hope the heavy ones are on the bottom. TypeScript is like having every box clearly labeled with its weight and contents. You can see immediately if you are putting a 50-pound box on top of an egg carton, and you fix it before the tower collapses.

TypeScript Is a Superset of JavaScript

The single most important thing to understand about TypeScript is that every valid JavaScript program is also a valid TypeScript program. TypeScript does not replace JavaScript; it extends it. You can take any .js file, rename it to .ts, and it will work (possibly with some type errors highlighted, but it will still compile).

TypeScript adds features on top of JavaScript:

  • Type annotations (: string, : number)
  • Interfaces and type aliases
  • Generics
  • Enums
  • Access modifiers (public, private, protected)

The TypeScript compiler (tsc) reads your .ts files, checks them for type errors, and outputs plain .js files. Browsers and Node.js never see TypeScript directly—they only run the compiled JavaScript. This means TypeScript has zero runtime cost: all the type information is stripped away during compilation.

TypeScript Compiler (tsc) app.ts ──────────────────────────────────> app.js (types + code) (just code) Your editor sees types Browser/Node runs JS and catches errors with no overhead

Installing and Configuring TypeScript

Installation

# Install TypeScript as a dev dependency
$ npm install --save-dev typescript

# Verify installation
$ npx tsc --version
Version 5.5.4

In a Next.js project (like CSK), TypeScript is included automatically. When you create a Next.js app with npx create-next-app@latest, it sets up TypeScript for you.

tsconfig.json: The Configuration File

The tsconfig.json file in your project root controls how TypeScript behaves. Let us examine the key options:

{
  "compilerOptions": {
    // What JavaScript version to output
    "target": "ES2017",

    // Module system (how imports/exports work)
    "module": "esnext",
    "moduleResolution": "bundler",

    // Strict type checking (highly recommended)
    "strict": true,
    "noImplicitAny": true,
    "strictNullChecks": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "noImplicitReturns": true,

    // Path aliases (import from '@/lib/supabase' instead of '../../../lib/supabase')
    "baseUrl": ".",
    "paths": {
      "@/*": ["./src/*"]
    },

    // JSX support for React
    "jsx": "preserve",

    // Other settings
    "esModuleInterop": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true,
    "resolveJsonModule": true,
    "isolatedModules": true,
    "incremental": true
  },
  "include": ["next-env.d.ts", "**/*.ts", "**/*.tsx"],
  "exclude": ["node_modules"]
}

Key Options Explained

OptionWhat It Does
targetThe JavaScript version to compile down to. "ES2017" supports modern browsers.
moduleThe module system to use. "esnext" supports modern import/export.
strictEnables ALL strict checks at once. The single most impactful setting.
pathsDefines import shortcuts. @/* maps to ./src/*, so you can write import { x } from '@/lib/utils'.
jsxHow to handle JSX (React's HTML-like syntax). "preserve" lets Next.js handle it.

The tsconfig.json configures @/ path aliases, so imports look like import { supabase } from '@/lib/supabase' instead of deeply nested relative paths. Types are defined in src/types/ for roles, gallery items, locations, and other domain objects.

Basic Types

TypeScript provides a set of fundamental types that correspond to the kinds of values in JavaScript. Let us go through each one.

Primitive Types

// String: text values
let name: string = "Computer Store KS";
let greeting: string = `Hello, ${name}`;

// Number: integers and decimals (no separate int/float)
let price: number = 299.99;
let quantity: number = 5;
let hex: number = 0xff;

// Boolean: true or false
let isOpen: boolean = true;
let hasDiscount: boolean = false;

null and undefined

These two types represent the absence of a value, but in slightly different ways:

// undefined: a variable that has been declared but not assigned a value
let middleName: string | undefined = undefined;

// null: an intentional absence of any value
let deletedAt: Date | null = null;

In practice, the convention is to use null when you intentionally want to represent "no value" and undefined when a value might not have been provided. With strict mode enabled, TypeScript forces you to check for these before using a value, preventing the dreaded "Cannot read property of null" error.

any — The Escape Hatch

// 'any' disables type checking for this variable
let data: any = "hello";
data = 42;        // No error
data = true;      // No error
data.foo.bar;     // No error (but will crash at runtime!)

Using any tells TypeScript "I do not care about the type, let anything through." This completely bypasses the type system and brings back all the problems of plain JavaScript. Avoid any whenever possible. It should be a last resort, not a habit.

unknown — The Safe Any

// 'unknown' is like 'any' but safe: you MUST check the type before using it
let input: unknown = getUserInput();

// This would be an error:
// input.toUpperCase();  // ERROR: 'input' is of type 'unknown'

// You must narrow the type first:
if (typeof input === "string") {
  input.toUpperCase();  // OK! TypeScript knows it's a string here
}

unknown is the type-safe alternative to any. Use it when you genuinely do not know what type a value will be (like parsing JSON or handling user input), and then narrow it down with type checks.

void and never

// void: function that does not return anything
function logMessage(message: string): void {
  console.log(message);
  // No return statement
}

// never: function that never returns (always throws or loops forever)
function throwError(message: string): never {
  throw new Error(message);
  // Code after this is unreachable
}

Type Annotations on Variables, Functions, and Returns

Type annotations are how you tell TypeScript what type a value should be. You add them with a colon after the name.

Variable Annotations

// Explicit type annotation
let city: string = "Topeka";
let zipCode: number = 66604;
let isActive: boolean = true;

// TypeScript can also INFER types (no annotation needed)
let state = "Kansas";        // TypeScript infers: string
let population = 125310;     // TypeScript infers: number
let founded = true;          // TypeScript infers: boolean

When you assign a value immediately, TypeScript is smart enough to figure out the type on its own. This is called type inference. You do not need to annotate every variable—only when the type is not obvious or when you want to be explicit.

Function Parameters and Return Types

// Annotate each parameter and the return type
function calculateDiscount(price: number, percent: number): number {
  return price * (percent / 100);
}

// Arrow function with types
const formatPrice = (amount: number): string => {
  return `$${amount.toFixed(2)}`;
};

// Function with no return value
function sendEmail(to: string, subject: string): void {
  // ... send the email
}

Annotating function parameters is the most important place to add types. This is where the most bugs are prevented, because it ensures that every caller passes the right kinds of arguments.

Arrays

TypeScript arrays are typed—you specify what kind of elements they contain.

// Two equivalent syntaxes for typed arrays
let prices: number[] = [299.99, 149.50, 89.00];
let names: Array<string> = ["Desktop", "Laptop", "Monitor"];

// TypeScript prevents wrong types
prices.push(199.99);     // OK
prices.push("free");     // ERROR: Argument of type 'string' is not
                         //   assignable to parameter of type 'number'

// Array of objects
let computers: { name: string; price: number }[] = [
  { name: "Gaming PC", price: 999 },
  { name: "Office PC", price: 499 }
];

Objects with Type Annotations

Objects in TypeScript have a specific shape—a set of properties with defined types.

// Inline object type
let computer: { name: string; price: number; inStock: boolean } = {
  name: "Custom Gaming PC",
  price: 1299.99,
  inStock: true
};

// Accessing properties works as expected
console.log(computer.name);    // "Custom Gaming PC"
console.log(computer.ram);     // ERROR: Property 'ram' does not exist

Inline object types get unwieldy quickly. That is where interfaces and type aliases come in.

Interfaces vs. Type Aliases

Both interfaces and type aliases let you define reusable type shapes. They are very similar, but each has strengths.

Interfaces

interface Computer {
  name: string;
  price: number;
  category: "desktop" | "laptop";
  specs: {
    cpu: string;
    ram: number;
    storage: string;
  };
}

// Use the interface as a type
const gamingPC: Computer = {
  name: "Custom Gaming PC",
  price: 1299.99,
  category: "desktop",
  specs: {
    cpu: "AMD Ryzen 7",
    ram: 32,
    storage: "1TB NVMe SSD"
  }
};

Interfaces can be extended, meaning you can build new interfaces on top of existing ones:

interface Product {
  name: string;
  price: number;
}

interface Computer extends Product {
  category: "desktop" | "laptop";
  specs: {
    cpu: string;
    ram: number;
  };
}

// Computer has name, price, category, AND specs

Type Aliases

type Computer = {
  name: string;
  price: number;
  category: "desktop" | "laptop";
};

// Type aliases can also represent non-object types
type ID = string | number;
type Status = "active" | "inactive" | "pending";
type PriceList = number[];
type Callback = (data: string) => void;

When to Use Which

Use Interfaces WhenUse Type Aliases When
Defining object shapes (most common case)Defining union types (string | number)
You want to extend/inherit from other typesDefining tuple types or complex types
Building APIs where others will extend your typesAliasing primitive types (type ID = string)

In practice, both work well for object types. Many teams pick one and use it consistently. The CSK project uses both: interfaces for component props and type aliases for union types and utility types.

Optional Properties

Not every property of an object is required. The ? operator marks a property as optional.

interface Customer {
  name: string;          // Required
  email: string;         // Required
  phone?: string;        // Optional (may be undefined)
  businessName?: string; // Optional
}

// This is valid even without phone and businessName
const customer: Customer = {
  name: "John Doe",
  email: "john@example.com"
};

// When accessing optional properties, check first
if (customer.phone) {
  console.log(`Call: ${customer.phone}`);
}

Union Types

A union type says "this value can be one of several types." You create unions with the | (pipe) operator.

// A value that could be a string OR a number
type ID = string | number;

let userId: ID = "abc-123";  // OK
userId = 42;                 // Also OK
userId = true;               // ERROR: Type 'boolean' is not assignable

// Function that accepts multiple types
function printId(id: string | number): void {
  // You need to check the type before using type-specific methods
  if (typeof id === "string") {
    console.log(id.toUpperCase());  // OK: TypeScript knows it's a string
  } else {
    console.log(id.toFixed(2));     // OK: TypeScript knows it's a number
  }
}

Literal Types

A literal type restricts a value to specific exact values, not just any value of that type.

// Instead of any string, only these specific strings are allowed
type TicketStatus = "new" | "diagnosing" | "repairing" | "ready_for_pickup" | "completed";

let status: TicketStatus = "new";        // OK
status = "diagnosing";                   // OK
status = "in_progress";                  // ERROR: not one of the allowed values

// Works with numbers too
type DiceRoll = 1 | 2 | 3 | 4 | 5 | 6;
let roll: DiceRoll = 4;    // OK
roll = 7;                  // ERROR

// Combine with interfaces for powerful modeling
interface GalleryItem {
  name: string;
  category: "desktop" | "laptop";
  condition: "new" | "refurbished" | "used";
  price: number;
}

Literal types are extremely useful for modeling domain concepts. Instead of accepting any string for a status field and hoping it is valid, you define exactly which values are allowed and TypeScript enforces it everywhere.

Type Narrowing and Type Guards

When a value has a union type, TypeScript does not let you use type-specific methods until you narrow the type. Narrowing means checking which specific type a value actually is at runtime, and TypeScript is smart enough to understand these checks.

typeof Guard

function processValue(value: string | number): string {
  if (typeof value === "string") {
    // TypeScript narrows: value is 'string' here
    return value.toUpperCase();
  } else {
    // TypeScript narrows: value is 'number' here
    return value.toFixed(2);
  }
}

instanceof Guard

function formatDate(value: string | Date): string {
  if (value instanceof Date) {
    // TypeScript narrows: value is 'Date' here
    return value.toISOString();
  } else {
    // TypeScript narrows: value is 'string' here
    return new Date(value).toISOString();
  }
}

in Operator Guard

interface Desktop {
  type: "desktop";
  towerSize: string;
}

interface Laptop {
  type: "laptop";
  screenSize: number;
  batteryLife: number;
}

type Computer = Desktop | Laptop;

function describeComputer(computer: Computer): string {
  if ("screenSize" in computer) {
    // TypeScript narrows: computer is 'Laptop' here
    return `Laptop with ${computer.screenSize}" screen`;
  } else {
    // TypeScript narrows: computer is 'Desktop' here
    return `Desktop with ${computer.towerSize} tower`;
  }
}

Discriminated Unions (Best Practice)

The most powerful narrowing pattern uses a shared property with literal types:

interface Desktop {
  type: "desktop";   // Discriminant property
  towerSize: string;
}

interface Laptop {
  type: "laptop";    // Discriminant property
  screenSize: number;
}

type Computer = Desktop | Laptop;

function getInfo(computer: Computer): string {
  switch (computer.type) {
    case "desktop":
      return `Tower: ${computer.towerSize}`;   // TS knows it's Desktop
    case "laptop":
      return `Screen: ${computer.screenSize}`; // TS knows it's Laptop
  }
}

Enums

Enums (enumerations) define a set of named constants. They are useful when you have a fixed set of related values.

// Numeric enum (values auto-increment from 0)
enum Direction {
  Up,      // 0
  Down,    // 1
  Left,    // 2
  Right    // 3
}

let move: Direction = Direction.Up;

// String enum (each value is explicitly set)
enum TicketStatus {
  New = "new",
  Diagnosing = "diagnosing",
  Repairing = "repairing",
  WaitingForParts = "waiting_for_parts",
  ReadyForPickup = "ready_for_pickup",
  Completed = "completed"
}

let status: TicketStatus = TicketStatus.New;
console.log(status);  // "new"

In modern TypeScript, many developers prefer union literal types over enums because they are simpler and have no runtime cost:

// Union literal: no runtime code generated, same type safety
type TicketStatus = "new" | "diagnosing" | "repairing" | "completed";

// Enum: generates runtime JavaScript code
enum TicketStatusEnum {
  New = "new",
  Diagnosing = "diagnosing"
}

Both approaches are valid. Use whichever your team prefers.

Generics

Generics let you write functions, interfaces, and types that work with multiple types while still maintaining type safety. Think of a generic as a type variable—a placeholder that gets filled in when you use it.

Analogy: A generic function is like a vending machine that works with any type of product. The machine does not care if it is dispensing sodas or snacks—the mechanism is the same. But once you put sodas in, it only dispenses sodas. Generics give you that flexibility without losing specificity.

Generic Functions

// Without generics: you would need separate functions for each type
function getFirstString(arr: string[]): string { return arr[0]; }
function getFirstNumber(arr: number[]): number { return arr[0]; }

// With generics: ONE function that works with ANY type
function getFirst<T>(arr: T[]): T {
  return arr[0];
}

// TypeScript infers T from what you pass
getFirst(["hello", "world"]);   // T is string, returns string
getFirst([1, 2, 3]);            // T is number, returns number
getFirst([true, false]);        // T is boolean, returns boolean

// You can also specify T explicitly
getFirst<string>(["hello"]);    // Explicitly set T to string

Generic Interfaces

// A reusable API response wrapper
interface ApiResponse<T> {
  data: T;
  status: number;
  message: string;
}

// Use it with different data types
type CustomerResponse = ApiResponse<Customer>;
// Equivalent to: { data: Customer; status: number; message: string }

type ComputerListResponse = ApiResponse<Computer[]>;
// Equivalent to: { data: Computer[]; status: number; message: string }

Practical Example: State Hook

// React's useState is a generic function
// You will see this pattern constantly in React + TypeScript
const [name, setName] = useState<string>("");
const [count, setCount] = useState<number>(0);
const [computers, setComputers] = useState<Computer[]>([]);

The @ Path Alias

In large projects, relative import paths get deeply nested and hard to read:

// Painful: deeply nested relative import
import { supabase } from '../../../lib/supabase';
import { Computer } from '../../../types/gallery';

The @/ path alias (configured in tsconfig.json) maps to your src/ directory:

// Clean: absolute import using the @ alias
import { supabase } from '@/lib/supabase';
import { Computer } from '@/types/gallery';

This works because of the paths configuration in tsconfig.json:

"paths": {
  "@/*": ["./src/*"]
}

No matter where a file is located in the project, imports always start from @/ (meaning src/). This makes refactoring easier because moving a file does not break its imports.

Strict Mode: What Each Flag Does

The "strict": true option in tsconfig.json enables a collection of individual strict checks. Here is what each one does:

FlagWhat It PreventsExample
noImplicitAny Using any by accident (when you forget to add a type) function greet(name) {} → Error: parameter has implicit any
strictNullChecks Using a value that might be null or undefined without checking const el = document.getElementById("x"); el.innerHTML = ""; → Error: el might be null
noUnusedLocals Declaring variables you never use (dead code) const x = 5; // never used → Error
noUnusedParameters Function parameters you never use function log(msg: string, level: number) { console.log(msg); } → level unused
noImplicitReturns Functions that sometimes return and sometimes do not An if branch returns but the else does not → Error
strictBindCallApply Incorrect arguments to .bind(), .call(), .apply() Passing wrong types to function.call() → Error
strictFunctionTypes Unsafe function type assignments Assigning a less specific function to a more specific type → Error

Strict mode catches more bugs but requires more discipline. It is strongly recommended for all new projects. Starting a project without strict mode and enabling it later is painful because you will have to fix hundreds of errors at once.

CSK Connection The CSK project runs TypeScript in full strict mode. Types for the project's domain objects live in src/types/—including types for user roles (admin, technician, reception), gallery items (desktops and laptops with specs and pricing), location data, and ticket statuses. The @/ path alias is used throughout the codebase, making imports clean and consistent. Every function parameter is typed, every return value is typed, and null/undefined values are always checked before use.

Complete tsconfig.json Walkthrough

Here is a reference for the most important tsconfig.json fields, grouped by purpose:

{
  "compilerOptions": {
    // === OUTPUT ===
    "target": "ES2017",           // JS version for output
    "module": "esnext",           // Module system
    "moduleResolution": "bundler",// How to find modules
    "outDir": "./dist",           // Where compiled JS goes (if using tsc directly)

    // === STRICTNESS ===
    "strict": true,               // Enable all strict checks
    "noImplicitAny": true,        // No accidental 'any'
    "strictNullChecks": true,     // Force null/undefined checks
    "noUnusedLocals": true,       // Flag unused variables
    "noUnusedParameters": true,   // Flag unused parameters
    "noImplicitReturns": true,    // All branches must return

    // === IMPORTS ===
    "baseUrl": ".",               // Root for path resolution
    "paths": { "@/*": ["./src/*"] }, // Path aliases
    "esModuleInterop": true,      // Better CommonJS/ESM compatibility
    "resolveJsonModule": true,    // Allow importing .json files

    // === REACT/NEXT.JS ===
    "jsx": "preserve",            // Let Next.js handle JSX
    "lib": ["dom", "ES2017"],     // Available APIs

    // === PERFORMANCE ===
    "incremental": true,          // Cache compilations
    "skipLibCheck": true,         // Skip checking node_modules types
    "isolatedModules": true       // Ensure each file can compile independently
  },
  "include": ["**/*.ts", "**/*.tsx"],
  "exclude": ["node_modules", "dist"]
}

Exercises

  1. Type annotations: Create a file called practice.ts. Declare variables with explicit types for: your name (string), your age (number), whether you are a student (boolean), and a list of your hobbies (string array). Try assigning a wrong type to each and observe the error messages.
  2. Function typing: Write a function greet that takes a name: string and returns a string. Write a function add that takes two numbers and returns a number. Write a function logItems that takes a string array and returns void. Try calling each with wrong argument types.
  3. Interface practice: Define an interface called Product with name (string), price (number), category (a union of "electronics" | "accessories" | "services"), and inStock (boolean, optional). Create three objects that conform to this interface.
  4. Union and narrowing: Write a function formatValue that accepts string | number | boolean. Use typeof guards to return: the string in uppercase, the number with 2 decimal places, or "Yes"/"No" for booleans.
  5. Generics: Write a generic function wrapInArray<T>(item: T): T[] that takes any value and returns it inside an array. Test it with a string, a number, and an object. Then write a generic interface ApiResponse<T> with data: T, success: boolean, and timestamp: string.
  6. Strict mode experiment: Create a tsconfig.json with "strict": false. Write a function with no parameter types and a variable that could be null. Then change strict to true and observe all the new errors that appear. Fix each one.
  7. Real-world modeling: Model a computer repair ticket with TypeScript. Create interfaces for Customer (name, email, phone optional), Ticket (id, customer, description, status using literal types, createdAt as Date), and a function createTicket that accepts the required fields and returns a Ticket.

Key Takeaways

  • TypeScript adds a type system to JavaScript that catches bugs at development time instead of runtime.
  • TypeScript is a superset of JavaScript—all valid JS is valid TS. TypeScript compiles to plain JS.
  • Basic types include string, number, boolean, null, undefined. Avoid any; prefer unknown for truly unknown values.
  • Interfaces define object shapes and can be extended. Type aliases can represent any type including unions.
  • The ? operator makes properties optional. Union types (string | number) allow multiple types.
  • Type narrowing with typeof, instanceof, and in lets you safely work with union types.
  • Generics (<T>) let you write reusable, type-safe functions and interfaces that work with any type.
  • The @/ path alias maps to src/, making imports clean regardless of file depth.
  • Always enable strict mode. It catches the most bugs and enforces the best practices.
  • tsconfig.json controls all TypeScript behavior: strictness, output, imports, and framework integration.
