Git & Version Control

Track every change, collaborate fearlessly, and never lose your work again — Git is the safety net every developer needs.

  • How to install and configure Git

  • The essential Git workflow: init, status, add, commit, log
  • Understanding and reading diffs

  • Branching, merging, and resolving merge conflicts
  • Working with GitHub: clone, push, pull, and pull requests

Why Version Control Matters

Imagine you are writing a research paper. You save it as paper.doc. Then you make some changes and save it as paper_v2.doc. Your professor gives feedback, so you save paper_v2_revised.doc. Then you decide to try a different approach: paper_v2_revised_experiment.doc. But the experiment does not work, so you go back to the revised version, but you have already made changes you want to keep: paper_v2_revised_FINAL.doc. Then one more change: paper_v2_revised_FINAL_actually_final.doc.

We have all been there. This is the chaos of working without version control. Now multiply this by thousands of files, and add five other people making changes at the same time. Software development without version control would be absolute mayhem.

Version control is a system that records changes to files over time so that you can recall specific versions later. It solves several critical problems:

  • History: You can see every change ever made to your project, who made it, when, and why.
  • Undo: You can revert any file, or the entire project, to any previous state.
  • Collaboration: Multiple people can work on the same project simultaneously without overwriting each other's work.
  • Experimentation: You can try new ideas in isolated branches. If they do not work, throw the branch away. If they do, merge it in.
  • Backup: With remote repositories (like GitHub), your code exists in multiple locations. If your laptop dies, your code survives.
Analogy: Think of Git like the "Track Changes" feature in Google Docs, but for your entire project. Every edit is recorded. You can see who wrote what and when. You can rewind to any point in time. And multiple people can edit simultaneously without conflicts—most of the time.

What Is Git?

Git is a distributed version control system (DVCS). It was created in 2005 by Linus Torvalds (the creator of Linux) because the existing version control tools were too slow for the massive Linux project. Git is now the overwhelmingly dominant version control system in software development. Virtually every open-source project and the vast majority of companies use Git.

The word "distributed" means that every developer has a complete copy of the project's entire history on their local machine. You do not need an internet connection to make commits, view history, create branches, or do anything else. The remote server (like GitHub) is just a convenient place to share and sync your work.

Git vs. GitHub

This is a common point of confusion for beginners. Git is the version control tool that runs on your computer. GitHub is a website and cloud service that hosts Git repositories and adds collaboration features like pull requests, issues, and project boards. Git works without GitHub. GitHub is built on top of Git. There are other hosting services too, like GitLab and Bitbucket, but GitHub is by far the most popular.

Installing and Configuring Git

Installation

Git may already be installed on your system. Check by running:

$ git --version
git version 2.43.0

If not installed:

  • Mac: Install Xcode Command Line Tools: xcode-select --install
  • Windows: Download from git-scm.com (includes Git Bash)
  • Linux: sudo apt install git (Ubuntu/Debian) or sudo dnf install git (Fedora)

Configuration

After installing, you need to tell Git who you are. This information is attached to every commit you make.

# Set your name (appears in commit history)
$ git config --global user.name "Your Name"

# Set your email (should match your GitHub email)
$ git config --global user.email "your.email@example.com"

# Set the default branch name to "main" (modern convention)
$ git config --global init.defaultBranch main

# Verify your settings
$ git config --list
user.name=Your Name
user.email=your.email@example.com
init.defaultbranch=main

The --global flag means these settings apply to all your Git repositories. You only need to do this once per computer.

Core Concepts: The Three Areas

Before you start using Git commands, you need to understand the three areas that Git uses to manage your files. This mental model is the key to understanding everything else about Git.

Working Directory Staging Area Repository (History) (your files on disk) (ready to commit) (permanent snapshots) +--------------+ +-----------+ +----------------+ | index.html | --add->| index.html| -commit->| Commit abc123 | | style.css | | | | "Add homepage"| | app.js | | | +----------------+ +--------------+ +-----------+ | Commit def456 | | "Add styles" | +----------------+

Working Directory

This is your actual project folder on your hard drive—the files you can see and edit. When you open a file in your text editor and make changes, you are changing the working directory. Git knows about these files but has not recorded your changes yet.

Staging Area (Index)

The staging area is like a preparation zone. When you use git add, you are telling Git: "I want to include this file's current state in my next commit." The staging area lets you carefully select exactly which changes to include in a commit, rather than committing everything at once.

Analogy: Think of the staging area like loading a moving truck. Your house (working directory) has many boxes. You pick specific boxes to load onto the truck (staging area). When the truck is loaded with exactly the boxes you want, you send the truck to storage (commit). You might have more boxes still in the house that you are not ready to move yet.

Repository (Commit History)

When you run git commit, Git takes a permanent snapshot of everything in the staging area and stores it in the repository. Each commit is like a save point in a video game—you can always go back to it. Commits are identified by a unique hash (a long string like a1b2c3d4e5f6) and include a message describing what changed.

The Essential Git Workflow

Here is the day-to-day workflow you will follow in every project. Let us walk through each command in detail.

git init — Create a Repository

This command creates a new Git repository in the current directory. It creates a hidden .git/ folder that stores all of Git's internal data.

$ mkdir my-project
$ cd my-project
$ git init
Initialized empty Git repository in /home/matthew/my-project/.git/

You only run git init once per project, at the very beginning.

git status — Check the State of Things

This is the command you will run most often. It tells you which files have been modified, which are staged, and which are untracked (new files Git has not seen before).

$ touch index.html style.css
$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        index.html
        style.css

nothing added to commit but untracked files present (use "git add" to track)

Git is telling you: "I see two new files, but they are not being tracked yet. Use git add to start tracking them."

git add — Stage Changes

Moves files from the working directory to the staging area.

# Stage a specific file
$ git add index.html

# Stage multiple files
$ git add index.html style.css

# Stage ALL changes (new, modified, and deleted files)
$ git add .

# Stage all files matching a pattern
$ git add *.css

The git add . command (with a dot) stages everything in the current directory and its subdirectories. It is the most common form, but sometimes you want to be selective and stage files individually.

git commit — Save a Snapshot

Creates a permanent snapshot of everything currently in the staging area.

# Commit with a message
$ git commit -m "feat: add homepage structure and base styles"

[main (root-commit) a1b2c3d] feat: add homepage structure and base styles
 2 files changed, 0 insertions(+), 0 deletions(-)
 create mode 100644 index.html
 create mode 100644 style.css

Every commit must have a message that describes what changed. The -m flag lets you write the message inline. Without -m, Git opens your default text editor for you to write a longer message.

git log — View Commit History

Shows the history of commits, most recent first.

$ git log
commit a1b2c3d4e5f6789012345678 (HEAD -> main)
Author: Your Name <your.email@example.com>
Date:   Wed Feb 5 10:00:00 2026 -0600

    feat: add homepage structure and base styles

# Compact one-line format
$ git log --oneline
a1b2c3d feat: add homepage structure and base styles

# Show a graph of branches
$ git log --oneline --graph --all
* a1b2c3d (HEAD -> main) feat: add homepage structure and base styles

Understanding Diffs

A diff (short for "difference") shows you exactly what changed between two versions of a file. Git uses diffs extensively, and learning to read them is an essential skill.

$ git diff
diff --git a/index.html b/index.html
index 83db48f..f73541a 100644
--- a/index.html
+++ b/index.html
@@ -1,3 +1,5 @@
 <!DOCTYPE html>
 <html>
+<head>
+  <title>My Site</title>
+</head>
 <body>
-  <h1>Hello</h1>
+  <h1>Hello World</h1>
 </body>

Reading a diff:

  • Lines starting with + (green) are additions—new content that was added.
  • Lines starting with - (red) are deletions—content that was removed.
  • Lines with no prefix are context—unchanged lines shown for reference.
  • The @@ line tells you which line numbers are affected.

You can view different types of diffs:

# Changes in working directory (not yet staged)
$ git diff

# Changes that are staged (ready to commit)
$ git diff --staged

# Changes between two specific commits
$ git diff a1b2c3d def4567

.gitignore: Excluding Files from Git

Not every file in your project should be tracked by Git. Some files are generated automatically (like node_modules/), some contain secrets (like .env), and some are operating system junk (like .DS_Store on Mac). The .gitignore file tells Git which files and directories to completely ignore.

Create a .gitignore file in the root of your project:

# Dependencies (auto-installed, huge, never commit)
node_modules/

# Environment variables (contain secrets)
.env
.env.local
.env.production

# Build output (generated from source code)
.next/
build/
dist/

# Operating system files
.DS_Store
Thumbs.db

# IDE settings (personal preference, not project code)
.vscode/settings.json
.idea/

# Debug logs
npm-debug.log*
yarn-debug.log*

Each line is a pattern. Lines starting with # are comments. A trailing / means "match directories." An asterisk * is a wildcard that matches anything. Git checks this file before tracking or committing anything, and silently skips anything that matches a pattern.

Commit .gitignore early! If you accidentally commit a file and then add it to .gitignore, Git will continue tracking it. The .gitignore only prevents new files from being tracked. To stop tracking an already-committed file, you need: git rm --cached filename. This is a common beginner mistake, especially with node_modules/ and .env files.
CSK Connection The CSK project's .gitignore excludes node_modules/ (over 1,000 packages totaling hundreds of megabytes), all .env files (which contain Supabase keys, Resend API keys, and session secrets), the .next/ build folder, and OS-specific files. Without .gitignore, these would bloat the repository and potentially expose secrets.

Branching

Branching is one of Git's most powerful features. A branch is an independent line of development. Think of your project's history as a timeline. When you create a branch, you fork the timeline into two parallel tracks. You can work on one track without affecting the other. When you are satisfied with the work on your branch, you merge it back into the main timeline.

Analogy: Imagine you are writing a novel. The main branch is the published manuscript. You want to try a new chapter, but you are not sure it will work. Instead of editing the original, you photocopy the manuscript and write your new chapter on the copy. If it works, you add it to the original. If not, you throw the copy away. The original was never at risk.

Creating and Switching Branches

# See all branches (the asterisk marks the current branch)
$ git branch
* main

# Create a new branch
$ git branch feature/add-navigation

# Switch to the new branch
$ git checkout feature/add-navigation

# Or create AND switch in one command (shortcut)
$ git checkout -b feature/add-navigation

# Modern alternative to checkout for switching
$ git switch feature/add-navigation

# Create and switch with the modern command
$ git switch -c feature/add-navigation

When you create a branch, it starts as an exact copy of whatever branch you were on. From that point forward, commits on the new branch do not affect the original branch, and vice versa.

Merging Branches

When the work on a branch is complete, you merge it back into the main branch.

# Switch to the branch you want to merge INTO
$ git checkout main

# Merge the feature branch into main
$ git merge feature/add-navigation
Updating a1b2c3d..e5f6789
Fast-forward
 src/components/Navigation.tsx | 45 +++++++++++++++++++++++++++
 1 file changed, 45 insertions(+)

Deleting Branches

After merging, you can safely delete the feature branch since its changes are now in main.

# Delete a merged branch
$ git branch -d feature/add-navigation
Deleted branch feature/add-navigation (was e5f6789).

# Force-delete an unmerged branch (careful!)
$ git branch -D experimental-branch

Remote Repositories and GitHub

So far, everything has been local—on your own computer. Remote repositories are copies of your project hosted on a server (like GitHub) that you and your team can push to and pull from.

git clone — Copy a Remote Repository

Downloading an existing project from GitHub:

$ git clone https://github.com/username/project-name.git
Cloning into 'project-name'...
remote: Counting objects: 156, done.
Receiving objects: 100% (156/156), 1.24 MiB, done.

$ cd project-name
$ ls
README.md  package.json  src/  public/

git clone creates a new folder, downloads all files and complete history, and automatically sets up the remote connection.

git push — Upload Your Commits

Sends your local commits to the remote repository.

# Push the current branch to the remote named "origin"
$ git push origin main

# If it is your first push for a branch, set upstream tracking
$ git push -u origin main

# After setting upstream, you can just use:
$ git push

git pull — Download and Merge Updates

Fetches new commits from the remote and merges them into your current branch.

# Pull the latest changes
$ git pull origin main

# Or simply, after upstream is set:
$ git pull

git fetch — Download Without Merging

git fetch downloads new commits from the remote but does not merge them. This lets you review changes before deciding to integrate them.

# Fetch updates from the remote
$ git fetch origin

# See what changed
$ git log origin/main --oneline

# Merge when ready
$ git merge origin/main

Pull Requests and Code Review

A pull request (PR) is a GitHub feature (not a Git feature) that lets you propose changes from one branch to another. Instead of directly merging your feature branch into main, you create a pull request that says: "Here are my changes. Please review them before merging."

The typical workflow is:

  1. Create a branch for your feature
  2. Make commits on that branch
  3. Push the branch to GitHub
  4. Open a pull request on GitHub's website
  5. Team members review the code, leave comments, and request changes
  6. After approval, the PR is merged

Pull requests are the standard way professional teams collaborate. They create a documented record of every change, the discussion around it, and who approved it. Even on solo projects, pull requests can be valuable for organizing your work and creating a clean history.

Merge Conflicts

A merge conflict happens when Git cannot automatically combine changes from two branches because both branches modified the same part of the same file differently. Git does not know which version to keep, so it asks you to decide.

Here is what a merge conflict looks like in a file:

<<<<<<< HEAD
  <h1>Welcome to Our Store</h1>
=======
  <h1>Welcome to Computer Store KS</h1>
>>>>>>> feature/update-heading

Git marks the conflict with special delimiters:

  • <<<<<<< HEAD — Start of YOUR current branch's version
  • ======= — Divider between the two versions
  • >>>>>>> feature/update-heading — Start of the INCOMING branch's version

To resolve the conflict:

  1. Open the file in your editor
  2. Find the conflict markers
  3. Choose which version to keep (or combine both)
  4. Delete the conflict markers (<<<, ===, >>>)
  5. Stage and commit the resolved file
# After manually resolving the conflict in your editor:
$ git add index.html
$ git commit -m "fix: resolve merge conflict in heading"
Do not panic about merge conflicts Merge conflicts are normal and happen regularly in team environments. They are not errors or failures. They simply mean two people edited the same area, and Git needs a human to make the decision about which changes to keep. With practice, resolving conflicts becomes routine.

Commit Message Conventions

Good commit messages are essential. They serve as documentation for your project's history. When something breaks, you look at the commit log to figure out what changed and when. If commit messages are vague ("updated stuff," "fixes," "WIP"), that history becomes useless.

We use Conventional Commits, a standard format used widely in the industry:

type: short description of the change
TypeWhen to UseExample
feat:New feature or functionalityfeat: add customer search to admin dashboard
fix:Bug fixfix: resolve login redirect loop
docs:Documentation changes onlydocs: update API endpoint descriptions
refactor:Code change that neither fixes nor addsrefactor: simplify authentication logic
test:Adding or updating teststest: add unit tests for email validation
chore:Maintenance taskschore: update dependencies
style:Formatting, no code logic changesstyle: fix indentation in header component

Guidelines for good messages:

  • Use the imperative mood: "add feature" not "added feature" or "adds feature"
  • Keep the first line under 72 characters
  • Do not end the subject line with a period
  • Explain what and why, not how (the code shows how)
CSK Connection The Computer Store KS project follows these exact commit conventions. Looking at the commit history, you will see messages like feat: add user authentication, fix: resolve login redirect loop, and docs: update API documentation. This makes it easy to scan the history and understand what each change did.

Complete Walkthrough: Your First Git Project

Let us put everything together in a complete, start-to-finish example. Follow along in your terminal.

# ---- Step 1: Create and initialize the project ----
$ mkdir git-practice && cd git-practice
$ git init
Initialized empty Git repository in /home/matthew/git-practice/.git/

# ---- Step 2: Create the initial files ----
$ echo "<!DOCTYPE html><html><body><h1>Hello</h1></body></html>" > index.html
$ echo "body { font-family: sans-serif; }" > style.css
$ echo "node_modules/" > .gitignore

# ---- Step 3: Check status ----
$ git status
Untracked files:
  .gitignore
  index.html
  style.css

# ---- Step 4: Stage and commit ----
$ git add .
$ git commit -m "feat: add initial project files"
[main (root-commit) abc1234] feat: add initial project files
 3 files changed, 3 insertions(+)

# ---- Step 5: Make changes and commit again ----
$ echo "h1 { color: navy; }" >> style.css
$ git status
Changes not staged for commit:
  modified:   style.css

$ git diff
+h1 { color: navy; }

$ git add style.css
$ git commit -m "style: add heading color"

# ---- Step 6: View the history ----
$ git log --oneline
def5678 style: add heading color
abc1234 feat: add initial project files

# ---- Step 7: Create a feature branch ----
$ git checkout -b feature/add-navigation

# ---- Step 8: Work on the feature ----
$ echo "<nav><a href='/'>Home</a></nav>" > nav.html
$ git add nav.html
$ git commit -m "feat: add navigation component"

# ---- Step 9: Switch back to main ----
$ git checkout main
$ ls
index.html  style.css  .gitignore
# Note: nav.html does NOT exist on main!

# ---- Step 10: Merge the feature branch ----
$ git merge feature/add-navigation
$ ls
index.html  nav.html  style.css  .gitignore
# Now nav.html is here!

# ---- Step 11: Delete the merged branch ----
$ git branch -d feature/add-navigation

# ---- Step 12: View the complete history ----
$ git log --oneline --graph --all
* ghi9012 (HEAD -> main) feat: add navigation component
* def5678 style: add heading color
* abc1234 feat: add initial project files
CSK Connection The CSK project uses a Production-branch workflow. All development work happens directly in the Production branch. Changes are tested locally with npm run dev, reviewed with the project owner, and then pushed to Production on GitHub. Render watches the Production branch and automatically deploys when new commits arrive. The .gitignore in the CSK project excludes node_modules/, all .env files, the .next/ build directory, and operating system artifacts like .DS_Store.

Exercises

  1. First repository: Create a new folder, initialize a Git repository, create three files (index.html, style.css, app.js), and make your first commit with a conventional commit message.
  2. Multi-commit history: Starting from your repository, make at least 5 separate commits, each modifying or adding different files. Use a variety of commit types (feat:, fix:, docs:, style:). View the history with git log --oneline.
  3. .gitignore practice: Create a .gitignore file that ignores node_modules/, .env, .DS_Store, and any .log files. Create a file called test.log and verify that git status does not show it.
  4. Branching exercise: Create a branch called feature/footer. Switch to it, create a file called footer.html, and commit it. Switch back to main and verify the file does not exist. Merge the branch and verify the file appears.
  5. Deliberate conflict: Create a branch. On main, edit line 1 of index.html and commit. Switch to your branch, edit the same line differently, and commit. Try to merge. Resolve the conflict manually, then complete the merge.
  6. Read a diff: Modify a file with several changes (add lines, remove lines, change lines). Before committing, run git diff and practice reading the output. Identify each addition, deletion, and context line.
  7. GitHub connection: Create a free GitHub account if you do not have one. Create a new repository on GitHub. Follow the instructions to push your local repository to GitHub. Practice git push and verify your code appears on the GitHub website.

Key Takeaways

  • Version control records every change so you can undo mistakes, collaborate safely, and maintain a complete project history.
  • Git is the tool (runs on your computer); GitHub is the hosting service (stores your code online).
  • The three areas: working directory (your files), staging area (selected for commit), repository (permanent history).
  • The core loop is: edit files, git add, git commit, repeat.
  • .gitignore prevents files like node_modules/ and .env from being committed. Create it early.
  • Branches let you experiment safely. Merge when done, delete the branch.
  • Merge conflicts are normal. Git marks the conflicts, you choose the resolution, then commit.
  • Conventional commit messages (feat:, fix:, docs:) create a readable, searchable project history.
  • git push uploads your work; git pull downloads teammates' work. Together they keep everyone in sync.
