What Are Database Triggers?

A trigger is a piece of code that the database runs automatically in response to a data event — an INSERT, UPDATE, or DELETE on a table. You do not call triggers directly; they fire on their own whenever the specified event happens.

Analogy: Think of a trigger like a motion-sensor light. You do not flip a switch — the light turns on automatically when it detects movement. A database trigger works the same way: when data "moves" (is inserted, updated, or deleted), the trigger automatically runs its code. You install it once and it works forever, regardless of which application or API route caused the data change.

Triggers are powerful because they enforce business logic at the database level. It does not matter if data changes come from your Next.js app, a webhook handler, the Supabase Dashboard, or a direct SQL query — the trigger fires regardless.

Trigger Timing: BEFORE vs AFTER

Triggers can fire at two different points in time:

TimingWhen It FiresCan Modify Data?Use Case
BEFORE Before the data change is saved Yes — can modify the row being written Auto-set timestamps, validate data, transform values
AFTER After the data change is saved No — the row is already committed Create related records, send notifications, audit logging
User's SQL statement arrives | v +-- BEFORE trigger fires --+ | Can modify NEW row | | Can cancel operation | +--------------------------+ | v Database writes the row | v +-- AFTER trigger fires ---+ | Row is committed | | Can do side effects | +--------------------------+ | v Result returned to user

Key difference: A BEFORE trigger can change the values being written (by modifying NEW). An AFTER trigger cannot change the row, but it can do things like insert rows into other tables.

Trigger Events: INSERT, UPDATE, DELETE

A trigger can respond to one or more of these events:

EventWhen It FiresAvailable References
INSERTA new row is being addedNEW (the row being inserted)
UPDATEAn existing row is being changedOLD (before change) and NEW (after change)
DELETEA row is being removedOLD (the row being deleted)

You can combine events:

-- Fire on both INSERT and UPDATE
CREATE TRIGGER my_trigger
  BEFORE INSERT OR UPDATE ON my_table
  FOR EACH ROW
  EXECUTE FUNCTION my_function();

The NEW and OLD Row References

NEW and OLD are special variables available inside trigger functions. They represent the row being affected:

VariableOn INSERTOn UPDATEOn DELETE
NEWThe row being insertedThe row after changesNot available
OLDNot availableThe row before changesThe row being deleted
 
-- Access specific columns via dot notation
NEW.updated_at    -- The value of updated_at in the new/modified row
OLD.status        -- The value of status before the update
NEW.name          -- The name being set on the row

Writing Trigger Functions in PL/pgSQL

Triggers in PostgreSQL work in two parts:

  1. A trigger function — the code that runs (written in PL/pgSQL)
  2. A trigger — the rule that connects the function to a table and event

PL/pgSQL (Procedural Language / PostgreSQL) is PostgreSQL's built-in programming language for writing functions. It looks like a mix of SQL and a simple scripting language.

Basic Trigger Function Structure

CREATE OR REPLACE FUNCTION my_trigger_function()
RETURNS TRIGGER AS $$
BEGIN
  -- Your logic here
  -- Modify NEW, insert into other tables, etc.

  RETURN NEW;  -- For BEFORE triggers: return the (possibly modified) row
               -- For AFTER triggers: return value is ignored but required
END;
$$ LANGUAGE plpgsql;

Key points:

  • The function must RETURN TRIGGER
  • For BEFORE INSERT/UPDATE triggers, return NEW (the modified row) to allow the operation, or NULL to cancel it
  • For BEFORE DELETE triggers, return OLD to allow the deletion, or NULL to cancel it
  • For AFTER triggers, the return value is ignored but RETURN NEW or RETURN OLD is conventional

Common Pattern: Auto-Updating updated_at

This is the single most common trigger in any application. It automatically sets the updated_at column to the current time whenever a row is modified.

-- Step 1: Create the trigger function (reusable across tables)
CREATE OR REPLACE FUNCTION update_updated_at_column()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = NOW();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- Step 2: Attach it to a table
CREATE TRIGGER update_blog_posts_updated_at
  BEFORE UPDATE ON blog_posts
  FOR EACH ROW
  EXECUTE FUNCTION update_updated_at_column();

Now every time a blog post is updated, updated_at is automatically set to the current time — no application code needed.

The beauty of this pattern is that the function is reusable. You can attach the same function to every table that has an updated_at column:

-- Same function, different tables
CREATE TRIGGER update_customers_updated_at
  BEFORE UPDATE ON customers
  FOR EACH ROW
  EXECUTE FUNCTION update_updated_at_column();

CREATE TRIGGER update_businesses_updated_at
  BEFORE UPDATE ON businesses
  FOR EACH ROW
  EXECUTE FUNCTION update_updated_at_column();

CREATE TRIGGER update_tickets_updated_at
  BEFORE UPDATE ON tickets
  FOR EACH ROW
  EXECUTE FUNCTION update_updated_at_column();
CSK Connection CSK's blog schema includes exactly this trigger. The update_updated_at_column() function is attached to blog_posts as update_blog_posts_updated_at. The businesses table has its own version called update_businesses_timestamp(). Both use the same BEFORE UPDATE pattern.

Common Pattern: Auto-Creating Related Records

Sometimes when data changes in one table, you need to automatically create or update data in another table. This is a perfect job for an AFTER trigger or a BEFORE trigger with side effects.

Example: Auto-Linking Customers to Businesses

When a customer's business_name changes, we want to automatically:

  1. Create the business in the businesses table if it does not exist
  2. Link the customer to that business via business_id
-- The trigger function
CREATE OR REPLACE FUNCTION link_customer_to_business()
RETURNS TRIGGER AS $$
BEGIN
  -- Only act if the customer has a business name
  IF NEW.business_name IS NOT NULL AND NEW.business_name != '' THEN
    -- Create the business if it does not exist
    INSERT INTO businesses (name)
    VALUES (NEW.business_name)
    ON CONFLICT (name) DO NOTHING;

    -- Look up the business ID and set it on the customer
    SELECT id INTO NEW.business_id
    FROM businesses
    WHERE name = NEW.business_name;
  ELSE
    -- No business name, clear the link
    NEW.business_id := NULL;
  END IF;

  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- Attach to the customers table
-- Fires on INSERT or when business_name specifically changes
CREATE TRIGGER trg_link_customer_business
  BEFORE INSERT OR UPDATE OF business_name ON rs_customers
  FOR EACH ROW
  EXECUTE FUNCTION link_customer_to_business();

Let us walk through what happens step by step:

Employee updates customer's business_name to "Acme Corp" | v BEFORE trigger fires: link_customer_to_business() | v Is business_name non-empty? YES | v INSERT INTO businesses (name) VALUES ('Acme Corp') ON CONFLICT (name) DO NOTHING -- If "Acme Corp" already exists, nothing happens -- If it is new, a row is created | v SELECT id INTO NEW.business_id FROM businesses WHERE name = 'Acme Corp' -- Sets the customer's business_id to the business's ID | v RETURN NEW (customer row now has business_id set) | v Database saves the customer row with the correct business_id
CSK Connection This is a real trigger from the CSK codebase. The trg_link_customer_business trigger on the rs_customers table automatically creates and links business records whenever a customer's business_name changes. This means no manual sync is needed for businesses — the database handles it automatically, whether the change comes from the web app, a webhook, or a direct database edit.

Common Pattern: Cascading Changes

Triggers can propagate changes from one table to related tables:

-- When a ticket status changes, log it to an audit table
CREATE OR REPLACE FUNCTION log_ticket_status_change()
RETURNS TRIGGER AS $$
BEGIN
  -- Only log if the status actually changed
  IF OLD.status IS DISTINCT FROM NEW.status THEN
    INSERT INTO ticket_status_history (
      ticket_id,
      old_status,
      new_status,
      changed_at
    ) VALUES (
      NEW.id,
      OLD.status,
      NEW.status,
      NOW()
    );
  END IF;

  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_log_ticket_status
  AFTER UPDATE ON tickets
  FOR EACH ROW
  EXECUTE FUNCTION log_ticket_status_change();

Notice the use of IS DISTINCT FROM instead of !=. This correctly handles NULL values — if either value is NULL, != returns NULL (not true), but IS DISTINCT FROM returns true.

FOR EACH ROW vs FOR EACH STATEMENT

Triggers can fire at two granularity levels:

ModeWhen It FiresUse Case
FOR EACH ROW Once per affected row Most triggers — modifying individual rows, logging per-row changes
FOR EACH STATEMENT Once per SQL statement (regardless of how many rows) Notification triggers, batch summary logging 
-- This fires once for EACH row being updated
-- If you UPDATE 100 rows, the function runs 100 times
CREATE TRIGGER update_timestamps
  BEFORE UPDATE ON blog_posts
  FOR EACH ROW
  EXECUTE FUNCTION update_updated_at_column();

-- This fires ONCE for the entire statement
-- If you UPDATE 100 rows, the function runs once
CREATE TRIGGER notify_bulk_update
  AFTER UPDATE ON blog_posts
  FOR EACH STATEMENT
  EXECUTE FUNCTION notify_admin_of_changes();

FOR EACH ROW is used in the vast majority of triggers because you typically need to work with individual rows (using NEW and OLD).

When Triggers Are Good

  • Auto-updating timestamps — simple, universal, no downside
  • Data integrity that spans tables — auto-linking related records
  • Audit logging — tracking who changed what and when
  • Derived/computed values — auto-calculating totals, setting slugs
  • Default values based on other columns — more complex than DEFAULT allows

When Triggers Are Dangerous

Trigger Pitfalls Triggers are invisible to the developer writing the SQL or application code. If you do not know a trigger exists, you may be confused by unexpected behavior. Use triggers judiciously and always document them.
  • Hidden side effects — Developers may not realize a trigger exists, leading to confusion when data changes "by itself"
  • Performance impact — Triggers add overhead to every matching operation. A slow trigger on a high-traffic table can cripple performance
  • Cascade chains — Trigger A updates Table B, which fires Trigger B on Table B, which updates Table C, which fires Trigger C... This can create hard-to-debug chains or even infinite loops
  • Difficult to test — Triggers run inside the database, outside your application's test framework
  • Complex business logic — If your trigger function is 100+ lines long, the logic probably belongs in your application code where it is easier to test, debug, and maintain

Rule of Thumb

Use a Trigger When...Use Application Code When...
Logic is simple (1-10 lines)Logic is complex (conditionals, loops, external calls)
Must apply regardless of data sourceOnly applies to specific API endpoints
Pure data transformation (no external services)Needs to call APIs, send emails, etc.
Critical data integrityBusiness logic that may change frequently

Debugging Triggers

Viewing Existing Triggers

-- List all triggers in your database
SELECT
  trigger_name,
  event_manipulation AS event,
  event_object_table AS table_name,
  action_timing AS timing,
  action_orientation AS scope
FROM information_schema.triggers
WHERE trigger_schema = 'public'
ORDER BY event_object_table, trigger_name;

Viewing Trigger Function Source Code

-- See the source code of a trigger function
SELECT prosrc
FROM pg_proc
WHERE proname = 'link_customer_to_business';

Temporarily Disabling a Trigger

-- Disable a specific trigger
ALTER TABLE rs_customers DISABLE TRIGGER trg_link_customer_business;

-- Test your operation without the trigger...

-- Re-enable it
ALTER TABLE rs_customers ENABLE TRIGGER trg_link_customer_business;

-- Disable ALL triggers on a table (dangerous!)
ALTER TABLE rs_customers DISABLE TRIGGER ALL;

Adding Debug Logging

CREATE OR REPLACE FUNCTION my_debug_trigger()
RETURNS TRIGGER AS $$
BEGIN
  -- RAISE NOTICE prints to the database logs
  RAISE NOTICE 'Trigger fired on %: OLD.name=%, NEW.name=%',
    TG_TABLE_NAME, OLD.name, NEW.name;

  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

RAISE NOTICE outputs messages to the PostgreSQL logs, which you can view in the Supabase Dashboard under Logs.

Special Trigger Variables

VariableValue
TG_NAMEName of the trigger that fired
TG_TABLE_NAMEName of the table that caused the trigger
TG_OPThe operation: 'INSERT', 'UPDATE', or 'DELETE'
TG_WHENThe timing: 'BEFORE' or 'AFTER'
 
-- A function that handles multiple events
CREATE OR REPLACE FUNCTION multi_event_handler()
RETURNS TRIGGER AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    -- Handle insert logic
    RETURN NEW;
  ELSIF TG_OP = 'UPDATE' THEN
    -- Handle update logic
    RETURN NEW;
  ELSIF TG_OP = 'DELETE' THEN
    -- Handle delete logic
    RETURN OLD;
  END IF;
END;
$$ LANGUAGE plpgsql;

Complete Example: Building a Full Trigger System

Let us build a complete trigger system for a ticket management table that:

  1. Auto-sets updated_at on every change
  2. Logs status changes to a history table
  3. Auto-sets resolved_at when status changes to "resolved"
-- The tables
CREATE TABLE tickets (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  subject TEXT NOT NULL,
  status VARCHAR(20) DEFAULT 'new',
  customer_id UUID NOT NULL,
  resolved_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE ticket_status_history (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  ticket_id UUID NOT NULL REFERENCES tickets(id) ON DELETE CASCADE,
  old_status VARCHAR(20),
  new_status VARCHAR(20) NOT NULL,
  changed_at TIMESTAMPTZ DEFAULT NOW()
);

-- Trigger 1: Auto-update updated_at
CREATE TRIGGER trg_tickets_updated_at
  BEFORE UPDATE ON tickets
  FOR EACH ROW
  EXECUTE FUNCTION update_updated_at_column();

-- Trigger 2: Log status changes and auto-set resolved_at
CREATE OR REPLACE FUNCTION handle_ticket_status_change()
RETURNS TRIGGER AS $$
BEGIN
  -- Only act if status actually changed
  IF OLD.status IS DISTINCT FROM NEW.status THEN
    -- Log the change
    INSERT INTO ticket_status_history (ticket_id, old_status, new_status)
    VALUES (NEW.id, OLD.status, NEW.status);

    -- Auto-set resolved_at when status becomes 'resolved'
    IF NEW.status = 'resolved' AND OLD.status != 'resolved' THEN
      NEW.resolved_at = NOW();
    END IF;

    -- Clear resolved_at if status changes away from 'resolved'
    IF NEW.status != 'resolved' AND OLD.status = 'resolved' THEN
      NEW.resolved_at = NULL;
    END IF;
  END IF;

  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_ticket_status_change
  BEFORE UPDATE ON tickets
  FOR EACH ROW
  EXECUTE FUNCTION handle_ticket_status_change();

Now when a ticket's status changes:

  • updated_at is set to NOW() (by trigger 1)
  • A row is added to ticket_status_history (by trigger 2)
  • If status is now "resolved," resolved_at is set (by trigger 2)
  • All automatically, regardless of what caused the status change

Hands-On Exercises

  1. Timestamp Trigger: Create a products table with id, name, price, created_at, and updated_at. Write and attach a trigger that auto-updates updated_at on every change.
  2. Auto-Slug Trigger: Write a BEFORE INSERT trigger on a blog_posts table that automatically generates a slug from the title if no slug is provided. (Hint: use LOWER() and REPLACE() functions.)
  3. Audit Trail: Create an audit_log table with columns: id, table_name, operation (INSERT/UPDATE/DELETE), row_id, old_data (JSONB), new_data (JSONB), and changed_at. Write a trigger function that logs changes to any table it is attached to. (Hint: use TG_TABLE_NAME, TG_OP, and row_to_json().)
  4. Conditional Trigger: Write a trigger that only fires when a specific column changes. For a tickets table, create a trigger that inserts into notifications only when the status column changes to 'ready_for_pickup'.
  5. Debugging Practice: Write a query to list all triggers in your database. Then write a trigger function that uses RAISE NOTICE to log the trigger name, table name, operation, and key values from NEW and OLD.
  6. Design Decision: For each scenario, decide whether a trigger or application code is more appropriate, and explain why: (a) auto-calculating a total from line items, (b) sending an email when an order is placed, (c) preventing deletion of an admin user, (d) resizing an uploaded image.

Key Takeaways

  • Triggers are database functions that fire automatically on INSERT, UPDATE, or DELETE.
  • BEFORE triggers can modify the row being written; AFTER triggers are for side effects.
  • NEW holds the row after changes; OLD holds the row before changes.
  • The auto-updating updated_at trigger is nearly universal — every table should have one.
  • Triggers can auto-create related records, like CSK's business auto-linking trigger.
  • Use FOR EACH ROW for most triggers; FOR EACH STATEMENT for batch operations.
  • IS DISTINCT FROM is the NULL-safe way to check if a value changed.
  • Triggers are powerful but invisible — document them well and keep logic simple.
  • Use triggers for data integrity (timestamps, links, constraints). Use application code for complex business logic (emails, API calls, user notifications).
  • Debug with RAISE NOTICE, information_schema.triggers, and temporary disabling.
