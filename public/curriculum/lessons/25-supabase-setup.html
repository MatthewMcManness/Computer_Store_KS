What Is Supabase?

Supabase is an open-source backend-as-a-service built on top of PostgreSQL. It provides a full PostgreSQL database with a generous free tier, plus additional services:

  • Database — A full PostgreSQL instance you can query with SQL or the JavaScript client
  • Authentication — Email/password, OAuth, magic links, and more
  • Storage — File uploads (images, documents) with access control
  • Realtime — Live subscriptions to database changes
  • Edge Functions — Serverless functions written in TypeScript
Analogy: If PostgreSQL is a powerful engine, Supabase is the complete car built around it. You get the engine (database), but also a dashboard (admin UI), API layer (REST endpoints), key ignition (authentication), trunk (file storage), and a radio (realtime updates) — all pre-wired and ready to go.

Supabase is often described as an "open-source Firebase alternative." Unlike Firebase (which uses a proprietary NoSQL database), Supabase gives you a standard PostgreSQL database that you fully own and can migrate away from at any time.

Creating a Supabase Project

Follow these steps to create your free Supabase project:

  1. Sign up at supabase.com
    Create an account using GitHub or email. The free tier allows up to 2 projects.
  2. Create a new project
    Click "New Project." Choose your organization, give the project a name (e.g., "computer-store-ks"), set a strong database password (save it somewhere safe), and pick a region close to your users (e.g., "East US").
  3. Wait for provisioning
    Supabase will take 1-2 minutes to create your PostgreSQL database and generate API keys.
  4. Copy your credentials
    Go to Settings → API. You will need three values:
    • Project URL — looks like https://xxxxx.supabase.co
    • anon (public) key — safe for client-side code
    • service_role (secret) key — server-side only, bypasses RLS
Never expose the service_role key! The service_role key bypasses all Row-Level Security policies and has full access to your database. Never put it in client-side code, never prefix it with NEXT_PUBLIC_, and never commit it to git. It belongs in environment variables on your server only.

Installing the Supabase Client

Supabase provides two main JavaScript libraries:

# Core JavaScript client (for general use)
npm install @supabase/supabase-js

# SSR helper (for Next.js server-side with cookies)
npm install @supabase/ssr
PackagePurposeWhere Used
@supabase/supabase-jsCore client for database operationsBoth client and server
@supabase/ssrCookie-based auth for server componentsServer components, middleware, API routes

Environment Variables

Store your Supabase credentials in environment variables. In Next.js, create a .env.local file at your project root:

# .env.local

# Public - safe for client-side (browser) code
NEXT_PUBLIC_SUPABASE_URL=https://xxxxx.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJhbGciOi...your-anon-key

# Secret - server-side ONLY (never prefix with NEXT_PUBLIC_!)
SUPABASE_SERVICE_ROLE_KEY=eyJhbGciOi...your-service-role-key

In Next.js, the NEXT_PUBLIC_ prefix means the variable is available in browser code. Variables without this prefix are only available on the server. This is a critical security boundary.

VariablePrefixAvailable InPurpose
NEXT_PUBLIC_SUPABASE_URLNEXT_PUBLIC_Client + ServerYour project's URL
NEXT_PUBLIC_SUPABASE_ANON_KEYNEXT_PUBLIC_Client + ServerPublic API key (respects RLS)
SUPABASE_SERVICE_ROLE_KEYNoneServer OnlyAdmin key (bypasses RLS)
Never commit .env.local to git! Add .env.local to your .gitignore file. Create a .env.example file with placeholder values to help other developers set up their environment.

Creating Supabase Clients

The Public Client (Anon Key)

The public client uses the anon key and respects Row-Level Security policies. Use this for operations that should be restricted by your RLS rules — typically public reads.

// src/lib/supabase.ts

import { createClient } from '@supabase/supabase-js';

const supabaseUrl = process.env.NEXT_PUBLIC_SUPABASE_URL!;
const supabaseAnonKey = process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!;

// Public client - respects Row-Level Security
export const supabase = createClient(supabaseUrl, supabaseAnonKey);

The Admin Client (Service Role Key)

The admin client uses the service_role key and bypasses all RLS policies. Use this for server-side operations that need full access — admin panels, webhooks, data sync.

// src/lib/supabase.ts (continued)

const supabaseServiceKey = process.env.SUPABASE_SERVICE_ROLE_KEY;

// Admin client - bypasses RLS, server-side ONLY!
export const supabaseAdmin = supabaseServiceKey
  ? createClient(supabaseUrl, supabaseServiceKey, {
      auth: {
        autoRefreshToken: false,   // Not needed for server-side
        persistSession: false,     // No session persistence on server
      },
    })
  : null;

Notice the conditional creation: if the service role key is not set (e.g., in client-side code), supabaseAdmin will be null. This is a safety measure.

Server-Side Client with Cookies

For server components and API routes that need to know which user is logged in, use @supabase/ssr. This client reads authentication cookies from the request.

// src/lib/supabase-server.ts

import { createServerClient } from '@supabase/ssr';
import { cookies } from 'next/headers';

export async function createSupabaseServerClient() {
  const cookieStore = await cookies();

  return createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      cookies: {
        getAll() {
          return cookieStore.getAll();
        },
        setAll(cookiesToSet) {
          try {
            cookiesToSet.forEach(({ name, value, options }) =>
              cookieStore.set(name, value, options)
            );
          } catch {
            // Ignore errors in read-only contexts (Server Components)
          }
        },
      },
    }
  );
}
CSK Connection CSK has exactly this pattern. src/lib/supabase.ts creates both supabase (public) and supabaseAdmin (admin) clients. src/lib/supabase-server.ts creates cookie-based SSR clients for server components and middleware. Every feature — blog, gallery, tickets, customers — reads and writes through these clients.

CRUD Operations

CRUD stands for Create, Read, Update, Delete — the four fundamental database operations. Here is how each one works with the Supabase JavaScript client.

Read: .select()

// Select all columns from all rows
const { data, error } = await supabase
  .from('blog_posts')
  .select('*');

// Select specific columns
const { data, error } = await supabase
  .from('blog_posts')
  .select('id, title, slug, status');

// Select with a filter
const { data, error } = await supabase
  .from('blog_posts')
  .select('*')
  .eq('status', 'published');

// Select a single row
const { data, error } = await supabase
  .from('blog_posts')
  .select('*')
  .eq('slug', 'my-first-post')
  .single();  // Returns one object instead of an array

Create: .insert()

// Insert a single row
const { data, error } = await supabaseAdmin
  .from('blog_posts')
  .insert({
    title: 'My New Post',
    slug: 'my-new-post',
    content: 'Hello, world!',
    author_name: 'Matthew',
    status: 'draft'
  })
  .select()     // Return the created row
  .single();    // As a single object

// Insert multiple rows
const { data, error } = await supabaseAdmin
  .from('blog_tags')
  .insert([
    { name: 'React', slug: 'react' },
    { name: 'Next.js', slug: 'nextjs' },
    { name: 'TypeScript', slug: 'typescript' }
  ])
  .select();

Update: .update()

// Update a specific row
const { data, error } = await supabaseAdmin
  .from('blog_posts')
  .update({
    status: 'published',
    published_at: new Date().toISOString()
  })
  .eq('id', postId)    // ALWAYS filter! Never update without .eq()
  .select()
  .single();

// Update multiple rows
const { data, error } = await supabaseAdmin
  .from('tickets')
  .update({ status: 'archived' })
  .eq('status', 'resolved')
  .lt('updated_at', '2025-01-01');

Delete: .delete()

// Delete specific rows
const { error } = await supabaseAdmin
  .from('blog_post_tags')
  .delete()
  .eq('post_id', postId);  // ALWAYS filter!

// Delete returns no data by default
// Add .select() if you need the deleted rows back
const { data, error } = await supabaseAdmin
  .from('sessions')
  .delete()
  .lt('expires_at', new Date().toISOString())
  .select();
Always filter your updates and deletes! Calling .update() or .delete() without a filter (like .eq()) will affect every row in the table. The Supabase client will even warn you about this. Always chain a filter method.

Filtering Methods

The Supabase client provides methods that mirror SQL WHERE clauses:

MethodSQL EquivalentExample
.eq(col, val)WHERE col = val.eq('status', 'published')
.neq(col, val)WHERE col != val.neq('status', 'draft')
.gt(col, val)WHERE col > val.gt('price', 500)
.gte(col, val)WHERE col >= val.gte('stock', 1)
.lt(col, val)WHERE col < val.lt('price', 1000)
.lte(col, val)WHERE col <= val.lte('quantity', 0)
.like(col, pat)WHERE col LIKE pat.like('name', '%Smith%')
.ilike(col, pat)WHERE col ILIKE pat.ilike('name', '%smith%')
.in(col, arr)WHERE col IN (...).in('status', ['new', 'open'])
.is(col, val)WHERE col IS val.is('archived_at', null)
.not(col, op, val)WHERE NOT ....not('status', 'eq', 'draft')
.or(filters)WHERE ... OR ....or('status.eq.new,status.eq.open')

Chaining Filters

Filters chain together like AND conditions:

// WHERE status = 'published' AND category_id IS NOT NULL
const { data } = await supabase
  .from('blog_posts')
  .select('*')
  .eq('status', 'published')
  .not('category_id', 'is', null)
  .order('published_at', { ascending: false })
  .limit(10);

Ordering and Pagination

// Sort by published_at descending (newest first)
const { data } = await supabase
  .from('blog_posts')
  .select('*')
  .order('published_at', { ascending: false });

// Sort by multiple columns
const { data } = await supabase
  .from('gallery_computers')
  .select('*')
  .eq('is_active', true)
  .order('sort_order')                              // First by sort_order ASC
  .order('created_at', { ascending: false });       // Then by newest

// Pagination with limit and range
const { data } = await supabase
  .from('blog_posts')
  .select('*')
  .eq('status', 'published')
  .order('published_at', { ascending: false })
  .range(0, 9);   // First 10 items (0-indexed, inclusive)

// Page 2: items 10-19
  .range(10, 19);

// Page 3: items 20-29
  .range(20, 29);

The .range(from, to) method is more flexible than .limit() alone. Both from and to are inclusive and zero-indexed.

Joining Related Data

One of Supabase's most powerful features is the ability to fetch related data from multiple tables in a single query, using the .select() syntax with embedded table references.

// Fetch blog posts WITH their category data
const { data } = await supabase
  .from('blog_posts')
  .select(`
    *,
    category:blog_categories(*)
  `)
  .eq('status', 'published');

// Result shape:
// {
//   id: 'uuid...',
//   title: 'My Post',
//   category: {
//     id: 'uuid...',
//     name: 'Tech Tips',
//     slug: 'tech-tips'
//   }
// }

The syntax category:blog_categories(*) means: "Join the blog_categories table and name the result category." Supabase automatically detects the foreign key relationship.

// Fetch specific columns from related tables
const { data } = await supabase
  .from('blog_posts')
  .select(`
    title,
    slug,
    published_at,
    category:blog_categories(name, slug)
  `)
  .eq('status', 'published');

// Fetch through a junction table (many-to-many)
const { data } = await supabase
  .from('blog_post_tags')
  .select(`
    tag_id,
    blog_tags(name, slug)
  `)
  .eq('post_id', postId);
CSK Connection The getPublishedPosts() function in src/lib/supabase.ts uses exactly this pattern: .select('*, category:blog_categories(*)') to get posts with their category in one query. Tags are fetched in a second query through the blog_post_tags junction table because the many-to-many relationship requires a separate call.

Error Handling: The { data, error } Pattern

Every Supabase operation returns an object with data and error. This is different from the try/catch pattern — Supabase does not throw exceptions on query failures.

const { data, error } = await supabase
  .from('blog_posts')
  .select('*')
  .eq('slug', 'nonexistent-post')
  .single();

if (error) {
  console.error('Database error:', error.message);
  // error.code contains the PostgreSQL error code
  // error.details provides more context
  return null;
}

// data is guaranteed to exist here
console.log('Found post:', data.title);

Common Error Codes

Error CodeMeaningHow to Handle
PGRST116.single() found zero or multiple rowsUse .maybeSingle() for optional results
23505Unique constraint violationThe slug/email already exists
23503Foreign key violationReferenced row does not exist
42501RLS policy violationUser does not have access

.single() vs .maybeSingle()

// .single() - ERRORS if zero or multiple rows found
const { data, error } = await supabase
  .from('customers')
  .select('*')
  .eq('email', 'jane@example.com')
  .single();
// error if no customer with that email exists!

// .maybeSingle() - Returns null if not found, no error
const { data, error } = await supabase
  .from('customers')
  .select('*')
  .eq('email', 'jane@example.com')
  .maybeSingle();
// data is null if not found (no error)
CSK Connection CSK consistently uses this pattern. Every database function checks if (error) before using the data. The getPublishedPostBySlug() function uses .maybeSingle() because a missing post is expected (not an error) — the user may have typed a wrong URL.

Putting It All Together — A Complete Module

Here is what a complete Supabase data access module looks like for a blog:

// src/lib/supabase.ts

import { createClient } from '@supabase/supabase-js';

// Environment variables
const supabaseUrl = process.env.NEXT_PUBLIC_SUPABASE_URL!;
const supabaseAnonKey = process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!;
const supabaseServiceKey = process.env.SUPABASE_SERVICE_ROLE_KEY;

// Public client (reads, respects RLS)
export const supabase = createClient(supabaseUrl, supabaseAnonKey);

// Admin client (full access, server-side only)
export const supabaseAdmin = supabaseServiceKey
  ? createClient(supabaseUrl, supabaseServiceKey, {
      auth: { autoRefreshToken: false, persistSession: false }
    })
  : null;

// ---- Public functions ----

export async function getPublishedPosts() {
  const { data, error } = await supabase
    .from('blog_posts')
    .select('*, category:blog_categories(*)')
    .eq('status', 'published')
    .order('published_at', { ascending: false });

  if (error) {
    console.error('Error fetching posts:', error);
    return [];
  }
  return data || [];
}

export async function getPostBySlug(slug: string) {
  const { data, error } = await supabase
    .from('blog_posts')
    .select('*, category:blog_categories(*)')
    .eq('slug', slug)
    .eq('status', 'published')
    .maybeSingle();

  if (error) {
    console.error('Error fetching post:', error);
    return null;
  }
  return data;
}

// ---- Admin functions ----

export async function createPost(input: {
  title: string;
  slug: string;
  content: string;
  author_name: string;
  status?: string;
}) {
  if (!supabaseAdmin) return null;

  const { data, error } = await supabaseAdmin
    .from('blog_posts')
    .insert(input)
    .select()
    .single();

  if (error) {
    console.error('Error creating post:', error);
    return null;
  }
  return data;
}

export async function updatePost(id: string, updates: object) {
  if (!supabaseAdmin) return null;

  const { data, error } = await supabaseAdmin
    .from('blog_posts')
    .update(updates)
    .eq('id', id)
    .select()
    .single();

  if (error) {
    console.error('Error updating post:', error);
    return null;
  }
  return data;
}

export async function deletePost(id: string) {
  if (!supabaseAdmin) return false;

  const { error } = await supabaseAdmin
    .from('blog_posts')
    .delete()
    .eq('id', id);

  return !error;
}

Hands-On Exercises

  1. Set Up a Project: Create a free Supabase project. Navigate to Settings → API and find your project URL, anon key, and service role key. Create a .env.local file with these values.
  2. Create a Table: In the Supabase SQL Editor, create a todos table with columns: id (UUID, primary key, auto-generated), title (text, not null), completed (boolean, default false), created_at (timestamptz, default now()).
  3. Client Setup: Install @supabase/supabase-js in a Next.js project and create a src/lib/supabase.ts file with both public and admin clients.
  4. CRUD Functions: Write four functions: getTodos(), createTodo(title), toggleTodo(id), and deleteTodo(id). Use proper error handling with the { data, error } pattern.
  5. Filtering Challenge: Write a function searchTodos(query, showCompleted) that uses .ilike() to search by title and optionally filters by completion status.
  6. Pagination: Write a function getPaginatedTodos(page, pageSize) that returns a specific page of todos, ordered by created_at descending.

Key Takeaways

  • Supabase is an open-source backend built on PostgreSQL with a generous free tier.
  • Create two clients: a public client (anon key, respects RLS) and an admin client (service role key, bypasses RLS).
  • Use @supabase/ssr for server-side clients that handle cookies and authentication.
  • Store credentials in environment variables; never expose the service role key to the browser.
  • CRUD with the JS client: .select(), .insert(), .update(), .delete().
  • Filter with .eq(), .neq(), .gt(), .lt(), .ilike(), .in(), and more.
  • Join related tables using .select('*, related_table(*)') syntax.
  • Every operation returns { data, error } — always check for errors before using data.
  • Use .maybeSingle() instead of .single() when a missing row is expected.
