TypeScript Fundamentals

JavaScript with compile-time type checking

What is TypeScript?

TypeScript is a statically-typed superset of JavaScript developed by Microsoft. It compiles to plain JavaScript, providing:

Type Safety

Catch errors at compile time rather than runtime

IDE Support

IntelliSense, refactoring, and navigation

Self-Documentation

Types serve as inline documentation

Type System Design Philosophy

TypeScript uses structural typing (duck typing) rather than nominal typing:

// Structural typing: shape matters, not name
interface Point {
  x: number;
  y: number;
}

interface Coordinate {
  x: number;
  y: number;
}

const p: Point = { x: 10, y: 20 };
const c: Coordinate = p;  // ✓ Valid! Same shape

TypeScript Strict Mode

Our tsconfig.json enables maximum type safety

// tsconfig.json - Strict mode configuration
{
  "compilerOptions": {
    "strict": true,                  // Master switch
    "noImplicitAny": true,            // No implicit 'any' type
    "strictNullChecks": true,         // null/undefined are distinct
    "noUncheckedIndexedAccess": true, // Array access may be undefined
    "noImplicitReturns": true,        // All paths must return
    "noFallthroughCasesInSwitch": true
  }
}

What strictNullChecks Enforces

Without strictNullChecks

function getUser(id: string) {
  return users.find(u => u.id === id);
}

// Dangerous! Could be undefined
const user = getUser('123');
console.log(user.name); // Runtime crash!

With strictNullChecks

function getUser(id: string): User | undefined {
  return users.find(u => u.id === id);
}

// Compiler forces null check
const user = getUser('123');
if (user) {
  console.log(user.name); // ✓ Safe
}
Key Insight: TypeScript's type system is sound by design in strict mode - if it compiles, the types are guaranteed correct (barring escape hatches like any or type assertions).

React 18 Deep Dive

The UI library powering our frontend

React's Core Philosophy

React is a declarative, component-based library for building user interfaces. Key principles:

Declarative

Describe what UI should look like, not how to update it

Component-Based

Build encapsulated components that manage their own state

Unidirectional Data Flow

Data flows down via props, events flow up via callbacks

The Virtual DOM

React maintains a lightweight in-memory representation of the DOM:

State Change
↓
New Virtual DOM
↓
Diff Algorithm
↓
Minimal DOM Updates

This reconciliation process uses an O(n) heuristic algorithm that compares trees level-by-level, making updates efficient.

React Hooks

State and lifecycle in functional components

Core Hooks Used in Our Codebase

useState - Local Component State

const [count, setCount] = useState(0);

// Functional updates for derived state

useEffect - Side Effects

useEffect(() => {
  // Runs after render

    const data = await getUser(id);

  };

  // Cleanup function
  return () => subscription.unsubscribe();

useCallback - Memoized Callbacks

// Prevents re-creating function on every render
const handleClick = useCallback((id: string) => {
  setSelected(id);
}, []); // Empty deps = never recreated

useMemo - Memoized Values

// Expensive computation cached
const filteredItems = useMemo(() => {
  return items.filter(
    item => item.name.includes(search)
  );
}, [items, search]);

useRef - Mutable Reference

const inputRef = useRef<HTMLInputElement>(null);

// Access DOM element directly
inputRef.current?.focus();
Hook Rules: Hooks must be called at the top level of your component (not inside loops, conditions, or nested functions) and only from React function components or custom hooks.

Custom Hooks in Our Codebase

Extracting reusable stateful logic

useBotProtection Hook

// src/hooks/useBotProtection.ts
// Implements honeypot + timing analysis for spam prevention

export function useBotProtection(options?: BotProtectionOptions) {
  const [startTime] = useState(() => Date.now());
  const [honeypotValue, setHoneypotValue] = useState('');
  const interactionCount = useRef(0);

  // Track user interactions
  useEffect(() => {
    const handler = () => { interactionCount.current++; };
    document.addEventListener('mousemove', handler);
    document.addEventListener('keydown', handler);
    return () => {
      document.removeEventListener('mousemove', handler);
      document.removeEventListener('keydown', handler);
    };
  }, []);

  const validate = useCallback(() => {
    const elapsed = Date.now() - startTime;
    const minTime = options?.minTimeMs ?? 3000;

    // Bot indicators: honeypot filled, too fast, no interactions
    return honeypotValue === '' &&
           elapsed > minTime &&
           interactionCount.current > 0;
  }, [honeypotValue, startTime, options?.minTimeMs]);

  return {
    honeypotProps: { value: honeypotValue, onChange: e => setHoneypotValue(e.target.value) },
    validate,
    isBot: !validate(),
  };
}
Pattern: Custom hooks encapsulate complex logic (state, effects, subscriptions) into reusable functions. The use prefix signals to React that hook rules apply.

Server vs Client Components

Next.js 14's hybrid rendering model

Server Components (Default)

  • Render on server only
  • Zero JavaScript sent to client
  • Direct database/API access
  • Can use async/await directly
  • No access to browser APIs
  • No useState, useEffect
// Default - Server Component
async function BlogList() {
  // Direct database query
  const posts = await getPublishedPosts();

  return (
    <ul>
      {posts.map(post => (
        <li key={post.id}>{post.title}</li>
      ))}
    </ul>
  );
}

Client Components

  • Render on client (hydrated)
  • JavaScript sent to browser
  • Fetch data via API calls
  • Can use hooks (useState, etc.)
  • Access to browser APIs
  • Event handlers work
'use client'; // Directive required

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(c => c + 1)}>
      Count: {count}
    </button>
  );
}

API Route Handlers

Backend endpoints with Next.js

Route Handlers allow you to create API endpoints using the Web Request and Response APIs:

// src/app/api/blog/route.ts
import { NextRequest, NextResponse } from 'next/server';
import { getPublishedPosts, createPost } from '@/lib/supabase';
import { getCurrentUser } from '@/lib/auth';

// GET /api/blog - Public endpoint
export async function GET(request: NextRequest) {
  const posts = await getPublishedPosts();
  return NextResponse.json(posts);
}

// POST /api/blog - Protected endpoint
export async function POST(request: NextRequest) {
  // Check authentication
  const user = await getCurrentUser();
  if (!user || user.role !== 'admin') {
    return NextResponse.json(
      { error: 'Unauthorized' },
      { status: 401 }
    );
  }

  // Parse and validate request body
  const body = await request.json();
  const validated = createPostSchema.parse(body);

  // Create the post
  const post = await createPost(validated);
  return NextResponse.json(post, { status: 201 });
}

Edge Middleware

Authentication and security at the edge

Middleware runs before every request, enabling authentication checks, redirects, and security headers:

// src/middleware.ts
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

export async function middleware(request: NextRequest) {
  const { pathname } = request.nextUrl;
  let response = NextResponse.next();

  // 1. Add security headers to ALL responses
  response.headers.set('X-Frame-Options', 'DENY');
  response.headers.set('X-Content-Type-Options', 'nosniff');
  response.headers.set('Referrer-Policy', 'strict-origin-when-cross-origin');

  // 2. Allow public routes without auth
  if (isPublicRoute(pathname)) {
    return response;
  }

  // 3. Check authentication from session cookie
  const sessionCookie = request.cookies.get('admin_session');
  if (!sessionCookie) {
    return NextResponse.redirect(new URL('/login', request.url));
  }

  // 4. Check role-based authorization
  const userRoles = getUserRoles(request);
  if (!canAccessRoute(userRoles, pathname)) {
    return NextResponse.redirect(new URL('/unauthorized', request.url));
  }

  return response;
}

export const config = {
  matcher: ['/((?!_next/static|_next/image|favicon.ico).*)'],

Row-Level Security (RLS)

PostgreSQL policies for authorization

How RLS Works

RLS policies are SQL expressions evaluated for every row during queries. They run in the database, not your application code.

-- Enable RLS on a table
ALTER TABLE blog_posts ENABLE ROW LEVEL SECURITY;

-- Policy: Anyone can read published posts
CREATE POLICY "Public read published posts"
ON blog_posts FOR SELECT
USING (status = 'published');

-- Policy: Users can only update their own posts
CREATE POLICY "Users update own posts"
ON blog_posts FOR UPDATE
USING (auth.uid() = author_id)
WITH CHECK (auth.uid() = author_id);

-- Policy: Admins can do anything
CREATE POLICY "Admins full access"
ON blog_posts FOR ALL
USING (
  EXISTS (
    SELECT 1 FROM user_profiles
    WHERE id = auth.uid()
    AND role = 'admin'
  )
);
Security Model: The anon key is safe for client-side use because RLS policies restrict what data can be accessed. The service_role key bypasses RLS and should ONLY be used server-side.

Session Cookie Encryption

// src/lib/session-cookie.ts
import crypto from 'crypto';

const ALGORITHM = 'aes-256-gcm';
const IV_LENGTH = 16;
const AUTH_TAG_LENGTH = 16;

export function encryptSession(data: SessionData): string {
  const iv = crypto.randomBytes(IV_LENGTH);
  const key = getSessionKey(); // From SESSION_SECRET env var

  const cipher = crypto.createCipheriv(ALGORITHM, key, iv);
  const encrypted = Buffer.concat([
    cipher.update(JSON.stringify(data), 'utf8'),
    cipher.final(),
  ]);

  // Format: iv:authTag:encrypted (base64)
  return [
    iv.toString('base64'),
    cipher.getAuthTag().toString('base64'),
    encrypted.toString('base64'),
  ].join(':');
}

// src/lib/role-helpers.ts
export function canAccessRoute(roles: string[], pathname: string): boolean {
  // Find matching route permission
  const permission = ROUTE_PERMISSIONS.find(p =>
    p.exact ? pathname === p.pattern : pathname.startsWith(p.pattern)
  );

  if (!permission) return true; // No restriction

  // Check if user has ANY of the required roles
  return permission.allowedRoles.some(role => roles.includes(role));
}

export function isEmployee(roles: string[]): boolean {

}

Runtime Validation with Zod

Type-safe schema validation

Why Zod?

TypeScript types exist only at compile time. For runtime validation (API requests, form data, external APIs), we use Zod:

import { z } from 'zod';

// Define schema
const createPostSchema = z.object({
  title: z.string().min(1).max(200),
  slug: z.string().regex(/^[a-z0-9-]+$/),
  content: z.string().min(10),
  status: z.enum(['draft', 'published']).default('draft'),
  category_id: z.string().uuid().optional(),
  tag_ids: z.array(z.string().uuid()).optional(),
});

// Infer TypeScript type from schema
type CreatePostInput = z.infer<typeof createPostSchema>;

// Usage in API route
export async function POST(request: NextRequest) {
  const body = await request.json();

  // parse() throws ZodError if invalid
  const validated = createPostSchema.parse(body);
  // validated is now type CreatePostInput

  // Or use safeParse for error handling
  const result = createPostSchema.safeParse(body);
  if (!result.success) {
    return NextResponse.json(
      { errors: result.error.format() },
      { status: 400 }
    );
  }
}
Key Benefit: Single source of truth - the Zod schema defines both the runtime validation and the TypeScript type, keeping them in sync.

Key Takeaways

Summary of the architecture

Type Safety Everywhere

TypeScript strict mode + Zod runtime validation ensures data integrity from database to UI.

Server-First Architecture

Server Components by default minimize client JavaScript, with Client Components only where interactivity is needed.

Security in Layers

Middleware auth → Route handler validation → Database RLS provides defense in depth.

Unified Backend

Supabase provides database, auth, and storage in one platform with consistent APIs.
