Lesson 39: Webhooks — Receiving External Events

When external services call YOUR API to tell you something happened

Learning Objectives

  • Explain what webhooks are and how they differ from traditional API polling
  • Describe how the "reverse API" model works: an external service calls your endpoint

  • Accept and parse incoming POST requests with JSON payloads
  • Verify webhook authenticity using HMAC signatures, IP allowlists, and shared secrets
  • Implement the "respond fast, process async" pattern for reliable webhook handling
  • Handle idempotency to prevent duplicate processing of the same event
  • Route different event types to appropriate handler functions
  • Test webhooks locally using tunnel tools like ngrok

What Are Webhooks?

In the previous two lessons, you learned about calling external APIs — your server reaches out to another service to send email or fetch data. Webhooks are the reverse: an external service reaches out to your server to tell you something happened.

Analogy: The Reverse API
Think about how you check if a package has been delivered. You could keep walking to your front door every 5 minutes to look (this is called polling — repeatedly asking "has anything changed?"). Or, you could install a doorbell camera that sends you a notification the moment the package arrives (this is a webhook — the delivery service tells you when it happens).

Polling is wasteful — 99 out of 100 checks find nothing new. Webhooks are efficient — you only hear about it when something actually happens. Instead of you asking "any new tickets? any new tickets? any new tickets?" every few seconds, RepairShopr simply tells you "a ticket was just created" the moment it happens.

Polling vs. Webhooks

Aspect Polling (You Ask Them) Webhooks (They Tell You)
Direction Your server calls their API repeatedly Their server calls your endpoint once
Efficiency Wastes requests when nothing changed Only fires when something actually happens
Timeliness Delayed by polling interval (seconds to minutes) Near real-time (within seconds of the event)
API usage High (constant requests even when idle) Low (only sends data on events)
Complexity Simple to implement (just call the API) Requires a publicly accessible endpoint
Reliability You control the schedule Depends on the sender's retry logic
POLLING (Your Server Asks Repeatedly): Your Server RepairShopr ========== =========== GET /tickets?since=... -----> "No new tickets" (wait 30 seconds) GET /tickets?since=... -----> "No new tickets" (wait 30 seconds) GET /tickets?since=... -----> "No new tickets" (wait 30 seconds) GET /tickets?since=... -----> "1 new ticket!" (30 seconds wasted before you knew) WEBHOOKS (RepairShopr Tells You): Your Server RepairShopr ========== =========== (doing nothing) (doing nothing) (doing nothing) <----- POST /api/webhooks/repairshopr "A ticket was just created!" (process immediately - near zero delay)

How Webhooks Work

The webhook lifecycle has four phases:

Phase 1: Registration

You tell the external service "when X happens, send a POST request to this URL." This is typically done through the service's dashboard or API.

// Example: Registering a webhook URL in a service's dashboard
Webhook URL: https://computerstoreks.com/api/webhooks/repairshopr
Events: ticket.created, ticket.updated, customer.updated, invoice.created
Format: JSON
Secret: your_webhook_secret_here

Phase 2: Event Occurs

Something happens in the external service — a customer creates a ticket, a payment is received, or an invoice is updated.

Phase 3: Delivery

The external service sends an HTTP POST request to your registered URL with a JSON payload containing the event data.

Phase 4: Processing

Your server receives the request, validates it, processes the data, and responds with a success status code (200 or 201) to acknowledge receipt.

Creating a Webhook Endpoint

In Next.js with the App Router, a webhook endpoint is simply an API route that handles POST requests. The file path determines the URL:

// File: src/app/api/webhooks/repairshopr/route.ts
// URL:  /api/webhooks/repairshopr

import { NextRequest, NextResponse } from 'next/server';

// Force dynamic rendering (webhooks should never be cached)
export const dynamic = 'force-dynamic';

export async function POST(request: NextRequest) {
  try {
    // 1. Read the raw request body
    const rawBody = await request.text();

    // 2. Validate authenticity (see next section)
    // ...

    // 3. Parse the JSON payload
    const payload = JSON.parse(rawBody);

    // 4. Process the event
    console.log('Webhook received:', payload);

    // 5. Respond quickly with 200 OK
    return NextResponse.json({ success: true });
  } catch (error) {
    console.error('Webhook error:', error);
    return NextResponse.json(
      { error: 'Processing failed' },
      { status: 500 }
    );
  }
}

// Optional: GET endpoint for health checks
export async function GET() {
  return NextResponse.json({
    status: 'ok',
    message: 'Webhook endpoint is active',
  });
}
Dynamic Route Pattern If you receive webhooks from multiple services, you can use a dynamic route segment: /api/webhooks/[service]/route.ts. The [service] parameter lets you have a single handler file that routes based on the service name (repairshopr, stripe, github, etc.).

Verifying Webhook Authenticity

Your webhook endpoint is a public URL. Anyone on the internet can send a POST request to it. You must verify that incoming requests actually came from the expected service, not from an attacker trying to inject fake data into your system.

Method 1: HMAC Signature Verification

The most secure method. The sender computes a hash of the payload using a shared secret, and includes it in a header. You compute the same hash and compare:

import { createHmac } from 'crypto';

function validateSignature(
  rawBody: string,
  signatureHeader: string | null
): boolean {
  const secret = process.env.WEBHOOK_SECRET;

  // If no secret configured, skip validation (not recommended for production)
  if (!secret) {
    console.warn('No webhook secret configured - skipping validation');
    return true;
  }

  if (!signatureHeader) {
    console.log('Missing signature header');
    return false;
  }

  // Compute the expected signature
  const expectedSignature = createHmac('sha256', secret)
    .update(rawBody)
    .digest('hex');

  // Compare (the header might include a "sha256=" prefix)
  return (
    signatureHeader === expectedSignature ||
    signatureHeader === `sha256=${expectedSignature}`
  );
}
Analogy: The Wax Seal
In medieval times, letters were sealed with wax stamped by the sender's unique signet ring. The recipient could verify the seal had not been broken and that it matched the expected sender. HMAC signatures work the same way — the sender "stamps" the message with a cryptographic seal created using a secret only you and they share. If the seal does not match, the message was either tampered with or not from who it claims to be.

Method 2: IP Allowlisting

Some services send webhooks from known IP addresses. You can check the source IP:

// Known webhook source IPs for RepairShopr
const ALLOWED_IPS = ['52.3.26.220'];

function validateSourceIP(request: NextRequest): boolean {
  const ip = request.headers.get('x-forwarded-for')?.split(',')[0]?.trim()
           || request.headers.get('x-real-ip')
           || 'unknown';

  return ALLOWED_IPS.includes(ip);
}

Method 3: Shared Secret in Headers

The simplest method — the sender includes a secret token in a custom header:

function validateToken(request: NextRequest): boolean {
  const token = request.headers.get('x-webhook-token');
  const expectedToken = process.env.WEBHOOK_TOKEN;

  return token === expectedToken;
}
Always Validate in Production Without validation, an attacker could send fake webhook payloads to your endpoint, potentially corrupting your database, triggering unauthorized actions, or injecting malicious data. At minimum, use HMAC signature verification. Ideally, combine it with IP allowlisting for defense in depth.
CSK Connection CSK's webhook handler at /api/webhooks/repairshopr/route.ts uses HMAC signature validation. The validateSignature() function reads the raw body, computes a SHA-256 HMAC using REPAIRSHOPR_WEBHOOK_SECRET, and compares it against the x-repairshopr-signature or x-webhook-signature header. If the secret is not configured, validation is skipped (useful during development but logged as a warning).

Parsing Webhook Payloads

Different services send different payload formats. You need to understand the structure of the data you are receiving.

Reading the Raw Body

For signature validation, you need the exact raw body bytes. That means reading request.text() first, then parsing JSON manually:

export async function POST(request: NextRequest) {
  // Read raw text FIRST (for signature validation)
  const rawBody = await request.text();

  // Validate signature using the raw text
  const signature = request.headers.get('x-webhook-signature');
  if (!validateSignature(rawBody, signature)) {
    return NextResponse.json({ error: 'Invalid signature' }, { status: 401 });
  }

  // THEN parse JSON from the raw text
  let payload;
  try {
    payload = JSON.parse(rawBody);
  } catch {
    return NextResponse.json({ error: 'Invalid JSON' }, { status: 400 });
  }

  // Now process the payload...
}
Do Not Use request.json() for Webhooks If you call await request.json(), the body stream is consumed and you cannot read it again for signature validation. Always use await request.text() first, validate the signature, then JSON.parse() the text. This is a common mistake that breaks webhook signature verification.

Determining Event Type

Most webhook systems send different types of events through the same endpoint. You need to determine what happened and route to the appropriate handler:

// RepairShopr sends: { text, html, link, attributes }
// The "link" URL path tells us the entity type

interface WebhookPayload {
  text: string;      // Human-readable description
  html: string;      // HTML notification
  link: string;      // URL like "https://subdomain.repairshopr.com/tickets/12345"
  attributes: Record<string, unknown>;  // Full entity data
}

function determineEntityType(payload: WebhookPayload): string {
  // Parse the link URL to determine entity type
  try {
    const url = new URL(payload.link);
    const firstPathSegment = url.pathname.split('/').filter(Boolean)[0];

    switch (firstPathSegment?.toLowerCase()) {
      case 'tickets':
        // Distinguish ticket events from comment events
        if ('ticket_id' in payload.attributes && 'body' in payload.attributes) {
          return 'comment'; // Comments have ticket_id pointing to parent
        }
        return 'ticket';
      case 'customers':
        return 'customer';
      case 'invoices':
        return 'invoice';
      default:
        return 'unknown';
    }
  } catch {
    return 'unknown';
  }
}
CSK Connection RepairShopr webhooks use a unique payload format: {text, html, link, attributes}. The link field is a URL like https://thecomputerstore.repairshopr.com/tickets/12345, and CSK parses the URL path to determine if the event is about a ticket, customer, or invoice. For comment events, CSK checks if the attributes object has both ticket_id and body fields (comments reference their parent ticket). The text field is also checked for phrases like "comment was added" as a fallback detection method.

Respond Fast, Process Later

This is the most important webhook design principle: return a 200 response as quickly as possible. Most webhook senders have a timeout (typically 5-30 seconds). If your endpoint does not respond in time, the sender assumes delivery failed and will retry, potentially causing duplicate processing.

Why Speed Matters

  • The sender is waiting for your response. Long processing blocks their system.
  • If you time out, the sender retries, and you might process the same event twice.
  • If your database is slow during processing, you risk the sender giving up entirely.

Strategy: Acknowledge First, Process After

For simple webhook handlers (like CSK's), you can process synchronously if your operations are fast (database upserts take milliseconds). But for complex processing, acknowledge receipt first and process asynchronously:

// Simple approach: Process synchronously (fine for fast operations)
export async function POST(request: NextRequest) {
  const startTime = Date.now();
  const payload = JSON.parse(await request.text());

  // Database upserts are fast (milliseconds)
  await syncToDatabase(payload);

  const duration = Date.now() - startTime;
  console.log(`Webhook processed in ${duration}ms`);

  return NextResponse.json({ success: true, duration: `${duration}ms` });
}

// Advanced approach: Acknowledge first, process in background
export async function POST(request: NextRequest) {
  const payload = JSON.parse(await request.text());

  // Store the event for background processing
  await storeEventInQueue(payload);

  // Return immediately (total time: ~10ms)
  return NextResponse.json({ success: true, queued: true });

  // A separate background worker picks up events from the queue
  // and processes them without time pressure
}
CSK Connection CSK uses the synchronous approach because its webhook operations are fast — database upserts to Supabase typically complete in 10-50ms. The handler logs the total processing duration: "Processed in 45ms: ticket:12345, customer:67890, comment:111". If a ticket webhook includes embedded customer and comment data, all three are synced in sequence within the same request.

Idempotency: Handling Duplicate Deliveries

Idempotency means that processing the same event multiple times produces the same result as processing it once. This is critical because webhook senders often retry failed deliveries, and network issues can cause the same event to arrive twice.

Analogy: The Light Switch
Flipping a light switch once turns the light on. Flipping it twice turns it off. That is NOT idempotent — the result depends on how many times you do it. But consider a thermostat set to 72 degrees. Telling it "set temperature to 72" once or a hundred times produces the same result: 72 degrees. That IS idempotent. Your webhook handler should work like the thermostat, not the light switch.

Using Upserts for Idempotency

The simplest way to achieve idempotency is to use database upserts (insert-or-update) instead of plain inserts:

// NOT idempotent - inserting duplicates
await supabase.from('rs_tickets').insert({
  repairshopr_id: ticket.id,  // Will fail on duplicate!
  subject: ticket.subject,
  status: ticket.status,
});

// IDEMPOTENT - upsert based on unique key
await supabase.from('rs_tickets').upsert(
  {
    repairshopr_id: ticket.id,
    subject: ticket.subject,
    status: ticket.status,
    synced_at: new Date().toISOString(),
  },
  { onConflict: 'repairshopr_id' }  // If this ID exists, update instead
);

// Result: Whether this runs once or ten times,
// the database contains exactly one row for this ticket
// with the latest data.

Other Idempotency Strategies

  • Track event IDs — Store the IDs of processed events. Before processing, check if you have seen this ID before.
  • Use "last write wins" — If you receive older data after newer data, the newer data should remain unchanged.
  • Timestamp comparison — Compare updated_at timestamps. Only process if the incoming data is newer than what you have.
CSK Connection CSK achieves idempotency through upserts on every sync operation. The syncTicket() function upserts to rs_tickets with onConflict: 'repairshopr_id'. The syncCustomer() function upserts to rs_customers with onConflict: 'repairshopr_id'. The syncComment() function upserts to rs_ticket_comments with onConflict: 'repairshopr_id'. If RepairShopr sends the same webhook event twice (which happens during network hiccups), the second processing simply overwrites the first with identical data — no duplicates, no errors.

Routing Different Event Types

A single webhook endpoint often receives multiple types of events. You need a clean way to route each type to its handler:

export async function POST(request: NextRequest) {
  const rawBody = await request.text();
  const payload = JSON.parse(rawBody);

  // Determine what type of event this is
  const entityType = determineEntityType(payload);
  const results: string[] = [];

  console.log(`Webhook received: ${entityType}`);

  // Route to the appropriate handler
  switch (entityType) {
    case 'ticket': {
      const ticket = payload.attributes;
      if (!ticket.id) break;

      await syncTicket(ticket);
      results.push(`ticket:${ticket.id}`);

      // Tickets may include embedded customer data
      if (ticket.customer?.id) {
        await syncCustomer(ticket.customer);
        results.push(`customer:${ticket.customer.id}`);
      }

      // Tickets may include embedded comments
      if (ticket.comments && Array.isArray(ticket.comments)) {
        for (const comment of ticket.comments) {
          await syncComment(comment);
          results.push(`comment:${comment.id}`);
        }
      }
      break;
    }

    case 'comment': {
      const comment = payload.attributes;
      if (!comment.id || !comment.ticket_id) break;
      await syncComment(comment);
      results.push(`comment:${comment.id}`);
      break;
    }

    case 'customer': {
      const customer = payload.attributes;
      if (!customer.id) break;
      await syncCustomer(customer);
      results.push(`customer:${customer.id}`);
      break;
    }

    case 'invoice': {
      const invoice = payload.attributes;
      if (!invoice.id) break;
      await syncInvoice(invoice);
      results.push(`invoice:${invoice.id}`);
      break;
    }

    default:
      console.log(`Unknown event type from webhook`);
  }

  return NextResponse.json({
    success: true,
    processed: results,
  });
}

Logging Webhook Events

Webhook debugging is challenging because you cannot see the incoming requests in your browser's developer tools. Comprehensive logging is your only window into what is happening:

// Log every webhook for debugging
console.log(JSON.stringify({
  event: 'webhook_received',
  timestamp: new Date().toISOString(),
  entity_type: entityType,
  text_preview: payload.text?.substring(0, 80),
  link: payload.link,
  attribute_keys: Object.keys(payload.attributes || {}),
}));

// Log processing results
console.log(JSON.stringify({
  event: 'webhook_processed',
  timestamp: new Date().toISOString(),
  duration_ms: Date.now() - startTime,
  results: results,
}));

// Log errors with full context
console.error(JSON.stringify({
  event: 'webhook_error',
  timestamp: new Date().toISOString(),
  entity_type: entityType,
  error: error.message,
  payload_preview: JSON.stringify(payload).substring(0, 500),
}));

Testing Webhooks Locally

The biggest challenge with webhooks is testing. External services need to reach your endpoint over the public internet, but during development, your server runs on localhost — which is not accessible from outside your network.

Solution: Tunnel Tools

Tools like ngrok create a temporary public URL that forwards requests to your local machine:

# 1. Start your development server
npm run dev
# Server running at http://localhost:3000

# 2. In another terminal, start ngrok
ngrok http 3000
# ngrok creates a public URL like:
# https://abc123.ngrok.io -> http://localhost:3000

# 3. Register the ngrok URL as your webhook URL in the external service:
# Webhook URL: https://abc123.ngrok.io/api/webhooks/repairshopr

# 4. Now when RepairShopr sends a webhook,
#    ngrok forwards it to your local server!
RepairShopr ngrok Cloud Your Laptop ============ =========== =========== POST /api/webhooks/ repairshopr ------> abc123.ngrok.io ------> localhost:3000 /api/webhooks/ repairshopr Response: 200 OK <------ Forwards back <------ { success: true }

What Happens When Your Endpoint Fails

When your webhook endpoint returns a non-2xx status code (or does not respond at all), the sender typically:

  1. Retries with backoff — Most services retry 3-5 times with increasing delays (1 min, 5 min, 30 min, etc.)
  2. Logs the failure — The service's dashboard shows failed webhook deliveries.
  3. Disables the webhook — After too many consecutive failures (often 100+), some services automatically disable the webhook and notify you.

Best Practices for Reliability

  • Return 200 quickly — Even if processing fails, consider returning 200 and handling errors asynchronously. This prevents the sender from retrying and creating duplicates.
  • Handle partial failures gracefully — If syncing a ticket succeeds but syncing its embedded comments fails, do not return 500. Log the error and return 200 for the parts that worked.
  • Use upserts, not inserts — Retried webhooks should produce the same result (idempotency).
  • Monitor your endpoint — Set up alerts for webhook processing errors so you can investigate before data gets too stale.
CSK Connection CSK's webhook handler at /api/webhooks/repairshopr/route.ts handles partial failures gracefully. When syncing a ticket, if the embedded customer sync fails, it logs the error but does not throw — the ticket sync still counts as successful. The same applies to embedded comment syncs. The handler also includes a GET endpoint that returns the webhook status (active/inactive and whether signature validation is enabled) for health monitoring.

Key Takeaways

  • Webhooks are the "reverse API" — instead of you asking "has anything changed?", the external service tells you when something happens by sending an HTTP POST to your endpoint.
  • Webhooks are more efficient than polling: they fire only on actual events, deliver near real-time, and use fewer API requests.
  • Always verify webhook authenticity using HMAC signatures, IP allowlists, or shared secrets. Without verification, anyone can send fake data to your endpoint.
  • Read the raw body with request.text() first for signature validation, then parse JSON manually. Do not use request.json() for webhook endpoints.
  • Respond with 200 as quickly as possible. Long processing times cause timeouts and retries.
  • Use database upserts (not inserts) to achieve idempotency. Processing the same event twice should produce the same result as processing it once.
  • Route different event types through a switch statement, with each case calling a dedicated handler function.
  • Use tunnel tools like ngrok to expose your local server for webhook testing during development.
