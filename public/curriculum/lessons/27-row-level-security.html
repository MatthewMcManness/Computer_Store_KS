What Is Row-Level Security?

Row-Level Security (RLS) is a PostgreSQL feature that controls which rows a user can see or modify in a table. Instead of securing data only in your application code, RLS enforces access rules at the database level — the data itself decides who can access it.

Analogy: Imagine an apartment building. Application-level security is like a doorman at the front entrance — he checks IDs and lets people in. But what if someone sneaks past the doorman (a bug in your code, a misconfigured API)? Row-Level Security is like every individual apartment having its own lock. Even if someone gets past the doorman, they can only enter the apartments they have keys to. RLS is the lock on every single row of data.

Why RLS Is Critical

Without RLS, your database trusts any request that reaches it. If there is a bug in your API, a misconfigured endpoint, or an attacker who bypasses your application layer, they get full access to all data. RLS prevents this:

Without RLSWith RLS
Bug in API exposes all customer dataBug in API still only shows data the user should see
Attacker who bypasses app code gets everythingAttacker is still limited by database policies
Developer mistake can leak sensitive dataDatabase enforces rules regardless of app code
Security depends entirely on application codeDefense in depth — multiple layers of protection

Enabling RLS

RLS is enabled per table with a single command:

-- Enable RLS on a table
ALTER TABLE blog_posts ENABLE ROW LEVEL SECURITY;

-- Enable on multiple tables
ALTER TABLE blog_categories ENABLE ROW LEVEL SECURITY;
ALTER TABLE blog_tags ENABLE ROW LEVEL SECURITY;
ALTER TABLE blog_post_tags ENABLE ROW LEVEL SECURITY;
Default Deny! Once RLS is enabled on a table, no one can access any rows unless you create explicit policies that grant access. This is "default deny" behavior and is intentional — it is better to accidentally block access than to accidentally expose data. If you enable RLS and your app suddenly returns empty results, it means you need to create policies.

You can check if RLS is enabled in the Supabase Dashboard under Database → Tables, or with SQL:

SELECT tablename, rowsecurity
FROM pg_tables
WHERE schemaname = 'public';

Creating Policies

Policies define the rules for who can do what. Each policy has:

  • A name (descriptive, for documentation)
  • A table it applies to
  • An operation (SELECT, INSERT, UPDATE, DELETE, or ALL)
  • A condition that determines which rows are affected

Basic Syntax

CREATE POLICY "policy_name"
  ON table_name
  FOR operation         -- SELECT, INSERT, UPDATE, DELETE, or ALL
  TO role_name          -- Optional: which role (default: public)
  USING (condition)     -- Which existing rows can be accessed
  WITH CHECK (condition); -- Which new/modified rows are allowed

USING vs WITH CHECK

This is the most important distinction in RLS:

ClauseApplies ToQuestion It Answers
USINGSELECT, UPDATE (existing rows), DELETE"Can the user see this existing row?"
WITH CHECKINSERT, UPDATE (new values)"Can the user write this new/modified row?"
  • USING filters which rows are visible — rows that do not match are invisible to the user
  • WITH CHECK validates what can be written — writes that do not match are rejected with an error
-- For SELECT: only USING matters
CREATE POLICY "Anyone can read published posts"
  ON blog_posts
  FOR SELECT
  USING (status = 'published');

-- For INSERT: only WITH CHECK matters
CREATE POLICY "Users can insert their own posts"
  ON blog_posts
  FOR INSERT
  WITH CHECK (auth.uid() = author_id);

-- For UPDATE: both matter
-- USING: which existing rows can the user see/target?
-- WITH CHECK: what values can the user set?
CREATE POLICY "Users can update their own posts"
  ON blog_posts
  FOR UPDATE
  USING (auth.uid() = author_id)         -- Can only target own posts
  WITH CHECK (auth.uid() = author_id);   -- Cannot change author_id to someone else

auth.uid() — Identifying the Current User

In Supabase, auth.uid() is a built-in function that returns the UUID of the currently authenticated user. It reads the user's identity from the JWT token in the request. If no user is authenticated, it returns NULL.

-- Only show rows belonging to the current user
CREATE POLICY "Users see own data"
  ON user_profiles
  FOR SELECT
  USING (id = auth.uid());

-- Users can only update their own profile
CREATE POLICY "Users update own profile"
  ON user_profiles
  FOR UPDATE
  USING (id = auth.uid())
  WITH CHECK (id = auth.uid());

auth.uid() is what makes RLS truly powerful — it lets you write policies that automatically adapt to whoever is making the request, without any application code.

Other Useful Auth Functions

auth.role()Current role ('authenticated', 'anon', 'service_role')Role-based access

Common RLS Patterns

Pattern 1: Public Read, Admin Write

This is the most common pattern for content like blog posts — anyone can read published content, but only admins can create, edit, or delete.

-- Enable RLS
ALTER TABLE blog_posts ENABLE ROW LEVEL SECURITY;

-- Anyone can read published posts (even anonymous visitors)
CREATE POLICY "Public can view published posts"
  ON blog_posts
  FOR SELECT
  USING (status = 'published');

-- Service role (admin) has full access
-- Note: service_role already bypasses RLS by default in Supabase,
-- but explicit policies make the intent clear
CREATE POLICY "Service role full access"
  ON blog_posts
  FOR ALL
  USING (auth.role() = 'service_role');

Pattern 2: Users Own Their Data

Each user can only see and modify their own data.

-- Enable RLS
ALTER TABLE user_settings ENABLE ROW LEVEL SECURITY;

-- Users can only read their own settings
CREATE POLICY "Users read own settings"
  ON user_settings
  FOR SELECT
  USING (user_id = auth.uid());

-- Users can only update their own settings
CREATE POLICY "Users update own settings"
  ON user_settings
  FOR UPDATE
  USING (user_id = auth.uid())
  WITH CHECK (user_id = auth.uid());

-- Users can only insert settings for themselves
CREATE POLICY "Users insert own settings"
  ON user_settings
  FOR INSERT
  WITH CHECK (user_id = auth.uid());

-- Users can only delete their own settings
CREATE POLICY "Users delete own settings"
  ON user_settings
  FOR DELETE
  USING (user_id = auth.uid());

Pattern 3: Public Read for Published, Full Access for Authenticated

A mixed pattern where some content is public and authenticated users have broader access.

-- Anyone can read public categories
CREATE POLICY "Public can view categories"
  ON blog_categories
  FOR SELECT
  USING (true);  -- true = always allow (no restriction)

-- Authenticated users can manage categories
CREATE POLICY "Authenticated users manage categories"
  ON blog_categories
  FOR ALL
  USING (auth.role() = 'authenticated');

Pattern 4: Junction Table Following Parent Access

For junction tables, policies often check the parent table:

-- Can see post-tag links only for published posts
CREATE POLICY "Public can view tags for published posts"
  ON blog_post_tags
  FOR SELECT
  USING (
    EXISTS (
      SELECT 1 FROM blog_posts
      WHERE blog_posts.id = blog_post_tags.post_id
      AND blog_posts.status = 'published'
    )
  );
CSK Connection CSK uses all of these patterns. Blog posts have public SELECT for published content and service role full access for the admin. Blog categories and tags allow public SELECT with USING (true). The blog_post_tags junction table uses a subquery to check that the linked post is published. Every single Supabase table in CSK has RLS enabled — it is a hard rule for the project.

The Service Role Key Bypasses RLS

When you use the service_role key to create a Supabase client, that client bypasses all RLS policies. It can read, write, and delete any row in any table, regardless of policies.

// This client respects RLS
const supabase = createClient(url, anonKey);

// This client bypasses RLS entirely
const supabaseAdmin = createClient(url, serviceRoleKey);

This is by design — your server-side code needs full access for admin operations, webhooks, data sync, and background tasks. But it means the service role key is extremely sensitive.

Service Role Key Security Rules
  • Never use in client-side (browser) code
  • Never prefix with NEXT_PUBLIC_
  • Never commit to git or share publicly
  • Only use in server-side code: API routes, server components, webhooks
  • Store in environment variables on the server only

When to Use Each Client

ScenarioClientWhy
Public blog page reading postsAnon (public)RLS policy allows public reads of published posts
User viewing their own profileAnon (public) with user sessionRLS policy allows users to read their own data
Admin creating a blog postService role (admin)Needs to bypass RLS for write operations
Webhook syncing customer dataService role (admin)No user session; needs full access
Background job cleaning up old dataService role (admin)System process, not a user action

Multiple Policies: OR Behavior

When multiple policies exist for the same operation on the same table, they are combined with OR logic. A row is accessible if any matching policy allows it.

-- Policy 1: Anyone can see published posts
CREATE POLICY "Public sees published"
  ON blog_posts FOR SELECT
  USING (status = 'published');

-- Policy 2: Authors can see their own drafts
CREATE POLICY "Authors see own drafts"
  ON blog_posts FOR SELECT
  USING (auth.uid() = author_id);

-- Result: A row is visible if:
--   status = 'published'  OR  auth.uid() = author_id
-- Published posts visible to everyone
-- Drafts visible only to their author

This OR behavior is useful because you can build up access incrementally — each policy adds a new reason to allow access.

Testing RLS Policies

Testing RLS is crucial. Incorrect policies can either block legitimate access or expose sensitive data.

Testing in the SQL Editor

-- Test as an anonymous user (no auth)
SET request.jwt.claim.role = 'anon';
SELECT * FROM blog_posts;
-- Should only see published posts

-- Test as an authenticated user
SET request.jwt.claim.sub = 'some-user-uuid';
SET request.jwt.claim.role = 'authenticated';
SELECT * FROM blog_posts;
-- Should see published posts + own drafts

-- Reset to service role (full access)
RESET request.jwt.claim.role;
RESET request.jwt.claim.sub;

Debugging Checklist

  1. Is RLS enabled on the table? (ALTER TABLE ... ENABLE ROW LEVEL SECURITY)
  2. Are there any policies for the operation you are trying? (Check in Dashboard → Authentication → Policies)
  3. Does the USING condition match your test case?
  4. For INSERT/UPDATE: is there a WITH CHECK policy?
  5. Are you using the right client? (anon vs service role)
  6. Is the user properly authenticated? (Check auth.uid() is not NULL)

Getting RLS right often takes several iterations, which is why each fix is a separate migration file rather than editing previous ones.

Complete RLS Example: Blog System

Here is a complete, production-ready RLS setup for a blog system:

-- =============================================
-- Enable RLS on all blog tables
-- =============================================
ALTER TABLE blog_posts ENABLE ROW LEVEL SECURITY;
ALTER TABLE blog_categories ENABLE ROW LEVEL SECURITY;
ALTER TABLE blog_tags ENABLE ROW LEVEL SECURITY;
ALTER TABLE blog_post_tags ENABLE ROW LEVEL SECURITY;

-- =============================================
-- Blog Posts Policies
-- =============================================

-- Anyone can read published posts
CREATE POLICY "Public can view published posts"
  ON blog_posts
  FOR SELECT
  USING (status = 'published');

-- Service role has full access (for admin operations)
CREATE POLICY "Service role full access to posts"
  ON blog_posts
  FOR ALL
  USING (auth.role() = 'service_role');

-- =============================================
-- Blog Categories Policies
-- =============================================

-- Anyone can read all categories
CREATE POLICY "Public can view categories"
  ON blog_categories
  FOR SELECT
  USING (true);

-- Service role manages categories
CREATE POLICY "Service role full access to categories"
  ON blog_categories
  FOR ALL
  USING (auth.role() = 'service_role');

-- =============================================
-- Blog Tags Policies
-- =============================================

-- Anyone can read all tags
CREATE POLICY "Public can view tags"
  ON blog_tags
  FOR SELECT
  USING (true);

-- Service role manages tags
CREATE POLICY "Service role full access to tags"
  ON blog_tags
  FOR ALL
  USING (auth.role() = 'service_role');

-- =============================================
-- Blog Post Tags Policies (Junction Table)
-- =============================================

-- Can see tag links for published posts only
CREATE POLICY "Public can view post tags for published posts"
  ON blog_post_tags
  FOR SELECT
  USING (
    EXISTS (
      SELECT 1 FROM blog_posts
      WHERE blog_posts.id = blog_post_tags.post_id
      AND blog_posts.status = 'published'
    )
  );

-- Service role manages post-tag links
CREATE POLICY "Service role full access to post_tags"
  ON blog_post_tags
  FOR ALL
  USING (auth.role() = 'service_role');

Hands-On Exercises

  1. Enable and Test: Create a notes table with columns id, user_id, content, and created_at. Enable RLS. Before creating any policies, try to SELECT from the table using the anon key — what happens?
  2. User Ownership: Write RLS policies for the notes table so that authenticated users can only see, create, update, and delete their own notes. Use auth.uid() for ownership checks.
  3. Public + Private: Add an is_public boolean column to the notes table. Write policies so that: (a) anyone can read public notes, (b) authenticated users can read their own private notes, and (c) only the owner can write to their notes.
  4. Policy Analysis: Given these two policies on the same table, describe exactly who can see what: 
    CREATE POLICY "Public reads" ON products
  FOR SELECT USING (is_active = true);

CREATE POLICY "Staff reads all" ON products
  FOR SELECT USING (auth.role() = 'authenticated');
  5. Junction Table Policy: Given tables projects (with owner_id) and project_members (junction: project_id, user_id), write an RLS policy on project_members so users can only see members of projects they belong to.
  6. Debug Scenario: A developer reports that their INSERT into the todos table returns no error but the data does not appear. RLS is enabled. What are the possible causes, and what steps would you take to debug?

Key Takeaways

  • RLS enforces data access rules at the database level — the last line of defense.
  • Enabling RLS defaults to deny all — you must create policies to grant access.
  • USING controls which existing rows are visible; WITH CHECK controls what can be written.
  • auth.uid() identifies the current user in Supabase policies.
  • Multiple policies on the same table/operation use OR logic.
  • The service role key bypasses all RLS — use it only on the server.
  • Common patterns: public read + admin write, user-owned data, junction table following parent access.
  • RLS policies often require multiple iterations to get right — test thoroughly.
  • Always enable RLS on every table in Supabase, even if the policy is permissive.
