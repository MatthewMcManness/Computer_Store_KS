Lesson 36: Error Handling Patterns

Build resilient applications that fail gracefully and communicate clearly when things go wrong

Learning Objectives

  • Explain why robust error handling is critical for both security and user experience
  • Use try/catch effectively in both synchronous and asynchronous code
  • Distinguish between user errors (4xx) and server errors (5xx) and handle each appropriately
  • Build a consistent error response format for API routes
  • Catch and format Zod validation errors, database errors, and external API errors
  • Implement React error boundaries and Next.js error.tsx for graceful UI failures
  • Apply the "fail fast" principle and implement retry patterns for transient failures
  • Log errors server-side without leaking sensitive information to clients

Why Errors Happen (and Why Handling Them Matters)

Every piece of software encounters errors. This is not a sign of bad code — it is an inevitable reality of building systems that interact with unpredictable users, unreliable networks, and complex databases. The difference between amateur and professional code is not whether errors occur, but how they are handled when they do.

Here are the most common sources of errors in a web application:

  • User input — Invalid form data, wrong file types, missing required fields
  • Network failures — Lost connections, timeouts, DNS failures
  • Database problems — Connection drops, constraint violations, deadlocks
  • External APIs — Third-party services go down, change their response format, or rate-limit you
  • Programming bugs — Null references, type mismatches, logic errors
  • Resource limits — Memory exhaustion, disk full, file handle limits
  • Authentication issues — Expired sessions, revoked tokens, invalid credentials
Analogy: The Safety Net
Think of error handling as a safety net for trapeze artists. The performers (your code) are skilled and usually perform flawlessly. But the safety net exists for when something unexpected happens — a slippery grip, a gust of wind, a momentary distraction. Without the net, a single mistake is catastrophic. With it, the show goes on. Error handling is your application's safety net. It catches failures, prevents crashes, and keeps the experience running for your users.

What Happens Without Error Handling

Consider an API route with no error handling:

// DANGEROUS: No error handling at all
export async function GET(request: NextRequest) {
  const { searchParams } = new URL(request.url);
  const id = searchParams.get('id');

  // What if id is null?
  // What if the database is down?
  // What if the post does not exist?
  const { data } = await supabase
    .from('blog_posts')
    .select('*')
    .eq('id', id)
    .single();

  // What if data is null?
  return NextResponse.json({ title: data.title });
}

This code has at least five ways to crash:

  1. id could be null, causing the database query to match nothing
  2. The Supabase connection could fail (network error, service outage)
  3. The query could fail (table does not exist, permission denied)
  4. data could be null (no post with that ID), causing data.title to throw
  5. The entire response could fail to serialize

When any of these happens, the user sees a cryptic 500 Internal Server Error with no useful information. Worse, the error might leak internal details (database connection strings, file paths, stack traces) that could help an attacker.

Try/Catch: Your Primary Error Handling Tool

The try/catch statement is JavaScript's mechanism for catching and handling errors. When code inside the try block throws an error, execution immediately jumps to the catch block instead of crashing the application.

Synchronous Try/Catch

// Basic try/catch structure
try {
  // Code that might throw an error
  const result = JSON.parse(someString);
  console.log(result.name);
} catch (error) {
  // This runs if ANY error is thrown in the try block
  console.error("Failed to parse JSON:", error);
} finally {
  // This ALWAYS runs, whether there was an error or not
  // Useful for cleanup (closing connections, releasing resources)
  console.log("Parsing attempt complete");
}

Async/Await Try/Catch

The same pattern works with async/await, which is how you will use it most often in Next.js API routes:

// Async try/catch
async function fetchUser(id: string) {
  try {
    const response = await fetch(`https://api.example.com/users/${id}`);

    if (!response.ok) {
      throw new Error(`HTTP error! Status: ${response.status}`);
    }

    const user = await response.json();
    return user;
  } catch (error) {
    console.error("Failed to fetch user:", error);
    throw error; // Re-throw if you want the caller to handle it too
  }
}

The Error Object

In the catch block, the error parameter contains information about what went wrong:

try {
  throw new Error("Something went wrong");
} catch (error) {
  if (error instanceof Error) {
    console.log(error.message);   // "Something went wrong"
    console.log(error.name);      // "Error"
    console.log(error.stack);     // Full stack trace (file names, line numbers)
  }
}
TypeScript and the Unknown Error Type In TypeScript, the catch parameter is typed as unknown (not Error), because anything can be thrown in JavaScript — strings, numbers, objects, not just Error instances. Always check the type before accessing properties: 
catch (error) {
  // Safe: check the type first
  if (error instanceof Error) {
    console.log(error.message);
  } else {
    console.log("An unknown error occurred:", error);
  }
}

User Errors vs. Server Errors

A critical skill in error handling is distinguishing between errors caused by the user (4xx) and errors caused by your server (5xx). The distinction determines what you tell the user and how you respond.

User Errors (4xx) — "You Did Something Wrong"

These errors are caused by the client sending a bad request. The client can fix the problem by changing their request:

Error Type Status Example What to Tell the User
Invalid input 400 / 422 Empty name field, invalid email Specific field errors: "Email must be valid"
Not authenticated 401 Missing or expired session "Please log in to continue"
Not authorized 403 Regular user accessing admin page "You do not have permission for this action"
Resource not found 404 Blog post with this ID does not exist "The requested item was not found"
Conflict 409 Duplicate email during registration "An account with this email already exists"
Rate limited 429 Too many requests in a short period "Too many requests. Please wait and try again."

For user errors, you should provide helpful, specific error messages that tell the user exactly what went wrong and how to fix it.

Server Errors (5xx) — "We Made a Mistake"

These errors are caused by problems on the server. The client did nothing wrong, and retrying the same request might work later:

Error Type Status Example What to Tell the User
Unhandled exception 500 Null pointer, undefined variable "Something went wrong. Please try again later."
Database failure 500 Connection pool exhausted, query timeout "Something went wrong. Please try again later."
External service down 502 Third-party API returned an error "A service we depend on is unavailable."
Overloaded 503 Server is too busy to handle requests "The service is temporarily unavailable."

For server errors, you should provide a generic, vague message that does not reveal internal details. The specific error should be logged server-side for debugging.

Never Expose Internal Errors to Clients A server error response should never contain stack traces, database connection strings, file paths, SQL queries, or any other internal detail. These leak information that attackers can exploit. Always log the full error internally and return a generic message to the client: 
// BAD: Exposing internal details
{ "error": "Connection to postgres://user:pass@db.supabase.co:5432 failed" }

// GOOD: Generic message, details logged server-side
{ "error": { "message": "An unexpected error occurred", "code": "INTERNAL_ERROR" } }

Building a Consistent Error Response Format

As we learned in Lesson 34, consistency is king. Every API route should return errors in the same shape so the frontend can handle them generically. Here is a robust error response format:

// The standard error response shape
{
  "error": {
    "message": "Human-readable description of what went wrong",
    "code": "MACHINE_READABLE_ERROR_CODE",
    "details": [                          // Optional: field-level errors
      {
        "field": "email",
        "message": "Please enter a valid email address"
      }
    ]
  }
}

Helper Functions for Error Responses

To avoid repeating error response code in every route, create helper functions:

// src/lib/api-errors.ts
import { NextResponse } from 'next/server';
import { z } from 'zod';

/**
 * Returns a 422 response with formatted Zod validation errors.
 */
export function validationError(zodError: z.ZodError) {
  return NextResponse.json(
    {
      error: {
        message: "Validation failed",
        code: "VALIDATION_ERROR",
        details: zodError.errors.map((err) => ({
          field: err.path.join('.'),
          message: err.message,
        })),
      },
    },
    { status: 422 }
  );
}

/**
 * Returns a 401 response for unauthenticated requests.
 */
export function unauthorizedError(message = "Authentication required") {
  return NextResponse.json(
    { error: { message, code: "AUTH_REQUIRED" } },
    { status: 401 }
  );
}

/**
 * Returns a 403 response for unauthorized requests.
 */
export function forbiddenError(message = "You do not have permission") {
  return NextResponse.json(
    { error: { message, code: "FORBIDDEN" } },
    { status: 403 }
  );
}

/**
 * Returns a 404 response for missing resources.
 */
export function notFoundError(resource = "Resource") {
  return NextResponse.json(
    { error: { message: `${resource} not found`, code: "NOT_FOUND" } },
    { status: 404 }
  );
}

/**
 * Returns a 500 response for unexpected server errors.
 * NEVER includes internal details in the response.
 */
export function internalError() {
  return NextResponse.json(
    { error: { message: "An unexpected error occurred", code: "INTERNAL_ERROR" } },
    { status: 500 }
  );
}

Now your API routes become clean and consistent:

// src/app/api/blog/[id]/route.ts
import { NextRequest } from 'next/server';
import { notFoundError, internalError, unauthorizedError } from '@/lib/api-errors';

export async function GET(
  request: NextRequest,
  { params }: { params: { id: string } }
) {
  try {
    const { data, error } = await supabase
      .from('blog_posts')
      .select('*')
      .eq('id', params.id)
      .single();

    if (error || !data) {
      return notFoundError("Blog post");
    }

    return NextResponse.json({ data });
  } catch (error) {
    console.error("Error fetching blog post:", error);
    return internalError();
  }
}

The API Route Error Handling Pattern

Every API route handler should follow this pattern. It is the most important pattern in this entire lesson:

// The standard API route error handling pattern
export async function POST(request: NextRequest) {
  try {
    // 1. Parse the request body
    let body;
    try {
      body = await request.json();
    } catch {
      return NextResponse.json(
        { error: { message: "Invalid JSON", code: "INVALID_JSON" } },
        { status: 400 }
      );
    }

    // 2. Validate the input (Zod)
    const validation = schema.safeParse(body);
    if (!validation.success) {
      return validationError(validation.error);
    }

    // 3. Check authentication/authorization
    const session = await getSession(request);
    if (!session) {
      return unauthorizedError();
    }

    // 4. Perform the business logic (database operations, etc.)
    const { data, error } = await supabase
      .from('table')
      .insert(validation.data)
      .select()
      .single();

    if (error) {
      // Handle specific database errors
      if (error.code === '23505') {
        // Unique constraint violation
        return NextResponse.json(
          { error: { message: "A record with this value already exists", code: "CONFLICT" } },
          { status: 409 }
        );
      }
      // Unknown database error
      console.error("Database error:", error);
      return internalError();
    }

    // 5. Return success
    return NextResponse.json({ data }, { status: 201 });

  } catch (error) {
    // 6. Catch-all for unexpected errors
    console.error("Unexpected error:", error);
    return internalError();
  }
}

Notice the structure: each type of error is caught at the appropriate level, and the outer try/catch serves as a safety net for anything unexpected. This ensures your API never returns an unformatted error or leaks internal information.

CSK Connection Every API route in Computer Store KS wraps its logic in try/catch. The blog API, gallery API, contact form, and authentication endpoints all follow this pattern. Authentication debug info is logged via middleware for troubleshooting, but no internal error details are ever sent to the client. If the Supabase database is unreachable, the health check at /api/health catches the error and returns a structured 503 response.

Logging Errors Server-Side

When a server error occurs, you need to know about it. But the information needs to stay on the server, not go to the client. This is what server-side logging is for.

What to Log

// Log enough detail to debug the problem
console.error("Error in POST /api/blog:", {
  error: error instanceof Error ? error.message : error,
  stack: error instanceof Error ? error.stack : undefined,
  requestBody: body,           // What the client sent
  userId: session?.user?.id,   // Who made the request
  timestamp: new Date().toISOString(),
});

What NOT to Log

  • Passwords — Never log raw passwords, even in error scenarios
  • Full credit card numbers — Log at most the last four digits
  • API keys or secrets — Mask them if you must log them (e.g., re_***abc)
  • Personal data unnecessarily — Only log what you need for debugging

Structured Logging

For production applications, structured logging (JSON-formatted logs) makes it much easier to search and analyze errors:

// Instead of console.error("Something went wrong")
// Use structured logging:
function logError(context: string, error: unknown, metadata?: Record<string, unknown>) {
  const logEntry = {
    level: "error",
    context,                    // e.g., "POST /api/blog"
    message: error instanceof Error ? error.message : String(error),
    stack: error instanceof Error ? error.stack : undefined,
    timestamp: new Date().toISOString(),
    ...metadata,
  };

  // In development: pretty print
  if (process.env.NODE_ENV === 'development') {
    console.error(`[ERROR] ${context}:`, logEntry);
  } else {
    // In production: JSON for log aggregation tools
    console.error(JSON.stringify(logEntry));
  }
}

// Usage
logError("POST /api/contact", error, {
  requestBody: { name: body.name, email: body.email },
  ip: request.headers.get('x-forwarded-for'),
});
Log Levels Most logging systems use these severity levels: debug (detailed diagnostic info), info (normal operations), warn (something unexpected but not an error), error (something failed), and fatal (the application cannot continue). In development, log everything. In production, log warn and above to avoid excessive log volume.

Handling Specific Error Types

Zod Validation Errors

You learned about Zod errors in Lesson 35. Here is how they fit into the API error handling pattern:

import { z } from 'zod';

const schema = z.object({
  name: z.string().min(1, "Name is required"),
  email: z.string().email("Invalid email"),
});

export async function POST(request: NextRequest) {
  try {
    const body = await request.json();
    const validation = schema.safeParse(body);

    if (!validation.success) {
      // Format Zod errors into our standard error shape
      return NextResponse.json(
        {
          error: {
            message: "Validation failed",
            code: "VALIDATION_ERROR",
            details: validation.error.errors.map((e) => ({
              field: e.path.join('.'),
              message: e.message,
            })),
          },
        },
        { status: 422 }
      );
    }

    // Continue with validated data...
  } catch (error) {
    console.error("Unexpected error:", error);
    return internalError();
  }
}

Database Errors

Database errors come in many forms. Here are the most common ones and how to handle them:

// Supabase returns { data, error } instead of throwing
const { data, error } = await supabase
  .from('blog_posts')
  .insert(postData)
  .select()
  .single();

if (error) {
  // Handle specific PostgreSQL error codes
  switch (error.code) {
    case '23505':
      // Unique constraint violation (duplicate entry)
      return NextResponse.json(
        { error: { message: "A record with this value already exists", code: "CONFLICT" } },
        { status: 409 }
      );

    case '23503':
      // Foreign key constraint violation (referenced record does not exist)
      return NextResponse.json(
        { error: { message: "Referenced record not found", code: "NOT_FOUND" } },
        { status: 422 }
      );

    case '23502':
      // NOT NULL violation (required field is missing)
      return NextResponse.json(
        { error: { message: "A required field is missing", code: "VALIDATION_ERROR" } },
        { status: 422 }
      );

    case 'PGRST116':
      // Supabase: row not found (for .single() queries)
      return notFoundError("Record");

    default:
      // Unknown database error — log it, return generic message
      console.error("Database error:", {
        code: error.code,
        message: error.message,
        details: error.details,
      });
      return internalError();
  }
}

External API Errors

When your server calls other APIs (like RepairShopr, Resend, or any third-party service), many things can go wrong:

async function callExternalAPI(url: string, options?: RequestInit) {
  try {
    const controller = new AbortController();
    const timeout = setTimeout(() => controller.abort(), 10000); // 10s timeout

    const response = await fetch(url, {
      ...options,
      signal: controller.signal,
    });

    clearTimeout(timeout);

    if (!response.ok) {
      // The external API returned an error status
      if (response.status === 401) {
        console.error("External API: Authentication failed. Check API key.");
        throw new ExternalAPIError("Authentication with external service failed", 502);
      }

      if (response.status === 429) {
        console.error("External API: Rate limited.");
        throw new ExternalAPIError("External service rate limit reached", 503);
      }

      console.error(`External API error: ${response.status} ${response.statusText}`);
      throw new ExternalAPIError("External service returned an error", 502);
    }

    return await response.json();

  } catch (error) {
    if (error instanceof ExternalAPIError) {
      throw error; // Re-throw our custom error
    }

    // Handle network-level errors
    if (error instanceof TypeError && error.message === 'fetch failed') {
      console.error("External API: Network connection failed");
      throw new ExternalAPIError("Cannot reach external service", 503);
    }

    if (error instanceof DOMException && error.name === 'AbortError') {
      console.error("External API: Request timed out");
      throw new ExternalAPIError("External service request timed out", 504);
    }

    throw error;
  }
}

Custom Error Classes

JavaScript's built-in Error class is generic. For better error handling, create custom error classes that carry additional information:

// src/lib/errors.ts

/**
 * Base class for all application errors.
 * Includes an HTTP status code for API responses.
 */
export class AppError extends Error {
  public readonly statusCode: number;
  public readonly code: string;

  constructor(message: string, statusCode: number, code: string) {
    super(message);
    this.name = 'AppError';
    this.statusCode = statusCode;
    this.code = code;
  }
}

/**
 * Thrown when validation fails.
 */
export class ValidationError extends AppError {
  public readonly details: Array<{ field: string; message: string }>;

  constructor(
    details: Array<{ field: string; message: string }>,
    message = "Validation failed"
  ) {
    super(message, 422, "VALIDATION_ERROR");
    this.name = 'ValidationError';
    this.details = details;
  }
}

/**
 * Thrown when a resource is not found.
 */
export class NotFoundError extends AppError {
  constructor(resource: string) {
    super(`${resource} not found`, 404, "NOT_FOUND");
    this.name = 'NotFoundError';
  }
}

/**
 * Thrown when authentication is required.
 */
export class AuthError extends AppError {
  constructor(message = "Authentication required") {
    super(message, 401, "AUTH_REQUIRED");
    this.name = 'AuthError';
  }
}

/**
 * Thrown when an external API fails.
 */
export class ExternalAPIError extends AppError {
  constructor(message: string, statusCode = 502) {
    super(message, statusCode, "EXTERNAL_SERVICE_ERROR");
    this.name = 'ExternalAPIError';
  }
}

Now your catch blocks can handle different error types differently:

export async function GET(request: NextRequest) {
  try {
    // Business logic that might throw custom errors
    const post = await getPostById(params.id);
    return NextResponse.json({ data: post });

  } catch (error) {
    // Handle our custom errors with appropriate responses
    if (error instanceof AppError) {
      const response: Record<string, unknown> = {
        error: {
          message: error.message,
          code: error.code,
        },
      };

      // Include validation details if present
      if (error instanceof ValidationError) {
        (response.error as Record<string, unknown>).details = error.details;
      }

      return NextResponse.json(response, { status: error.statusCode });
    }

    // Unknown error — log and return generic response
    console.error("Unexpected error:", error);
    return internalError();
  }
}

React Error Boundaries

Everything we have covered so far handles errors on the server side (API routes). But what about errors in the frontend (React components)? When a React component throws an error during rendering, the entire component tree crashes and the user sees a blank screen. Error boundaries prevent this.

What Is an Error Boundary?

An error boundary is a React component that catches JavaScript errors anywhere in its child component tree, logs the error, and displays a fallback UI instead of crashing the entire page.

// src/components/ErrorBoundary.tsx
'use client';
import React, { Component, ReactNode } from 'react';

interface Props {
  children: ReactNode;
  fallback?: ReactNode;
}

interface State {
  hasError: boolean;
  error: Error | null;
}

export class ErrorBoundary extends Component<Props, State> {
  constructor(props: Props) {
    super(props);
    this.state = { hasError: false, error: null };
  }

  static getDerivedStateFromError(error: Error): State {
    // Update state so the next render shows the fallback UI
    return { hasError: true, error };
  }

  componentDidCatch(error: Error, errorInfo: React.ErrorInfo) {
    // Log the error for debugging
    console.error("Error boundary caught an error:", error, errorInfo);

    // In production, you might send this to an error tracking service
    // like Sentry, LogRocket, or Datadog
  }

  render() {
    if (this.state.hasError) {
      // Render fallback UI
      return this.props.fallback || (
        <div style={{ padding: '2rem', textAlign: 'center' }}>
          <h2>Something went wrong</h2>
          <p>We are sorry for the inconvenience. Please try refreshing the page.</p>
          <button onClick={() => this.setState({ hasError: false, error: null })}>
            Try Again
          </button>
        </div>
      );
    }

    return this.props.children;
  }
}

Wrap your components with the error boundary:

// Usage in a layout or page
import { ErrorBoundary } from '@/components/ErrorBoundary';

export default function DashboardPage() {
  return (
    <div>
      <h1>Dashboard</h1>
      <ErrorBoundary fallback={<p>Failed to load tickets.</p>}>
        <TicketList />
      </ErrorBoundary>
      <ErrorBoundary fallback={<p>Failed to load stats.</p>}>
        <StatsPanel />
      </ErrorBoundary>
    </div>
  );
}

// If TicketList crashes, only that section shows the fallback.
// StatsPanel continues to work normally.
Why Are Error Boundaries Class Components? Error boundaries require the componentDidCatch lifecycle method, which is only available in class components. There is no hook equivalent (useErrorBoundary) in React yet. This is one of the very few cases where you still need a class component in modern React. Libraries like react-error-boundary provide a more modern API if you prefer.

error.tsx in Next.js

Next.js provides built-in error handling through special file conventions. The error.tsx file acts as an error boundary for an entire route segment.

// src/app/admin/error.tsx
'use client'; // Error components must be Client Components

interface ErrorProps {
  error: Error & { digest?: string };
  reset: () => void;
}

export default function AdminError({ error, reset }: ErrorProps) {
  return (
    <div className="flex flex-col items-center justify-center min-h-[400px]">
      <h2 className="text-2xl font-bold text-red-600 mb-4">
        Something went wrong
      </h2>
      <p className="text-gray-600 mb-6">
        An error occurred while loading this page.
        Please try again or contact support if the problem persists.
      </p>
      <button
        onClick={() => reset()}
        className="px-4 py-2 bg-blue-600 text-white rounded-lg hover:bg-blue-700"
      >
        Try Again
      </button>
    </div>
  );
}

How it works:

  • error.tsx in a route folder catches errors from all pages and components within that route segment
  • The error prop contains the error object (message is sanitized in production for security)
  • The reset function attempts to re-render the route segment, which may succeed if the error was transient
  • The file must use 'use client' because error handling requires client-side interactivity

Loading States and Error States in UI Components

Every component that fetches data should handle three states: loading, success, and error. Forgetting any one of these leads to a poor user experience.

// A component that handles all three states
'use client';
import { useState, useEffect } from 'react';

interface Post {
  id: number;
  title: string;
  content: string;
}

export function BlogPostList() {
  const [posts, setPosts] = useState<Post[]>([]);
  const [isLoading, setIsLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    async function fetchPosts() {
      try {
        setIsLoading(true);
        setError(null);

        const response = await fetch('/api/blog');

        if (!response.ok) {
          throw new Error(`Failed to load posts (${response.status})`);
        }

        const json = await response.json();
        setPosts(json.data);

      } catch (err) {
        setError(
          err instanceof Error
            ? err.message
            : "An unexpected error occurred"
        );
      } finally {
        setIsLoading(false);
      }
    }

    fetchPosts();
  }, []);

  // Loading state
  if (isLoading) {
    return (
      <div className="animate-pulse">
        <div className="h-6 bg-gray-200 rounded mb-4"></div>
        <div className="h-6 bg-gray-200 rounded mb-4 w-3/4"></div>
        <div className="h-6 bg-gray-200 rounded mb-4 w-1/2"></div>
      </div>
    );
  }

  // Error state
  if (error) {
    return (
      <div className="p-4 bg-red-50 border border-red-200 rounded-lg">
        <p className="text-red-700">{error}</p>
        <button
          onClick={() => window.location.reload()}
          className="mt-2 text-red-600 underline"
        >
          Try again
        </button>
      </div>
    );
  }

  // Empty state (success but no data)
  if (posts.length === 0) {
    return <p className="text-gray-500">No blog posts found.</p>;
  }

  // Success state
  return (
    <ul>
      {posts.map((post) => (
        <li key={post.id}>{post.title}</li>
      ))}
    </ul>
  );
}
Analogy: The Loading Dock
Imagine ordering a package online. There are four possible states: In transit (loading — you see a tracking progress animation), Delivered (success — you see the package), Failed to deliver (error — you see a "delivery failed" notice with a retry option), or Nothing ordered (empty state — you see "no orders yet"). A good delivery service communicates all four states clearly. Your UI should do the same.

Graceful Degradation

Graceful degradation means that when part of your application fails, the rest continues to work. Instead of showing a blank page when one component crashes, you show a helpful fallback message while keeping the rest of the page functional.

// Example: A dashboard with independent sections
export default function AdminDashboard() {
  return (
    <div className="grid grid-cols-2 gap-4">
      <ErrorBoundary fallback={<FallbackCard title="Tickets" />}>
        <TicketSummary />
      </ErrorBoundary>

      <ErrorBoundary fallback={<FallbackCard title="Recent Activity" />}>
        <RecentActivity />
      </ErrorBoundary>

      <ErrorBoundary fallback={<FallbackCard title="Statistics" />}>
        <Statistics />
      </ErrorBoundary>

      <ErrorBoundary fallback={<FallbackCard title="Notifications" />}>
        <NotificationFeed />
      </ErrorBoundary>
    </div>
  );
}

function FallbackCard({ title }: { title: string }) {
  return (
    <div className="p-4 bg-gray-50 rounded-lg border border-gray-200">
      <h3 className="font-bold text-gray-500">{title}</h3>
      <p className="text-sm text-gray-400">Unable to load. Try refreshing the page.</p>
    </div>
  );
}

If the Statistics component crashes, the rest of the dashboard (tickets, activity, notifications) continues working. The user sees a polite message where Statistics would be, and every other section is unaffected.

The "Fail Fast" Principle

The fail fast principle says that when an error is detected, you should stop processing immediately rather than continuing with potentially corrupted data. Failing early and loudly is better than failing silently and causing cascading problems later.

// GOOD: Fail fast — validate inputs before doing anything
export async function POST(request: NextRequest) {
  const body = await request.json();

  // Check EVERYTHING before doing any work
  const validation = schema.safeParse(body);
  if (!validation.success) return validationError(validation.error);

  const session = await getSession(request);
  if (!session) return unauthorizedError();

  if (session.role !== 'admin') return forbiddenError();

  // Only NOW do the actual work (database insert, email send, etc.)
  const { data, error } = await supabase.from('posts').insert(validation.data);
  // ...
}

// BAD: Not failing fast — doing work before checking everything
export async function POST(request: NextRequest) {
  const body = await request.json();

  // Start doing work BEFORE validating
  const slug = generateSlug(body.title);  // What if title is undefined?
  const imageUrl = await uploadImage(body.image); // Wasted upload if auth fails
  await supabase.from('posts').insert({ ...body, slug, imageUrl }); // No validation!

  // Check auth AFTER the work is already done (too late!)
  const session = await getSession(request);
  if (!session) return unauthorizedError(); // Data already written!
}

In the bad example, the image is uploaded and the database record is created before checking if the user is authorized. If the auth check fails, you have wasted resources and potentially created orphaned data. The good example checks everything first, then does work only when all preconditions are met.

Retry Patterns for Transient Failures

Some errors are transient — they happen once and then go away. A momentary network glitch, a database connection that dropped, an external API that hiccupped. For these, retrying the operation often succeeds.

/**
 * Retries a function up to maxRetries times with exponential backoff.
 * Only retries on transient errors, not on validation or auth errors.
 */
async function withRetry<T>(
  fn: () => Promise<T>,
  options: {
    maxRetries?: number;
    baseDelay?: number;
    shouldRetry?: (error: unknown) => boolean;
  } = {}
): Promise<T> {
  const {
    maxRetries = 3,
    baseDelay = 1000,
    shouldRetry = isTransientError,
  } = options;

  let lastError: unknown;

  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      return await fn();
    } catch (error) {
      lastError = error;

      // Do not retry if the error is not transient
      if (!shouldRetry(error)) {
        throw error;
      }

      // Do not retry if we are out of attempts
      if (attempt === maxRetries) {
        break;
      }

      // Wait with exponential backoff: 1s, 2s, 4s, 8s, etc.
      const delay = baseDelay * Math.pow(2, attempt);
      console.warn(
        `Attempt ${attempt + 1} failed, retrying in ${delay}ms:`,
        error instanceof Error ? error.message : error
      );
      await new Promise((resolve) => setTimeout(resolve, delay));
    }
  }

  throw lastError;
}

/**
 * Determines if an error is transient (worth retrying).
 */
function isTransientError(error: unknown): boolean {
  // Network errors are transient
  if (error instanceof TypeError && error.message === 'fetch failed') {
    return true;
  }

  // Timeout errors are transient
  if (error instanceof DOMException && error.name === 'AbortError') {
    return true;
  }

  // HTTP 429 (rate limited) and 5xx (server errors) are transient
  if (error instanceof AppError) {
    return error.statusCode === 429 || error.statusCode >= 500;
  }

  return false;
}

// Usage:
const data = await withRetry(
  () => callExternalAPI('https://api.example.com/data'),
  { maxRetries: 3, baseDelay: 1000 }
);
When NOT to Retry Never retry these types of errors:
  • Validation errors (400, 422) — The input is wrong; retrying will not fix it
  • Authentication errors (401) — The credentials are wrong or expired
  • Authorization errors (403) — The user lacks permission
  • Not found errors (404) — The resource does not exist
  • Conflict errors (409) — The operation conflicts with existing data
Only retry transient failures: network errors, timeouts, rate limits (429), and server errors (5xx).

Key Takeaways

  • Every API route handler must be wrapped in try/catch. The outer catch block is your safety net for unexpected errors — it ensures your API always returns a formatted response, never an unhandled crash.
  • User errors (4xx) should include helpful, specific messages that tell the client how to fix the problem. Server errors (5xx) should return generic messages and log full details server-side.
  • Build a consistent error response format ({ error: { message, code, details } }) and use helper functions to construct error responses. This makes frontend error handling predictable and reliable.
  • Handle specific error types at the appropriate level: Zod errors become 422, database constraint violations become 409, auth failures become 401/403, and unknown errors become 500.
  • Never expose internal error details (stack traces, database URLs, file paths) to clients. Log them server-side for debugging.
  • React error boundaries catch render errors and display fallback UI instead of blank screens. In Next.js, error.tsx provides route-level error handling with a reset mechanism.
  • The "fail fast" principle says to validate all inputs and check all preconditions before doing any work. This prevents wasted resources and cascading failures.
  • Retry only transient errors (network failures, timeouts, 429, 5xx) with exponential backoff. Never retry client errors (400, 401, 403, 404).
