What Is Node.js?

In the early days of the web, JavaScript could only run inside a web browser. If you wanted to write server-side code (the backend), you had to use a completely different language like PHP, Python, Ruby, or Java. This meant web developers often needed to know two very different languages: one for the frontend (JavaScript) and one for the backend.

In 2009, Ryan Dahl created Node.js, which took the V8 JavaScript engine from Google Chrome and made it possible to run JavaScript outside the browser—on servers, on your laptop, anywhere. This was revolutionary. Suddenly, the same language you used to build interactive web pages could also power web servers, command-line tools, APIs, and anything else you could imagine.

Node.js is a JavaScript runtime environment. A runtime is the software that actually executes your code. Chrome's runtime runs JavaScript in the browser. Node.js's runtime runs JavaScript on your operating system directly, with access to the file system, network, and other system resources that browsers intentionally block for security.

Analogy: Think of JavaScript as a language you speak. The browser is like a phone call—you can speak the language, but you are limited to what the phone allows (no touching physical objects, no accessing files). Node.js is like speaking the same language in person—you can do everything: open doors, read papers, talk to multiple people. Same language, vastly more capabilities.

Why Node.js Matters

  • One language everywhere: JavaScript for frontend, backend, scripts, tools—everything. This drastically simplifies development.
  • Massive ecosystem: Over 2 million packages available through npm, the Node.js package manager.
  • Non-blocking I/O: Node.js handles many concurrent connections efficiently, making it excellent for web servers and APIs.
  • Industry standard: Used by Netflix, LinkedIn, Uber, NASA, and millions of other applications.

Installing Node.js with nvm

While you can download Node.js directly from nodejs.org, professional developers use nvm (Node Version Manager) to install and manage Node.js. The reason is simple: different projects may require different Node.js versions. One project might need Node 18, another Node 20, and another Node 22. nvm lets you switch between versions instantly.

Installing nvm

# On Mac/Linux, run this single command:
$ curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.39.7/install.sh | bash

# Close and reopen your terminal, then verify:
$ nvm --version
0.39.7

On Windows, use nvm-windows, a separate project with similar functionality.

Installing Node.js with nvm

# Install a specific version
$ nvm install 22

# Use a specific version
$ nvm use 22

# Verify the installation
$ node --version
v22.16.0

$ npm --version
10.9.2

When you install Node.js, npm (Node Package Manager) is automatically included. npm is the tool you use to install libraries, manage dependencies, and run scripts. They come as a pair.

The .nvmrc File

A .nvmrc file in your project's root directory specifies which Node.js version the project requires. When anyone opens the project, they can simply run nvm use and nvm will automatically switch to the correct version.

# Create the .nvmrc file
$ echo "22" > .nvmrc

# Now anyone can use it:
$ nvm use
Found '.nvmrc' with version <22>
Now using node v22.16.0 (npm v10.9.2)
CSK Connection The CSK project pins Node.js version 22 using both an .nvmrc file and the engines field in package.json. This ensures that every developer and the Render deployment platform all use the exact same Node.js version. Render's default Node.js version is 22.16.0, so we match it locally to avoid "works on my machine" bugs.

package.json: The Heart of Every Node.js Project

Every Node.js project has a package.json file in its root directory. This file is the project's identity card and instruction manual combined. It tells npm (and the world) everything about your project: its name, version, what libraries it depends on, and what scripts it can run.

Let us examine every important field:

{
  "name": "computer-store-ks",
  "version": "1.0.0",
  "description": "Website for Computer Store KS - a computer repair shop in Topeka, Kansas",
  "private": true,
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "next start",
    "lint": "next lint",
    "type-check": "tsc --noEmit"
  },
  "dependencies": {
    "next": "^14.2.0",
    "react": "^18.3.0",
    "react-dom": "^18.3.0",
    "@supabase/supabase-js": "^2.45.0",
    "resend": "^3.2.0",
    "zod": "^3.23.0"
  },
  "devDependencies": {
    "typescript": "^5.5.0",
    "@types/react": "^18.3.0",
    "@types/node": "^22.0.0",
    "tailwindcss": "^3.4.0",
    "eslint": "^8.57.0"
  },
  "engines": {
    "node": ">=22.0.0 <23.0.0"
  }
}

Field-by-Field Breakdown

FieldPurpose
nameThe project's identifier. Must be lowercase, no spaces. Used if you publish to npm.
versionCurrent version of your project following semantic versioning (more on this below).
descriptionA brief summary of what the project is. Shows up in npm search results.
privateIf true, npm refuses to publish the package. Set this for applications (not libraries).
scriptsCustom commands you can run with npm run <name>. This is where you define your development workflow.

devDependenciesPackages needed only during development (not in production).
enginesSpecifies which Node.js versions the project supports. Some platforms enforce this.

Creating package.json

You can create a package.json interactively or with defaults:

# Interactive creation (asks questions)
$ npm init

# Create with all defaults (no questions)
$ npm init -y

Installing Packages: npm install

The primary job of npm is installing packages (libraries) that your project needs. When you run npm install, three things happen:

  1. npm reads package.json to find which packages are listed under dependencies and devDependencies.
  2. npm downloads those packages (and all their dependencies, and all their dependencies) into a folder called node_modules/.
  3. npm creates or updates package-lock.json to record the exact version of every package installed.

Installing a New Package

# Add a package to dependencies
$ npm install axios
# This adds "axios": "^1.7.0" to package.json under "dependencies"

# Add a package to devDependencies
$ npm install --save-dev prettier
# This adds "prettier": "^3.3.0" under "devDependencies"

# Install all packages listed in package.json (what you run after cloning)
$ npm install

The node_modules/ Folder

When you install packages, they all go into the node_modules/ directory. This folder can be enormous—hundreds of megabytes for a typical project, containing thousands of sub-folders. Each package may have its own dependencies, which have their own dependencies, creating a deep tree.

Never commit node_modules/ to Git! This folder is always listed in .gitignore. It is generated content—anyone can recreate it by running npm install. Committing it would bloat your repository by hundreds of megabytes and make every Git operation painfully slow.

package-lock.json

The lock file records the exact version of every installed package and all its sub-dependencies. While package.json might say "react": "^18.3.0" (meaning any version 18.x), package-lock.json records that you specifically installed version 18.3.1. This ensures that every developer and every server installs the exact same versions.

Always commit package-lock.json to Git. It is the guarantee of reproducible builds.

npm install vs. npm ci

This distinction is critically important for professional development and deployment.

Featurenpm installnpm ci
When to useDuring development, when adding packagesIn CI/CD pipelines, automated builds, fresh setups
Readspackage.json (primary), updates lock filepackage-lock.json (primary), ignores package.json ranges
node_modules/Merges with existing folderDeletes it first, then does a clean install
Lock fileMay update package-lock.jsonNever modifies package-lock.json
SpeedSlower (resolves versions, diffs existing)Faster (skips resolution, clean install)
ReproducibilityMay produce slightly different resultsGuarantees exact same versions every time

npm ci stands for "clean install." It is the command you should use when you want to be absolutely sure that the installed packages match exactly what is in package-lock.json. This is critical for deployment: you want your production server to install the exact same package versions that you tested with, not slightly newer ones.

# Development: adding and updating packages
$ npm install
$ npm install new-package

# CI/CD and deployment: exact reproduction
$ npm ci
CSK Connection Render's build command for CSK is npm ci && npm run build. The npm ci ensures that every deployment installs the exact same package versions that were tested locally. This eliminates an entire category of bugs where "it works on my machine but not in production."

Dependencies vs. devDependencies

Packages in your project fall into two categories, and it matters which one you choose:

Dependencies (dependencies)

These are packages that your application needs to run in production. Without them, the deployed website would break. Examples:

  • next — The web framework (the application literally will not start without it)
  • react — The UI library
  • @supabase/supabase-js — Database client
  • resend — Email sending
  • zod — Data validation (used at runtime)

devDependencies (devDependencies)

These are packages needed only during development or the build process. They are not included in the final production bundle. Examples:

  • typescript — Compiles TypeScript to JavaScript (only needed during build)
  • @types/react — TypeScript type definitions (only needed during development)
  • eslint — Code quality checker (only needed during development)
  • prettier — Code formatter (only needed during development)
  • tailwindcss — CSS framework (generates CSS at build time)
# Install as a dependency (needed in production)
$ npm install axios

# Install as a devDependency (needed only in development)
$ npm install --save-dev eslint
Analogy: Building a house. Dependencies are the bricks, wood, and pipes—they become part of the house and must be there for people to live in it. devDependencies are the scaffolding, cranes, and power tools—essential during construction, but removed once the house is complete.

npm Scripts

The "scripts" section in package.json is where you define custom commands for your project. Instead of remembering long, complex commands, you give them short, memorable names.

"scripts": {
  "dev": "next dev",
  "build": "next build",
  "start": "next start",
  "lint": "next lint",
  "type-check": "tsc --noEmit",
  "format": "prettier --write src/",
  "clean": "rm -rf .next node_modules",
  "preinstall": "echo 'Installing dependencies...'"
}

Running Scripts

# Run a script defined in package.json
$ npm run dev
$ npm run build
$ npm run lint

# Special scripts: "start" and "test" do not need "run"
$ npm start     # same as npm run start
$ npm test      # same as npm run test

Scripts can be anything: shell commands, tool executions, sequences of operations. They are the standard way to define your project's development workflow. When a new developer joins the team, they look at the scripts section to understand how to work with the project.

The deployment pipeline runs npm ci && npm run build, and the production server starts with npm run start. Every developer uses npm run dev daily.

Semantic Versioning

Every npm package follows semantic versioning (semver), a system that communicates what kind of changes each version contains. Understanding semver is essential because it determines which package updates are safe and which might break your code.

A version number has three parts: MAJOR.MINOR.PATCH

  18.3.1
   |  | |
   |  | └── PATCH: Bug fixes, no new features, nothing breaks
   |  └──── MINOR: New features added, nothing breaks
   └─────── MAJOR: Breaking changes, things might not work the same
Change TypeVersion BumpExampleSafe to Update?
Bug fixPATCH: 1.2.3 → 1.2.4Fixed a crash on loginYes, always
New featureMINOR: 1.2.3 → 1.3.0Added a new componentYes, usually
Breaking changeMAJOR: 1.2.3 → 2.0.0Changed the API completelyNo, read migration guide

Version Ranges in package.json

In package.json, you rarely specify an exact version. Instead, you use symbols that define a range of acceptable versions:

SymbolMeaningExampleMatches
^ (caret)Same major version^18.3.018.3.0, 18.4.2, 18.9.1 (not 19.0.0)
~ (tilde)Same major.minor~18.3.018.3.0, 18.3.5 (not 18.4.0)
(none)Exact version18.3.1Only 18.3.1, nothing else
*Any version*Any version (dangerous!)

The caret (^) is the default and most common. When you run npm install react, npm adds "react": "^18.3.1" to your package.json. This means "install any version that is compatible with 18.3.1"—which in practice means any 18.x version.

Why not always use exact versions? Exact versions give you maximum control but prevent you from automatically receiving bug fixes and security patches. The caret (^) is a good balance: you get patches and minor features, but you are protected from breaking changes. The lock file (package-lock.json) ensures everyone gets the exact same resolved version anyway.

npx: Running Packages Without Installing

npx is a companion tool that comes with npm. It lets you run a package's command without permanently installing it. This is useful for one-off operations and scaffolding tools.

# Create a new Next.js project (without installing create-next-app globally)
$ npx create-next-app@latest my-project

# Run a local project binary
$ npx eslint src/

# Run a specific version of a tool
$ npx prettier@3.3.0 --write .

When you use npx, it first checks if the package is installed locally in node_modules/.bin/. If not, it temporarily downloads the package, runs it, and removes it. This keeps your system clean and ensures you always use the latest version of scaffolding tools.

Putting It All Together: Starting a Project from Scratch

# Step 1: Create the project directory
$ mkdir my-node-project && cd my-node-project

# Step 2: Create .nvmrc to pin Node version
$ echo "22" > .nvmrc
$ nvm use

# Step 3: Initialize the project
$ npm init -y

# Step 4: Add the engines field to package.json
# (Open package.json in your editor and add:)
# "engines": { "node": ">=22.0.0 <23.0.0" }

# Step 5: Install dependencies
$ npm install next react react-dom
$ npm install --save-dev typescript @types/react @types/node

# Step 6: Add scripts to package.json
# "scripts": {
#   "dev": "next dev",
#   "build": "next build",
#   "start": "next start"
# }

# Step 7: Create .gitignore
$ echo "node_modules/" > .gitignore
$ echo ".next/" >> .gitignore
$ echo ".env*" >> .gitignore

# Step 8: Verify everything works
$ npm run dev

# Step 9: Test the CI/CD install
$ rm -rf node_modules
$ npm ci
# If this succeeds, Render will be able to build your project!
CSK Connection The CSK project has over 25 dependencies including Next.js, React, Supabase, Resend, Zod, and more. Its package.json specifies Node 22 in the engines field, and its .nvmrc ensures developers use the correct version. The development workflow is: nvm use to set the correct Node version, npm install to install packages, and npm run dev to start the local server at http://localhost:3000.

Exercises

  1. Create a project: Create a new directory, run npm init -y, and examine the generated package.json. Identify each field and what it means.
  2. Install packages: Install lodash as a dependency and prettier as a devDependency. Open package.json and verify they appear in the correct sections. Look at the node_modules/ folder and count how many sub-folders were created.
  3. npm ci vs install: Delete your node_modules/ folder. Run npm ci. Then delete it again and run npm install. Compare the behavior. Try deleting package-lock.json and running npm ci—what happens?
  4. Write scripts: Add a script called "hello" that runs echo "Hello from npm!". Add another called "info" that runs node -e "console.log(process.version)". Run both with npm run hello and npm run info.
  5. Version ranges: Look at the dependencies in your package.json. For each package, explain what the ^ symbol means. What is the highest version that ^18.3.0 would accept? What about ~18.3.0?
  6. npx practice: Use npx to run cowsay "Hello World" (a fun text tool). Then use npx create-next-app@latest test-app to scaffold a Next.js project. Examine the generated files.
  7. .nvmrc and engines: Create a .nvmrc file with the content 22. Add an "engines" field to your package.json requiring Node 22. Run nvm use and verify the correct version is active with node --version.

Key Takeaways

  • Node.js lets you run JavaScript outside the browser, enabling full-stack development in one language.
  • Use nvm to manage Node.js versions and .nvmrc to pin the version per project.
  • package.json is the project manifest—it defines dependencies, scripts, and metadata.
  • node_modules/ contains installed packages. Never commit it. Recreate it with npm install.
  • package-lock.json locks exact versions. Always commit it. Use npm ci in CI/CD to respect it exactly.
  • dependencies are needed in production; devDependencies are only needed during development/build.
  • npm scripts define your project workflow: dev, build, start, lint, test.
  • Semantic versioning (MAJOR.MINOR.PATCH) communicates what kind of changes a version contains.
  • npx runs packages without permanent installation—ideal for scaffolding and one-off tools.
