Planning Tables from Business Requirements

Designing a database starts with understanding the business. Before writing any SQL, you need to answer these questions:

  1. What entities exist? (Customers, tickets, products, posts...)
  2. What attributes does each entity have? (Name, email, price, status...)
  3. How are entities related? (A customer has many tickets, a post has many tags...)
  4. What rules must the data follow? (Emails must be unique, prices cannot be negative...)

Walkthrough: Designing a Blog System

Let us work through a real example. The business requirements say:

  • The blog has posts with a title, content, excerpt, featured image, author, and status (draft/published/archived)
  • Posts are organized into categories (one category per post)
  • Posts can have multiple tags, and tags can apply to multiple posts
  • Published posts should show the publication date
  • We need to track when everything was created and last updated

Step 1: Identify the entities

  • Blog Posts
  • Categories
  • Tags

Step 2: Identify the relationships

  • Post → Category: many-to-one (each post has one category, each category has many posts)
  • Post ↔ Tag: many-to-many (each post has many tags, each tag has many posts)

Step 3: Design the tables

-- 1. Categories table (the "one" side)
CREATE TABLE blog_categories (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  name VARCHAR(100) NOT NULL UNIQUE,
  slug VARCHAR(100) NOT NULL UNIQUE,
  description TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- 2. Tags table
CREATE TABLE blog_tags (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  name VARCHAR(50) NOT NULL UNIQUE,
  slug VARCHAR(50) NOT NULL UNIQUE,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- 3. Posts table (the "many" side of post-category)
CREATE TABLE blog_posts (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  title VARCHAR(255) NOT NULL,
  slug VARCHAR(255) NOT NULL UNIQUE,
  excerpt TEXT,
  content TEXT NOT NULL,
  featured_image_url TEXT,
  category_id UUID REFERENCES blog_categories(id) ON DELETE SET NULL,
  author_name VARCHAR(100) NOT NULL,
  author_email VARCHAR(255),
  status VARCHAR(20) DEFAULT 'draft'
    CHECK (status IN ('draft', 'published', 'archived')),
  published_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- 4. Junction table for many-to-many (posts ↔ tags)
CREATE TABLE blog_post_tags (
  post_id UUID REFERENCES blog_posts(id) ON DELETE CASCADE,
  tag_id UUID REFERENCES blog_tags(id) ON DELETE CASCADE,
  PRIMARY KEY (post_id, tag_id)
);

Every design decision maps back to a business requirement:

RequirementDesign Decision
Post has one categorycategory_id FK on blog_posts
Post has many tagsJunction table blog_post_tags
Category can be removed without deleting postsON DELETE SET NULL
Deleting a post cleans up its tag linksON DELETE CASCADE
Status limited to specific valuesCHECK constraint
Slugs must be unique for URLsUNIQUE constraint on slug

Normalization in Practice

In Lesson 23, we learned the theory of normalization (1NF, 2NF, 3NF). Here is how it works in real schema design:

When to Split (Normalize)

  • Data is repeated across rows — category names appearing on every post should be in their own table
  • Data can change independently — a category's name might change; you want to update it once, not on every post
  • You need to query the data independently — "show all categories" requires a categories table

When to Keep Together (Denormalize)

  • The data never changes independently — author_name on a blog post is fine because it is a historical record of who wrote it
  • Performance requires it — avoiding a JOIN on a frequently accessed query
  • The data is inherently part of the record — a computer's specs stored as JSONB directly on the gallery row
Analogy: Normalization is like organizing a kitchen. Spices go in the spice rack (their own table), not scattered in every drawer. But the recipe card (blog post) should include the author's name directly — you do not need a separate filing cabinet for recipe authors in a small kitchen.

Junction Tables for Many-to-Many

When two entities have a many-to-many relationship, you need a junction table. Let us look at the complete pattern:

-- The two main entities
CREATE TABLE blog_posts (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  title VARCHAR(255) NOT NULL
);

CREATE TABLE blog_tags (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name VARCHAR(50) NOT NULL UNIQUE,
  slug VARCHAR(50) NOT NULL UNIQUE
);

-- The junction table
CREATE TABLE blog_post_tags (
  post_id UUID REFERENCES blog_posts(id) ON DELETE CASCADE,
  tag_id UUID REFERENCES blog_tags(id) ON DELETE CASCADE,
  PRIMARY KEY (post_id, tag_id)
);

-- Index for reverse lookups (find all posts for a tag)
CREATE INDEX idx_blog_post_tags_tag ON blog_post_tags(tag_id);

Working with Junction Tables

-- Add tags to a post
INSERT INTO blog_post_tags (post_id, tag_id) VALUES
  ('post-uuid', 'tag-uuid-1'),
  ('post-uuid', 'tag-uuid-2'),
  ('post-uuid', 'tag-uuid-3');

-- Remove a tag from a post
DELETE FROM blog_post_tags
WHERE post_id = 'post-uuid' AND tag_id = 'tag-uuid-2';

-- Replace all tags on a post (common pattern)
-- Step 1: Remove all existing tags
DELETE FROM blog_post_tags WHERE post_id = 'post-uuid';
-- Step 2: Add new tags
INSERT INTO blog_post_tags (post_id, tag_id) VALUES
  ('post-uuid', 'new-tag-1'),
  ('post-uuid', 'new-tag-2');

-- Find all tags for a post
SELECT t.name, t.slug
FROM blog_tags t
JOIN blog_post_tags pt ON pt.tag_id = t.id
WHERE pt.post_id = 'post-uuid';

-- Find all posts with a specific tag
SELECT p.title, p.slug
FROM blog_posts p
JOIN blog_post_tags pt ON pt.post_id = p.id
JOIN blog_tags t ON t.id = pt.tag_id
WHERE t.slug = 'linux';
CSK Connection CSK uses this exact "delete all then re-insert" pattern when updating blog post tags. In src/lib/supabase.ts, the updatePost() function first deletes all rows from blog_post_tags for the post, then inserts the new tag associations. This is simpler and more reliable than trying to diff the old and new tag lists.

Timestamp Patterns

Almost every table should track when rows were created and updated. Here are the standard patterns:

created_at

-- Set automatically when the row is inserted, never changed
created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()

TIMESTAMP WITH TIME ZONE (often shortened to TIMESTAMPTZ) stores the date, time, and timezone. DEFAULT NOW() means PostgreSQL automatically fills in the current time when a row is inserted.

updated_at

-- Also defaults to NOW() on insert, but should be updated on every change
updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()

The updated_at column needs a trigger to automatically update when the row changes (we will cover triggers in detail in Lesson 28):

-- Function that sets updated_at to now
CREATE OR REPLACE FUNCTION update_updated_at_column()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = NOW();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- Attach it to a table
CREATE TRIGGER update_blog_posts_updated_at
  BEFORE UPDATE ON blog_posts
  FOR EACH ROW
  EXECUTE FUNCTION update_updated_at_column();

Soft Delete Patterns

As we discussed in Lesson 24, soft deletes mark data as removed without actually deleting it. There are two common patterns:

Pattern 1: Boolean Flag

-- Table definition
CREATE TABLE gallery_computers (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT NOT NULL,
  price NUMERIC NOT NULL,
  is_active BOOLEAN DEFAULT true,
  archived_at TIMESTAMPTZ,  -- When it was "deleted"
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- "Delete" (soft)
UPDATE gallery_computers
SET is_active = false, archived_at = NOW()
WHERE id = 'some-uuid';

-- "Restore"
UPDATE gallery_computers
SET is_active = true, archived_at = NULL
WHERE id = 'some-uuid';

-- Query only active items (most common)
SELECT * FROM gallery_computers WHERE is_active = true;

-- Query archived items (admin feature)
SELECT * FROM gallery_computers WHERE is_active = false;

Pattern 2: Timestamp Only

-- Table definition (no boolean, just timestamp)
CREATE TABLE products (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT NOT NULL,
  archived_at TIMESTAMPTZ  -- NULL means active
);

-- "Delete"
UPDATE products SET archived_at = NOW() WHERE id = 'some-uuid';

-- "Restore"
UPDATE products SET archived_at = NULL WHERE id = 'some-uuid';

-- Query active items
SELECT * FROM products WHERE archived_at IS NULL;

CSK uses Pattern 1 (boolean + timestamp) for the gallery, which makes queries simpler and more readable.

UUID Generation

PostgreSQL offers two functions for generating UUIDs:

-- From the uuid-ossp extension (older, requires enabling)
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
id UUID PRIMARY KEY DEFAULT uuid_generate_v4()

-- Built-in (PostgreSQL 13+, recommended)
id UUID PRIMARY KEY DEFAULT gen_random_uuid()

Both generate random (v4) UUIDs. gen_random_uuid() is preferred in modern PostgreSQL because it does not require an extension.

What Are Migrations?

A database migration is a versioned SQL script that changes the database schema. Migrations are the database equivalent of git commits — they provide a chronological record of every change to your schema.

Analogy: Imagine renovating a house. Each renovation project (adding a room, installing plumbing, painting walls) is documented with blueprints, dated and numbered. If something goes wrong, you can look at the blueprints to understand what changed and when. Migrations are your database's renovation blueprints.

Why Migrations Matter

Problem Without MigrationsSolution With Migrations
"What tables exist on production?"Run all migrations in order to recreate the schema
"Who changed the customers table?"Check the migration file's git history
"New developer cannot set up their database"Run all migrations to get up to date
"Production and development schemas are different"Same migrations run on all environments
"I broke something, need to undo it"Write a "down" migration to reverse changes

Writing Migration Files

Initial Schema Migration

The first migration creates all tables from scratch:

-- migrations/001-initial-schema.sql
-- Description: Create initial blog tables
-- Date: 2026-01-01

-- Enable extensions
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";

-- Categories
CREATE TABLE IF NOT EXISTS blog_categories (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  name VARCHAR(100) NOT NULL UNIQUE,
  slug VARCHAR(100) NOT NULL UNIQUE,
  description TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- Tags
CREATE TABLE IF NOT EXISTS blog_tags (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  name VARCHAR(50) NOT NULL UNIQUE,
  slug VARCHAR(50) NOT NULL UNIQUE,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- Posts
CREATE TABLE IF NOT EXISTS blog_posts (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  title VARCHAR(255) NOT NULL,
  slug VARCHAR(255) NOT NULL UNIQUE,
  content TEXT NOT NULL,
  category_id UUID REFERENCES blog_categories(id) ON DELETE SET NULL,
  status VARCHAR(20) DEFAULT 'draft'
    CHECK (status IN ('draft', 'published', 'archived')),
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- Junction table
CREATE TABLE IF NOT EXISTS blog_post_tags (
  post_id UUID REFERENCES blog_posts(id) ON DELETE CASCADE,
  tag_id UUID REFERENCES blog_tags(id) ON DELETE CASCADE,
  PRIMARY KEY (post_id, tag_id)
);

-- Indexes
CREATE INDEX IF NOT EXISTS idx_blog_posts_slug ON blog_posts(slug);
CREATE INDEX IF NOT EXISTS idx_blog_posts_status ON blog_posts(status);

Note the use of IF NOT EXISTS throughout — this makes the migration safe to run multiple times (idempotent).

Additive Migration

Most subsequent migrations add things to existing tables:

-- migrations/002-add-blog-features.sql
-- Description: Add excerpt, featured image, and author fields to blog posts
-- Date: 2026-01-15

ALTER TABLE blog_posts
  ADD COLUMN IF NOT EXISTS excerpt TEXT,
  ADD COLUMN IF NOT EXISTS featured_image_url TEXT,
  ADD COLUMN IF NOT EXISTS author_name VARCHAR(100),
  ADD COLUMN IF NOT EXISTS author_email VARCHAR(255),
  ADD COLUMN IF NOT EXISTS published_at TIMESTAMPTZ;

-- Backfill: set author_name for existing posts
UPDATE blog_posts SET author_name = 'Admin' WHERE author_name IS NULL;

-- Now make it required
ALTER TABLE blog_posts ALTER COLUMN author_name SET NOT NULL;

Notice the pattern: add the column as nullable first, backfill existing data, then add the NOT NULL constraint. This is the safe way to add required columns to tables that already have data.

Structural Migration

Sometimes you need to add entirely new tables or restructure relationships:

-- migrations/003-add-businesses.sql
-- Description: Create businesses table and link to customers
-- Date: 2026-01-20

-- 1. Create the new table
CREATE TABLE IF NOT EXISTS businesses (
  id SERIAL PRIMARY KEY,
  name TEXT NOT NULL UNIQUE,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- 2. Add the foreign key column to existing table
ALTER TABLE rs_customers
  ADD COLUMN IF NOT EXISTS business_id INTEGER REFERENCES businesses(id);

-- 3. Create index for the new column
CREATE INDEX IF NOT EXISTS idx_rs_customers_business_id
  ON rs_customers(business_id);

-- 4. Populate from existing data
INSERT INTO businesses (name)
SELECT DISTINCT business_name
FROM rs_customers
WHERE business_name IS NOT NULL AND business_name != ''
ON CONFLICT (name) DO NOTHING;

-- 5. Link existing rows
UPDATE rs_customers c
SET business_id = b.id
FROM businesses b
WHERE c.business_name = b.name;

Supabase Migration Workflow

Supabase provides CLI tools for managing migrations:

Option 1: Manual SQL (What CSK Uses)

Write SQL migration files and run them in the Supabase SQL Editor. This is the simplest approach and works well for small teams.

  1. Write the migration SQL in a file (e.g., docs/database/migrations/2026-02-01-add-feature.sql)
  2. Test it locally or in a development Supabase project first
  3. Open the Supabase Dashboard → SQL Editor
  4. Paste and run the migration
  5. Commit the migration file to git

Option 2: Supabase CLI

For teams that want more automation:

# Generate a migration from schema changes you made in the dashboard
npx supabase db diff --file my_migration_name

# This creates: supabase/migrations/20260201120000_my_migration_name.sql

# Push migrations to your remote database
npx supabase db push

# Reset local database and replay all migrations
npx supabase db reset

Migration Naming Conventions

ConventionExampleBenefit
Date prefix2026-01-27-fix-rls-policies.sqlNatural chronological order

The most important thing is consistency — pick a convention and stick with it.

Rolling Back Migrations

Sometimes a migration needs to be undone. The safest approach is to write a new "down" migration that reverses the changes:

-- UP migration: 004-add-phone-column.sql
ALTER TABLE customers ADD COLUMN phone TEXT;

-- DOWN migration: 004-remove-phone-column.sql (run if you need to undo)
ALTER TABLE customers DROP COLUMN IF EXISTS phone;
Not All Migrations Are Reversible! Adding a column is easy to reverse (drop it). But dropping a column, deleting data, or changing a column's type may lose data permanently. Always think about reversibility before writing a migration, and always back up production data before running destructive migrations.

Safe Rollback Patterns

ChangeRollbackData Loss?
Add columnDrop columnYes (column data lost)
Add tableDrop tableYes (all table data lost)
Add indexDrop indexNo
Add constraintDrop constraintNo
Rename columnRename backNo
Drop columnCannot fully reverseAlready lost!

Migration Best Practices

  • One concern per migration — do not mix unrelated changes in a single file
  • Use IF NOT EXISTS / IF EXISTS — make migrations idempotent (safe to re-run)
  • Test on development first — never run untested migrations on production
  • Commit migrations to git — they are as important as application code
  • Never edit a migration that has been run on production — write a new one instead
  • Add comments to your SQL — explain why, not just what
  • Backfill data before adding NOT NULL — add column nullable, fill in values, then add constraint
  • Keep migrations small — easier to understand, test, and roll back

Hands-On Exercises

  1. Design from Requirements: A local library needs a database. Requirements: Books have a title, author, ISBN (unique), and publication year. Members have a name, email (unique), and join date. Members can borrow many books, and each book can be borrowed by many members over time (track borrow_date and return_date). Design the tables with proper data types, constraints, and relationships.
  2. Junction Table Practice: Given a students table and a courses table, write the CREATE TABLE for a junction table called enrollments that also tracks when the student enrolled (enrolled_at) and their grade (grade, nullable).
  3. Write a Migration: Your existing blog_posts table needs a new reading_time_minutes column (integer, nullable) and a featured boolean (default false). Write a migration file that adds these columns safely.
  4. Soft Delete Migration: Your products table currently uses hard deletes. Write a migration that adds is_active (boolean, default true) and archived_at (timestamptz, nullable) columns. Include an UPDATE to set all existing rows to active.
  5. Rollback Practice: Write both an "up" and "down" migration for adding a phone column to a customers table and creating an index on it.
  6. Schema Review: Look at the blog schema SQL shown in this lesson. Identify: (a) all foreign keys and their ON DELETE behavior, (b) all constraints, (c) which columns are optional vs required, and (d) where normalization was applied and where it was intentionally skipped.

Key Takeaways

  • Start schema design by identifying entities, attributes, relationships, and rules from business requirements.
  • Use junction tables for many-to-many relationships with a composite primary key.
  • Every table should have created_at (auto-set, never changed) and updated_at (auto-updated via trigger).
  • Use soft deletes (is_active boolean or archived_at timestamp) instead of hard deletes in production.
  • Migrations are versioned SQL scripts that track every change to your database schema.
  • Migrations ensure reproducibility (anyone can recreate the schema) and coordination (team members stay in sync).
  • Use IF NOT EXISTS to make migrations idempotent (safe to re-run).
  • Never edit a migration that has been run on production — write a new one.
  • Real schemas evolve through many small migrations — this is normal and expected.
