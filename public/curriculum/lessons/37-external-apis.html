What Are External APIs?

Throughout this curriculum, you have been building your own API routes — endpoints that your frontend calls to fetch data from your database, authenticate users, or process form submissions. An external API (also called a third-party API) is an API that someone else built and maintains, and your application calls it over the internet to use their service.

Think about it this way: your application does not need to know how to deliver email, process credit card payments, look up weather data, or manage a customer's repair tickets. Other companies have already built those capabilities and exposed them through APIs. By calling their API, you can add those features to your application without building them from scratch.

Analogy: Hiring Specialists
Imagine you are building a house. You could try to do everything yourself — plumbing, electrical, roofing, painting. But it is far more practical to hire specialists for each task. External APIs work the same way. Instead of building an email delivery system (which requires understanding SMTP servers, spam filters, and deliverability), you "hire" Resend to handle it. Instead of building a payment system (which requires PCI compliance and bank integrations), you hire Stripe. Each specialist does their job, and your application coordinates them all.

Why Use External APIs?

  • Faster development — Adding email delivery takes minutes with Resend, but months if you build it yourself.
  • Expert quality — The company behind the API has a team of engineers dedicated to making it reliable, secure, and fast.
  • Compliance handled — Payment processors handle PCI compliance. Email services handle CAN-SPAM. You do not have to worry about it.
  • Scale without effort — These services handle millions of requests per day across all their customers. Your application benefits from that infrastructure.
  • Focus on your product — Your time is better spent building features unique to your business, not reinventing the wheel.
CSK Connection Computer Store KS integrates with 6+ external APIs: RepairShopr (ticket and customer management), Resend (email delivery), Supabase (database and storage), Google Business Profile (reviews and business info), NinjaOne (remote device monitoring), and GitHub (image storage via the Octokit library). Each integration adds critical capabilities that would take months or years to build from scratch.

API Authentication Methods

Before any API will respond to your requests, you need to prove who you are. This is called authentication. Different APIs use different methods depending on their security requirements. Here are the four most common approaches:

1. API Key Authentication

The simplest method. The API provider gives you a unique string (your "API key") that you include in every request. It is like a password for your application.

// API Key in a header (most common)
const response = await fetch('https://api.example.com/data', {
  headers: {
    'X-Api-Key': 'your_api_key_here',
    'Content-Type': 'application/json',
  },
});

// API Key as a query parameter (less secure, visible in URLs)
const response = await fetch(
  'https://api.example.com/data?api_key=your_api_key_here'
);
CSK Connection RepairShopr uses API key authentication. In CSK's repairshopr.ts client, the API key is passed as a query parameter: /customers?api_key=${encodeURIComponent(apiToken)}. The key is stored in the REPAIRSHOPR_API_KEY environment variable and is never exposed to the browser.

2. Bearer Token Authentication

Similar to API keys, but follows a standardized format. You include the token in the Authorization header with the prefix Bearer.

// Bearer token in the Authorization header
const response = await fetch('https://api.resend.com/emails', {
  method: 'POST',
  headers: {
    'Authorization': 'Bearer re_123abc456def',
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({
    from: 'noreply@example.com',
    to: 'customer@example.com',
    subject: 'Hello',
    html: '<p>Welcome!</p>',
  }),
});

3. Basic Authentication

Combines a username and password into a single Base64-encoded string. Less common in modern APIs but still found in older systems.

// Basic authentication
const credentials = btoa('username:password'); // Base64 encode

const response = await fetch('https://api.example.com/data', {
  headers: {
    'Authorization': `Basic ${credentials}`,
    'Content-Type': 'application/json',
  },
});

4. OAuth 2.0

The most complex but most flexible method. Used when an application needs to access data on behalf of a user (for example, reading someone's Google reviews) or when machine-to-machine authentication is needed. We will explore OAuth 2.0 in detail later in this lesson.

Authentication Methods Comparison

Method Complexity Security Level Best For Example APIs
API Key (header) Simple Medium Server-to-server calls RepairShopr, many SaaS tools
API Key (query param) Simple Low Quick testing, legacy APIs Some older APIs
Bearer Token Simple Medium-High Modern REST APIs Resend, Supabase, Stripe

Never Put API Keys in Client-Side Code API keys must always live on the server, stored in environment variables. If you put an API key in your React component or JavaScript bundle, anyone can open their browser's developer tools and steal it. That is why all external API calls in CSK happen in API routes (server-side code), never in React components.

Making HTTP Requests from Server Code

When your server needs to call an external API, you use the fetch() function — the same function available in the browser, but now running on your server in a Next.js API route or Server Component.

Basic GET Request

// Fetch a list of customers from an external API
async function getCustomers(query: string) {
  const API_KEY = process.env.EXTERNAL_API_KEY;

  const response = await fetch(
    `https://api.example.com/v1/customers?query=${encodeURIComponent(query)}`,
    {
      method: 'GET',
      headers: {
        'Authorization': `Bearer ${API_KEY}`,
        'Accept': 'application/json',
      },
    }
  );

  // Always check if the response was successful
  if (!response.ok) {
    throw new Error(`API error: ${response.status} ${response.statusText}`);
  }

  // Parse the JSON body
  const data = await response.json();
  return data.customers;
}

Basic POST Request

// Create a new ticket in an external system
async function createTicket(customerName: string, issue: string) {
  const API_KEY = process.env.EXTERNAL_API_KEY;

  const response = await fetch('https://api.example.com/v1/tickets', {
    method: 'POST',
    headers: {
      'Authorization': `Bearer ${API_KEY}`,
      'Content-Type': 'application/json',  // Tell the API we are sending JSON
      'Accept': 'application/json',         // Tell the API we want JSON back
    },
    body: JSON.stringify({
      customer_name: customerName,
      subject: issue,
      status: 'New',
    }),
  });

  if (!response.ok) {
    const errorBody = await response.text();
    throw new Error(`Failed to create ticket: ${response.status} - ${errorBody}`);
  }

  const data = await response.json();
  return data.ticket;
}

Parsing Responses and Handling Errors

External APIs can fail in many ways: the server might be down, your API key might be expired, you might exceed the rate limit, or your request might have invalid data. Robust error handling is critical.

Checking HTTP Status Codes

The response.ok property is true for status codes in the 200-299 range and false for everything else. But different non-2xx codes mean different things:

async function makeAPIRequest(url: string, options: RequestInit) {
  const response = await fetch(url, options);

  // Handle specific error codes
  if (!response.ok) {
    switch (response.status) {
      case 400:
        throw new Error('Bad Request: Check your request parameters');
      case 401:
        throw new Error('Unauthorized: Your API key is invalid or expired');
      case 403:
        throw new Error('Forbidden: You do not have permission for this action');
      case 404:
        throw new Error('Not Found: The requested resource does not exist');
      case 422:
        // Validation errors usually include details in the body
        const validationErrors = await response.json();
        throw new Error(`Validation failed: ${JSON.stringify(validationErrors)}`);
      case 429:
        throw new Error('Rate limited: Too many requests, try again later');
      case 500:
      case 502:
      case 503:
        throw new Error('Server error: The external service is having problems');
      default:
        throw new Error(`API error: ${response.status} ${response.statusText}`);
    }
  }

  return response.json();
}

Parsing JSON Responses Safely

Not every response contains valid JSON. The server might return HTML error pages or empty responses. Always parse defensively:

async function safeParseJSON(response: Response) {
  // First, get the raw text
  const text = await response.text();

  // If empty, return a default
  if (!text) {
    return {};
  }

  // Try to parse as JSON
  try {
    return JSON.parse(text);
  } catch {
    console.error('Response was not valid JSON:', text.substring(0, 200));
    throw new Error('Invalid JSON response from API');
  }
}
CSK Connection In CSK's repairshopr.ts, the private request() method handles all of this. It checks response.ok, attempts to parse error bodies as JSON to extract detailed error messages, maps status codes to specific error codes (like RATE_LIMIT_EXCEEDED or UNAUTHORIZED), and wraps everything in a custom RepairShoprAPIError class with status and code properties.

Building Reusable API Client Modules

When your application integrates with an external API, you do not want to scatter fetch() calls throughout your codebase. Instead, you build a dedicated API client module that encapsulates all the API interaction logic in one place. This follows the same principle as creating a supabase.ts module for your database — centralization, reusability, and maintainability.

The Factory Pattern

The factory pattern creates pre-configured instances of your API client. Instead of passing configuration everywhere, you configure once and use everywhere:

// lib/weather-api.ts

// The client class encapsulates all API logic
class WeatherAPIClient {
  private readonly baseUrl: string;
  private readonly apiKey: string;

  constructor(apiKey: string) {
    this.baseUrl = 'https://api.weather.com/v1';
    this.apiKey = apiKey;
  }

  // Private method handles all HTTP requests
  private async request<T>(endpoint: string): Promise<T> {
    const response = await fetch(`${this.baseUrl}${endpoint}`, {
      headers: {
        'Authorization': `Bearer ${this.apiKey}`,
        'Accept': 'application/json',
      },
    });

    if (!response.ok) {
      throw new Error(`Weather API error: ${response.status}`);
    }

    return response.json() as Promise<T>;
  }

  // Public methods provide a clean interface
  async getCurrentWeather(city: string) {
    return this.request<{ temp: number; description: string }>(
      `/current?city=${encodeURIComponent(city)}`
    );
  }

  async getForecast(city: string, days: number = 5) {
    return this.request<{ daily: Array<{ date: string; high: number; low: number }> }>(
      `/forecast?city=${encodeURIComponent(city)}&days=${days}`
    );
  }
}

// Factory function: reads config from environment, returns ready-to-use client
export function createWeatherClient(): WeatherAPIClient {
  const apiKey = process.env.WEATHER_API_KEY;

  if (!apiKey) {
    throw new Error(
      'WEATHER_API_KEY environment variable is required. ' +
      'Please set it in your .env file.'
    );
  }

  return new WeatherAPIClient(apiKey);
}

// Usage in an API route:
// const client = createWeatherClient();
// const weather = await client.getCurrentWeather('Topeka');

Why This Pattern Works

  • Single responsibility — The client handles all HTTP details. Your API routes just call clean methods.
  • Type safety — Each method has a typed return value. Your IDE provides autocompletion.
  • Error handling in one place — The private request() method handles errors for every endpoint.
  • Easy to test — You can create the client with a test URL or mock the class entirely.
  • Environment isolation — The factory function reads environment variables once. The rest of your code never touches process.env.
CSK Connection CSK uses this exact pattern for every integration. repairshopr.ts exports a RepairShoprClient class with methods like searchCustomers(), getTicket(), and createTicket(), plus a createRepairShoprClient() factory function that reads REPAIRSHOPR_SUBDOMAIN from the environment. Similarly, ninjaone.ts exports a NinjaOneClient class with a createNinjaOneClient() factory that reads three environment variables.

Critical Security Rules
  • Add .env.local to your .gitignore file so it is never committed.
  • Create a .env.example file with placeholder values so team members know which variables are needed.

  • If a key is accidentally committed, revoke it immediately and generate a new one. The old key is compromised forever.

Rate Limiting Awareness

Every external API limits how many requests you can make in a given time period. This is called rate limiting, and it protects the API provider's servers from being overwhelmed. If you exceed the limit, the API responds with a 429 Too Many Requests status code.

Reading Rate Limit Headers

Most APIs include rate limit information in their response headers:

// After making a request, check the rate limit headers
const response = await fetch('https://api.example.com/data', {
  headers: { 'Authorization': `Bearer ${apiKey}` },
});

// Common rate limit headers
const remaining = response.headers.get('X-RateLimit-Remaining');  // "47"
const limit = response.headers.get('X-RateLimit-Limit');          // "100"
const resetTime = response.headers.get('X-RateLimit-Reset');      // "1706800000"
const retryAfter = response.headers.get('Retry-After');           // "60"

console.log(`Rate limit: ${remaining}/${limit} remaining`);
console.log(`Resets at: ${new Date(Number(resetTime) * 1000)}`);

Client-Side Rate Tracking

You can proactively track your own request rate to avoid hitting the limit:

// Track requests to avoid hitting limits
const RATE_LIMIT_MAX = 180;            // 180 requests per minute
const RATE_LIMIT_WINDOW_MS = 60_000;   // 1 minute in milliseconds

let requestCount = 0;
let windowStart = Date.now();

function checkRateLimit(): boolean {
  const now = Date.now();

  // Reset window if expired
  if (now - windowStart >= RATE_LIMIT_WINDOW_MS) {
    requestCount = 0;
    windowStart = now;
  }

  // Check if we are at the limit
  if (requestCount >= RATE_LIMIT_MAX) {
    return false; // Cannot make request
  }

  requestCount++;
  return true; // Safe to proceed
}
CSK Connection CSK's RepairShopr client tracks rate limits internally. The RepairShoprClient class has a rateLimitState property that counts requests within a 60-second window. If the count reaches 180, it throws a RepairShoprAPIError with status 429 and tells you how many seconds to wait.

Retry Logic with Exponential Backoff

When an API call fails due to a temporary issue (rate limiting, network glitch, server overload), you should not just give up. Instead, implement retry logic — try again after a short delay. Exponential backoff means each retry waits longer than the last, which prevents hammering the already-struggling server.

Attempt 1: Request fails (429 Rate Limited) Wait 1 second Attempt 2: Request fails again (429) Wait 2 seconds (doubled) Attempt 3: Request fails again (429) Wait 4 seconds (doubled again) Attempt 4: Request succeeds! Return data. Formula: delay = baseDelay * 2^(attempt - 1) Attempt 1: 1000ms * 2^0 = 1 second Attempt 2: 1000ms * 2^1 = 2 seconds Attempt 3: 1000ms * 2^2 = 4 seconds Attempt 4: 1000ms * 2^3 = 8 seconds

Here is a practical implementation:

const MAX_RETRIES = 3;
const BASE_DELAY_MS = 1000;

async function fetchWithRetry<T>(
  url: string,
  options: RequestInit,
  attempt: number = 1
): Promise<T> {
  const response = await fetch(url, options);

  // If rate limited and we have retries left
  if (response.status === 429 && attempt < MAX_RETRIES) {
    // Check if the API tells us how long to wait
    const retryAfter = parseInt(
      response.headers.get('Retry-After') || '60',
      10
    );

    // Calculate delay with exponential backoff
    const delay = Math.min(
      retryAfter * 1000,
      BASE_DELAY_MS * Math.pow(2, attempt - 1)
    );

    console.log(
      `Rate limited. Retrying in ${delay}ms (attempt ${attempt}/${MAX_RETRIES})`
    );

    // Wait, then retry
    await new Promise(resolve => setTimeout(resolve, delay));
    return fetchWithRetry<T>(url, options, attempt + 1);
  }

  // If server error (5xx) and we have retries left
  if (response.status >= 500 && attempt < MAX_RETRIES) {
    const delay = BASE_DELAY_MS * Math.pow(2, attempt - 1);
    await new Promise(resolve => setTimeout(resolve, delay));
    return fetchWithRetry<T>(url, options, attempt + 1);
  }

  if (!response.ok) {
    throw new Error(`API error after ${attempt} attempts: ${response.status}`);
  }

  return response.json() as Promise<T>;
}
When NOT to Retry Only retry on temporary failures: 429 (rate limited), 500-504 (server errors), and network timeouts. Never retry on 400 (bad request), 401 (unauthorized), 403 (forbidden), or 404 (not found) — these errors will not fix themselves by trying again.
CSK Connection CSK's ninjaone.ts client implements retry with exponential backoff directly in its request() method. When it receives a 429 response, it reads the Retry-After header, calculates a delay using BASE_RETRY_DELAY_MS * Math.pow(2, attempt - 1), waits, and then recursively retries up to MAX_RETRY_ATTEMPTS (3) times. If all retries fail, it throws a NinjaOneAPIError.

OAuth 2.0 Explained

OAuth 2.0 is an authorization framework that allows applications to access resources on behalf of a user (or on their own behalf) without sharing passwords. It is the standard used by Google, GitHub, Facebook, and thousands of other services.

Analogy: The Hotel Key Card
Imagine checking into a hotel. You do not get a copy of the hotel's master key. Instead, you get a key card that only opens your room, only works during your stay, and can be deactivated at any time. OAuth 2.0 works the same way — instead of sharing your Google password with an app, Google gives the app a limited-access token (the key card) that can only do specific things (read reviews, but not delete your account) and expires after a set period.

OAuth 2.0 Flows

OAuth 2.0 defines several "flows" (also called "grant types") for different situations:

Flow 1: Client Credentials (Machine-to-Machine)

Used when your server needs to access an API on its own behalf, with no user involved. Your server proves its identity with a client ID and client secret, and receives an access token.

YOUR SERVER API PROVIDER ============ ============ 1. POST /oauth/token client_id=abc123 client_secret=secret789 grant_type=client_credentials -------> 2. <------- { "access_token": "eyJhbG...", "expires_in": 3600, "token_type": "Bearer" } 3. GET /api/devices Authorization: Bearer eyJhbG... ------> 4. <------- { "devices": [...] } 
// Client Credentials flow (machine-to-machine)
async function getAccessToken(): Promise<string> {
  const response = await fetch('https://api.example.com/oauth/token', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/x-www-form-urlencoded',
    },
    body: new URLSearchParams({
      grant_type: 'client_credentials',
      client_id: process.env.CLIENT_ID!,
      client_secret: process.env.CLIENT_SECRET!,
      scope: 'monitoring management',
    }),
  });

  if (!response.ok) {
    throw new Error('Failed to authenticate');
  }

  const data = await response.json();
  return data.access_token; // Use this token for subsequent requests
}
CSK Connection NinjaOne uses the Client Credentials flow. CSK's ninjaone.ts client calls POST /ws/oauth/token with the client ID and secret from environment variables, receives a time-limited access token, caches it (with a 5-minute expiry buffer), and automatically refreshes when it expires.

Flow 2: Authorization Code (User-Authorized Access)

Used when your application needs to access a user's data (for example, their Google Business reviews). The user is redirected to Google, logs in, approves your app, and Google sends you a one-time authorization code that you exchange for tokens.

USER'S BROWSER YOUR SERVER GOOGLE ============== =========== ====== 1. User clicks "Connect Google" ---> 2. Redirect to Google ------> 3. User logs in and approves 4. Redirect back with <------ ?code=abc123 5. Exchange code for tokens POST /token code=abc123 -------> <------- 6. { access_token: "...", refresh_token: "...", expires_in: 3600 } 7. Store refresh_token in env / database 8. Use access_token for API calls

Understanding Refresh Tokens

Access tokens expire (typically in 1 hour). A refresh token is a long-lived credential that you use to get new access tokens without requiring the user to log in again.

// Using a refresh token to get a new access token
async function refreshAccessToken(): Promise<string> {
  const response = await fetch('https://oauth2.googleapis.com/token', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/x-www-form-urlencoded',
    },
    body: new URLSearchParams({
      client_id: process.env.GOOGLE_CLIENT_ID!,
      client_secret: process.env.GOOGLE_CLIENT_SECRET!,
      refresh_token: process.env.GOOGLE_REFRESH_TOKEN!,
      grant_type: 'refresh_token',
    }),
  });

  if (!response.ok) {
    throw new Error('Failed to refresh access token');
  }

  const data = await response.json();
  return data.access_token;
}
CSK Connection Google Business Profile uses OAuth 2.0 with refresh tokens. CSK's google-business.ts stores the GOOGLE_BUSINESS_REFRESH_TOKEN in an environment variable (obtained during a one-time setup process). Every time CSK needs to fetch reviews or business info, it calls getAccessToken(), which sends the refresh token to https://oauth2.googleapis.com/token and receives a fresh access token. The access token is then used with Authorization: Bearer headers.

Building a Complete API Client Wrapper

Let us put everything together and build a production-quality API client that combines all the patterns from this lesson: TypeScript class structure, factory function, authentication, error handling, rate limiting, and retry logic.

// lib/inventory-api.ts - A complete API client example

// Custom error class for typed error handling
export class InventoryAPIError extends Error {
  public readonly status: number;
  public readonly code: string;

  constructor(message: string, status: number, code: string = 'API_ERROR') {
    super(message);
    this.name = 'InventoryAPIError';
    this.status = status;
    this.code = code;
  }
}

// TypeScript interfaces for API responses
interface Product {
  id: number;
  name: string;
  price: number;
  quantity: number;
}

// The API client class
export class InventoryAPIClient {
  private readonly baseUrl: string;
  private readonly apiKey: string;
  private requestCount = 0;
  private windowStart = Date.now();

  constructor(baseUrl: string, apiKey: string) {
    this.baseUrl = baseUrl;
    this.apiKey = apiKey;
  }

  // Rate limit check
  private checkRateLimit(): boolean {
    const now = Date.now();
    if (now - this.windowStart >= 60_000) {
      this.requestCount = 0;
      this.windowStart = now;
    }
    if (this.requestCount >= 100) return false;
    this.requestCount++;
    return true;
  }

  // Core request method with retry logic
  private async request<T>(
    endpoint: string,
    options: RequestInit = {},
    attempt: number = 1
  ): Promise<T> {
    // Check our own rate limit tracking
    if (!this.checkRateLimit()) {
      throw new InventoryAPIError('Rate limit exceeded', 429, 'RATE_LIMITED');
    }

    const url = `${this.baseUrl}${endpoint}`;

    try {
      const response = await fetch(url, {
        ...options,
        headers: {
          'Authorization': `Bearer ${this.apiKey}`,
          'Content-Type': 'application/json',
          'Accept': 'application/json',
          ...options.headers,
        },
      });

      // Retry on rate limit or server error
      if ((response.status === 429 || response.status >= 500) && attempt < 3) {
        const delay = 1000 * Math.pow(2, attempt - 1);
        await new Promise(r => setTimeout(r, delay));
        return this.request<T>(endpoint, options, attempt + 1);
      }

      if (!response.ok) {
        let errorMessage = `HTTP ${response.status}`;
        try {
          const body = await response.json();
          errorMessage = body.error || body.message || errorMessage;
        } catch { /* use default message */ }
        throw new InventoryAPIError(errorMessage, response.status);
      }

      return response.json() as Promise<T>;
    } catch (error) {
      if (error instanceof InventoryAPIError) throw error;
      throw new InventoryAPIError(
        error instanceof Error ? error.message : 'Unknown error',
        0,
        'NETWORK_ERROR'
      );
    }
  }

  // Public API methods
  async getProducts(): Promise<Product[]> {
    const data = await this.request<{ products: Product[] }>('/products');
    return data.products;
  }

  async getProduct(id: number): Promise<Product> {
    const data = await this.request<{ product: Product }>(`/products/${id}`);
    return data.product;
  }

  async updateStock(id: number, quantity: number): Promise<Product> {
    const data = await this.request<{ product: Product }>(`/products/${id}`, {
      method: 'PATCH',
      body: JSON.stringify({ quantity }),
    });
    return data.product;
  }
}

// Factory function
export function createInventoryClient(): InventoryAPIClient {
  const apiKey = process.env.INVENTORY_API_KEY;
  const baseUrl = process.env.INVENTORY_API_URL || 'https://api.inventory.com/v1';

  if (!apiKey) {
    throw new Error('INVENTORY_API_KEY environment variable is required');
  }

  return new InventoryAPIClient(baseUrl, apiKey);
}

Now using this client is clean and simple:

// In an API route: src/app/api/inventory/route.ts
import { createInventoryClient } from '@/lib/inventory-api';

export async function GET() {
  const client = createInventoryClient();

  try {
    const products = await client.getProducts();
    return Response.json({ products });
  } catch (error) {
    if (error instanceof InventoryAPIError) {
      return Response.json(
        { error: error.message },
        { status: error.status || 500 }
      );
    }
    return Response.json({ error: 'Internal error' }, { status: 500 });
  }
}

Key Takeaways

  • External APIs let you use other companies' backends to add features (email, payments, data) without building them yourself.
  • API documentation tells you the base URL, authentication method, available endpoints, request/response formats, and rate limits.
  • The four main authentication methods are API keys (simplest), Bearer tokens (standardized), Basic auth (legacy), and OAuth 2.0 (most flexible).
  • Always store API credentials in environment variables, never in your source code or client-side JavaScript.
  • Build reusable API client modules using the factory pattern: a TypeScript class for the client, a factory function for configuration.
  • Handle errors by checking response status codes and mapping them to meaningful error messages using custom error classes.
  • Implement retry logic with exponential backoff for temporary failures (429, 5xx), but never retry client errors (400, 401, 404).
  • OAuth 2.0 Client Credentials flow is for machine-to-machine auth; Authorization Code flow is for user-authorized access with refresh tokens.
