Understanding how the web knows who you are and what you can do

Authentication vs. Authorization

These two words sound similar but mean very different things. Every secure web application needs both, and confusing them is a common source of security bugs.

Authentication: "Who Are You?"

Authentication (often shortened to "authn") is the process of verifying someone's identity. When you type your email and password into a login form, you are authenticating -- proving that you are who you claim to be.

Common authentication methods include:

  • Email and password -- the most traditional approach
  • Magic links -- a one-time link sent to your email
  • OAuth -- "Sign in with Google" or "Sign in with GitHub"
  • Biometrics -- fingerprint or face recognition on your device
  • API keys -- a secret string that identifies an application

Authorization: "What Can You Do?"

Authorization (often shortened to "authz") is the process of determining what an authenticated user is allowed to access. You already proved who you are; now the system checks your permissions.

For example, a technician at a computer repair shop can view and update repair tickets, but they cannot delete customer records or change employee pay rates. An owner can do all of those things. Both users are authenticated, but they have different authorization levels.

Analogy: Think of a hotel. Authentication is showing your ID at the front desk to prove you are the person who booked the room. Authorization is the key card they give you -- it opens your room (Room 301) but not someone else's room (Room 405), and it does not open the staff-only office behind the desk.
Aspect Authentication Authorization
Question "Who are you?" "What can you do?"
Happens First (before authorization) Second (after authentication)
Determined by Credentials (password, token, etc.) Roles, permissions, policies
Example failure "Invalid email or password" "You do not have permission to access this page"
CSK Connection In Computer Store KS, authentication happens when employees or customers log in via Supabase Auth (email + password). Authorization happens in the middleware, where the system checks the user's roles array (e.g., ['technician', 'social_media']) against the permissions required by the route they are trying to visit.

The Stateless Nature of HTTP

Before we talk about sessions and cookies, you need to understand a fundamental property of the web: HTTP is stateless.

Every time your browser makes an HTTP request to a server, the server treats that request as completely independent. It has no built-in memory of previous requests. The server does not inherently know if the person making Request #47 is the same person who logged in during Request #12.

Request 1: GET /dashboard Server: "Who are you? I don't know you." Request 2: POST /login (email + password) Server: "Credentials valid! You are Matthew." Request 3: GET /dashboard Server: "Who are you? I don't know you." (The server already forgot Request 2!)

This is a problem. If the server forgets us after every request, we would have to send our username and password with every single request. That would be terrible for usability and security.

The solution? We need a mechanism that lets the server "remember" who we are across multiple requests. This is exactly what sessions and cookies provide.

Sessions: The Server Remembers You

A session is a way for the server to store information about a user between requests. Here is how traditional session-based authentication works:

  1. User logs in: The user submits their email and password. The server verifies the credentials.
  2. Server creates a session: The server generates a unique, random session ID (like abc123xyz789) and stores it along with user data (user ID, role, expiration time) in a session store (database, memory, or file system).
  3. Server sends session ID to browser: The server puts the session ID into a cookie and sends it back in the HTTP response.
  4. Browser sends cookie automatically: On every subsequent request, the browser automatically includes the cookie containing the session ID.
  5. Server looks up the session: The server reads the session ID from the cookie, looks it up in the session store, and knows who the user is.
Browser Server | | |--- POST /login (email, password) --| | | 1. Verify credentials | | 2. Create session: {id: "abc123", user: "Matthew", role: "admin"} | | 3. Store session in database |<- Set-Cookie: session_id=abc123 ---| | | |--- GET /dashboard | | Cookie: session_id=abc123 ---| | | 4. Look up "abc123" in session store | | 5. Found! User is Matthew (admin) |<- 200 OK (dashboard HTML) ---------| | | |--- GET /settings | | Cookie: session_id=abc123 ---| | | 6. Look up "abc123" again | | 7. Found! Still Matthew (admin) |<- 200 OK (settings HTML) ----------|

The key insight is that the session ID is just a meaningless random string -- it contains no user data itself. All the actual user information lives on the server. The cookie is like a claim ticket at a coat check: the ticket itself tells you nothing about the coat, but the attendant can use it to find your coat.

Cookies: How the Browser Remembers

A cookie is a small piece of data that a server sends to a browser. The browser stores it and automatically sends it back with every subsequent request to that same server. Cookies are the most common mechanism for maintaining sessions.

How Cookies Are Set

The server includes a Set-Cookie header in its HTTP response:

HTTP/1.1 200 OK
Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Lax; Max-Age=28800; Path=/

The browser then stores this cookie and includes it in every future request to the same domain:

GET /dashboard HTTP/1.1
Host: computerstoreks.com
Cookie: session_id=abc123

This all happens automatically. The developer does not need to write any client-side JavaScript to manage session cookies -- the browser handles it.

Cookie Attributes (Critical for Security)

Cookies have several attributes that control their behavior and security. Understanding these is essential because misconfigured cookies are one of the most common sources of security vulnerabilities.

Attribute Purpose Recommended Value
HttpOnly Prevents JavaScript from reading the cookie true for session cookies
Secure Cookie only sent over HTTPS true in production
SameSite Controls when cookie is sent with cross-site requests Lax or Strict
Max-Age Seconds until cookie expires Depends on use case
Path Which URL paths receive the cookie / (entire site)
Domain Which domains receive the cookie Your domain (default)

HttpOnly: Protection Against XSS

When a cookie is marked HttpOnly, JavaScript running in the browser cannot read it via document.cookie. This is critical for session cookies because if an attacker injects malicious JavaScript into your page (called a Cross-Site Scripting or XSS attack), they cannot steal the session cookie.

// Without HttpOnly, an attacker's injected script could do this:
document.cookie  // "session_id=abc123"
// They steal this value and send it to their server.
// Now they can impersonate you!

// With HttpOnly:
document.cookie  // "" (session cookie is invisible to JavaScript)
// The attacker cannot steal what they cannot see.
Security Rule: Session cookies must ALWAYS have HttpOnly set to true. There is no legitimate reason for client-side JavaScript to access a session token.

Secure: HTTPS Only

When a cookie is marked Secure, the browser will only send it over encrypted HTTPS connections, never over plain HTTP. This prevents an attacker on the same network (like a coffee shop WiFi) from intercepting the cookie.

SameSite: CSRF Protection

The SameSite attribute controls whether the browser sends the cookie with requests that come from other websites. This protects against Cross-Site Request Forgery (CSRF) attacks.

  • Strict -- Cookie is never sent with cross-site requests. The most secure option, but it means that if someone clicks a link to your site from an email, they will not be logged in on the first page load.
  • Lax -- Cookie is sent with top-level navigation (clicking a link) but not with embedded requests (images, iframes, AJAX from another site). This is the recommended default -- it prevents CSRF while still allowing normal link navigation.
  • None -- Cookie is always sent, even cross-site. This requires Secure to be set and should only be used for specific cross-site use cases (like embedded widgets).

Max-Age and Expires

Max-Age sets how many seconds the cookie lives before the browser deletes it. Expires sets a specific date. If neither is set, the cookie is a "session cookie" that disappears when the browser closes.

// Cookie that lasts 8 hours (28,800 seconds)
Set-Cookie: session_id=abc123; Max-Age=28800

// Cookie that lasts 30 days
Set-Cookie: remember_me=token456; Max-Age=2592000
CSK Connection Computer Store KS sets session cookies with all the recommended security attributes. Here is the actual cookie configuration from auth.ts: 
cookieStore.set(SESSION_COOKIE_NAME, encryptedSession, {
  httpOnly: true,                          // No JS access
  secure: process.env.NODE_ENV === 'production',  // HTTPS only in prod
  sameSite: 'lax',                         // CSRF protection
  maxAge: SESSION_MAX_AGE,                 // 8 hours for employees
  path: '/',                               // Entire site
});
Employee sessions expire after 8 hours. Customer sessions last 30 days.

JSON Web Tokens (JWT)

Sessions store user data on the server and give the client a meaningless ID. JSON Web Tokens (JWT) take a different approach: they store user data inside the token itself.

JWT Structure

A JWT is a string made up of three parts, separated by dots:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VySWQiOjEsImVtYWlsIjoibWF0dEBleGFtcGxlLmNvbSIsInJvbGUiOiJhZG1pbiIsImV4cCI6MTcwMTIzNDU2N30.Kj8G2dL1xN7RvQpB3mZ5yKfE9hL2wXcJ4nO5dF6gH0s

|_____________header____________|._____________payload_______________|.___________signature___________|

Each part is Base64-encoded (not encrypted -- anyone can read it):

1. Header

Tells the server which algorithm was used to create the signature:

{
  "alg": "HS256",   // HMAC SHA-256 signing algorithm
  "typ": "JWT"      // Token type
}

2. Payload

Contains the actual user data (called "claims"):

{
  "userId": 1,
  "email": "matt@example.com",
  "role": "admin",
  "exp": 1701234567        // Expiration time (Unix timestamp)
}

3. Signature

Created by signing the header and payload with a secret key that only the server knows:

HMAC-SHA256(
  base64(header) + "." + base64(payload),
  server_secret_key
)

The signature is what makes JWTs secure. If anyone modifies the header or payload, the signature will not match, and the server will reject the token. But remember: JWTs are not encrypted. Anyone can decode the payload and read the data. The signature only prevents tampering, not reading.

Important: Never put sensitive data (passwords, credit card numbers, social security numbers) in a JWT payload. The payload is only Base64-encoded, not encrypted. Anyone with the token can decode it and read the contents.

JWT vs. Sessions: Tradeoffs

Feature Session-Based Auth JWT-Based Auth
Where data lives Server (database/memory) Client (inside the token)
Server storage needed Yes (session store) No (stateless)
Revocation (force logout) Easy (delete from store) Hard (token valid until expiry)
Scalability Needs shared session store Scales naturally (no shared state)
Size Small cookie (just an ID) Larger cookie (contains all data)
Works across services Hard (all services need same store) Easy (any service can verify the signature)
Best for Traditional web apps APIs, microservices, mobile apps
Real-World Reality Many modern applications use both. Supabase, for example, uses JWTs for its authentication tokens but stores session data in cookies managed by the @supabase/ssr library. The JWT handles stateless authentication while cookies handle browser session management. You do not always have to choose one or the other.
CSK Connection Computer Store KS uses a hybrid approach. Supabase Auth issues JWTs that the @supabase/ssr library manages in cookies. In parallel, the app creates its own custom encrypted session cookie (admin_session) using AES-256-GCM encryption. This custom session stores the user's roles, user type, and location data. The middleware checks these custom cookies first for authorization decisions.

Password Security

Password handling is the single most critical security responsibility in an authentication system. Let us examine the right and wrong ways to handle passwords.

Never Store Plaintext Passwords

If your database stores passwords as plain text, a single data breach exposes every user's password. Since people reuse passwords across sites, a breach on your site could compromise their bank account, email, or social media.

-- CATASTROPHICALLY WRONG: plaintext passwords
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  email TEXT NOT NULL,
  password TEXT NOT NULL  -- "mysecretpassword123" stored as-is
);

-- If hackers steal this database, they get EVERY password instantly.
Absolute Rule: NEVER store passwords in plain text. Not in a database. Not in a log file. Not in an email. Not anywhere. There are zero exceptions to this rule.

Hashing: One-Way Transformation

A hash function takes an input (like a password) and produces a fixed-length string of characters. The critical property is that hashing is a one-way operation -- you cannot reverse a hash to get the original password.

// Hashing is one-way
hash("mysecretpassword123")  -->  "a7f8b2c9d1e4f6..."

// You CANNOT reverse it
reverse("a7f8b2c9d1e4f6...")  -->  IMPOSSIBLE

When a user logs in, you hash the password they submit and compare it to the stored hash. If the hashes match, the password is correct:

// During registration:
storedHash = hash("mysecretpassword123")  // Store this in database

// During login:
inputHash = hash("mysecretpassword123")   // Hash what user typed
if (inputHash === storedHash) {
  // Passwords match! User is authenticated.
}

Salting: Preventing Rainbow Table Attacks

Even with hashing, attackers can use precomputed tables (called "rainbow tables") that map common passwords to their hashes. If two users have the same password, they have the same hash -- and the attacker knows both passwords at once.

A salt is a unique, random string added to each password before hashing. This means even identical passwords produce different hashes:

// Without salt -- identical passwords produce identical hashes (BAD)
hash("password123")  -->  "abc123..."
hash("password123")  -->  "abc123..."  (Same! Attacker knows both)

// With salt -- identical passwords produce different hashes (GOOD)
hash("randomsalt1" + "password123")  -->  "xyz789..."
hash("randomsalt2" + "password123")  -->  "def456..."  (Different!)

Each user gets their own unique salt, which is stored alongside their hash (the salt is not secret -- it only needs to be unique).

bcrypt: The Industry Standard

bcrypt is a password hashing algorithm specifically designed for passwords. It automatically handles salting and has a configurable "cost factor" that controls how slow the hashing is. Why would you want slow hashing? Because attackers trying to crack passwords need to hash millions of guesses, and making each hash take 100ms instead of 1 microsecond makes brute force impractical.

import bcrypt from 'bcryptjs';

// Hash a password (salt rounds = 12 means 2^12 = 4096 iterations)
const hash = await bcrypt.hash('userPassword123', 12);
// Result: "$2a$12$LJ3m5Z..." (includes algorithm, cost, salt, and hash)

// Verify a password
const isMatch = await bcrypt.compare('userPassword123', hash);
// Returns true if password matches the hash

The number 12 is the "salt rounds" (or cost factor). Each increment doubles the computation time. A value of 10-12 is standard in 2026, taking about 100-250ms to hash.

Password Length Beats Complexity

Research has consistently shown that password length is more important than complexity rules. A long, memorable passphrase like correct horse battery staple is much harder to crack than a short, complex password like P@$$w0rd!.

Password Length Approx. Time to Crack
P@$$w0rd! 9 chars Hours to days
MyDogLikesToEat 15 chars Centuries
correct horse battery staple 28 chars Heat death of universe

Modern best practice: require a minimum of 12 characters and skip forced complexity rules (no "must include uppercase, number, special character"). Users who are forced to include symbols just add ! at the end, which attackers know.

CSK Connection CSK uses bcryptjs for password hashing in auth.ts. When creating customer portal accounts, passwords are hashed with bcrypt.hash(password, 12) before storage. During login, bcrypt.compare() verifies the password against the stored hash. Supabase Auth also handles its own password hashing internally for users authenticated through Supabase.

OAuth: "Sign in with Google"

OAuth (Open Authorization) is a protocol that lets users log into your application using their existing account at another service (Google, GitHub, Facebook, etc.). The user never gives your application their Google password -- instead, Google verifies their identity and tells your application "yes, this person is who they say they are."

The flow works like this:

  1. User clicks "Sign in with Google" on your site.
  2. Your site redirects them to Google's login page.
  3. User enters their Google credentials (on Google's site, not yours).
  4. Google asks "Do you want to allow [Your App] to access your profile?"
  5. User clicks "Allow."
  6. Google redirects back to your site with an authorization code.
  7. Your server exchanges that code for user profile data (email, name, etc.).
  8. Your server creates a session for the user.

The benefit is that you never handle the user's password at all -- less security responsibility for you, and the user does not need to create yet another password to remember.

CSK Connection CSK supports Google OAuth via Supabase Auth. The signInWithGoogle() function in supabase-auth.ts redirects users to Google, and after authentication, they return to /auth/callback where a session is created.

Multi-Factor Authentication (MFA)

Multi-Factor Authentication requires users to prove their identity using two or more different types of evidence. The "factors" come from different categories:

  • Something you know -- a password or PIN
  • Something you have -- a phone (receives SMS codes or generates TOTP codes), a hardware key (like YubiKey)
  • Something you are -- a fingerprint, face scan, or other biometric

True MFA requires factors from at least two different categories. Entering a password and then answering a security question is NOT MFA because both are "something you know."

The most common MFA implementation is a password (something you know) plus a six-digit code from an authenticator app on your phone (something you have). Even if an attacker steals your password, they cannot log in without also having your phone.

TOTP (Time-based One-Time Password) Authenticator apps (Google Authenticator, Authy) use the TOTP algorithm. The app and the server share a secret key. Every 30 seconds, both sides use the current time and the secret key to independently generate the same 6-digit code. The code changes every 30 seconds, so even if an attacker sees one code, it is useless 30 seconds later.

Key Takeaways

  • Authentication verifies identity ("who are you?"); authorization checks permissions ("what can you do?").
  • HTTP is stateless -- sessions and cookies solve this by letting the server remember users across requests.
  • Session cookies must use httpOnly (prevents XSS), secure (HTTPS only), and sameSite (prevents CSRF).
  • JWTs store user data inside the token itself (stateless) while sessions store data on the server (stateful).
  • JWTs are signed (tamper-proof) but NOT encrypted -- do not put secrets in them.
  • NEVER store passwords in plain text. Always use bcrypt with salt rounds of 10-12.
  • Password length matters more than complexity. Require 12+ characters minimum.
  • OAuth lets users log in with existing accounts (Google, GitHub) without sharing their password with you.
  • MFA requires two different types of proof (something you know + something you have) for stronger security.
