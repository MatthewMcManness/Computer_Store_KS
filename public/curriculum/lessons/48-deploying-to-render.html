Deploying to Render

Take your application from localhost to the live internet -- learn to deploy, configure, and manage a production web service on Render.

What You Will Learn

  • Understand what Render is and how it compares to other hosting platforms
  • Create a Render account and connect a GitHub repository
  • Write a render.yaml blueprint for Infrastructure as Code
  • Configure web services: runtime, build command, start command
  • Set environment variables in the Render dashboard
  • Understand auto-deploy on git push and how it works
  • Read and troubleshoot build logs
  • Understand deploy statuses: live, building, and failed

  • Configure custom domains and automatic SSL certificates

What Is Render?

Render is a cloud platform for hosting web applications. It takes your code from GitHub, builds it on their servers, and serves it to the world over the internet. You do not need to configure servers, manage operating systems, or worry about networking. You push code, Render does the rest.

At its core, Render does three things:

  1. Builds your application from source code (runs npm install and npm run build)
  2. Runs your application on their infrastructure (executes npm run start or node server.js)
  3. Serves your application to users over HTTPS with automatic SSL certificates
Analogy: If building a website is like cooking a meal, then hosting platforms like Render are the restaurant kitchen. You provide the recipe (your code), and the kitchen (Render) has the ovens, refrigerators, and serving staff to turn your recipe into a meal delivered to customers. You focus on the recipe; the kitchen handles the infrastructure.

Alternatives to Render

Render is not the only hosting platform. Here is how it compares to the most popular alternatives:

Platform Best For Free Tier Trade-Offs
Render Full-stack apps, simple deployment Yes (spins down after 15 min) Cold starts on free tier; simple but less flexible than AWS
Vercel Next.js (they created it) Yes (generous) Best Next.js support but more opinionated; can get expensive at scale
Railway Full-stack apps, databases $5 credit/month Developer-friendly but no truly free tier
Fly.io Global edge deployment Yes (limited) Great performance but more complex setup
AWS / GCP / Azure Enterprise, full control Yes (complex) Maximum flexibility but requires deep DevOps knowledge

We use Render for this curriculum because it offers a straightforward setup, a usable free tier, and good compatibility with Next.js standalone output.

Getting Started with Render

Step 1: Create a Render Account

  1. Go to render.com
  2. Click "Get Started for Free"
  3. Sign up with your GitHub account (recommended) or email
  4. Verify your email address

Signing up with GitHub is recommended because it simplifies the next step -- connecting your repository.

Step 2: Connect Your GitHub Repository

  1. In the Render dashboard, click "New" and select "Web Service"
  2. Choose "Build and deploy from a Git repository"
  3. Click "Connect GitHub" and authorize Render to access your repositories
  4. Select the repository you want to deploy
  5. Choose the branch to deploy from (e.g., main or Production)

Render reads your repository on every push to the connected branch. When it detects changes, it automatically starts a new build and deployment.

Step 3: Configure Your Web Service

Render needs to know how to build and run your application. You configure this either through the dashboard or through a render.yaml file.

Setting Value for Next.js Standalone Purpose
Name my-app-production Identifies the service in Render dashboard
Runtime Node Tells Render to use Node.js
Build Command npm install && npm run build How to compile your application
Start Command npm run start or node .next/standalone/server.js How to run the compiled application
Branch Production or main Which Git branch triggers builds
Region Oregon (US West) Where the server is physically located
Plan Free Pricing tier

render.yaml: Infrastructure as Code

Instead of clicking through the Render dashboard to configure your service, you can define everything in a render.yaml file at the root of your repository. This is called Infrastructure as Code (IaC) -- your deployment configuration is version-controlled alongside your application code.

Why Infrastructure as Code Matters

  • Reproducibility: Anyone can deploy the same service by reading the file. No tribal knowledge about "which buttons to click."
  • Version control: Changes to deployment configuration are tracked in Git, just like code changes.
  • Review: Pull requests can include infrastructure changes, making them visible to the team.
  • Disaster recovery: If a service is accidentally deleted, you can recreate it from the file.

render.yaml Structure

# render.yaml -- Render deployment blueprint

services:
  # ===========================================
  # PRODUCTION SERVICE
  # ===========================================
  - type: web                          # Service type (web, worker, cron)
    name: my-app-production            # Service name in Render
    env: node                          # Runtime environment
    branch: Production                 # Git branch to deploy from
    buildCommand: npm install && npm run build
    startCommand: npm run start
    envVars:
      # Non-secret values set directly
      - key: NODE_ENV
        value: production
      - key: PORT
        value: 3000
      - key: HOSTNAME
        value: 0.0.0.0

      # Secrets managed through Render dashboard
      - key: RESEND_API_KEY
        sync: false                    # "Set this in the dashboard"
      - key: SUPABASE_SERVICE_ROLE_KEY
        sync: false
      - key: SESSION_SECRET
        sync: false

      # Public variables (safe to set in file)
      - key: NEXT_PUBLIC_SUPABASE_URL
        sync: false                    # Still secret-ish, managed in dashboard
      - key: NEXT_PUBLIC_APP_URL
        value: https://myapp.com

The Standalone Build Command

When using Next.js standalone output, the build command needs extra steps to copy static files into the standalone directory. Here is the complete build command and what each part does:

# The full build command, broken down:
npm install &&                                          # 1. Install dependencies
npm run build &&                                        # 2. Run Next.js build
cp -r .next/static .next/standalone/.next/static &&     # 3. Copy static assets
rm -rf .next/standalone/public &&                       # 4. Remove any stale public dir
cp -R public .next/standalone/ &&                       # 5. Copy public folder
cp -r node_modules .next/standalone/ &&                 # 6. Copy node_modules
cp package.json .next/standalone/                       # 7. Copy package.json

# The start command for standalone:
cd .next/standalone && node server.js

Steps 3-7 are necessary because standalone mode does not automatically include static files and the public directory. Without these copies, your CSS, JavaScript bundles, images, and other static assets would be missing.

Multiple Services

A single render.yaml can define multiple services. This is useful for running both a production and development environment:

services:
  # Production -- deploys from Production branch
  - type: web
    name: my-app-production
    env: node
    branch: Production
    buildCommand: npm install && npm run build
    startCommand: npm run start
    envVars:
      - key: NODE_ENV
        value: production
      - key: NEXT_PUBLIC_APP_URL
        value: https://myapp.com

  # Development -- deploys from Development branch
  - type: web
    name: my-app-development
    env: node
    branch: Development
    buildCommand: npm install && npm run build
    startCommand: npm run start
    envVars:
      - key: NODE_ENV
        value: production          # Still "production" build, different data
      - key: NEXT_PUBLIC_APP_URL
        value: https://my-app-development.onrender.com
NODE_ENV in Development Service Notice that even the development service sets NODE_ENV=production. This is because NODE_ENV controls how Next.js and React behave (optimization, error messages, etc.), and you want production-like behavior even in a staging environment. The environment variables that point to test databases and test API keys are what make it a "development" environment, not the NODE_ENV value.
CSK Connection The CSK render.yaml defines two services: CSK-Production (deploying from the Production branch to computerstoreks.com) and CSK-Development (deploying from the Development branch). Both use the standalone build command with the copy steps. Each service has its own set of environment variables, with secrets marked as sync: false for dashboard management.

Environment Variables in the Render Dashboard

For variables marked with sync: false in render.yaml (or for any variable you want to manage through the UI), you set values in the Render dashboard:

  1. Navigate to your service in the Render dashboard
  2. Click "Environment" in the left sidebar
  3. Click "Add Environment Variable"
  4. Enter the key and value
  5. Click "Save Changes"
  6. The service will automatically restart with the new values

Render stores all environment variable values encrypted at rest. They are only decrypted when injected into your running application.

Restart Required After changing environment variables, your service needs to restart for the changes to take effect. For NEXT_PUBLIC_ variables, you need a full rebuild (not just a restart) because these values are embedded at build time. Click "Manual Deploy" and select "Clear build cache & deploy" to force a fresh build with the new values.

Auto-Deploy: From Git Push to Live Site

One of Render's most powerful features is auto-deploy. Every time you push code to the connected branch, Render automatically detects the change and starts a new build and deployment.

The Auto-Deploy Flow

Developer pushes to Production branch | v GitHub notifies Render (webhook) | v Render pulls latest code | v Render runs build command (npm install && npm run build) | v Build succeeds? ──No──> Build FAILED | (old version stays live) Yes | v Render starts new server (npm run start / node server.js) | v Health check passes? ──No──> Deploy FAILED | (old version stays live) Yes | v Traffic switches to new version (zero-downtime deployment) | v Old version shuts down Site is live with new code!

Key points about this flow:

  • Zero-downtime deployment: Render starts the new version alongside the old one. Only after the new version is healthy does it switch traffic. Users never see downtime during a deploy.
  • Automatic rollback: If the new version fails to start or fails the health check, Render keeps the old version running. Your site stays live even when a deploy fails.
  • Build isolation: Each build runs in a fresh environment. There are no leftover files from previous builds (unless you use the build cache).

Disabling Auto-Deploy

In some cases, you may want to control exactly when deployments happen. You can disable auto-deploy in the service settings and instead trigger deploys manually from the dashboard or via the Render API.

Build Logs: Reading and Troubleshooting

When a build runs, Render captures every line of output from your build command. These logs are your primary tool for diagnosing deployment issues.

Anatomy of a Successful Build Log

==> Cloning from https://github.com/yourname/your-repo...
==> Using Node version 20.11.0 (from .node-version or NODE_VERSION env var)
==> Running 'npm install'

added 287 packages in 12s

==> Running 'npm run build'

   Creating an optimized production build...
   Compiled successfully.

   Route (app)                    Size     First Load JS
   ┌ ○ /                           5.2 kB        89 kB
   ├ λ /admin                      12.4 kB      102 kB
   ├ ○ /about                      1.8 kB        85 kB
   └ ○ /contact                    3.1 kB        87 kB

==> Build successful!
==> Uploading build...
==> Starting service with 'cd .next/standalone && node server.js'
==> Your service is live!

Common Build Failures

# 1. Missing environment variable
Error: Missing required environment variable: SUPABASE_SERVICE_ROLE_KEY
  --> Fix: Add the variable in Render's Environment tab

# 2. Node.js version mismatch
error engine: Unsupported engine { node: '>=22.0.0', npm: '*' }
  --> Fix: Set NODE_VERSION env var to match your .nvmrc

# 3. Dependency installation failure
npm ERR! 404 Not Found - GET https://registry.npmjs.org/nonexistent-package
  --> Fix: Check package.json for typos in dependency names

# 4. TypeScript error (if ignoreBuildErrors is false)
Type error: Property 'id' is missing in type '{}'
  --> Fix: Fix the TypeScript error in your code

# 5. Out of memory
FATAL ERROR: CALL_AND_RETRY_LAST Allocation failed - JavaScript heap out of memory
  --> Fix: Add NODE_OPTIONS=--max-old-space-size=4096 as env var

# 6. Build timeout
==> Build exceeded maximum time of 30 minutes
  --> Fix: Optimize build or upgrade to a paid plan with longer timeouts
Build Logs Are Temporary Render keeps build logs for a limited time. If you need to reference a build log later, copy the relevant parts before they expire. For critical deployments, consider copying the build output to a team communication channel.

Deploy Statuses

Every deployment in Render goes through a lifecycle with clear status indicators:

Status Meaning Action Required
In Progress Build or deploy is currently running Wait. Check build logs for progress.
Live Deploy succeeded, new version is serving traffic None. Verify the site works as expected.
Build Failed The build command exited with an error Read build logs, fix the error, push a fix.
Deploy Failed Build succeeded but the server failed to start Check start command and runtime errors.
Canceled A newer push arrived during build, canceling this one None. The newer deploy will proceed.

When a deploy fails, the previous working version stays live. This is a critical safety feature. Your users continue to see the last successful deployment while you fix the problem.

Free Tier: Limitations and Strategies

Render's free tier is generous enough to run real applications, but it has limitations you need to understand:

Limitation Impact Workaround
Spins down after 15 min of inactivity First request after idle takes 30-60 seconds (cold start) Use UptimeRobot to ping every 5 minutes (covered in Lesson 49)
750 hours/month per service One free service can run ~31 days (enough for always-on) Multiple free services share the 750-hour pool
Limited CPU and memory Slower builds and responses under heavy load Optimize your application and bundle size
No persistent disk Uploaded files are lost on redeploy Use Supabase Storage or other external storage
Shared infrastructure Performance can vary ("noisy neighbor" effect) Upgrade to paid tier for dedicated resources

When to Upgrade

Consider upgrading from the free tier when:

  • Cold starts are unacceptable for your users (upgrade eliminates spin-down)
  • You need more CPU/memory for faster builds and responses
  • You need persistent disk storage
  • You need custom domains with more control over SSL
  • You need guaranteed uptime SLAs for business-critical applications

Custom Domains and SSL

By default, Render gives your service a URL like my-app.onrender.com. For a professional site, you want your own domain name (like computerstoreks.com).

Adding a Custom Domain

  1. Purchase a domain from a registrar (Namecheap, Google Domains, Cloudflare, etc.)
  2. In Render, go to your service and click "Settings"
  3. Scroll to "Custom Domains" and click "Add Custom Domain"
  4. Enter your domain name (e.g., computerstoreks.com)
  5. Render will display the DNS records you need to add

DNS Configuration

You need to add DNS records at your domain registrar. The exact records depend on whether you are using the root domain or a subdomain:

Domain Type Record Type Name Value
Root (example.com) A @ Render's IP addresses
Subdomain (www.example.com) CNAME www your-service.onrender.com

DNS changes take time to propagate -- usually a few minutes, but sometimes up to 48 hours. Render shows you the verification status and notifies you when the domain is connected.

Automatic SSL with Let's Encrypt

Once your custom domain is verified, Render automatically provisions an SSL certificate from Let's Encrypt, a free certificate authority. This means your site is served over HTTPS with no extra cost or configuration.

Render handles certificate renewal automatically. Let's Encrypt certificates expire every 90 days, but Render renews them before expiration. You never need to think about SSL certificates.

CSK Connection The CSK production service at computerstoreks.com uses a custom domain with automatic SSL from Let's Encrypt. The development service uses the default Render URL: csk-development.onrender.com. DNS is configured at the domain registrar with A records pointing to Render's IP addresses.

Complete Deployment Walkthrough

Let us walk through a complete deployment from start to finish, using the exact steps you would follow for a real project.

Step 1: Prepare Your Code

# Make sure your code builds locally
$ npm run build

# Verify it runs correctly
$ npm run start
# Test at http://localhost:3000

# Commit everything
$ git add .
$ git commit -m "feat: ready for production deployment"

Step 2: Create render.yaml

# Create render.yaml at the root of your project
services:
  - type: web
    name: my-app-production
    env: node
    branch: main
    buildCommand: npm install && npm run build
    startCommand: npm run start
    envVars:
      - key: NODE_ENV
        value: production
      - key: PORT
        value: 3000
      - key: HOSTNAME
        value: 0.0.0.0
      - key: NEXT_PUBLIC_SUPABASE_URL
        sync: false
      - key: NEXT_PUBLIC_SUPABASE_ANON_KEY
        sync: false
      - key: SUPABASE_SERVICE_ROLE_KEY
        sync: false
      - key: RESEND_API_KEY
        sync: false
      - key: SESSION_SECRET
        sync: false

Step 3: Push to GitHub

$ git add render.yaml
$ git commit -m "chore: add render deployment blueprint"
$ git push origin main

Step 4: Create the Service in Render

  1. Log into Render, click "New" and select "Blueprint"
  2. Connect your GitHub repository
  3. Render reads render.yaml and creates the service(s)
  4. Fill in the values for variables marked sync: false
  5. Click "Apply"

Step 5: Watch the Build

Render starts building immediately. Click on your service and then "Events" or "Logs" to watch the build progress. A typical build takes 2-5 minutes for a Next.js application.

Step 6: Verify the Deployment

# Visit your Render URL
$ curl https://my-app-production.onrender.com/api/health

# Expected response:
{
  "status": "ok",
  "timestamp": "2026-02-05T12:00:00.000Z",
  "database": { "success": true }
}

Step 7: Subsequent Deployments

From now on, deploying is as simple as pushing to your branch:

# Make changes to your code
$ git add .
$ git commit -m "feat: add contact form"
$ git push origin main

# Render automatically detects the push and starts a new build
# Within 2-5 minutes, the changes are live
Analogy: The first deployment is like setting up a new phone -- connecting accounts, configuring settings, entering passwords. Subsequent deployments are like installing app updates: they happen automatically in the background with minimal effort.

Exercises

  1. Create a Render account: Sign up at render.com using your GitHub account. Explore the dashboard and familiarize yourself with the interface.
  2. Write a render.yaml: For a Next.js project with Supabase and Resend, write a complete render.yaml that defines both a production service (deploying from main) and a development service (deploying from dev). Include all necessary environment variables with appropriate sync: false flags.
  3. Deploy a simple app: Create a minimal Next.js application (even just a homepage), push it to GitHub, and deploy it to Render's free tier. Verify that the URL works.
  4. Trigger auto-deploy: Make a visible change to your deployed application (like changing the homepage text), push it to GitHub, and watch the auto-deploy process in Render's dashboard. Time how long it takes from push to live.
  5. Read build logs: Intentionally introduce a build error (like a missing dependency or broken import), push to trigger a build, and read the build logs in Render. Identify the exact error, fix it, and push the fix.
  6. Domain research: Research the DNS configuration needed to point a custom domain to Render. Draw a diagram showing the flow from a user typing a domain name to the response arriving in their browser, including DNS resolution, Render's load balancer, and your application.

Key Takeaways

  • Render is a cloud platform that builds, runs, and serves your web application from a GitHub repository.
  • render.yaml defines your deployment configuration as code: service type, build/start commands, and environment variables. This makes deployments reproducible and version-controlled.
  • Auto-deploy triggers a new build every time you push to the connected branch. Render handles zero-downtime deployments and automatic rollback on failure.
  • Environment variables with real secrets use sync: false in render.yaml and are set through the Render dashboard.
  • Build logs are your primary debugging tool for deployment failures. Learn to read them carefully.
  • The free tier spins down after 15 minutes of inactivity, causing cold starts. UptimeRobot (next lesson) solves this.
  • Custom domains are added in Render settings and require DNS records at your registrar. SSL certificates are automatic via Let's Encrypt.
  • For standalone Next.js output, the build command must copy static files and public assets into the standalone directory.
  • When a deploy fails, the previous working version stays live. Your site never goes down due to a bad deployment.
