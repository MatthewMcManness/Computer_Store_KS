Lesson 01: How the Web Works

Understanding what happens behind the scenes every time you visit a website

Learning Objectives

The Internet vs. The World Wide Web

Before we dive into how the web works, let us clear up a common misconception: the Internet and the World Wide Web are not the same thing. The Internet is the massive global network of computers connected by cables, fiber optics, and wireless signals. Think of it as the highway system itself — the physical roads, bridges, and tunnels. The World Wide Web (or simply "the web") is one of many services that runs on top of the Internet, just like cars are one of many types of vehicles that use highways. Email, video calls, online gaming, and file sharing all use the Internet too, but they are not part of the web.

The web was invented in 1989 by Tim Berners-Lee, a British scientist working at CERN (a particle physics lab in Switzerland). He created three foundational technologies that still power the web today: HTML (a language for structuring web pages), URLs (addresses for locating pages), and HTTP (a protocol for transferring pages between computers). We will explore all three of these in this lesson and throughout this curriculum.

Analogy: The Postal System
Think of the Internet like the entire postal system — trucks, planes, sorting facilities, and mail carriers. The World Wide Web is like the letter-writing service that uses that postal system. You can also send packages (file transfers), make phone calls (VoIP), or send telegrams (instant messages) through the same postal infrastructure, but letter-writing (the web) is just one use of it.

What Happens When You Type a URL

Every time you type an address into your browser (like https://computerstoreks.com) and press Enter, an astonishing sequence of events unfolds in milliseconds. Let us walk through each step.

Step 1: Parsing the URL

A URL (Uniform Resource Locator) is simply an address that tells your browser where to find something on the web. Let us break one apart:

https://www.computerstoreks.com/services/diagnostics
  |        |                        |
  |        |                        +-- Path (specific page)
  |        +-- Domain name (which server)
  +-- Protocol (how to communicate)

The protocol (https://) tells the browser which language to speak when talking to the server. The domain name (www.computerstoreks.com) identifies which computer on the Internet to contact. The path (/services/diagnostics) tells the server which specific page you want. Think of the protocol as the language you speak, the domain name as the street address, and the path as the room number inside the building.

Step 2: DNS Lookup — Finding the Server's Address

Computers do not understand domain names like computerstoreks.com. They communicate using IP addresses, which are numerical labels like 216.24.57.1. An IP address works exactly like a phone number — it uniquely identifies one computer on the Internet.

So how does your browser convert a domain name into an IP address? It uses the Domain Name System (DNS), which functions like the Internet's phone book. Here is what happens:

  1. Your browser first checks its own memory (cache) — "Have I looked up this name recently?"
  2. If not found, it asks your operating system (Windows, Mac, or Linux), which has its own cache.
  3. If still not found, your computer asks your Internet Service Provider's (ISP's) DNS server.
  4. If the ISP does not know, the request travels up to a root DNS server, then to a TLD (Top-Level Domain) server (which knows about all .com addresses), and finally to the authoritative DNS server for that specific domain.
  5. The IP address is returned all the way back to your browser.
Analogy: Finding a Phone Number
Imagine you want to call "The Computer Store." You check your own contacts first. If it is not there, you ask a family member. If they do not know, you look it up in the phone book. DNS works the same way — it is a series of lookups, starting with the fastest source (your own cache) and working outward until the answer is found.

Step 3: TCP Connection — Establishing a Reliable Channel

Now that your browser knows the server's IP address, it needs to establish a reliable connection. This is done through TCP (Transmission Control Protocol), which uses a process called the three-way handshake:

  1. SYN — Your browser says: "Hello, I would like to connect." (Synchronize)
  2. SYN-ACK — The server replies: "Hello! I acknowledge your request and am ready." (Synchronize-Acknowledge)
  3. ACK — Your browser confirms: "Great, let us begin!" (Acknowledge)

TCP guarantees that data arrives completely and in the correct order. If a piece of data gets lost during transmission, TCP detects the loss and retransmits it. This is critical for web pages — you would not want half a page to load or for paragraphs to arrive scrambled.

Analogy: A Phone Call
The TCP handshake is like the start of a phone call. You dial the number (SYN), the other person picks up and says "Hello?" (SYN-ACK), and you say "Hi, it's me!" (ACK). Now both sides know the connection is working, and the conversation can begin.

Step 4: TLS Handshake (for HTTPS)

If the URL uses https:// (which it should — more on this later), there is an additional step after TCP connects. TLS (Transport Layer Security) encrypts the connection so that nobody between you and the server can read the data. During the TLS handshake:

  1. The server presents a digital certificate (like a verified ID card) to prove it really is computerstoreks.com.
  2. Your browser verifies the certificate was issued by a trusted authority.
  3. Both sides agree on an encryption method and exchange keys.
  4. All future communication is encrypted.

This entire handshake happens in about 50-100 milliseconds. After it completes, everything sent between your browser and the server is scrambled in a way that only those two parties can unscramble.

Step 5: HTTP Request — Asking for the Page

With a secure, reliable connection in place, your browser sends an HTTP request to the server. This request is a structured message that says: "Please send me this specific page." Here is a simplified version of what that request looks like:

GET /services/diagnostics HTTP/2
Host: computerstoreks.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
Accept: text/html,application/xhtml+xml
Accept-Language: en-US,en
Accept-Encoding: gzip, deflate, br
Connection: keep-alive

Let us decode each line:

  • GET /services/diagnostics HTTP/2 — "I want to GET the page at /services/diagnostics, and I speak HTTP version 2."
  • Host — The domain name of the server (needed because one server can host multiple websites).
  • User-Agent — Information about your browser and operating system.
  • Accept — The types of content your browser can handle.
  • Accept-Language — Your preferred language.
  • Accept-Encoding — Compression methods your browser supports (to speed up transfer).

Step 6: Server Processing

The server receives your request and decides how to respond. For a static website, the server simply finds the requested file on its hard drive and sends it back. For a dynamic website (like Computer Store KS), the server runs code to generate the page. This might involve querying a database, checking if you are logged in, fetching the latest inventory, and assembling all of that data into an HTML page specifically for you.

Step 7: HTTP Response — The Server Replies

The server sends back an HTTP response, which looks something like this:

HTTP/2 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 42378
Content-Encoding: gzip
Strict-Transport-Security: max-age=31536000
X-Content-Type-Options: nosniff

<!DOCTYPE html>
<html lang="en">
  <head>
    <title>Diagnostics - Computer Store KS</title>
    ...
  </head>
  <body>
    ...
  </body>
</html>

The first line, HTTP/2 200 OK, tells your browser that the request was successful. The headers provide metadata about the response (content type, size, encoding, security policies). And then the actual HTML content of the page follows.

Step 8: Browser Rendering

Finally, your browser takes the HTML it received and transforms it into the visual page you see on screen. This is a complex process:

  1. Parse HTML — The browser reads the HTML and builds a tree structure called the DOM (Document Object Model).
  2. Request additional resources — The HTML references CSS files, JavaScript files, images, and fonts. The browser sends additional HTTP requests for each of these.
  3. Parse CSS — Style rules are applied to determine how each element should look.
  4. Layout — The browser calculates the exact position and size of every element.
  5. Paint — Pixels are drawn to the screen.
  6. Execute JavaScript — Any interactive behavior (animations, button clicks, form validation) is enabled.

All of this — from DNS lookup to the final painted pixel — typically happens in under one second.

CSK Connection When you visit computerstoreks.com, this exact process happens. The browser contacts Render's servers (where CSK is hosted), the Next.js application processes the request, queries Supabase for data like blog posts or gallery items, assembles the HTML, and sends it back. Clients and Servers

You have probably heard the terms "client" and "server" used in computing, and they are foundational to understanding web development. In the simplest terms:

  • A client is the program that makes requests. Your web browser (Chrome, Firefox, Safari, Edge) is a client. Your phone's browser is a client. Even a mobile app that connects to the internet is a client.
  • A server is the program that receives requests and sends back responses. It is a computer (or program running on a computer) that is always on, always connected to the Internet, and always waiting for clients to ask it for things.
Analogy: The Restaurant
Imagine a restaurant. You are the client — you sit at the table and make requests ("I'd like the pasta, please"). The waiter is like the HTTP protocol — they carry your request to the kitchen and bring back the response. The kitchen is the server — it receives orders, prepares the food (processes the request), and sends the finished dish back to you.

Just as multiple customers can order from the same kitchen simultaneously, millions of clients can make requests to the same server. And just as a restaurant can have different kitchens for different cuisines, the web has different servers for different websites.

An important nuance: "client" and "server" are roles, not physical devices. The same computer can be a client in one moment (when your laptop's browser requests a web page) and a server in another (if you run server software on your laptop for testing). In professional web development, servers are typically powerful computers housed in data centers — huge buildings full of rack-mounted machines with fast Internet connections, backup power, and climate control.

The Client-Server Model in Practice

The client-server model is a fundamental architectural pattern in computing. Here is how it plays out in a typical web interaction:

Aspect Client (Your Browser) Server (The Website)
Location Your device (laptop, phone, tablet) A data center (Render, AWS, Google Cloud)
Initiates Sends requests Waits for and responds to requests
Displays Renders the visual page Has no display (runs in the background)
Access Anyone with a browser Only the developer/admin can manage it
Trust Not trusted (user can manipulate) Trusted (controlled by developer)
Security Principle: Never Trust the Client Because users can modify anything in their browser (using developer tools, browser extensions, or scripts), the server must always validate data it receives. If a form says "maximum 100 characters," the server must enforce that limit too — a malicious user can easily bypass the client-side check. This principle of never trusting the client is a cornerstone of web security that we will revisit repeatedly throughout this curriculum.

HTTP Methods

HTTP (HyperText Transfer Protocol) is the language that clients and servers use to communicate on the web. Every HTTP request includes a method (sometimes called a "verb") that tells the server what action the client wants to perform. While there are several HTTP methods, two are by far the most common:

GET — "Give me something"

A GET request asks the server to send back a resource. When you type a URL into your browser, click a link, or load an image, your browser sends a GET request. GET requests should never change anything on the server — they only retrieve data. You can think of GET as a "read" operation.

Examples of GET requests:

  • Loading a web page: GET /about
  • Loading an image: GET /images/logo.png
  • Searching: GET /search?q=laptop+repair
  • Loading CSS: GET /styles/main.css

POST — "Here is some data, do something with it"

A POST request sends data to the server, typically to create something new or trigger an action. When you submit a form (like a contact form, login form, or checkout page), your browser usually sends a POST request. POST requests can change things on the server — creating database records, sending emails, processing payments, etc.

Examples of POST requests:

  • Submitting a contact form: POST /api/contact
  • Logging in: POST /api/auth/login
  • Uploading an image: POST /api/gallery/upload
  • Creating a blog post: POST /api/blog

Other HTTP Methods

As you progress through this curriculum, you will encounter additional HTTP methods:

Method Purpose Example
GET Retrieve data Load a page, fetch a list of products
POST Create new data Submit a form, create a new blog post
PUT Replace existing data Update an entire customer record
PATCH Partially update data Change just the status of a ticket
DELETE Remove data Delete a gallery item
Did You Know? Together, these methods form the basis of "CRUD" operations — Create (POST), Read (GET), Update (PUT/PATCH), and Delete (DELETE). Almost every web application is built around these four operations. You will learn to build CRUD APIs yourself in Phase 4 of this curriculum.

HTTP Status Codes

Every HTTP response from a server includes a three-digit status code that tells the client what happened. These codes fall into five categories, grouped by their first digit:

Range Category Meaning
1xx Informational Request received, continuing process
2xx Success The request worked as expected
3xx Redirection You need to go somewhere else
4xx Client Error Something was wrong with the request
5xx Server Error Something went wrong on the server

The Status Codes You Must Know

200 OK — The gold standard. Everything worked perfectly. The server found what you asked for and is sending it back. This is the most common status code by far, and the one you will see most often when browsing the web normally.

201 Created — A close cousin of 200, this means the server successfully created something new. You will see this when a form submission creates a database record, like when someone submits a new blog post.

301 Moved Permanently — The page you requested has permanently moved to a new address. The server tells you the new address, and your browser automatically goes there. This is commonly used when a website restructures its URLs. Search engines will update their records to use the new address.

302 Found (Temporary Redirect) — Similar to 301, but the move is temporary. The browser goes to the new address this time, but it will check the original address again next time.

404 Not Found — Probably the most famous status code. It means the server cannot find what you asked for. You have likely seen a "404 page" before — that is the website's way of saying "this page doesn't exist." This often happens when a URL is typed wrong, a page has been deleted, or a link is broken.

403 Forbidden — The server understood your request but refuses to fulfill it. You do not have permission. This might happen if you try to access an admin page without being logged in.

500 Internal Server Error — Something went wrong on the server side. This is not the client's fault — it means the server's code crashed, the database is unreachable, or some other unexpected error occurred. When you see a 500 error on a website, it means the developers need to fix something.

Analogy: Restaurant Responses
Back to our restaurant analogy:
200 — "Here is your pasta, enjoy!" (Success)
301 — "We moved to the building next door permanently." (Permanent redirect)
404 — "We do not have that dish on our menu." (Not found)
403 — "That dish is only for VIP members." (Forbidden)
500 — "Sorry, the kitchen is on fire." (Server error)
CSK Connection The Computer Store KS website uses these status codes throughout its API. For example, GET /api/blog returns 200 with a list of blog posts. POST /api/contact returns 201 when a contact form is successfully submitted. If you try to access /api/gallery/upload without being logged in as an admin, you get a 403 Forbidden. And if the Supabase database is temporarily unreachable, the health check endpoint at /api/health returns 503 Service Unavailable.

HTTPS and TLS — Why the Padlock Matters

Look at your browser's address bar right now. You should see a small padlock icon to the left of the URL. That padlock means the connection between your browser and the server is encrypted using HTTPS (HyperText Transfer Protocol Secure).

What Problem Does HTTPS Solve?

Without encryption, HTTP traffic travels across the Internet as plain text. Anyone who can intercept the data (your ISP, someone on the same WiFi network, a government agency) can read everything: the pages you view, the forms you submit, the passwords you type. This is called a man-in-the-middle attack.

HTTPS solves this by wrapping all HTTP communication in a layer of encryption called TLS (Transport Layer Security). With HTTPS:

  • Encryption — Data is scrambled so only your browser and the server can read it.
  • Authentication — The server proves its identity with a digital certificate, so you know you are really talking to computerstoreks.com and not an imposter.
  • Integrity — Data cannot be modified in transit without detection.

HSTS — Enforcing HTTPS

Even though HTTPS exists, what if someone tries to visit your site using plain http://? A technique called HSTS (HTTP Strict Transport Security) tells browsers: "Always use HTTPS for this website, no exceptions." Once a browser sees the HSTS header, it will automatically convert any http:// request to https:// before even contacting the server.

Strict-Transport-Security: max-age=31536000; includeSubDomains

This header says: "For the next 31,536,000 seconds (one year), always use HTTPS for this domain and all its subdomains."

CSK Connection The Computer Store KS website enforces HTTPS using HSTS headers set in two places: middleware.ts (which intercepts every request and adds security headers) and next.config.mjs (which configures additional response headers). This means even if someone types http://computerstoreks.com, they are automatically and securely redirected to the HTTPS version.
No Padlock = No Trust If a website does not show the padlock icon, you should never enter sensitive information like passwords, credit card numbers, or personal details. Modern browsers actually warn you with messages like "Your connection is not private" or "Not Secure" in the address bar when a site lacks HTTPS.

Static vs. Dynamic Websites

Websites fall into two broad categories, and understanding the difference is crucial for web development.

Static Websites

A static website consists of pre-built files (HTML, CSS, images) stored on a server. When you request a page, the server simply sends the file as-is, without any processing. Every visitor sees the exact same content.

Characteristics of static websites:

  • Content is the same for every visitor
  • Pages are pre-built files (not generated on-the-fly)
  • No database is needed
  • Very fast (just serving files)
  • Simple to host (any web server works)
  • Good for: portfolios, brochure sites, documentation

Dynamic Websites

A dynamic website generates pages on-the-fly using server-side code. When you request a page, the server runs a program that may query a database, check your login status, personalize content based on your location, and then assemble the HTML specifically for your request. Different visitors may see different content.

Characteristics of dynamic websites:

  • Content can be different for each visitor
  • Pages are generated by running code on the server
  • Typically uses a database to store and retrieve data
  • Can provide personalized, real-time experiences
  • More complex to build and host
  • Good for: e-commerce, social media, dashboards, blogs
CSK Connection The Computer Store KS website is a dynamic website built with Next.js. The public-facing pages (homepage, services, about) have some static characteristics — they look the same for every visitor. But the admin dashboard is fully dynamic: it queries the Supabase database in real-time to show the latest tickets, customer information, and gallery inventory. The blog is also dynamic — blog posts are stored in the database and rendered on-the-fly. Next.js actually blends both approaches, which is one of its superpowers.

The Modern Spectrum

In practice, most modern websites are not purely static or purely dynamic — they sit somewhere on a spectrum. Modern frameworks like Next.js (which powers CSK) can render some pages statically at build time (for speed), while rendering others dynamically at request time (for freshness). This hybrid approach gives you the best of both worlds. We will explore this deeply in Phase 4 when we study Next.js.

What Does "Full-Stack" Mean?

You will often hear the term "full-stack developer" in the industry, and this entire curriculum is designed to make you one. But what does it actually mean?

A web application has multiple layers (sometimes called the "stack"):

Layer Also Called Technologies What It Does
Frontend Client-side HTML, CSS, JavaScript, React What the user sees and interacts with
Backend Server-side Node.js, Next.js API routes, Python, Java Business logic, data processing, API endpoints
Database Data layer PostgreSQL, MySQL, MongoDB, Supabase Stores and retrieves data persistently
Infrastructure DevOps Render, AWS, DNS, CI/CD pipelines Hosting, deployment, monitoring

A frontend developer specializes in the user interface — making things look good and work smoothly in the browser. A backend developer specializes in the server-side logic — handling data, security, and business rules. A full-stack developer can work across all of these layers. They can design a beautiful UI, write the API that powers it, set up the database that stores the data, and deploy the whole thing to a production server.

Analogy: Building a House
Think of building a house. The frontend is the interior design — the paint colors, furniture arrangement, light fixtures, and everything you see and interact with. The backend is the plumbing, electrical wiring, and HVAC — critical systems that visitors do not see but that make the house functional. The database is the filing cabinet where you keep all your important documents. The infrastructure is the land, foundation, and utility connections that make the house habitable. A full-stack developer is the rare contractor who can handle all of these.
CSK Connection The Computer Store KS project is a full-stack application. Its frontend includes React components, Tailwind CSS styles, and client-side interactivity. Its backend includes Next.js API routes that handle contact form submissions, authentication, gallery management, and ticket operations. Its database is Supabase (PostgreSQL) storing blog posts, tickets, customers, and more. And its infrastructure includes Render for hosting, GitHub for code storage, and UptimeRobot for monitoring. By the end of this curriculum, you will understand every layer of this application.

Seeing HTTP in Action: Browser Developer Tools

You do not have to take our word for all of this — you can see HTTP requests and responses happening live in your own browser. Every modern browser includes Developer Tools (often called "DevTools") that let you peek behind the curtain.

To open Developer Tools:

  • Chrome/Edge: Press F12 or Ctrl+Shift+I (Windows/Linux) or Cmd+Option+I (Mac)
  • Firefox: Press F12 or Ctrl+Shift+I
  • Safari: First enable the Develop menu in Preferences > Advanced, then press Cmd+Option+I

Once open, click the Network tab. Now refresh the page. You will see a list of every HTTP request your browser made, the response status code, the size of each response, and how long each request took. Click on any request to see the full headers, the request body (for POST requests), and the response body.

Try It Now! Open your browser's Developer Tools right now and go to the Network tab. Navigate to https://computerstoreks.com and watch the requests appear. You should see the initial HTML document (status 200), followed by CSS files, JavaScript bundles, images, and font files. This is everything we discussed in this lesson, happening in real time.

Key Takeaways

  • When you type a URL, your browser performs a DNS lookup (to find the server's IP address), establishes a TCP connection (for reliable delivery), negotiates TLS encryption (for security), sends an HTTP request, and receives an HTTP response.
  • The client (your browser) makes requests; the server receives them, processes them, and sends back responses. This is the client-server model.
  • HTTP methods define what action a request performs: GET retrieves data, POST sends new data, PUT replaces data, and DELETE removes data.
  • HTTP status codes communicate the result: 200 means success, 301 means moved permanently, 404 means not found, and 500 means the server had an error.
  • HTTPS encrypts communication between client and server using TLS. The padlock icon confirms a connection is secure. HSTS headers force browsers to always use HTTPS.
  • Static websites serve pre-built files unchanged; dynamic websites generate content on-the-fly using server-side code and databases. Most modern sites are a hybrid of both.
  • Full-stack development spans all layers: frontend (what users see), backend (server logic), database (data storage), and infrastructure (hosting and deployment).
