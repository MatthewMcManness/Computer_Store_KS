Monitoring & Uptime

Know when your site is down before your users tell you -- build health checks, set up monitoring, and keep your services alive.

What You Will Learn

  • Understand why monitoring matters and what it means to be proactive about outages
  • Build a health check endpoint (/api/health) that verifies database connectivity
  • Set up UptimeRobot for free monitoring with 5-minute check intervals
  • Use UptimeRobot pings to keep Render free-tier services awake
  • Configure alert notifications via email, SMS, and Slack
  • Create a public status page for transparency
  • Know what to monitor: uptime, response time, SSL expiry, and DNS
  • Understand application-level monitoring: error rates and slow endpoints
  • Implement structured logging with appropriate log levels
  • Follow incident response basics when the site goes down

Why Monitoring Matters

Your website is deployed. It is live. Users are visiting. Everything is working perfectly. And then one day, at 3 AM, the database connection expires. Or the SSL certificate fails to renew. Or a dependency update breaks a critical API route. Your site is down, and you do not know about it.

Without monitoring, you find out about outages from angry users, lost customers, or a panicked phone call from your client. By the time you hear about it, the site may have been down for hours. Every minute of downtime costs money, trust, and reputation.

Monitoring is the practice of automatically checking your application's health at regular intervals and alerting you the moment something goes wrong. With proper monitoring:

  • You know about outages within 5 minutes instead of 5 hours
  • You can diagnose problems from your phone with alert details
  • You have historical data showing when outages occurred and how long they lasted
  • Your clients see a professional status page instead of an unexplained outage
Analogy: Monitoring is like a smoke detector for your website. You could check every room for fire every 5 minutes yourself, or you could install a smoke detector that watches 24/7 and screams the instant something is wrong. The smoke detector does not prevent fires, but it gives you the earliest possible warning to respond.

Health Check Endpoints: The /api/health Pattern

A health check endpoint is an API route that reports whether your application is functioning correctly. External monitoring services ping this endpoint at regular intervals. If it responds with a success status, the application is healthy. If it fails to respond or returns an error, something is wrong.

What a Good Health Check Does

A health check should verify that the critical components your application depends on are working:

  • Database connectivity: Can the application reach the database and execute a query?
  • External services: Are critical APIs (like Supabase) responding?
  • Response time: Is the application responding within an acceptable time frame?

Building a Health Check Endpoint

// src/app/api/health/route.ts
import { NextResponse } from 'next/server';
import { createClient } from '@supabase/supabase-js';

export async function GET() {
  const startTime = Date.now();

  // Check 1: Are environment variables configured?
  const hasSupabaseUrl = !!process.env.NEXT_PUBLIC_SUPABASE_URL;
  const hasServiceKey = !!process.env.SUPABASE_SERVICE_ROLE_KEY;

  // Check 2: Can we connect to the database?
  let dbStatus = { connected: false, error: null as string | null };

  if (hasSupabaseUrl && hasServiceKey) {
    try {
      const supabase = createClient(
        process.env.NEXT_PUBLIC_SUPABASE_URL!,
        process.env.SUPABASE_SERVICE_ROLE_KEY!
      );

      // Execute a simple query to verify connectivity
      const { count, error } = await supabase
        .from('rs_customers')
        .select('*', { count: 'exact', head: true });

      if (error) {
        dbStatus = { connected: false, error: error.message };
      } else {
        dbStatus = { connected: true, error: null };
      }
    } catch (e) {
      dbStatus = {
        connected: false,
        error: e instanceof Error ? e.message : 'Unknown database error',
      };
    }
  } else {
    dbStatus = {
      connected: false,
      error: 'Database credentials not configured',
    };
  }

  // Calculate response time
  const responseTime = Date.now() - startTime;

  // Determine overall status
  const isHealthy = dbStatus.connected;

  // Return health report
  return NextResponse.json(
    {
      status: isHealthy ? 'healthy' : 'degraded',
      timestamp: new Date().toISOString(),
      responseTime: `${responseTime}ms`,
      checks: {
        database: dbStatus,
        environment: {
          supabaseUrl: hasSupabaseUrl,
          serviceKey: hasServiceKey,
        },
      },
    },
    { status: isHealthy ? 200 : 503 }
  );
}

Understanding the Response

When everything is working:

// GET /api/health -> 200 OK
{
  "status": "healthy",
  "timestamp": "2026-02-05T15:30:00.000Z",
  "responseTime": "45ms",
  "checks": {
    "database": { "connected": true, "error": null },
    "environment": { "supabaseUrl": true, "serviceKey": true }
  }
}

When the database is down:

// GET /api/health -> 503 Service Unavailable
{
  "status": "degraded",
  "timestamp": "2026-02-05T15:30:00.000Z",
  "responseTime": "5023ms",
  "checks": {
    "database": { "connected": false, "error": "Connection timed out" },
    "environment": { "supabaseUrl": true, "serviceKey": true }
  }
}

The 503 status code is important. Monitoring services check the HTTP status code, not the response body. A 200 means healthy; anything else means a problem.

Do Not Expose Sensitive Information Health check responses should never include actual credentials, connection strings, or internal IP addresses. Report whether something is working (boolean), not the details of how it connects. An attacker checking your health endpoint should learn nothing useful.

It reports whether the Supabase client and admin client are configured, whether GitHub integration is connected, and whether the database query succeeded. The response includes status (ok or degraded), a timestamp, and environment configuration flags.

UptimeRobot: Free Monitoring Made Simple

UptimeRobot is a free monitoring service that checks your website at regular intervals and alerts you when it goes down. The free tier includes up to 50 monitors with 5-minute check intervals -- more than enough for most projects.

Setting Up UptimeRobot

  1. Go to uptimerobot.com and create a free account
  2. Click "Add New Monitor"
  3. Configure the monitor:
    • Monitor Type: HTTP(s)
    • Friendly Name: My App - Production
    • URL: https://my-app.onrender.com/api/health
    • Monitoring Interval: 5 minutes
  4. Set up alert contacts (email is included free)
  5. Click "Create Monitor"

UptimeRobot will now check your health endpoint every 5 minutes. If the endpoint returns a non-200 status code or fails to respond within the timeout period, UptimeRobot marks the site as down and sends you an alert.

Keeping Free-Tier Services Awake

Remember from Lesson 48 that Render's free tier spins down your service after 15 minutes of inactivity. When a user visits after spin-down, they wait 30-60 seconds for the server to start up (a "cold start"). This is a terrible user experience.

UptimeRobot solves this problem accidentally (and beautifully). Because it pings your health endpoint every 5 minutes, the service never sits idle for 15 minutes. The monitoring request keeps the service awake 24/7.

UptimeRobot pings /api/health every 5 minutes | 0 min: Ping! (service active) 5 min: Ping! (service stays active) 10 min: Ping! (service stays active) 15 min: Ping! (would have spun down, but ping keeps it alive) 20 min: Ping! (still active!) ... 24/7 -- the service never spins down!

This means free monitoring has a dual benefit: it alerts you when things break and prevents the cold-start problem on Render's free tier.

Public Status Pages

A status page is a public webpage that shows the current health of your services. When your site has an outage, users can check the status page to see if you are aware of the problem and working on it. This builds trust and reduces "is the site down?" support tickets.

UptimeRobot includes a free status page feature:

  1. In UptimeRobot, go to "Status Pages"
  2. Click "Add Status Page"
  3. Select which monitors to display
  4. Customize the design and branding
  5. Publish the page (you get a URL like stats.uptimerobot.com/your-page)

The status page automatically shows:

  • Current status of each monitored service (up/down)
  • Uptime percentage over the last 30, 60, and 90 days
  • Recent incidents and their duration
  • Average response time

You can optionally use a custom domain for your status page (like status.computerstoreks.com) by adding a CNAME DNS record.

What to Monitor

Health check endpoints are the foundation, but comprehensive monitoring covers several dimensions:

1. Uptime (Is the Site Reachable?)

The most basic check: can a user reach your site? UptimeRobot handles this by pinging your URL every 5 minutes. If the ping fails (timeout, DNS error, HTTP error), the site is down.

2. Response Time (Is the Site Fast?)

A site can be "up" but unusably slow. Monitor response time to catch performance degradation before users notice. UptimeRobot logs response times for every check, and you can set alerts for responses that exceed a threshold (e.g., alert if response time exceeds 5 seconds).

3. SSL Certificate Expiry

If your SSL certificate expires, browsers will show a scary "Your connection is not private" warning. While Render auto-renews Let's Encrypt certificates, monitoring SSL expiry catches edge cases where renewal fails. UptimeRobot checks SSL expiry and alerts you when a certificate is within 30 days of expiring.

4. DNS Resolution

DNS converts your domain name (computerstoreks.com) into an IP address. If DNS fails, no one can reach your site even if the server is running perfectly. Monitoring DNS ensures that domain resolution is working correctly.

5. Application Health (Internal Checks)

Your health endpoint can check multiple internal systems:

  • Database: Can we query the database?
  • External APIs: Is RepairShopr/Supabase responding?
  • Email service: Is Resend configured and reachable?
  • Storage: Can we access file storage?
  • Memory/CPU: Are system resources within normal ranges?

Application-Level Monitoring

Uptime monitoring tells you "is the site reachable?" Application monitoring tells you "is the site working correctly?" These are different questions. A site can be reachable (health check passes) but still broken for specific users or specific features.

Error Rate Monitoring

Track how many API requests result in errors (4xx or 5xx status codes). A sudden spike in error rates indicates something is broken, even if the health check still passes.

// Example: logging errors in an API route
export async function POST(request: NextRequest) {
  try {
    const result = await processOrder(request);
    return NextResponse.json(result);
  } catch (error) {
    // Log the error with context for later analysis
    console.error('[ORDER_API]', {
      error: error instanceof Error ? error.message : 'Unknown error',
      timestamp: new Date().toISOString(),
      path: '/api/orders',
      method: 'POST',
    });

    return NextResponse.json(
      { error: 'Failed to process order' },
      { status: 500 }
    );
  }
}

Slow Endpoint Detection

Track response times for your API endpoints. If a normally 100ms endpoint starts taking 5 seconds, something has changed -- maybe a database query is missing an index, or an external API is throttling you.

// Example: timing API responses
export async function GET(request: NextRequest) {
  const startTime = Date.now();

  try {
    const data = await fetchData();
    const duration = Date.now() - startTime;

    // Log slow responses
    if (duration > 3000) {
      console.warn('[SLOW_RESPONSE]', {
        path: '/api/data',
        duration: `${duration}ms`,
        timestamp: new Date().toISOString(),
      });
    }

    return NextResponse.json(data);
  } catch (error) {
    return NextResponse.json({ error: 'Failed' }, { status: 500 });
  }
}

Structured Logging

Logs are the record of what your application is doing. When something goes wrong, logs are the first place you look for clues. Structured logging means writing logs in a consistent, machine-parseable format instead of random console.log strings.

Log Levels

Not all log messages are equally important. Log levels help you filter noise and focus on what matters:

Level When to Use Example
error Something broke and needs immediate attention Database connection failed, API key invalid
warn Something unexpected but not critical Slow query, deprecated feature used, retry succeeded
info Normal operations worth recording User logged in, order placed, email sent
debug Detailed information for troubleshooting Request payload, query parameters, intermediate values

Structured Log Format

// Instead of this (unstructured):
console.log('User signed in');
console.log('Error: ' + error.message);

// Do this (structured):
console.info(JSON.stringify({
  level: 'info',
  event: 'user_signin',
  userId: user.id,
  timestamp: new Date().toISOString(),
}));

console.error(JSON.stringify({
  level: 'error',
  event: 'database_error',
  error: error.message,
  table: 'rs_customers',
  operation: 'SELECT',
  timestamp: new Date().toISOString(),
}));

Structured logs are easier to search, filter, and analyze than plain text. When you have thousands of log lines, being able to filter by level: "error" or event: "database_error" saves enormous amounts of time.

Render's Log Viewer Render captures all console.log, console.error, and console.warn output from your application and displays it in the "Logs" tab of your service dashboard. You can filter, search, and download logs. For free-tier services, logs are retained for a limited period.

Incident Response: When the Site Goes Down

Even with monitoring and best practices, outages happen. What matters is how quickly and effectively you respond. Here is a basic incident response playbook:

Step 1: Acknowledge (0-5 minutes)

  • You receive an alert from UptimeRobot
  • Verify the outage is real (visit the site yourself, check health endpoint)
  • If you have a status page, update it: "Investigating an issue"

Step 2: Diagnose (5-15 minutes)

  • Check Render dashboard: Is the service running? Any failed deploys?
  • Check the health endpoint response: What specifically is failing?
  • Check Render logs: Are there error messages?
  • Check Supabase dashboard: Is the database healthy?
  • Check recent changes: Did someone push code recently? Did a deploy just finish?

Step 3: Fix (15 minutes - variable)

  • If caused by a bad deploy: roll back to the previous version in Render
  • If caused by an environment variable: fix the value in Render dashboard
  • If caused by database: check Supabase for issues
  • If caused by external service: check that service's status page

Step 4: Verify and Communicate (after fix)

  • Confirm the health endpoint returns 200
  • Test critical user flows (can users log in? can they submit forms?)
  • Update the status page: "Resolved"
  • Notify the client/team that the issue is fixed

Step 5: Post-Mortem (within 24 hours)

  • What happened? (Timeline of events)
  • Why did it happen? (Root cause)
  • How did we detect it? (Monitoring, user report)
  • How did we fix it? (Specific actions taken)
  • How do we prevent it from happening again? (Action items)
Do Not Panic Outages feel urgent, and they are. But panicking leads to mistakes that make things worse. Follow the playbook methodically. Most outages are caused by simple things: a bad deploy, an expired API key, or a misconfigured environment variable. Systematic diagnosis finds the answer faster than frantic guessing.

Exercises

  1. Build a health check: Create an /api/health endpoint in a Next.js project that checks at least two things: database connectivity and the presence of critical environment variables. Return appropriate JSON with status, timestamp, and response time. Return HTTP 200 when healthy and 503 when degraded.
  2. Set up UptimeRobot: Create a free UptimeRobot account and add a monitor for your deployed application (or any public website). Configure email alerts. Wait for the first check to confirm monitoring is active.
  3. Test the alerting: If you have a deployed application, temporarily break the health endpoint (return 503), push the change, and wait for UptimeRobot to alert you. Measure how long it takes from the break to the alert. Then fix it and observe the "back up" notification.
  4. Create structured logs: Add structured logging to an API route in your project. Log the request method, path, response status, and duration for every request. Then add specific error logging in the catch block.
  5. Write an incident playbook: For your deployed application, write a one-page incident response document that lists: (a) what to check first, (b) how to access Render and Supabase dashboards, (c) how to roll back a bad deploy, and (d) who to notify.
  6. Monitor research: Visit the status pages of three major services (GitHub, Supabase, and Render). Study how they communicate outages. Note what information they include, how they describe severity, and how they communicate resolution timelines.

Key Takeaways

  • Monitoring lets you know about outages before your users do, giving you time to fix problems before they escalate.
  • A health check endpoint (/api/health) verifies database connectivity and critical service availability, returning HTTP 200 when healthy and 503 when degraded.
  • UptimeRobot provides free monitoring with 5-minute intervals and email alerts. Its regular pings also keep Render free-tier services awake, eliminating cold starts.
  • Monitor uptime, response time, SSL certificate expiry, and DNS resolution as a minimum. Application-level monitoring (error rates, slow endpoints) provides deeper insight.
  • Use structured logging with consistent log levels (error, warn, info, debug) so logs are searchable and useful during incident investigation.
  • Public status pages build trust by showing users you are transparent about your service health.
  • Follow a structured incident response process: acknowledge, diagnose, fix, verify, post-mortem. Do not panic.
  • Health check responses should report status without exposing sensitive configuration details.
