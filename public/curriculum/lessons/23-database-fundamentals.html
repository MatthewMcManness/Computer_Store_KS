What Is a Database?

At its simplest, a database is an organized collection of data that a computer program can quickly store, retrieve, and manipulate. Almost every application you use daily — social media, banking, online shopping — depends on a database behind the scenes.

You have probably already used something similar: a spreadsheet. A spreadsheet stores data in rows and columns, lets you sort and filter, and even do calculations. So why not just use spreadsheets for everything?

Analogy: Spreadsheet vs. Database
Imagine you run a small repair shop (sound familiar?). You start tracking customers in a single Excel sheet. At first it works. But as the business grows, problems appear: duplicate customer names, ticket data mixed with payment data, no way to enforce rules like "every ticket must have a customer." A database is like upgrading from a single messy notebook to a well-organized filing cabinet with labeled drawers, folders, and cross-references — plus a librarian who enforces the rules for you.

Spreadsheet vs. Database — Side by Side

Feature Spreadsheet Database
Data validationManual, easy to bypassEnforced by the system (constraints)
Concurrent usersRisky — merge conflictsBuilt-in — handles thousands simultaneously
Data relationshipsCopy-paste between sheetsForeign keys link data automatically
Query powerFilters, VLOOKUPSQL — infinitely flexible
Data sizeSlows down past ~100K rowsHandles millions or billions of rows
SecurityFile-level permissionsRow-level security, roles, encryption
Backup/RecoverySave copies manuallyAutomated, point-in-time recovery

Relational Databases Explained

There are many kinds of databases (document stores, graph databases, key-value stores), but the most widely used type is the relational database. It stores data in tables (also called relations) that can be linked together through shared values.

The language you use to talk to a relational database is called SQL (Structured Query Language). The specific relational database system we use in this curriculum is PostgreSQL (often shortened to "Postgres") — one of the most powerful and popular open-source databases in the world. Supabase, which we will set up in Lesson 25, is built on top of PostgreSQL.

Core Vocabulary

Here is what a simple customers table might look like:

Each row is one customer. Each column stores a specific piece of information about that customer. The id column uniquely identifies every row — more on that shortly.

Data Types

Every column in a table has a data type that defines what kind of value it can hold. Think of it like labeling a filing cabinet drawer: the "Names" drawer only holds text, the "Prices" drawer only holds numbers. Here are the data types you will encounter most often in PostgreSQL:

Data Type What It Stores Example Values
TEXT Strings of any length 'Jane Smith', 'jane@example.com'
VARCHAR(n) Text with a maximum length of n characters 'draft' (max 20 chars)
INTEGER / BIGINT Whole numbers 42, 1000000, -7
NUMERIC / DECIMAL Exact decimal numbers (money, measurements) 29.99, 1234.56
BOOLEAN True or false true, false
TIMESTAMP WITH TIME ZONE A date and time with timezone info '2026-01-15T14:30:00Z'
UUID A universally unique identifier (128-bit) 'a1b2c3d4-e5f6-7890-abcd-ef1234567890'
JSONB Binary JSON — stores structured data inside a single column '{"cpu": "i7", "ram": "16GB"}'
SERIAL / BIGSERIAL Auto-incrementing integer (shortcut for ID columns) 1, 2, 3, ...
CSK Connection The Computer Store KS database uses many of these types. Blog post titles are VARCHAR(255), the status column uses a CHECK constraint to limit values to 'draft', 'published', or 'archived'. The assets_updated flag on customers is a BOOLEAN. Timestamps like created_at appear on virtually every table. The gallery stores computer specs as JSONB arrays.

Primary Keys

Every table needs a way to uniquely identify each row. This is the job of the primary key (PK). A primary key is a column (or combination of columns) where:

  • Every value is unique — no two rows can share the same PK value
  • The value is never null — every row must have a PK
Analogy: Think of a primary key like a Social Security number or a driver's license number. No two people share the same one, and you cannot leave it blank on official forms. It is the one piece of data that definitively identifies a specific record.

Auto-Increment IDs vs. UUIDs

There are two main strategies for generating primary keys:

Strategy 1: Auto-Increment (SERIAL)

The database assigns sequential integers: 1, 2, 3, 4, and so on. Simple and human-readable.

CREATE TABLE customers (
  id SERIAL PRIMARY KEY,   -- 1, 2, 3, 4...
  name TEXT NOT NULL,
  email TEXT NOT NULL
);
ProsCons
Easy to read and typePredictable — users can guess other IDs
Small storage sizeProblems with distributed systems
Natural orderingMerging data from multiple sources causes conflicts

Strategy 2: UUID (Universally Unique Identifier)

A 128-bit randomly generated identifier. Looks like: a1b2c3d4-e5f6-7890-abcd-ef1234567890. Virtually impossible to duplicate, even across different databases on different continents.

CREATE TABLE customers (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT NOT NULL,
  email TEXT NOT NULL
);
ProsCons
Globally unique — safe to merge dataHarder for humans to read
Unpredictable — more secure in URLsLarger storage size (16 bytes vs. 4)
Can be generated client-side before insertNot naturally ordered (slightly slower inserts on large tables)
CSK Connection The CSK database uses UUIDs as primary keys on most tables — blog_posts, blog_categories, blog_tags, gallery_computers, and more. Generated with DEFAULT uuid_generate_v4() or DEFAULT gen_random_uuid(). The businesses table, however, uses SERIAL (auto-increment) because it was designed as an internal lookup table.

Column Constraints

Constraints are rules the database enforces on your data. They are your safety net — they prevent bad data from ever entering the system.

NOT NULL

This column must have a value. You cannot leave it empty.

name TEXT NOT NULL,       -- Every customer must have a name
email TEXT NOT NULL        -- Every customer must have an email

UNIQUE

No two rows can have the same value in this column.

email TEXT NOT NULL UNIQUE,   -- No duplicate emails allowed
slug VARCHAR(255) NOT NULL UNIQUE  -- No duplicate URL slugs

DEFAULT

If no value is provided when inserting, use this default.

status VARCHAR(20) DEFAULT 'draft',       -- New posts start as drafts
created_at TIMESTAMPTZ DEFAULT NOW(),     -- Auto-set to current time
is_active BOOLEAN DEFAULT true            -- Items start as active

CHECK

The value must satisfy a condition.

status VARCHAR(20) CHECK (status IN ('draft', 'published', 'archived')),
price NUMERIC CHECK (price >= 0)     -- No negative prices

Combining Constraints

Constraints stack together to form powerful rules:

CREATE TABLE blog_posts (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  title VARCHAR(255) NOT NULL,                    -- Required, max 255 chars
  slug VARCHAR(255) NOT NULL UNIQUE,              -- Required, must be unique
  content TEXT NOT NULL,                           -- Required, unlimited length
  status VARCHAR(20) DEFAULT 'draft'
    CHECK (status IN ('draft', 'published', 'archived')),  -- Limited values
  published_at TIMESTAMPTZ,                       -- Optional (nullable)
  created_at TIMESTAMPTZ DEFAULT NOW(),           -- Auto-set
  updated_at TIMESTAMPTZ DEFAULT NOW()            -- Auto-set
);
Common Beginner Mistake Forgetting NOT NULL on important columns. If you leave a column nullable by accident, your application may crash when it tries to use a null value it did not expect. Always think: "Can this field ever legitimately be empty?" If not, add NOT NULL.

Foreign Keys — Linking Tables Together

So far, each table stands alone. But real data is interconnected: a customer creates tickets, tickets generate invoices, invoices record payments. Foreign keys are how we express these connections.

A foreign key is a column in one table that references the primary key of another table. It says: "This value must exist as a primary key in that other table."

Analogy: Think of a foreign key like a cross-reference in a filing cabinet. In the "Tickets" folder, each ticket has a field called "Customer Number." That number must match an actual customer in the "Customers" folder. If someone tries to file a ticket with a nonexistent customer number, the system rejects it.

Here is a concrete example with two tables:

-- The "parent" table
CREATE TABLE customers (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT NOT NULL,
  email TEXT NOT NULL UNIQUE
);

-- The "child" table
CREATE TABLE tickets (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  subject TEXT NOT NULL,
  description TEXT,
  customer_id UUID NOT NULL REFERENCES customers(id),  -- Foreign key!
  created_at TIMESTAMPTZ DEFAULT NOW()
);

The line customer_id UUID NOT NULL REFERENCES customers(id) creates a foreign key. This means:

  • Every ticket must have a customer_id (NOT NULL)
  • That customer_id must match an existing id in the customers table
  • You cannot delete a customer who still has tickets (unless you set up a cascade rule)
CUSTOMERS TABLE TICKETS TABLE +--------+-------------+ +--------+-----------------+-------------+ | id | name | | id | subject | customer_id | +--------+-------------+ +--------+-----------------+-------------+ | uuid-1 | Jane Smith | <----------- | uuid-A | Screen broken | uuid-1 | | uuid-2 | Bob Johnson | <--+ | uuid-B | Virus removal | uuid-1 | +--------+-------------+ +-------- | uuid-C | Slow computer | uuid-2 | +--------+-----------------+-------------+ customer_id in tickets REFERENCES id in customers

ON DELETE Behavior

What happens when you delete a parent row that has child rows pointing to it? PostgreSQL gives you options:

BehaviorWhat HappensWhen to Use
RESTRICT (default)Block the delete. Error.Prevent data loss (customers with tickets)
CASCADEDelete child rows tooTags on a deleted blog post
SET NULLSet the FK column to NULLOptional relationships (category deleted, post keeps existing)
SET DEFAULTSet the FK to its default valueRarely used
 
-- When a category is deleted, posts keep existing but lose their category
category_id UUID REFERENCES blog_categories(id) ON DELETE SET NULL

-- When a post is deleted, its tag links are removed too
post_id UUID REFERENCES blog_posts(id) ON DELETE CASCADE
CSK Connection In CSK's blog schema, blog_posts.category_id uses ON DELETE SET NULL — if a category is removed, posts are not deleted; they just lose their category. The blog_post_tags junction table uses ON DELETE CASCADE on both foreign keys — if a post or tag is deleted, the link rows are automatically removed.

Relationship Types

Tables can be related in three fundamental ways. Understanding these is key to designing good database schemas.

One-to-One (1:1)

One row in Table A relates to exactly one row in Table B, and vice versa. This is the rarest type.

Example: Each employee has exactly one user profile. Each user profile belongs to exactly one employee.

CREATE TABLE employees (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT NOT NULL,
  hire_date DATE NOT NULL
);

CREATE TABLE user_profiles (
  id UUID PRIMARY KEY REFERENCES employees(id),  -- Same ID as employee!
  role TEXT NOT NULL DEFAULT 'technician',
  avatar_url TEXT
);

Notice the user_profiles primary key directly references the employees primary key. This enforces the one-to-one relationship.

One-to-Many (1:N)

One row in Table A relates to many rows in Table B, but each row in B relates to only one in A. This is the most common relationship.

Example: One customer can have many tickets, but each ticket belongs to one customer.

ONE-TO-MANY: Customer --< Tickets CUSTOMER: Jane Smith | +-- Ticket: "Screen cracked" +-- Ticket: "Need data transfer" +-- Ticket: "Install antivirus" CUSTOMER: Bob Johnson | +-- Ticket: "Computer won't boot" 
-- One customer...
CREATE TABLE customers (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT NOT NULL
);

-- ...has many tickets
CREATE TABLE tickets (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  subject TEXT NOT NULL,
  customer_id UUID NOT NULL REFERENCES customers(id)
  -- The FK goes on the "many" side
);

Rule of thumb: The foreign key always goes on the "many" side of the relationship.

Many-to-Many (M:N)

One row in Table A can relate to many rows in Table B, and one row in Table B can relate to many rows in Table A.

Example: One blog post can have many tags, and one tag can be applied to many posts.

Relational databases cannot represent many-to-many directly with a single foreign key. Instead, we create a junction table (also called a "join table," "bridge table," or "linking table") that sits between the two tables.

MANY-TO-MANY: Posts >--< Tags (via junction table) blog_posts blog_post_tags blog_tags +--------+ +----------+----------+ +---------+ | id | | post_id | tag_id | | id | +--------+ +----------+----------+ +---------+ | post-1 | <------ | post-1 | tag-A | ------> | tag-A | "Hardware" | post-2 | <--+--- | post-1 | tag-B | --+---> | tag-B | "How-To" +--------+ | | post-2 | tag-A | -/ | tag-C | "Linux" +---- | post-2 | tag-C | --------+ +----------+----------+ Post 1 has tags: Hardware, How-To Post 2 has tags: Hardware, Linux Tag "Hardware" applies to: Post 1, Post 2 
CREATE TABLE blog_posts (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  title VARCHAR(255) NOT NULL
);

CREATE TABLE blog_tags (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name VARCHAR(50) NOT NULL UNIQUE
);

-- Junction table: connects posts to tags
CREATE TABLE blog_post_tags (
  post_id UUID REFERENCES blog_posts(id) ON DELETE CASCADE,
  tag_id UUID REFERENCES blog_tags(id) ON DELETE CASCADE,
  PRIMARY KEY (post_id, tag_id)  -- Composite primary key!
);

Notice the composite primary key: PRIMARY KEY (post_id, tag_id). This means the combination of post and tag must be unique — you cannot tag the same post with the same tag twice.

CSK Connection CSK's blog uses exactly this pattern. The blog_post_tags junction table connects blog_posts to blog_tags with a composite primary key and ON DELETE CASCADE on both foreign keys. This is a textbook many-to-many implementation.

Indexes — Making Queries Fast

As your tables grow from hundreds to thousands to millions of rows, queries can become slow. An index is a separate data structure that the database maintains to speed up searches on specific columns.

Analogy: Think of a textbook index at the back of a book. Instead of reading every page to find where "PostgreSQL" is mentioned, you flip to the index, find "PostgreSQL" alphabetically, and it tells you the exact pages. A database index works the same way — it lets the database jump directly to matching rows instead of scanning the entire table.

How It Works (Simplified)

The most common index type is a B-tree (balanced tree). Imagine the data sorted into a tree structure:

[M] / \ [D] [R] / \ / \ [A-C] [E-L] [N-Q] [S-Z] Looking up "Jones"? 1. Start at [M] -- "J" comes before "M", go left 2. At [D] -- "J" comes after "D", go right 3. At [E-L] -- found the leaf containing "Jones"! Only 3 steps instead of scanning all rows!

Without an index, the database performs a sequential scan (reading every single row). With an index, it performs an index scan (jumping directly to matching rows). The difference can be dramatic: milliseconds vs. seconds on large tables.

Creating an Index

-- Speed up lookups by slug
CREATE INDEX idx_blog_posts_slug ON blog_posts(slug);

-- Speed up filtering by status
CREATE INDEX idx_blog_posts_status ON blog_posts(status);

-- Speed up sorting by date (descending)
CREATE INDEX idx_blog_posts_published_at ON blog_posts(published_at DESC);

When to Create Indexes

Create an Index When...Skip the Index When...
A column is used frequently in WHERE clausesThe table has very few rows (under a few hundred)
A column is used in JOIN conditionsThe column has very few distinct values (e.g., a boolean)
A column is used in ORDER BYThe table is written to much more than read from
A column is used for unique lookups (slugs, emails)You already have too many indexes slowing down writes
Index Trade-off Indexes speed up reads but slow down writes (INSERT, UPDATE, DELETE), because the database must update the index every time data changes. Do not index every column — only the ones you actually query on.
CSK Connection The CSK blog schema creates six targeted indexes: on slug (for URL lookups), status (for filtering published posts), published_at (for sorting by date), category_id (for category pages), and indexes on category and tag slugs. Each one targets a specific query pattern used by the application.

Database Normalization

Normalization is the process of organizing your tables to reduce data duplication and prevent inconsistencies. There are several "normal forms" — think of them as levels of organization. For most applications, reaching Third Normal Form (3NF) is sufficient.

First Normal Form (1NF)

Rule: Each column contains only atomic (indivisible) values. No lists, no repeated groups.

Bad (violates 1NF):

| customer | phones | |----------|---------------------------| | Jane | 555-0101, 555-0102 | <-- Multiple values in one cell! | Bob | 555-0203 |

Good (satisfies 1NF):

CUSTOMERS PHONES | id | customer | | id | customer_id | phone | |----|----------| |----|-------------|----------| | 1 | Jane | | 1 | 1 | 555-0101 | | 2 | Bob | | 2 | 1 | 555-0102 | | 3 | 2 | 555-0203 |

Second Normal Form (2NF)

Rule: Already in 1NF, plus every non-key column depends on the entire primary key (relevant when you have composite primary keys).

Bad (violates 2NF):

ORDER_ITEMS (composite PK: order_id + product_id) | order_id | product_id | product_name | quantity | |----------|------------|--------------|----------| | 1 | 100 | Keyboard | 2 | | 1 | 200 | Mouse | 1 | | 2 | 100 | Keyboard | 5 | "product_name" depends only on product_id, NOT on the full key (order_id + product_id)

Good (satisfies 2NF): Move product_name to its own table.

PRODUCTS ORDER_ITEMS | product_id | product_name | | order_id | product_id | quantity | |------------|------------- | |----------|------------|----------| | 100 | Keyboard | | 1 | 100 | 2 | | 200 | Mouse | | 1 | 200 | 1 | | 2 | 100 | 5 |

Third Normal Form (3NF)

Rule: Already in 2NF, plus no non-key column depends on another non-key column (no transitive dependencies).

Bad (violates 3NF):

EMPLOYEES | id | name | department_id | department_name | |----|------|---------------|-----------------| | 1 | Jane | 10 | Engineering | | 2 | Bob | 10 | Engineering | <-- "Engineering" is duplicated! | 3 | Sue | 20 | Marketing | "department_name" depends on "department_id", NOT directly on the PK "id"

Good (satisfies 3NF): Create a departments table.

DEPARTMENTS EMPLOYEES | department_id | name | | id | name | department_id | |---------------|----------- | |----|------|---------------| | 10 | Engineering| | 1 | Jane | 10 | | 20 | Marketing | | 2 | Bob | 10 | | 3 | Sue | 20 |

Now "Engineering" is stored once. If the department name changes, you update one row instead of hundreds.

When Not to Normalize

Sometimes a little intentional duplication is acceptable for performance or simplicity. For example, storing a customer's name directly on a ticket (alongside the foreign key) can avoid an expensive JOIN when you just need to display a list. This is called denormalization and should be a deliberate choice, not an accident.

CSK Connection The CSK database is well-normalized. Categories are in their own blog_categories table rather than being strings repeated on every post. Tags are in blog_tags with a junction table. Businesses are extracted from customer business_name into a separate businesses table with a trigger that auto-links. The blog_posts table stores author_name directly (a small denormalization) because the blog does not have a separate authors table — a practical choice for a small team.

Putting It All Together — A Complete Example

Let us design a small schema for a computer repair shop. Notice how all the concepts we learned work together:

-- Customers table
CREATE TABLE customers (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),  -- UUID primary key
  name TEXT NOT NULL,                              -- Required
  email TEXT NOT NULL UNIQUE,                      -- Required, unique
  phone TEXT,                                      -- Optional
  is_active BOOLEAN DEFAULT true,                  -- Default value
  created_at TIMESTAMPTZ DEFAULT NOW()             -- Auto-timestamp
);

-- Tickets (one-to-many with customers)
CREATE TABLE tickets (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  subject TEXT NOT NULL,
  description TEXT,
  status VARCHAR(20) DEFAULT 'new'
    CHECK (status IN ('new', 'in_progress', 'resolved')),  -- CHECK constraint
  customer_id UUID NOT NULL REFERENCES customers(id),       -- Foreign key
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- Invoices (one-to-many with customers AND tickets)
CREATE TABLE invoices (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  amount NUMERIC NOT NULL CHECK (amount >= 0),              -- No negative amounts
  customer_id UUID NOT NULL REFERENCES customers(id),
  ticket_id UUID REFERENCES tickets(id) ON DELETE SET NULL, -- Optional link
  paid_at TIMESTAMPTZ,                                       -- NULL means unpaid
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- Indexes for common queries
CREATE INDEX idx_tickets_customer ON tickets(customer_id);
CREATE INDEX idx_tickets_status ON tickets(status);
CREATE INDEX idx_invoices_customer ON invoices(customer_id);

This schema demonstrates:

  • UUID primary keys on all three tables
  • NOT NULL constraints on required fields
  • UNIQUE constraint on email
  • DEFAULT values for status, is_active, and timestamps
  • CHECK constraints limiting status values and preventing negative amounts
  • Foreign keys linking tickets to customers and invoices to both
  • Indexes on columns used for filtering and joining
  • Normalization — each entity in its own table, no duplicated data

Key Takeaways

  • A database is organized, rule-enforced data storage — far more powerful than a spreadsheet for applications.
  • Tables hold data in rows (records) and columns (fields), each column with a defined data type.
  • Every table needs a primary key — UUIDs are preferred for web apps (globally unique, unpredictable).
  • Constraints (NOT NULL, UNIQUE, CHECK, DEFAULT) enforce data integrity at the database level.
  • Foreign keys link tables together and enforce referential integrity — the referenced row must exist.
  • Relationships come in three flavors: one-to-one, one-to-many (most common), and many-to-many (requires a junction table).
  • Indexes dramatically speed up reads but add overhead to writes — create them on columns you query frequently.
  • Normalization (1NF, 2NF, 3NF) eliminates duplication and keeps your data consistent.
