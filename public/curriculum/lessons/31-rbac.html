Role-Based Access Control (RBAC)

Designing and implementing a multi-role permission system for real business needs

Why Simple Admin/User Is Not Enough

Many tutorials teach a simple two-role system: users are either "admin" (can do everything) or "user" (can do very little). This works for a personal blog, but it falls apart quickly in a real business.

Consider a computer repair shop. The business has employees with very different job responsibilities:

  • The receptionist checks in customers, creates tickets, and answers the phone. They need access to customer data and the intake form, but they should not be able to change ticket statuses that only a technician understands.
  • The technician diagnoses and repairs computers. They need to update ticket statuses and add technical notes, but they should not manage employee accounts or view financial data.
  • The owner needs to see everything -- employee management, financial reports, customer data, and system settings.
  • The social media person writes blog posts. They need blog access but nothing else in the admin portal.

With only "admin" and "user," you would have to give the social media person full admin access just so they can write blog posts. That violates the principle of least privilege: every user should have only the minimum permissions needed to do their job.

Analogy: Think of a hospital. Doctors, nurses, lab technicians, and billing staff all need access to different parts of the hospital and different patient records. You would not give every employee the master key that opens every door. You give each person keys only to the rooms they need.

Designing Roles: Analyzing Business Needs

Before writing any code, you need to understand the business. Ask these questions:

  1. Who are the different types of users? List every distinct group.
  2. What does each group need to do? List their daily tasks.
  3. What should each group NOT be able to do? This is often more important.
  4. Is there a hierarchy? Do some roles inherit the abilities of others?
  5. Can someone hold multiple roles? Could a technician also be the social media manager?

Example: Computer Repair Shop Roles

After analyzing the business needs of a computer repair shop, you might design this role hierarchy:

BUSINESS ROLE HIERARCHY owner (Level 5) Everything | manager (Level 4) Employees + finances + everything below | lead_technician (Level 3) Lead tech features + everything below | technician (Level 2) Repairs + gallery + everything below | receptionist (Level 1) Intake, customers, tickets, invoices --- ADD-ON ROLES (can be combined with any business role) --- social_media Blog access (for non-managers) lead_developer Superuser (full system access, IT admin)

The hierarchy means each level automatically inherits all permissions from the levels below it. A manager can do everything a lead_technician can do, plus manage employees and finances. A lead_technician can do everything a technician can do, plus lead-specific features.

Role Level Key Capabilities
receptionist 1 Customer intake, view tickets, view customers, manage invoices
technician 2 Everything above + update ticket work, manage gallery, view devices
lead_technician 3 Everything above + lead tech dashboard, assign work
manager 4 Everything above + manage employees, view reports, blog access
owner 5 Everything above + system settings, billing, full admin
social_media Add-on Blog management only (combine with any business role)
lead_developer Add-on Full system access, IT superuser (bypasses all restrictions)

Multi-Role Users

In a small business, people wear many hats. The receptionist might also manage social media. A technician might be the lead developer who maintains the website. A single-role system forces you into awkward workarounds.

The solution is to store roles as an array. Each user can have one or more roles, and their effective permissions are the combination of all their roles:

// Single role (old, limited approach)
{ role: 'technician' }  // Can only be one thing

// Multi-role (flexible, real-world approach)
{ roles: ['technician', 'social_media'] }  // Technician who also writes blog posts
{ roles: ['receptionist'] }                 // Just a receptionist
{ roles: ['owner', 'lead_developer'] }      // Owner who also does IT

Rules for Multi-Role Assignment

  • Every user must have at least one role.
  • The customer role cannot be combined with employee roles (you are either a customer or an employee, never both).
  • Add-on roles (social_media, lead_developer) can be combined with any business role.
  • Having multiple business roles is allowed but usually unnecessary because of the hierarchy (a manager already has all technician permissions).
CSK Connection CSK stores roles as a PostgreSQL TEXT[] (text array) in the user_profiles table. The roles column can contain any combination like ['technician', 'social_media'] or ['owner', 'lead_developer']. A validateRoles() function in role-helpers.ts enforces the rules: at least one role required, customer cannot be mixed with employee roles.

The user_profiles Table

Supabase Auth handles the core authentication (email, password, sessions), but your application needs additional data about each user -- their roles, display name, location, and business-specific IDs. This data lives in a user_profiles table that links to the Supabase auth user:

CREATE TABLE user_profiles (
  id UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  email TEXT NOT NULL,
  full_name TEXT,
  role TEXT DEFAULT 'customer',       -- Legacy single-role field
  roles TEXT[] DEFAULT '{customer}',  -- Multi-role array (primary)
  location_id UUID REFERENCES locations(id),
  repairshopr_user_id INTEGER,       -- Link to legacy system
  repairshopr_customer_id INTEGER,
  created_at TIMESTAMPTZ DEFAULT now(),
  updated_at TIMESTAMPTZ DEFAULT now()
);

-- Enable Row-Level Security
ALTER TABLE user_profiles ENABLE ROW LEVEL SECURITY;

-- Users can read their own profile
CREATE POLICY "Users can read own profile"
  ON user_profiles FOR SELECT
  USING (auth.uid() = id);

-- Only admins can update profiles
CREATE POLICY "Admins can update profiles"
  ON user_profiles FOR UPDATE
  USING (
    EXISTS (
      SELECT 1 FROM user_profiles
      WHERE id = auth.uid()
      AND 'owner' = ANY(roles)
    )
  );

Key design decisions:

  • The id column is the same UUID as the Supabase auth user, linked with a foreign key. When the auth user is deleted, the profile is automatically deleted too (ON DELETE CASCADE).
  • Both role (single string) and roles (array) exist for backward compatibility during migration. New code always reads from roles.
  • RLS policies ensure users can only see their own profile, while admins can modify any profile.

Role Expansion with Inheritance

Because of the hierarchy, a manager inherits all permissions from lead_technician, technician, and receptionist. We need a function that "expands" a user's roles to include all inherited roles:

// Define which roles each business role inherits
const ROLE_HIERARCHY: Record<string, string[]> = {
  owner:           ['manager', 'lead_technician', 'technician', 'receptionist'],
  manager:         ['lead_technician', 'technician', 'receptionist'],
  lead_technician: ['technician', 'receptionist'],
  technician:      ['receptionist'],
  receptionist:    [],
};

/**
 * Expand a set of roles to include all inherited roles.
 * Example: expandRoles(['manager']) returns
 *   ['manager', 'lead_technician', 'technician', 'receptionist']
 */
function expandRoles(roles: string[]): string[] {
  const expanded = new Set<string>(roles);

  for (const role of roles) {
    const inherited = ROLE_HIERARCHY[role];
    if (inherited) {
      for (const r of inherited) {
        expanded.add(r);
      }
    }
  }

  return Array.from(expanded);
}

// Usage:
expandRoles(['technician'])
// ['technician', 'receptionist']

expandRoles(['manager', 'social_media'])
// ['manager', 'lead_technician', 'technician', 'receptionist', 'social_media']

Add-on roles like social_media and lead_developer are not part of the hierarchy -- they do not inherit from or grant other roles. They simply add specific permissions on top of whatever business role the user has.

Building a Permission System

Roles define who you are. Permissions define what you can do. The mapping between roles and permissions is where the real power of RBAC lives.

Defining Permissions

// Each permission is a specific capability
type Permission =
  | 'view_reception_dashboard'
  | 'manage_intake'
  | 'view_customers'
  | 'manage_customers'
  | 'view_tickets'
  | 'manage_tickets'
  | 'view_tech_dashboard'
  | 'manage_ticket_work'
  | 'view_gallery'
  | 'manage_gallery'
  | 'view_employees'
  | 'manage_employees'
  | 'view_blog'
  | 'manage_blog'
  | 'view_admin_dashboard'
  | 'manage_system_settings';

Checking Permissions

/**
 * Get all permissions for a user based on their roles.
 * Expands roles with inheritance first, then collects all permissions.
 */
function getEffectivePermissions(roles: string[]): Permission[] {
  const permissions = new Set<Permission>();
  const expandedRoles = expandRoles(roles);

  for (const role of expandedRoles) {
    const rolePerms = ROLE_PERMISSIONS[role];
    if (rolePerms) {
      for (const perm of rolePerms) {
        permissions.add(perm);
      }
    }
  }

  return Array.from(permissions);
}

/**
 * Check if a user has a specific permission.
 */
function hasPermission(roles: string[], permission: Permission): boolean {
  const permissions = getEffectivePermissions(roles);
  return permissions.includes(permission);
}

/**
 * Check if a user has ANY of the required permissions.
 */
function hasAnyPermission(roles: string[], required: Permission[]): boolean {
  const permissions = getEffectivePermissions(roles);
  return required.some(p => permissions.includes(p));
}

// Usage:
hasPermission(['technician'], 'manage_gallery')     // true
hasPermission(['receptionist'], 'manage_gallery')    // false
hasPermission(['manager'], 'view_tickets')           // true (inherited)

Route-to-Role Mapping

Now we connect routes (URLs) to the permissions required to access them:

const ROUTE_PERMISSIONS: Record<string, Permission[]> = {
  // Reception section
  '/admin':              ['view_reception_dashboard', 'view_tech_dashboard',
                          'view_lead_tech_dashboard', 'view_admin_dashboard'],
  '/admin/reception':    ['view_reception_dashboard'],
  '/admin/intake':       ['manage_intake'],
  '/admin/customers':    ['view_customers'],
  '/admin/tickets':      ['view_tickets'],
  '/admin/invoices':     ['view_invoices'],

  // Technician section
  '/admin/tech':         ['view_tech_dashboard'],
  '/admin/gallery':      ['view_gallery'],
  '/admin/devices':      ['view_devices'],

  // Lead technician section
  '/admin/lead-tech':    ['view_lead_tech_dashboard'],

  // Management section
  '/admin/employees':    ['view_employees'],
  '/admin/blog':         ['view_blog'],
  '/admin/reports':      ['view_reports'],

  '/admin/settings':     ['manage_system_settings'],
};

Implementing Route Checks in Middleware

function canAccessRoute(roles: string[], pathname: string): boolean {
  // Lead developer can access everything
  if (roles.includes('lead_developer')) {
    return true;
  }

  // Look up required permissions for this route
  const requiredPermissions = ROUTE_PERMISSIONS[pathname];
  if (requiredPermissions) {
    return hasAnyPermission(roles, requiredPermissions);
  }

  // Check for prefix matches (e.g., /admin/blog/new matches /admin/blog)
  for (const [route, permissions] of Object.entries(ROUTE_PERMISSIONS)) {
    if (pathname.startsWith(route) && route !== '/admin') {
      return hasAnyPermission(roles, permissions);
    }
  }

  // Unknown route -- deny by default for security
  return false;
}
Default Deny: When a route is not listed in the permissions map, it is denied by default. This is the safest approach because new routes are automatically protected. The alternative (default allow) means any new page you create is accidentally public until you remember to add permissions.

Client-Side Role Checks for UI Elements

While the server enforces authorization (preventing unauthorized API calls and page access), the client should also hide UI elements that the user cannot use. This is not for security -- it is for user experience. Showing a "Manage Employees" button to a receptionist who will just get an error is confusing.

// components/admin/admin-sidebar.tsx
'use client';

import { useSession } from '@/hooks/useSession';
import { hasAnyPermission } from '@/lib/role-helpers';

export function AdminSidebar() {
  const { user } = useSession();
  const roles = user?.roles || [];

  return (
    <nav>
      {/* Everyone with reception access sees this */}
      {hasAnyPermission(roles, ['view_reception_dashboard']) && (
        <SidebarSection title="Reception">
          <SidebarLink href="/admin/reception">Dashboard</SidebarLink>
          <SidebarLink href="/admin/customers">Customers</SidebarLink>
          <SidebarLink href="/admin/tickets">Tickets</SidebarLink>
        </SidebarSection>
      )}

      {/* Only technicians and above see this */}
      {hasAnyPermission(roles, ['view_tech_dashboard']) && (
        <SidebarSection title="Technician">
          <SidebarLink href="/admin/tech">Tech Dashboard</SidebarLink>
          <SidebarLink href="/admin/gallery">Gallery</SidebarLink>
        </SidebarSection>
      )}

      {/* Only managers and above see this */}
      {hasAnyPermission(roles, ['view_employees']) && (
        <SidebarSection title="Management">
          <SidebarLink href="/admin/employees">Employees</SidebarLink>
        </SidebarSection>
      )}

      {/* Blog access: social_media role OR manager+ */}
      {hasAnyPermission(roles, ['view_blog']) && (
        <SidebarSection title="Content">
          <SidebarLink href="/admin/blog">Blog Posts</SidebarLink>
        </SidebarSection>
      )}
    </nav>
  );
}
Client-side checks are NOT security. A determined user can modify the JavaScript in their browser to show hidden elements. Always enforce permissions on the server (middleware and API routes). Client-side checks are purely for a cleaner user experience.

Role Helper Utilities

To keep role checks consistent across your codebase, build a utility module with helper functions:

// lib/role-helpers.ts

/** Check if user has any of the target roles (exact match) */
export function hasAnyRole(userRoles: string[], targetRoles: string[]): boolean {
  return targetRoles.some(role => userRoles.includes(role));
}

/** Check if user is a customer (only the customer role) */
export function isCustomer(roles: string[]): boolean {
  return roles.includes('customer') && roles.length === 1;
}

/** Check if user is any type of employee */
export function isEmployee(roles: string[]): boolean {
  const employeeRoles = [
    'receptionist', 'technician', 'lead_technician',
    'manager', 'owner', 'social_media', 'lead_developer',
  ];
  return roles.some(role => employeeRoles.includes(role));
}

/** Check if user is management level (manager, owner, or lead_developer) */
export function isManagement(roles: string[]): boolean {
  return hasAnyRole(roles, ['manager', 'owner', 'lead_developer']);
}

/** Check if user is the lead developer (superuser) */
export function isLeadDeveloper(roles: string[]): boolean {
  return roles.includes('lead_developer');
}

/** Check if user has blog access */
export function hasBlogAccess(roles: string[]): boolean {
  return hasAnyRole(roles, ['social_media', 'manager', 'owner', 'lead_developer']);
}

/** Check if user can manage employees */
export function canManageEmployees(roles: string[]): boolean {
  return hasAnyRole(roles, ['manager', 'owner', 'lead_developer']);
}

/** Get the default dashboard for a user based on their highest role */
export function getDefaultDashboard(roles: string[]): string {
  if (hasAnyRole(roles, ['lead_developer', 'owner', 'manager'])) {
    return '/admin';
  }
  if (roles.includes('lead_technician')) return '/admin/lead-tech';
  if (roles.includes('technician')) return '/admin/tech';
  if (roles.includes('receptionist')) return '/admin/reception';
  return '/admin';
}

/** Validate that a roles array is valid */
export function validateRoles(roles: string[]): { valid: boolean; error?: string } {
  if (!roles || roles.length === 0) {
    return { valid: false, error: 'At least one role is required' };
  }

  const hasCustomer = roles.includes('customer');
  const hasEmployee = roles.some(r =>
    ['receptionist','technician','lead_technician','manager','owner',
     'social_media','lead_developer'].includes(r)
  );

  if (hasCustomer && hasEmployee) {
    return { valid: false, error: 'Customer role cannot be combined with employee roles' };
  }

  return { valid: true };
}
CSK Connection CSK's role-helpers.ts contains all of these functions plus additional ones like expandRoles(), getEffectivePermissions(), canAccessRoute(), and getFilteredSidebar(). The roles type system is defined in types/roles.ts with the full hierarchy of 5 business roles (receptionist through owner) plus 2 add-on roles (social_media, lead_developer). The middleware uses canAccessRoute() for permission-based route protection, and the sidebar component uses getFilteredSidebar() to show only relevant navigation items.

Testing RBAC

RBAC is one of the most critical systems to test thoroughly. A bug here means either users cannot do their jobs (too restrictive) or they can access things they should not (too permissive).

What to Test

  1. Each role can access their allowed routes: A technician can access /admin/tech and /admin/gallery.
  2. Each role CANNOT access restricted routes: A receptionist cannot access /admin/employees.
  3. Role inheritance works: A manager can access technician routes without explicitly having the technician role.
  4. Multi-role combinations work: A ['receptionist', 'social_media'] user can access both reception and blog.
  5. Lead developer bypasses all restrictions: The superuser can access everything.
  6. Unauthenticated users are redirected to login.
  7. Customers cannot access admin routes.

Example Test Cases

// role-helpers.test.ts
describe('canAccessRoute', () => {
  test('receptionist can access reception dashboard', () => {
    expect(canAccessRoute(['receptionist'], '/admin/reception')).toBe(true);
  });

  test('receptionist cannot access employee management', () => {
    expect(canAccessRoute(['receptionist'], '/admin/employees')).toBe(false);
  });

  test('manager inherits technician permissions', () => {
    expect(canAccessRoute(['manager'], '/admin/gallery')).toBe(true);
  });

  test('social_media add-on grants blog access', () => {
    expect(canAccessRoute(['receptionist', 'social_media'], '/admin/blog')).toBe(true);
  });

  test('lead_developer can access everything', () => {
    expect(canAccessRoute(['lead_developer'], '/admin/settings')).toBe(true);
    expect(canAccessRoute(['lead_developer'], '/admin/employees')).toBe(true);
    expect(canAccessRoute(['lead_developer'], '/admin/anything')).toBe(true);
  });

  test('customer cannot access admin routes', () => {
    expect(canAccessRoute(['customer'], '/admin')).toBe(false);
  });
});

Key Takeaways

  • Simple admin/user roles do not work for real businesses. RBAC lets you model the actual organizational hierarchy.
  • Design roles by analyzing who does what in the business, then apply the principle of least privilege.
  • Store roles as an array -- real people often need multiple roles (e.g., technician + social media).
  • Role hierarchy with inheritance reduces redundancy: a manager automatically gets all technician permissions.
  • Permissions are the bridge between roles and features: roles grant permissions, permissions gate features.
  • Route-to-permission mapping in middleware enforces authorization on every request.
  • Default to deny: unknown routes should be blocked, not allowed.
  • Client-side role checks are for UX only. Server-side checks are the actual security.
  • Test every role against every route to catch both "too restrictive" and "too permissive" bugs.
