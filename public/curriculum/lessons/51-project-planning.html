Phase 12: Capstone — Putting It All Together

Project Planning & Architecture

Before you write a single line of code, learn how to gather requirements, design architecture, and scaffold a project that is set up for success from day one.

What You Will Learn

  • Interview a client to extract real business requirements and translate them into technical specifications
  • Create a sitemap diagram that defines every page and its relationships
  • Map user flows for different types of users (customers, admins, employees)
  • Build low-fidelity wireframes before writing any code
  • Design a database schema that maps requirements to tables, columns, and relationships
  • Evaluate third-party services using structured criteria (cost, documentation, reliability)
  • Make informed tech stack decisions, including when Next.js is the right choice and when it is not
  • Scaffold a complete project with create-next-app, TypeScript, Tailwind, and Supabase
  • Set up environment variables, Git, documentation, and directory structure from the start

Why Planning Matters More Than Coding

You have spent fifty lessons learning HTML, CSS, JavaScript, React, Next.js, databases, authentication, APIs, integrations, deployment, and more. You now have every individual skill needed to build a production website. But here is the truth that separates junior developers from professionals: the hardest part of building software is not writing code — it is deciding what to build and how to build it.

A developer who jumps straight into coding without a plan will inevitably:

  • Build features the client never asked for (and miss features they need)
  • Redesign the database three times because the initial schema did not account for real requirements
  • Refactor the file structure halfway through because it became unmanageable
  • Choose a third-party service that turns out to be too expensive or poorly documented
  • Deliver a project late because "quick fixes" compound into days of rework

Professional developers spend 20 to 40 percent of their time planning before writing a single line of code. This lesson teaches you that planning process from start to finish, using a realistic scenario: building a business website for a local computer repair shop.

Analogy: You would never start building a house by nailing boards together and hoping it turns into a kitchen. You start with blueprints, permits, material lists, and a construction schedule. Software works the same way. The planning phase is your blueprint.

Step 1: Interviewing the Client

Every project starts with a conversation. Your client has a business problem, and they are hiring you to solve it with technology. But most clients do not think in terms of "API routes" or "database schemas" — they think in terms of their business. Your job is to ask the right questions, listen carefully, and translate their answers into technical requirements.

The Questions to Ask

Here is a structured interview framework. These questions work for virtually any small business website project:

Business Understanding

Question Why You Ask It
What does your business do? Understand the domain, vocabulary, and customer base
Who are your customers? Define the target audience for the public site
What problems are you solving for customers? Identify what content and services to highlight
What services or products do you offer? Determine the number of service/product pages needed
Who are your competitors? What do their websites do well? Understand industry expectations and find opportunities
Do you have a logo, brand colors, or existing marketing materials? Determine if you need to create a visual identity or match one

Website Goals

Question Why You Ask It
What is the primary goal of the website? Focus the design around the main conversion action
Do you need a contact form, phone number display, or both? Plan the contact system and email integration
Do you want a blog or news section? Determine if you need a content management system
Do you need an admin dashboard for employees? Scope the authentication and admin portal work
Do you have existing software (CRM, inventory, POS)? Identify integration requirements
Do you need e-commerce (selling online)? Determines whether you need payment processing

Technical and Operational

Question Why You Ask It
Do you already have a domain name? Plan DNS configuration and SSL
How many employees need to access the admin area? Scope authentication, roles, and permissions
Will you update the website content yourself, or do you need us to? Determine how user-friendly the CMS needs to be
What is your budget? Determines free-tier vs. paid service choices
What is your timeline? Helps prioritize features and plan phases
CSK Connection When planning Computer Store KS, these exact questions were asked. The answers shaped every architectural decision: the client needed a public website showcasing 11 services, a blog for SEO, a gallery of refurbished computers for sale, a contact form, and an admin portal for employees to manage tickets, customers, blog posts, and gallery inventory. They already used RepairShopr as their CRM, which led to the integration requirements. The budget dictated using free-tier services (Supabase, Render free plan, Resend free tier).

Step 2: Defining the Page Structure (Sitemap)

A sitemap is a visual diagram showing every page on the website and how they connect. It is the "table of contents" for your project. Creating a sitemap before coding ensures you know exactly how many pages to build and how they relate to each other.

How to Create a Sitemap

Start by listing every page, then organize them into a hierarchy. You can draw this on paper, a whiteboard, or use free tools like Figma, draw.io, or even a text-based diagram:

                        Homepage (/)
                            |
        +--------+----------+----------+---------+--------+
        |        |          |          |         |        |
     About    Services    Blog      Gallery   Contact  Reviews
    (/about)  (/services) (/blog)   (/gallery) (/contact) (/reviews)
                 |          |
    +------------+---+      +--- /blog/[slug]
    |    |    |      |           (individual posts)
  /data  /os  /custom ...
  (11 service detail pages)


                     Admin Portal (/admin)
                            |
        +--------+----------+----------+---------+--------+
        |        |          |          |         |        |
    Dashboard  Customers  Tickets    Gallery    Blog   Employees
    (/admin)   (/admin/   (/admin/   (/admin/  (/admin/ (/admin/
               customers) tickets)   gallery)  blog)    employees)
                            |          |         |
                      /admin/     /admin/    /admin/
                      tickets/    gallery/   blog/new
                      [id]        new        /admin/
                                  /admin/    blog/[id]
                                  gallery/
                                  [id]

This diagram tells you:

  • The public site has approximately 20 pages (homepage, about, services hub, 11 service detail pages, blog listing, blog post template, gallery, contact, reviews)
  • The admin portal has approximately 12 pages (dashboard, customers, tickets list, ticket detail, gallery list, gallery new/edit, blog list, blog new/edit, employees)
  • Two dynamic route patterns: [slug] for blog posts and [id] for ticket/gallery detail pages
  • Two distinct layout groups: public pages (with header and footer) and admin pages (with sidebar)
Tip: Number your pages. If you count more than 30 pages for an initial launch, consider phasing the project. Build the essential pages first (homepage, services, contact) and add features like blog and gallery in a second phase.

Step 3: Mapping User Flows

A user flow is the path a specific type of user takes through your website to accomplish a goal. Different users have different goals, and your website needs to support all of them.

Identify Your User Types

For a computer repair shop website, there are three main user types:

User Type Primary Goals Key Pages
Customer (potential) Learn about services, get contact info, request help Homepage, Services, Contact
Customer (returning) Check repair status, browse gallery, read blog Blog, Gallery, Reviews
Employee Manage tickets, update customers, add blog/gallery Admin dashboard, Tickets, Blog editor

Diagramming a User Flow

        |

  business owner         "We'll be in touch!"

And here is the employee flow for managing a repair ticket:

EMPLOYEE FLOW: "Update a repair ticket"

Login Page (/admin/login)
        |
        v
  Dashboard (sees recent activity, call-customer alerts)
        |

User flows help you identify:

  • Critical paths — the most important journeys that must work flawlessly
  • Call-to-action placement — where to place buttons that guide users forward
  • Edge cases — what happens if a form fails? If a page is not found?
  • Required features — each step in the flow becomes a feature to build
Analogy: User flows are like driving directions. You do not just tell someone the destination — you map out every turn, every highway exit, and every landmark along the way. Without directions, your users wander aimlessly and leave.

Step 5: Database Schema Design

Now that you know what the website needs to do, you can design the database. The schema should flow directly from your requirements document. For each feature that stores data, ask: "What tables do I need? What columns? What relationships?"

Mapping Requirements to Tables

Requirement Table(s) Needed Key Columns
Blog system blog_posts, blog_categories, blog_tags, blog_post_tags title, slug, content, status, category_id, created_at
Gallery / Inventory gallery_items name, type, specs, price, sale_price, images, status
Contact form submissions (none — send email, do not store) N/A (or optional contact_submissions for logging)
Employee authentication user_profiles email, name, role, created_at
Customer management customers name, email, phone, business_name, notes
Ticket system tickets, ticket_comments, ticket_status_overrides subject, description, status, customer_id, assigned_to

Schema Diagram

+---------------+       +------------------+      +-------------+
| id (PK)       |<------| id (PK)          |      | id (PK)     |
| name           |       | title            |      | name        |
| slug           |       | slug             |      | slug        |
+---------------+       | content          |      +-------------+
                         | excerpt          |           |
                         | category_id (FK) |     blog_post_tags
                         | status           |    +----------------+
                         | featured_image   |    | post_id (FK)   |
                         | created_at       |    | tag_id  (FK)   |
                         | updated_at       |    +----------------+
                         +------------------+
                               |
                               | (one post has many tags
                               |  via junction table)

customers                tickets                  ticket_comments
+---------------+       +------------------+      +-----------------+
| id (PK)       |<------| id (PK)          |      | id (PK)         |
| name           |       | subject          |      | ticket_id (FK)  |
| email          |       | description      |      | body            |
| phone          |       | status           |      | is_private      |
| business_name  |       | customer_id (FK) |      | created_at      |
+---------------+       | assigned_to      |      +-----------------+
                         | created_at       |
                         +------------------+

Schema Design Principles

  • Every table needs a primary key — Use id with auto-incrementing integers or UUIDs
  • Add timestamps — Include created_at and updated_at on every table
  • Use foreign keys — Link related tables with explicit foreign key constraints
  • Normalize first — Do not store categories as comma-separated strings; use separate tables
  • Plan for RLS — Think about who should access what rows (this shapes your policy design)
  • Start small — You can always add columns later; removing them is harder
CSK Connection The CSK database schema evolved directly from this process. The blog required four tables (posts, categories, tags, junction table). The ticket system needed status overrides because RepairShopr's built-in statuses did not match the shop's workflow. The devices table was added later when the shop wanted per-device tracking — proving that requirements evolve, and good schema design accommodates change.

Step 6: Choosing Third-Party Services

Every modern web project relies on third-party services for things like databases, authentication, email, image storage, and hosting. Choosing the wrong service can cost you thousands of dollars or force a painful migration later. Here is a structured evaluation framework:

Evaluation Criteria

Criterion Questions to Ask
Cost Is there a free tier? What are the limits? When does pricing jump? Is it per-user, per-request, or flat-rate?
Documentation Is the documentation clear and complete? Are there code examples in your language? Is there a quick-start guide?
Reliability What is the uptime guarantee (SLA)? Does the service have a public status page? How do they handle outages?
Developer Experience Is the SDK well-maintained? How easy is integration? Is there a community for support?
Vendor Lock-in Can you export your data? How hard is it to switch to an alternative? Does the service use standard protocols?
Scalability Will it handle growth? Can you upgrade seamlessly? Are there rate limits that could block you?

CSK Service Evaluation Example

Need Chosen Service Why Alternatives Considered
Database Supabase (free tier) PostgreSQL, generous free tier, built-in auth, real-time, excellent docs PlanetScale, Neon, Firebase
Hosting Render (free tier) Free web services, auto-deploy from Git, custom domains, render.yaml Vercel, Railway, Fly.io
Email Resend (free tier) 100 emails/day free, simple API, React email templates SendGrid, Mailgun, Postmark
Monitoring UptimeRobot (free tier) 50 free monitors, 5-min intervals, keeps Render awake Better Uptime, Pingdom
Image Storage Supabase Storage Already using Supabase, integrated, 1GB free Cloudinary, AWS S3, GitHub API
Budget Warning: Always calculate the worst-case monthly cost before committing to a service. Free tiers have limits. Know exactly when you would start paying and how much. For CSK, the entire stack runs on free tiers with the exception of the Render Professional workspace at $19/month (needed for unlimited custom domains).

Step 7: Tech Stack Decisions

Choosing a tech stack is one of the most consequential decisions in a project. The stack you choose determines what is easy, what is hard, and what is impossible.

When Next.js Is the Right Choice

  • You need a mix of static pages (marketing, about) and dynamic pages (dashboard, user-generated content)
  • SEO matters (server-side rendering gives search engines full HTML)
  • You want both frontend and backend in one project (API routes)
  • You are building a content-driven site (blog, services, portfolio)
  • You need fast page loads (automatic code splitting, image optimization)
  • You want to use React (the largest ecosystem of UI components)

When Next.js Might NOT Be the Right Choice

Scenario Better Alternative Reason
Simple static site with no interactivity Astro, Hugo, plain HTML/CSS No JavaScript framework needed; simpler and faster
Heavy real-time application (chat, collaboration) SvelteKit, Remix, or dedicated WebSocket backend Next.js is request/response focused, not event-stream focused
Mobile app with API backend Express.js, Fastify, or Go for the API; React Native for mobile Next.js includes frontend rendering you do not need
WordPress-style CMS for non-technical users WordPress, Wix, Squarespace Client needs to edit content without touching code
Extremely high-performance, latency-critical API Go, Rust, Elixir Node.js/Next.js adds overhead compared to compiled languages

For our computer repair shop project, Next.js is an excellent fit. We need a mix of static marketing pages and dynamic admin features, SEO is critical for local search, and a single project housing both frontend and API keeps the architecture simple.

Principle: Choose boring technology. The best tech stack is not the newest or trendiest — it is the one you know well, that has strong documentation, a large community, and a proven track record. Next.js, TypeScript, Tailwind, PostgreSQL, and Node.js are "boring" in the best sense: they are reliable, well-documented, and battle-tested.

Step 8: Project Scaffolding

Now it is time to create the project. This is where planning turns into a tangible codebase.

Creating the Next.js Project

npx create-next-app@latest computer-store-ks

When prompted, select these options:

Would you like to use TypeScript?             Yes
Would you like to use ESLint?                  Yes
Would you like to use Tailwind CSS?            Yes
Would you like your code inside a `src/` directory?  Yes
Would you like to use App Router?              Yes
Would you like to use Turbopack for next dev?  Yes
Would you like to customize the import alias?  No (keep @/*)

Setting Up Supabase

  1. Go to supabase.com and create a free account
  2. Click "New Project" and choose a name and region
  3. Copy your project URL and API keys from the Settings → API page
  4. Install the Supabase client library: 
    cd computer-store-ks
npm install @supabase/supabase-js
  5. Create the Supabase client utility: 
    // src/lib/supabase.ts
import { createClient } from '@supabase/supabase-js';

const supabaseUrl = process.env.NEXT_PUBLIC_SUPABASE_URL!;
const supabaseAnonKey = process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!;

export const supabase = createClient(supabaseUrl, supabaseAnonKey);

Creating .env.example

Every project needs an .env.example file that documents all required environment variables without revealing actual values:

# .env.example
# Copy this file to .env.local and fill in the values

# ============================================
# Supabase - Database and Authentication
# ============================================
# Get these from: https://supabase.com/dashboard/project/YOUR_PROJECT/settings/api
NEXT_PUBLIC_SUPABASE_URL=https://your-project-id.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=your-anon-key-here
SUPABASE_SERVICE_ROLE_KEY=your-service-role-key-here

# ============================================
# Email - Contact Form Notifications
# ============================================
# Get these from: https://resend.com/api-keys
RESEND_API_KEY=re_your-api-key-here
NOTIFICATION_EMAIL=owner@yourdomain.com

# ============================================
# Authentication
# ============================================
# Generate with: openssl rand -hex 32
SESSION_SECRET=generate-a-64-character-hex-string

# ============================================
# Application
# ============================================
NEXT_PUBLIC_SITE_URL=http://localhost:3000
Critical: Add .env.local and .env.production to your .gitignore immediately. Never commit files containing real API keys, passwords, or secrets. The .env.example file (with placeholder values) is the only environment file that should be committed.

Complete Example: Planning a Local Shop Website

Let us walk through the entire planning process end to end, condensed into a summary:

  1. Client Interview: "We are a computer repair shop. We need a website that shows our services, lets customers contact us, has a blog for SEO, displays our refurbished computers for sale, and gives our employees a dashboard to manage tickets."
  2. Requirements Document: 20+ public pages, admin portal with 5 sections, 3 integrations (CRM, email, storage), free-tier budget constraint.
  3. Sitemap: Two main sections (public with 20 pages, admin with 12 pages), two dynamic routes ([slug] and [id]).
  4. User Flows: Customer discovery flow (Google → homepage → services → contact), employee management flow (login → dashboard → tickets → status update).
  5. Wireframes: Low-fidelity sketches for homepage, services hub, contact form, admin dashboard, ticket detail page.
  6. Database Schema: Blog tables (4), gallery table (1), customer/ticket tables (synced from CRM), status override tables (2), user profiles (1).
  7. Service Selection: Supabase (database), Render (hosting), Resend (email), UptimeRobot (monitoring) — all free tier.
  8. Tech Stack: Next.js 14, TypeScript, Tailwind CSS, App Router. Justified because we need SSR for SEO, mixed static/dynamic pages, and API routes.
  9. Scaffolding: npx create-next-app@latest with TypeScript, Tailwind, App Router. Install Supabase client.
  10. Environment Setup: .env.example with all variables documented. .nvmrc set to Node 22.
  11. Documentation: README.md with setup instructions. CLAUDE.md with architecture decisions.
  12. Git: Initial commit with clean .gitignore. Push to GitHub.
  13. Directory Structure: All folders and placeholder files created following the planned architecture.

After this process, you have not written a single line of application code — and yet you are more prepared to build a successful project than someone who spent those same hours coding without a plan.

CSK Connection This entire planning process is exactly what happened before the first line of CSK code was written. The client interview shaped the requirements. The requirements shaped the sitemap and schema. The schema shaped the Supabase project. The service evaluation led to the Render + Supabase + Resend stack. And the directory structure planned in this phase is the exact structure you see in the CSK codebase today.

Exercises

  1. Client Interview Roleplay: Imagine a local bakery hires you to build their website. Write down at least 15 questions you would ask in the initial interview, organized by category (business understanding, website goals, technical requirements).
  2. Requirements Document: Using the bakery scenario, write a requirements document listing all public pages, admin features, and integrations the project would need.
  3. Sitemap Creation: Draw a sitemap (text-based or using a free tool) for the bakery website showing all pages and their hierarchy.
  4. User Flow Diagram: Map out the user flow for a customer who wants to order a custom cake online. Include every page they visit and every action they take.
  5. Database Schema: Design the database tables needed for the bakery website. Include tables for menu items, orders, blog posts, and customer inquiries. Define columns and relationships.
  6. Service Evaluation: Research and compare two hosting platforms (e.g., Render vs. Vercel) for the bakery project. Create a comparison table with cost, free tier limits, deployment method, and custom domain support.
  7. Project Scaffold: Run npx create-next-app@latest bakery-website with TypeScript and Tailwind. Create a .env.example file, .nvmrc, and README.md. Make your initial Git commit.
  8. Directory Structure: Plan and create the full directory structure for the bakery project inside src/app/, including route groups, API routes, and component folders. Create empty placeholder files with comments describing what each will contain.

Key Takeaways

  • Professional developers spend 20-40% of their time planning before writing code. This investment saves far more time than it costs.
  • A structured client interview uncovers business requirements, website goals, and technical constraints that shape every architectural decision.
  • A sitemap defines every page and its relationships, giving you a clear picture of the project's scope before you start building.
  • User flows map the paths different users take through your site, ensuring every critical journey is supported.
  • Wireframes are low-fidelity sketches that validate layout and functionality before you invest time in code.
  • Database schema design maps requirements to tables, columns, and relationships. Always plan for timestamps, foreign keys, and Row-Level Security.
  • Evaluate third-party services on cost, documentation, reliability, developer experience, vendor lock-in, and scalability.
  • Choose your tech stack based on project requirements, not trends. Next.js excels at SEO-driven, mixed static/dynamic sites with API needs.
  • Scaffold with create-next-app, set up .env.example, .nvmrc, .gitignore, and documentation from the very first commit.
  • Plan your directory structure up front so every file has a clear, logical home.
