Learning Objectives

  • Structure consistent JSON response shapes using the data/error/meta pattern
  • Implement pagination, filtering, and sorting through query parameters
  • Understand API versioning strategies and the HATEOAS concept
  • Design a complete REST API from scratch for a real-world application

What Is REST?

REST stands for Representational State Transfer. It is an architectural style (not a strict protocol or specification) for designing networked applications. REST was defined by Roy Fielding in his doctoral dissertation in the year 2000, and it has since become the most widely used approach for building web APIs.

But what does "Representational State Transfer" actually mean? Let us break it apart:

  • Representational — When you ask a server for data, it sends you a representation of that data (typically JSON or XML), not the actual database record itself. The server describes the current state of a resource in a format the client can understand.
  • State — Every resource has a current state (its data at this moment). A blog post has a title, content, and publish date. A customer has a name, email, and phone number. That is its state.
  • Transfer — The client and server transfer these representations back and forth over HTTP. The client can read the state, create new state, update existing state, or delete state.
Analogy: The Library Catalog
Imagine a public library. The books on the shelves are the actual resources. The library catalog (or card catalog, for older readers) contains representations of those books — the title, author, ISBN, and shelf location. When you search the catalog, you get a representation of the book's information. You can then use that information to go find the actual book. REST APIs work the same way: you request a representation of data, and the server sends back a description of its current state.

The Six Constraints of REST

REST is defined by six architectural constraints. You do not need to memorize these for day-to-day work, but understanding them helps you appreciate why REST APIs behave the way they do:

Constraint What It Means Why It Matters
Client-Server The client and server are separate and independent The frontend and backend can evolve independently
Stateless Each request contains all the information needed to process it The server does not remember previous requests, making it easier to scale
Cacheable Responses can be marked as cacheable or non-cacheable Clients and intermediaries can cache responses to improve performance
Uniform Interface All resources are accessed through a consistent, standardized interface Once you learn how one endpoint works, you can predict how others work
Layered System The client cannot tell whether it is connected directly to the server or through intermediaries Load balancers, caches, and security layers can sit between client and server
Code on Demand (optional) The server can send executable code (like JavaScript) to the client Extends client functionality without requiring updates

The most important of these for everyday API design is the uniform interface. It means that if your API is well-designed, anyone who understands REST conventions can predict how your API works without reading extensive documentation. That is the goal we are working toward in this lesson.

REST vs. Other API Styles REST is not the only way to build APIs. GraphQL (created by Facebook) lets clients request exactly the fields they need. gRPC (created by Google) uses binary protocols for high-performance communication between services. WebSockets enable real-time, bidirectional communication. Each has its place, but REST remains the default choice for most web applications due to its simplicity and universality. When someone says "API" without further qualification, they almost always mean a REST API.

Resources as Nouns: Designing Your URLs

The single most important principle in REST API design is this: URLs represent resources (things), and HTTP methods represent actions (verbs). A resource is any entity that your application manages — users, blog posts, products, orders, tickets, customers.

The URL (also called the endpoint) identifies what you are working with. The HTTP method specifies what you want to do with it. This separation is what makes REST APIs predictable and intuitive.

URL Structure Basics

REST URLs follow a simple pattern:

/api/<collection>              — The entire collection of resources
/api/<collection>/<id>         — A single, specific resource

Examples:
/api/users                      — All users
/api/users/123                  — The user with ID 123
/api/posts                      — All blog posts
/api/posts/456                  — The blog post with ID 456
/api/products                   — All products
/api/products/abc-widget        — The product with slug "abc-widget"

Rule 1: Use Plural Nouns

Always use plural nouns for your resource URLs. This is the most universally agreed-upon convention in REST API design:

Correct Incorrect Why
/api/users /api/user The collection endpoint represents multiple users
/api/posts /api/post Consistency — /api/posts/123 reads naturally
/api/categories /api/category Even the single-resource URL uses plural: /api/categories/5

The reason is consistency. When /api/users returns a list of users and /api/users/123 returns one specific user, the URL pattern is perfectly predictable. Mixing singular and plural creates confusion: would /api/user/123 mean the same as /api/users/123? Which should you use? Stick with plural and the question never arises.

Rule 2: No Verbs in URLs

Since HTTP methods already express the action, you should never put verbs in your URLs:

Correct Incorrect Why
GET /api/users GET /api/getUsers GET already means "get" — the verb is redundant
POST /api/users POST /api/createUser POST already means "create"
DELETE /api/users/123 POST /api/deleteUser/123 DELETE already means "delete"
Common Mistake: RPC-Style URLs Beginners often design URLs that look like function calls: /api/getUserById, /api/createNewPost, /api/updateCustomerEmail. This is called RPC (Remote Procedure Call) style, and while it works, it misses the point of REST entirely. REST treats URLs as addresses for things, not names for actions. Think of URLs as nouns ("the collection of users") and HTTP methods as verbs ("get it", "create one", "delete it").

Rule 3: Nesting for Relationships

When one resource belongs to another, you can nest the URL to express that relationship:

/api/users/123/posts          — All posts by user 123
/api/posts/456/comments        — All comments on post 456
/api/customers/789/tickets     — All tickets for customer 789
/api/tickets/101/notes         — All notes on ticket 101

Nesting makes relationships explicit and readable. However, do not nest too deeply. One level of nesting is common and clear. Two or more levels become hard to work with:

// Good: one level of nesting
/api/users/123/posts

// Acceptable: two levels when truly needed
/api/users/123/posts/456

// Bad: too deep — hard to read and hard to implement
/api/users/123/posts/456/comments/789/likes

When you find yourself going three or more levels deep, consider whether the nested resource should have its own top-level endpoint instead. For example, instead of /api/users/123/posts/456/comments, you could use /api/posts/456/comments (since comments belong to a post, not a user).

Rule 4: Use Kebab-Case for Multi-Word URLs

When a resource name contains multiple words, use hyphens (kebab-case):

/api/blog-posts               — Correct (kebab-case)
/api/blog_posts               — Acceptable (snake_case)
/api/blogPosts                — Avoid (camelCase)
/api/BlogPosts                — Avoid (PascalCase)

URLs are case-insensitive by convention, and hyphens are the most readable separator in URLs. Some APIs use underscores, which is also fine as long as you are consistent throughout your entire API.

CSK Connection The Computer Store KS API follows these REST conventions. Resources use plural nouns: /api/blog for blog posts, /api/gallery for gallery computers. Nesting expresses relationships: /api/repairshopr/customers/[id]/tickets retrieves all tickets for a specific customer. /api/repairshopr/tickets/[id]/notes retrieves all notes for a specific ticket. The URL structure makes the API predictable and self-documenting.

HTTP Methods as Verbs: CRUD Operations

Now that we know how to name our resources (the nouns), let us learn how to express actions (the verbs). REST maps the four fundamental data operations — Create, Read, Update, Delete (CRUD) — to specific HTTP methods:

HTTP Method CRUD Operation URL Pattern Description
GET Read /api/posts List all posts
GET Read /api/posts/123 Get one specific post
POST Create /api/posts Create a new post
PUT Update (full) /api/posts/123 Replace the entire post
PATCH Update (partial) /api/posts/123 Update specific fields of the post
DELETE Delete /api/posts/123 Delete the post

Let us explore each method in detail.

GET — Read Data (Safe and Idempotent)

GET retrieves data without modifying anything on the server. It is safe (it does not change data) and idempotent (calling it once or a hundred times produces the same result).

// List all published blog posts
GET /api/posts
Response: 200 OK
{
  "data": [
    { "id": 1, "title": "Getting Started with Next.js", "status": "published" },
    { "id": 2, "title": "Understanding TypeScript", "status": "published" }
  ],
  "meta": { "total": 2, "page": 1, "limit": 20 }
}

// Get a single blog post by ID
GET /api/posts/1
Response: 200 OK
{
  "data": {
    "id": 1,
    "title": "Getting Started with Next.js",
    "content": "...",
    "author": "Matthew",
    "status": "published",
    "created_at": "2026-01-15T10:30:00Z"
  }
}

POST — Create New Data

POST sends data to the server to create a new resource. POST is neither safe nor idempotent — calling it multiple times creates multiple resources.

// Create a new blog post
POST /api/posts
Content-Type: application/json

{
  "title": "Understanding REST APIs",
  "content": "REST stands for Representational State Transfer...",
  "status": "draft"
}

Response: 201 Created
{
  "data": {
    "id": 3,
    "title": "Understanding REST APIs",
    "content": "REST stands for Representational State Transfer...",
    "status": "draft",
    "created_at": "2026-02-05T14:00:00Z"
  }
}

Notice the response returns 201 Created (not 200 OK) and includes the newly created resource with its server-generated fields (like id and created_at).

PUT — Full Update (Replace)

PUT replaces an entire resource with new data. The client sends a complete representation, and the server replaces whatever was there before. PUT is idempotent — sending the same PUT request multiple times produces the same result.

// Replace the entire blog post
PUT /api/posts/3
Content-Type: application/json

{
  "title": "Understanding REST APIs (Updated)",
  "content": "REST is an architectural style...",
  "status": "published"
}

Response: 200 OK
{
  "data": {
    "id": 3,
    "title": "Understanding REST APIs (Updated)",
    "content": "REST is an architectural style...",
    "status": "published",
    "created_at": "2026-02-05T14:00:00Z",
    "updated_at": "2026-02-05T15:30:00Z"
  }
}
PUT Replaces Everything If you send a PUT request and forget to include a field, that field will be set to null (or its default value). For example, if you PUT a blog post without the content field, the content will be erased. This is by design — PUT means "replace this resource with exactly what I am sending." If you only want to change specific fields, use PATCH instead.

PATCH — Partial Update

PATCH updates only the specified fields of a resource, leaving everything else unchanged. This is the more common update method in practice because you rarely need to replace an entire resource.

// Update only the status of the blog post
PATCH /api/posts/3
Content-Type: application/json

{
  "status": "published"
}

Response: 200 OK
{
  "data": {
    "id": 3,
    "title": "Understanding REST APIs (Updated)",
    "content": "REST is an architectural style...",
    "status": "published",
    "created_at": "2026-02-05T14:00:00Z",
    "updated_at": "2026-02-05T16:00:00Z"
  }
}

Only the status field changed. The title and content remain untouched.

DELETE — Remove Data

DELETE removes a resource. It is idempotent — deleting the same resource twice has the same end result (the resource is gone).

// Delete a blog post
DELETE /api/posts/3

Response: 204 No Content
(empty body)

The 204 No Content status code means "success, and there is nothing to send back." Some APIs return 200 OK with the deleted resource in the body instead, but 204 is the more RESTful convention for DELETE.

Analogy: The Filing Cabinet
Imagine your API resources are folders in a filing cabinet. GET is opening the cabinet and reading a folder (or listing all folders). POST is creating a brand new folder and filing it. PUT is pulling out a folder, throwing away its contents, and replacing them entirely. PATCH is pulling out a folder and updating just one page inside it. DELETE is removing a folder from the cabinet entirely.

Method Properties: Safety and Idempotency

Two important properties help you understand when and how to use each method:

Method Safe? Idempotent? Has Request Body?
GET Yes Yes No
POST No No Yes
PUT No Yes Yes
PATCH No Not guaranteed Yes
DELETE No Yes Usually no

Safe means the method does not modify data. Idempotent means calling it multiple times produces the same result as calling it once. These properties matter for caching, retry logic, and browser behavior. For example, browsers freely cache GET requests and will warn users before resubmitting POST forms.

CSK Connection The Computer Store KS blog API maps perfectly to REST methods. GET /api/blog lists all posts. POST /api/blog creates a new post. GET /api/blog/[id] reads a single post. PUT /api/blog/[id] updates a post. DELETE /api/blog/[id] deletes a post. The gallery API follows the same pattern: GET /api/gallery, POST /api/gallery, PUT /api/gallery/[id], DELETE /api/gallery/[id].

HTTP Status Codes in Detail

In Lesson 01, you learned the basics of HTTP status codes. Now let us go deep. A well-designed REST API uses status codes precisely to communicate what happened with each request. Here is every status code you need to know as an API designer.

Success Codes (2xx)

Code Name When to Use Example
200 OK The request succeeded and the response body contains data GET request returns a list of posts
201 Created A new resource was successfully created POST request creates a new blog post
204 No Content The request succeeded but there is nothing to return DELETE request removes a resource

Client Error Codes (4xx)

These codes mean the problem is on the client's side — the request was somehow wrong, and the client needs to fix it before trying again.

Code Name When to Use Example
400 Bad Request The request body is malformed or missing required data Sending invalid JSON or missing a required field
401 Unauthorized The client is not authenticated (no credentials or expired token) Making a request without a login session
403 Forbidden The client is authenticated but lacks permission for this action A regular user trying to access admin-only endpoints
404 Not Found The requested resource does not exist Requesting /api/posts/999 when post 999 does not exist
409 Conflict The request conflicts with the current state of the resource Creating a user with an email that already exists
422 Unprocessable Entity The JSON is valid but the data fails validation rules Email field contains "not-an-email" instead of a valid email address
429 Too Many Requests The client has exceeded the rate limit Sending more than 100 requests per minute
400 vs. 422: What Is the Difference? This is a common source of confusion. Use 400 Bad Request when the request body is not valid JSON at all (the syntax is broken). Use 422 Unprocessable Entity when the JSON is syntactically valid but the data does not pass your validation rules (for example, the email field is present but contains an invalid email). In practice, many APIs use 400 for both situations, which is acceptable. The important thing is to be consistent.

Server Error Codes (5xx)

Code Name When to Use Example
500 Internal Server Error An unexpected error occurred on the server Unhandled exception, null pointer, code bug
502 Bad Gateway The server received an invalid response from an upstream service Your API calls another API that returns garbage
503 Service Unavailable The server is temporarily unable to handle requests Server is overloaded, maintenance mode, database down
401 vs. 403: Know the Difference This distinction trips up many developers. 401 Unauthorized (confusingly named — it should be "Unauthenticated") means the server does not know who you are. You have not provided credentials, or your session has expired. The fix is to log in. 403 Forbidden means the server knows exactly who you are, but you do not have permission to do what you are asking. The fix is to get a higher permission level. Think of it this way: 401 = "Who are you?" and 403 = "I know who you are, and the answer is no."

Consistent Response Shapes

One of the most impactful decisions you can make in API design is establishing a consistent response structure. Every endpoint, whether it succeeds or fails, should return JSON in a predictable shape. This makes it dramatically easier for frontend developers to consume your API.

The Data / Error / Meta Pattern

A widely used convention is to wrap all responses in an object with three possible top-level keys:

// Successful response with data
{
  "data": { ... },     // The requested resource or list of resources
  "meta": { ... }      // Optional metadata (pagination, counts, etc.)
}

// Error response
{
  "error": {
    "message": "...",   // Human-readable error message
    "code": "...",      // Machine-readable error code
    "details": [ ... ]  // Optional array of specific field errors
  }
}

Let us see this pattern applied to different scenarios:

// GET /api/posts (list) — success
{
  "data": [
    { "id": 1, "title": "First Post" },
    { "id": 2, "title": "Second Post" }
  ],
  "meta": {
    "total": 47,
    "page": 1,
    "limit": 20,
    "totalPages": 3
  }
}

// GET /api/posts/1 (single resource) — success
{
  "data": {
    "id": 1,
    "title": "First Post",
    "content": "Hello world...",
    "author": "Matthew"
  }
}

// POST /api/posts (create) — success
{
  "data": {
    "id": 48,
    "title": "New Post",
    "status": "draft",
    "created_at": "2026-02-05T14:30:00Z"
  }
}

// POST /api/posts (create) — validation error
{
  "error": {
    "message": "Validation failed",
    "code": "VALIDATION_ERROR",
    "details": [
      { "field": "title", "message": "Title is required" },
      { "field": "content", "message": "Content must be at least 10 characters" }
    ]
  }
}

// GET /api/posts/999 — not found
{
  "error": {
    "message": "Blog post not found",
    "code": "NOT_FOUND"
  }
}

// Any request — server error
{
  "error": {
    "message": "An unexpected error occurred",
    "code": "INTERNAL_ERROR"
  }
}

Why Consistency Matters

With a consistent structure, the frontend can write generic error handling:

// Frontend code that works with ANY endpoint
async function apiRequest(url: string, options?: RequestInit) {
  const response = await fetch(url, options);
  const json = await response.json();

  // Every response has the same shape!
  if (json.error) {
    // Handle error — works for ANY endpoint
    throw new ApiError(json.error.message, json.error.code, json.error.details);
  }

  // Success — data is always in json.data
  return json.data;
}

Without consistency, the frontend would need custom parsing logic for every single endpoint, which is error-prone and frustrating.

CSK Connection The CSK API uses consistent response shapes. Success responses wrap data in a data field. Error responses include a descriptive error message and appropriate status code. For example, GET /api/blog returns { data: [...posts] } for public access and includes admin-only drafts when ?admin=true is passed. Error responses return { error: "Description of what went wrong" }.

Pagination: Handling Large Collections

When your collection contains hundreds or thousands of resources, you cannot send them all in one response. That would be slow, memory-intensive, and wasteful. Instead, you break the collection into pages. There are two common pagination strategies.

Offset-Based Pagination (Limit/Offset)

This is the most common and simplest approach. The client specifies how many items they want (limit) and where to start (offset):

// First page: items 0-19
GET /api/posts?limit=20&offset=0

// Second page: items 20-39
GET /api/posts?limit=20&offset=20

// Third page: items 40-59
GET /api/posts?limit=20&offset=40

Some APIs use page and limit (or per_page) instead:

// First page
GET /api/posts?page=1&limit=20

// Second page
GET /api/posts?page=2&limit=20

The response includes metadata so the client knows how many pages exist:

{
  "data": [ ... ],
  "meta": {
    "total": 147,
    "page": 2,
    "limit": 20,
    "totalPages": 8
  }
}

Advantages: Simple to implement, clients can jump to any page. Disadvantages: Can return duplicate or missing items if data changes between requests (a new post is created while you are paging through). Performance degrades for very large offsets because the database must skip past all the skipped rows.

Cursor-Based Pagination

Cursor-based pagination uses an opaque marker (cursor) that points to a specific item in the dataset. The server returns a cursor that the client sends to get the next page:

// First page
GET /api/posts?limit=20

Response:
{
  "data": [ ... ],
  "meta": {
    "hasMore": true,
    "nextCursor": "eyJpZCI6MjB9"
  }
}

// Next page (use the cursor from the previous response)
GET /api/posts?limit=20&cursor=eyJpZCI6MjB9

Response:
{
  "data": [ ... ],
  "meta": {
    "hasMore": true,
    "nextCursor": "eyJpZCI6NDB9"
  }
}

// Last page
GET /api/posts?limit=20&cursor=eyJpZCI6MTQwfQ

Response:
{
  "data": [ ... ],
  "meta": {
    "hasMore": false,
    "nextCursor": null
  }
}

Advantages: No duplicate or missing items, consistent performance regardless of position. Disadvantages: Cannot jump to an arbitrary page, slightly more complex to implement.

Which Should You Choose? Use offset-based pagination for admin dashboards, tables with page numbers, and small to medium datasets. Use cursor-based pagination for infinite scroll feeds, real-time data, large datasets, and public APIs where data changes frequently. For most beginning projects, offset-based is the right choice because it is simpler.

Filtering and Sorting via Query Parameters

Real-world APIs need to let clients filter and sort results. The convention is to use query parameters for these operations, keeping the URL path clean for resource identification.

Filtering

Filter parameters narrow down the results:

// Get only published posts
GET /api/posts?status=published

// Get posts in the "tutorials" category
GET /api/posts?category=tutorials

// Get posts by a specific author
GET /api/posts?author=matthew

// Combine multiple filters (logical AND)
GET /api/posts?status=published&category=tutorials&author=matthew

// Date range filtering
GET /api/posts?created_after=2026-01-01&created_before=2026-02-01

// Search (text search across fields)
GET /api/posts?q=typescript+basics

Sorting

Sort parameters control the order of results. A common convention uses a sort parameter with a prefix to indicate direction:

// Sort by creation date, newest first (descending)
GET /api/posts?sort=-created_at

// Sort by title, alphabetically (ascending)
GET /api/posts?sort=title

// Sort by multiple fields (primary sort first)
GET /api/posts?sort=-created_at,title

The - prefix means descending order. No prefix (or a + prefix) means ascending order. This convention is concise and widely understood.

Combining Everything

Pagination, filtering, and sorting work together naturally through query parameters:

// Page 2 of published tutorials, sorted newest first, 10 per page
GET /api/posts?status=published&category=tutorials&sort=-created_at&page=2&limit=10

This URL is readable and self-documenting. Anyone looking at it can understand exactly what data is being requested.

CSK Connection The CSK API uses query parameters for filtering. GET /api/blog returns only published posts by default for public users, while GET /api/blog?admin=true returns all posts including drafts for admin users. The /api/repairshopr/tickets endpoint accepts ?q=search+term for text search and ?status=open for status filtering. Query params modify behavior without changing the resource being accessed.

API Versioning Strategies

As your API evolves, you will eventually need to make breaking changes — renaming fields, changing response structures, or removing endpoints. But existing clients depend on the current behavior. How do you evolve without breaking things? API versioning.

Strategy 1: URL Path Versioning

The most common approach puts the version number directly in the URL path:

GET /api/v1/posts         — Version 1 of the posts endpoint
GET /api/v2/posts         — Version 2, might have a different response shape

Pros: Extremely clear, easy to test, easy to route. Cons: Changes every URL, can lead to code duplication on the server.

Strategy 2: Header Versioning

The version is specified in a request header:

GET /api/posts
Accept: application/vnd.myapi.v2+json

Pros: Clean URLs, does not change the URL structure. Cons: Hidden (not visible in the URL), harder to test in a browser.

Strategy 3: Query Parameter Versioning

The version is passed as a query parameter:

GET /api/posts?version=2

Pros: Simple, easy to use. Cons: Can conflict with other query parameters, not very conventional.

Which Strategy Should You Use?

For most projects, especially early-stage ones, URL path versioning is the best choice. It is the most explicit, the most widely used, and the easiest to understand. Many large APIs (Stripe, GitHub, Twitter) use this approach.

That said, for small to medium projects like Computer Store KS, you often do not need versioning at all. If you control both the API and the only client consuming it (the Next.js frontend), you can evolve both together. Versioning becomes important when you have third-party consumers who cannot update their code in sync with your changes.

HATEOAS: The Self-Describing API

HATEOAS stands for Hypermedia As The Engine Of Application State. It is the most advanced (and most debated) REST concept. The idea is that API responses should include links that tell the client what actions are available next.

// GET /api/posts/1
{
  "data": {
    "id": 1,
    "title": "First Post",
    "status": "draft"
  },
  "links": {
    "self": "/api/posts/1",
    "author": "/api/users/42",
    "comments": "/api/posts/1/comments",
    "publish": "/api/posts/1/publish"
  }
}

With HATEOAS, the client does not need to know the URL structure in advance. It discovers available actions by following links in the response, similar to how you navigate a website by clicking links rather than typing URLs.

In practice, very few APIs implement full HATEOAS because it adds complexity for marginal benefit in most applications. However, including a self link (the URL of the current resource) and links to related resources is a helpful practice that improves API discoverability.

HATEOAS in the Real World The GitHub REST API is one of the best real-world examples of HATEOAS. Every response includes a links section with URLs you can follow. For example, when you list a user's repositories, the response includes a link to the next page, the user's profile, and each repository's detail URL. This makes the API explorable — you can start with one URL and discover the entire API by following links.

Why API Documentation Matters

An API is only as good as its documentation. Even the most beautifully designed REST API is useless if developers cannot figure out how to use it. Good API documentation should include:

  • Endpoint reference — Every endpoint with its URL, HTTP method, description, and authentication requirements
  • Request examples — Complete request bodies with all required and optional fields
  • Response examples — What the response looks like for success and error cases
  • Parameter descriptions — What each query parameter, header, and body field means
  • Authentication guide — How to obtain and use credentials
  • Error reference — All possible error codes and what causes them
  • Rate limits — How many requests clients can make and what happens when they exceed limits
  • Getting started guide — A quick tutorial to make the first successful request

Tools like OpenAPI (Swagger) let you define your API in a structured format (YAML or JSON) that can automatically generate interactive documentation pages. Developers can try out endpoints directly from the docs page. Other popular documentation tools include Postman (for collections), Redoc, and Stoplight.

Complete Example: Designing a Blog API from Scratch

Let us put everything together and design a complete REST API for a blog system. This mirrors the actual blog API in the Computer Store KS codebase.

Step 1: Identify the Resources

Our blog has these resources:

  • Posts — Blog articles
  • Categories — Groupings for posts
  • Tags — Labels attached to posts
  • Comments — Reader comments on posts

Step 2: Define the Endpoints

Method Endpoint Description Auth Required
GET /api/posts List all published posts (paginated) No
GET /api/posts/:id Get a single post by ID or slug No
POST /api/posts Create a new post Yes (admin)
PUT /api/posts/:id Update a post (full replacement) Yes (admin)
DELETE /api/posts/:id Delete a post Yes (admin)
GET /api/posts/:id/comments List comments on a post No
POST /api/posts/:id/comments Add a comment to a post No (public)
GET /api/categories List all categories No
GET /api/tags List all tags No

Step 3: Define the Query Parameters

// Posts listing supports these query parameters:
GET /api/posts
  ?status=published|draft      // Filter by status (admin only for draft)
  &category=tutorials           // Filter by category
  &tag=javascript               // Filter by tag

Step 6: Implement in Next.js

Here is how this design translates to actual Next.js API route code:

// src/app/api/posts/route.ts
import { NextRequest, NextResponse } from 'next/server';

// GET /api/posts — List posts with filtering and pagination
export async function GET(request: NextRequest) {
  const { searchParams } = new URL(request.url);

  // Parse query parameters
  const status = searchParams.get('status') || 'published';
  const category = searchParams.get('category');
  const sort = searchParams.get('sort') || '-created_at';
  const page = parseInt(searchParams.get('page') || '1');
  const limit = Math.min(parseInt(searchParams.get('limit') || '20'), 100);
  const offset = (page - 1) * limit;

  // Build query (using Supabase as an example)
  let query = supabase
    .from('blog_posts')
    .select('*', { count: 'exact' })
    .eq('status', status)
    .range(offset, offset + limit - 1);

  // Apply optional filters
  if (category) {
    query = query.eq('category', category);
  }

  // Apply sorting
  const sortField = sort.startsWith('-') ? sort.slice(1) : sort;
  const sortDirection = sort.startsWith('-') ? false : true;  // false = descending
  query = query.order(sortField, { ascending: sortDirection });

  const { data, count, error } = await query;

  if (error) {
    return NextResponse.json(
      { error: { message: 'Failed to fetch posts', code: 'DATABASE_ERROR' } },
      { status: 500 }
    );
  }

  return NextResponse.json({
    data,
    meta: {
      total: count,
      page,
      limit,
      totalPages: Math.ceil((count || 0) / limit)
    }
  });
}

// POST /api/posts — Create a new post
export async function POST(request: NextRequest) {
  // Check authentication (simplified)
  const session = await getSession(request);
  if (!session) {
    return NextResponse.json(
      { error: { message: 'Authentication required', code: 'AUTH_REQUIRED' } },
      { status: 401 }
    );
  }

  // Parse and validate request body
  const body = await request.json();

  if (!body.title || !body.content) {
    return NextResponse.json(
      {
        error: {
          message: 'Validation failed',
          code: 'VALIDATION_ERROR',
          details: [
            ...(!body.title ? [{ field: 'title', message: 'Title is required' }] : []),
            ...(!body.content ? [{ field: 'content', message: 'Content is required' }] : [])
          ]
        }
      },
      { status: 422 }
    );
  }

  // Create the post
  const { data, error } = await supabase
    .from('blog_posts')
    .insert({ ...body, author_id: session.user.id })
    .select()
    .single();

  if (error) {
    return NextResponse.json(
      { error: { message: 'Failed to create post', code: 'DATABASE_ERROR' } },
      { status: 500 }
    );
  }

  // Return 201 Created with the new resource
  return NextResponse.json({ data }, { status: 201 });
}
URL Design Cheat Sheet Here is a quick reference for designing REST URLs:

GET /api/things — List all things
GET /api/things/:id — Get one thing
POST /api/things — Create a thing
PUT /api/things/:id — Replace a thing
PATCH /api/things/:id — Update parts of a thing
DELETE /api/things/:id — Delete a thing
GET /api/things/:id/sub-things — List sub-things of a thing
?key=value — Filter, sort, paginate

Key Takeaways

  • REST (Representational State Transfer) is an architectural style where URLs represent resources (nouns) and HTTP methods represent actions (verbs).
  • Use plural nouns for resource URLs (/api/users, not /api/user), never put verbs in URLs, and nest resources to express relationships (/api/users/123/posts).
  • Map CRUD operations to HTTP methods: GET (read), POST (create), PUT (full update), PATCH (partial update), DELETE (remove).
  • Use precise HTTP status codes: 200 OK, 201 Created, 204 No Content for success; 400, 401, 403, 404, 409, 422, 429 for client errors; 500, 502, 503 for server errors.
  • Establish a consistent response shape (data/error/meta pattern) across all endpoints so frontend code can handle responses generically.
  • Use query parameters for filtering (?status=published), sorting (?sort=-created_at), and pagination (?page=2&limit=20).
  • URL path versioning (/api/v1/...) is the most common and clearest approach to API versioning.
  • Good API documentation is just as important as good API design. An undocumented API is an unusable API.
