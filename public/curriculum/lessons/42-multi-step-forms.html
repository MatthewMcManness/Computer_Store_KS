Phase 10: Advanced UI Patterns

Multi-Step Forms & Wizards

Break complex data entry into manageable steps — guide users through long forms without overwhelming them.

What You Will Learn

  • When and why to use multi-step forms instead of single-page forms
  • How to manage wizard state: current step index and shared form data
  • Building step navigation: next, back, and jump-to-step controls
  • Creating a visual step indicator and progress bar component
  • Implementing per-step validation before allowing the user to proceed
  • The shared form data pattern: parent state passed down to step children
  • Structuring each step as its own isolated component
  • Combining all step data for final submission
  • Handling error recovery when submission fails after completing all steps
  • Persisting partial data with localStorage so users do not lose progress
  • Accessibility: focus management and screen reader announcements between steps

Why Multi-Step Forms Exist

Imagine you are signing up for a new service and the website presents you with a single page containing 25 form fields: your name, email, password, address, phone number, billing information, preferences, notification settings, and a terms of service checkbox. Even though all of those fields are necessary, seeing them all at once creates a wall of inputs that feels exhausting before you even start. Research consistently shows that long, single-page forms have significantly higher abandonment rates than shorter forms. Users see the length, feel overwhelmed, and leave.

Multi-step forms (also called wizards) solve this problem by breaking one large form into several smaller, focused steps. Instead of 25 fields on one page, you might have four steps with 5–7 fields each. Each step has a clear purpose: "Personal Information," "Address," "Preferences," "Review & Submit." The user sees only one manageable chunk at a time, completes it, clicks Next, and moves to the next chunk. A progress indicator at the top shows how far they have come and how much remains.

This pattern works because of several psychological principles. Chunking reduces cognitive load by grouping related information together. Progress visibility motivates completion because users can see they are 50% done and feel invested enough to finish. Focused attention on fewer fields at once reduces errors because users are not scanning past unrelated inputs.

Analogy: Think about assembling furniture from a box. If the instruction sheet showed all 47 steps at once in a single wall of text, you would feel overwhelmed. But when the instructions are broken into stages — "Step 1: Attach the legs," "Step 2: Mount the shelves" — each stage feels achievable. A multi-step form is the same concept applied to data entry.

When to Use Multi-Step Forms

Not every form needs multiple steps. A simple contact form with name, email, and message is perfectly fine as a single form. Use multi-step forms when:

  • The form has more than 8–10 fields — Enough to feel overwhelming on one page
  • Fields can be logically grouped — Personal info, address, payment, and preferences are natural groups
  • Later steps depend on earlier answers — Conditional logic that shows different fields based on previous choices
  • The process has a natural sequence — Like an intake process that must happen in order
  • You need a review step — Letting users confirm everything before final submission
CSK Connection The Computer Store KS admin panel has a customer intake wizard at /admin/intake. When a customer walks into the shop, the receptionist uses this wizard to guide them through: (1) looking up or creating the customer, (2) registering their device, (3) setting up passwords and access info, and (4) creating a repair ticket. Each of these steps is complex enough on its own that combining them into a single page would be chaotic. The wizard keeps the process organized and ensures no steps are missed.

State Management for Wizards

A multi-step form needs to track two pieces of state: which step the user is currently on and the form data collected across all steps. Both pieces of state live in the parent component that wraps the entire wizard. The individual step components receive this state as props and call callbacks to update it.

The Core State Shape

Here is what the state looks like for a typical wizard:

// The parent wizard component manages all state
const [currentStep, setCurrentStep] = useState(0);
const [formData, setFormData] = useState({
  // Step 1: Personal Info
  firstName: '',
  lastName: '',
  email: '',
  phone: '',

  // Step 2: Address
  street: '',
  city: '',
  state: '',
  zip: '',

  // Step 3: Preferences
  newsletter: false,
  contactMethod: 'email',
  theme: 'light',

  // Step 4: (Review step uses all the above)
});

The currentStep is a simple integer. Step 0 is the first step, step 1 is the second, and so on. We use a zero-based index because it maps directly to array indices, which makes it easy to look up step components and labels from an array.

The formData is a single object that contains every field from every step. This is the shared form data pattern. All steps read from and write to the same object. When the user goes back to a previous step, their earlier answers are still there because everything lives in one place.

Updating Shared Form Data

Each step component needs a way to update the shared form data. The parent passes down an update function:

// In the parent wizard component
function updateFormData(newFields) {
  setFormData(prev => ({
    ...prev,    // Keep all existing fields
    ...newFields // Override only the changed fields
  }));
}

// Later, pass it to each step component:
<StepPersonalInfo
  data={formData}
  onUpdate={updateFormData}
/>

Inside a step component, updating a field is straightforward:

// Inside StepPersonalInfo component
function StepPersonalInfo({ data, onUpdate }) {
  return (
    <div>
      <label htmlFor="firstName">First Name</label>
      <input
        id="firstName"
        type="text"
        value={data.firstName}
        onChange={(e) => onUpdate({ firstName: e.target.value })}
      />

      <label htmlFor="lastName">Last Name</label>
      <input
        id="lastName"
        type="text"
        value={data.lastName}
        onChange={(e) => onUpdate({ lastName: e.target.value })}
      />

      <label htmlFor="email">Email</label>
      <input
        id="email"
        type="email"
        value={data.email}
        onChange={(e) => onUpdate({ email: e.target.value })}
      />
    </div>
  );
}

Notice how each onChange only passes the single field that changed. The updateFormData function in the parent merges it into the full object using the spread operator. This pattern is simple, predictable, and scales to any number of fields.

Why One Object Instead of Separate States? You could use separate useState calls for each field, but that becomes unwieldy with 15+ fields. A single form data object keeps everything together, makes it easy to serialize (for localStorage or submission), and simplifies the props you pass to each step. For very complex forms, you might consider useReducer instead of useState, but a single state object with a merge function works well for most wizards.

Step Navigation: Next, Back, and Jump

The wizard needs controls for moving between steps. At minimum, you need a "Next" button and a "Back" button. Some wizards also allow users to click on the step indicator to jump directly to any completed step.

Basic Navigation Functions

const STEPS = [
  { label: 'Personal Info', component: StepPersonalInfo },
  { label: 'Address',       component: StepAddress },
  { label: 'Preferences',   component: StepPreferences },
  { label: 'Review',        component: StepReview },
];

const totalSteps = STEPS.length;

function goToNext() {
  setCurrentStep(prev => Math.min(prev + 1, totalSteps - 1));
}

function goToBack() {
  setCurrentStep(prev => Math.max(prev - 1, 0));
}

function goToStep(index) {
  // Only allow jumping to completed steps or the current step
  if (index <= currentStep) {
    setCurrentStep(index);
  }
}

const isFirstStep = currentStep === 0;
const isLastStep = currentStep === totalSteps - 1;

The Math.min and Math.max calls are safety guards. goToNext ensures you never go past the last step. goToBack ensures you never go before the first step. These prevent crashes if a button somehow gets clicked when it should be disabled.

Rendering the Current Step

The STEPS array makes rendering dynamic. Instead of a chain of if/else statements, you just look up the component by index:

// Get the current step's component from the array
const CurrentStepComponent = STEPS[currentStep].component;

// In the JSX:
return (
  <div className="wizard">
    <StepIndicator
      steps={STEPS}
      currentStep={currentStep}
      onStepClick={goToStep}
    />

    <div className="wizard-body">
      <CurrentStepComponent
        data={formData}
        onUpdate={updateFormData}
      />
    </div>

    <div className="wizard-footer">
      {!isFirstStep && (
        <button type="button" onClick={goToBack}>
          Back
        </button>
      )}

      {isLastStep ? (
        <button type="button" onClick={handleSubmit}>
          Submit
        </button>
      ) : (
        <button type="button" onClick={handleNext}>
          Next
        </button>
      )}
    </div>
  </div>
);

A few key details here. The Back button is hidden on the first step because there is nowhere to go back to. On the last step, the Next button is replaced with a Submit button. The handleNext function (which we will define shortly) includes validation before calling goToNext.

Building a Step Indicator and Progress Bar

A step indicator gives users a visual map of the wizard. It shows all the steps, highlights which one they are currently on, and marks which ones they have completed. This is critical for user confidence — it answers the questions "How much have I done?" and "How much is left?"

The Step Indicator Component

function StepIndicator({ steps, currentStep, onStepClick }) {
  return (
    <div className="step-indicator" role="navigation" aria-label="Form progress">
      {/* Progress bar behind the circles */}
      <div className="step-progress-track">
        <div
          className="step-progress-fill"
          style={{ width: `${(currentStep / (steps.length - 1)) * 100}%` }}
        />
      </div>

      {/* Step circles */}
      <div className="step-circles">
        {steps.map((step, index) => {
          const isCompleted = index < currentStep;
          const isCurrent = index === currentStep;
          const isClickable = index <= currentStep;

          return (
            <button
              key={index}
              type="button"
              className={`step-circle ${
                isCompleted ? 'completed' :
                isCurrent ? 'current' : 'upcoming'
              }`}
              onClick={() => isClickable && onStepClick(index)}
              disabled={!isClickable}
              aria-current={isCurrent ? 'step' : undefined}
              aria-label={`Step ${index + 1}: ${step.label}${
                isCompleted ? ' (completed)' :
                isCurrent ? ' (current)' : ''
              }`}
            >
              {isCompleted ? (
                <span aria-hidden="true">&#10003;</span>
              ) : (
                <span>{index + 1}</span>
              )}
              <span className="step-label">{step.label}</span>
            </button>
          );
        })}
      </div>
    </div>
  );
}

The progress bar width is calculated as a percentage. If you are on step 0 out of 4 steps (indices 0–3), the fill is 0%. On step 1, it is 33%. On step 2, it is 67%. On step 3 (the last step), it is 100%. The formula (currentStep / (steps.length - 1)) * 100 produces this scaling.

Each circle button has three possible states: completed (the user has been here and moved on), current (the user is here now), and upcoming (the user has not reached this step yet). Completed steps show a checkmark and are clickable so the user can go back. Upcoming steps are grayed out and disabled.

Per-Step Validation

One of the biggest advantages of multi-step forms is that you can validate each step before the user moves forward. Instead of showing 15 errors at the end, you catch problems immediately. The user fixes them on the current step and then proceeds with confidence that their earlier answers are correct.

Defining Validation Rules Per Step

// Validation functions return an object of field-level errors
// An empty object means the step is valid

function validatePersonalInfo(data) {
  const errors = {};

  if (!data.firstName.trim()) {
    errors.firstName = 'First name is required';
  }
  if (!data.lastName.trim()) {
    errors.lastName = 'Last name is required';
  }
  if (!data.email.trim()) {
    errors.email = 'Email is required';
  } else if (!/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(data.email)) {
    errors.email = 'Please enter a valid email address';
  }

  return errors;
}

function validateAddress(data) {
  const errors = {};

  if (!data.street.trim()) {
    errors.street = 'Street address is required';
  }
  if (!data.city.trim()) {
    errors.city = 'City is required';
  }
  if (!data.state.trim()) {
    errors.state = 'State is required';
  }
  if (!data.zip.trim()) {
    errors.zip = 'ZIP code is required';
  } else if (!/^\d{5}(-\d{4})?$/.test(data.zip)) {
    errors.zip = 'Please enter a valid ZIP code';
  }

  return errors;
}

function validatePreferences(data) {
  // Preferences are optional, so this step might always pass
  return {};
}

// No validation needed for the review step
function validateReview() {
  return {};
}

Integrating Validation with Navigation

// Associate each step with its validation function
const STEPS = [
  { label: 'Personal Info', component: StepPersonalInfo, validate: validatePersonalInfo },
  { label: 'Address',       component: StepAddress,      validate: validateAddress },
  { label: 'Preferences',   component: StepPreferences,  validate: validatePreferences },
  { label: 'Review',        component: StepReview,        validate: validateReview },
];

// Track errors in state
const [errors, setErrors] = useState({});

// The handleNext function validates before proceeding
function handleNext() {
  const validateFn = STEPS[currentStep].validate;
  const stepErrors = validateFn(formData);

  if (Object.keys(stepErrors).length > 0) {
    // There are errors - show them and stay on this step
    setErrors(stepErrors);
    return;
  }

  // No errors - clear any previous errors and move forward
  setErrors({});
  goToNext();
}

The parent passes the errors object down to each step component:

<CurrentStepComponent

/>

Inside the step component, render error messages next to the relevant fields:

function StepPersonalInfo({ data, onUpdate, errors }) {

          aria-invalid={errors.firstName ? 'true' : 'false'}
          aria-describedby={errors.firstName ? 'firstName-error' : undefined}
          className={errors.firstName ? 'input-error' : ''}
        />
        {errors.firstName && (
          <p id="firstName-error" className="error-message" role="alert">
            {errors.firstName}
          </p>
        )}
      </div>

      <div className="form-field">
        <label htmlFor="email">Email *</label>
        <input
          id="email"
          type="email"
          value={data.email}
          onChange={(e) => onUpdate({ email: e.target.value })}
          aria-invalid={errors.email ? 'true' : 'false'}
          aria-describedby={errors.email ? 'email-error' : undefined}
          className={errors.email ? 'input-error' : ''}
        />
        {errors.email && (
          <p id="email-error" className="error-message" role="alert">
            {errors.email}
          </p>
        )}
      </div>
    </div>

}
Clear Errors When Going Back When the user clicks "Back," always clear the current errors: setErrors({}). Otherwise, they will see stale error messages from the step they just left, which is confusing and discouraging. Errors should only appear after the user attempts to move forward.

The Step Component Pattern

Each step of the wizard should be its own component. This is not just good organization — it makes each step testable in isolation, reusable if needed, and easy to rearrange. Every step component follows the same interface: it receives the shared form data, an update callback, and an errors object.

The Step Interface

// TypeScript interface that every step component follows
interface StepProps {
  data: FormData;                          // The shared form data
  onUpdate: (fields: Partial<FormData>) => void;  // Update callback
  errors: Record<string, string>;          // Validation errors
}

// Step 1
function StepPersonalInfo({ data, onUpdate, errors }: StepProps) {
  return ( /* ... personal info fields ... */ );
}

// Step 2
function StepAddress({ data, onUpdate, errors }: StepProps) {
  return ( /* ... address fields ... */ );
}

// Step 3
function StepPreferences({ data, onUpdate, errors }: StepProps) {
  return ( /* ... preference fields ... */ );
}

// Step 4 - Review step (read-only)
function StepReview({ data }: StepProps) {
  return (
    <div className="review-step">
      <h3>Review Your Information</h3>

      <section>
        <h4>Personal Information</h4>
        <p><strong>Name:</strong> {data.firstName} {data.lastName}</p>
        <p><strong>Email:</strong> {data.email}</p>
        <p><strong>Phone:</strong> {data.phone || 'Not provided'}</p>
      </section>

      <section>
        <h4>Address</h4>
        <p>{data.street}</p>
        <p>{data.city}, {data.state} {data.zip}</p>
      </section>

      <section>
        <h4>Preferences</h4>
        <p><strong>Newsletter:</strong> {data.newsletter ? 'Yes' : 'No'}</p>
        <p><strong>Contact Method:</strong> {data.contactMethod}</p>
        <p><strong>Theme:</strong> {data.theme}</p>
      </section>
    </div>
  );
}

The review step is different from the others: it displays data in a read-only format so the user can double-check everything before submitting. It does not need the onUpdate or errors props, but it still receives them (and ignores them) because all steps share the same interface. If the user spots a mistake, they can click Back or click a previous step in the step indicator to fix it.

Final Submission: Combining All Step Data

Because all steps write to the same shared formData object, submission is straightforward. When the user clicks Submit on the final step, you send the entire formData object to your API.

const [isSubmitting, setIsSubmitting] = useState(false);
const [submitError, setSubmitError] = useState(null);

async function handleSubmit() {
  // Run final validation on all steps
  for (let i = 0; i < STEPS.length; i++) {
    const stepErrors = STEPS[i].validate(formData);
    if (Object.keys(stepErrors).length > 0) {
      // Jump the user to the step with errors
      setCurrentStep(i);
      setErrors(stepErrors);
      return;
    }
  }

  setIsSubmitting(true);
  setSubmitError(null);

  try {
    const response = await fetch('/api/register', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(formData),
    });

    if (!response.ok) {
      throw new Error('Registration failed. Please try again.');
    }

    const result = await response.json();

    // Success! Clear saved data and redirect
    localStorage.removeItem('registration-draft');
    router.push('/welcome');

  } catch (error) {
    setSubmitError(error.message);
  } finally {
    setIsSubmitting(false);
  }
}

Notice the "full validation sweep" before submission. Even though each step validates individually, a final check ensures nothing was missed. If a step has errors, the wizard jumps the user back to that step with the errors displayed. This handles edge cases like a user going back, changing a valid field to an invalid one, and then skipping forward to the review step.

Error Recovery After Submission Failure

What happens when the user completes all four steps, clicks Submit, and the server returns an error? This is a frustrating experience if handled poorly. The user just invested time filling out the form, and now they are told it failed. Good error recovery is essential.

Strategy 1: Show the Error on the Review Step

// In the wizard JSX, below the Submit button:
{submitError && (
  <div className="submit-error" role="alert">
    <p><strong>Submission failed:</strong> {submitError}</p>
    <p>Your information has been saved. Please try again.</p>
    <button type="button" onClick={handleSubmit}>
      Retry
    </button>
  </div>
)}

The key phrase is "Your information has been saved." The form data is still in React state, so nothing is lost. The user can click Retry or go back and make changes. This is the minimum viable error recovery.

Strategy 2: Server-Side Field Errors

Sometimes the server rejects specific fields (for example, "This email is already registered"). The server should return structured error information that you can map back to specific steps:

// Server returns: { errors: { email: "Already registered" } }

// Map server errors to the correct step
const fieldToStep = {
  firstName: 0, lastName: 0, email: 0, phone: 0,
  street: 1, city: 1, state: 1, zip: 1,
  newsletter: 2, contactMethod: 2, theme: 2,
};

function handleServerErrors(serverErrors) {
  // Find which step has the first error
  const firstErrorField = Object.keys(serverErrors)[0];
  const targetStep = fieldToStep[firstErrorField];

  // Jump to that step and show the errors
  setCurrentStep(targetStep);
  setErrors(serverErrors);
}
Never Lose User Data The cardinal rule of multi-step form error recovery is: never lose the user's data. If submission fails, all form fields should remain populated exactly as the user left them. The user should only need to fix the specific problem and retry — never re-enter everything from scratch.

Persisting Partial Data with localStorage

What if the user accidentally closes the browser tab halfway through the wizard? Without persistence, all their progress is lost. By saving form data to localStorage, you can restore their progress when they return.

Auto-Saving on Every Change

const STORAGE_KEY = 'registration-draft';

// Load saved data on mount
const [formData, setFormData] = useState(() => {
  if (typeof window === 'undefined') return defaultFormData;

  const saved = localStorage.getItem(STORAGE_KEY);
  if (saved) {
    try {
      return { ...defaultFormData, ...JSON.parse(saved) };
    } catch {
      return defaultFormData;
    }
  }
  return defaultFormData;
});

// Save to localStorage whenever formData changes
useEffect(() => {
  localStorage.setItem(STORAGE_KEY, JSON.stringify(formData));
}, [formData]);

The initial state uses a lazy initializer (a function passed to useState) to check localStorage on the first render. If saved data exists, it is merged with the defaults (so any new fields added to the form since the save still have initial values). The useEffect saves the data every time it changes.

Saving the Current Step Too

// Also persist which step the user was on
const [currentStep, setCurrentStep] = useState(() => {
  if (typeof window === 'undefined') return 0;

  const savedStep = localStorage.getItem(STORAGE_KEY + '-step');
  return savedStep ? parseInt(savedStep, 10) : 0;
});

useEffect(() => {
  localStorage.setItem(STORAGE_KEY + '-step', String(currentStep));
}, [currentStep]);

Clearing Saved Data After Successful Submission

// After successful submission
localStorage.removeItem(STORAGE_KEY);
localStorage.removeItem(STORAGE_KEY + '-step');

Offering a "Start Fresh" Option

If the user returns and sees partially filled data, give them the option to continue or start over:

const [showResumeDialog, setShowResumeDialog] = useState(false);

useEffect(() => {
  const saved = localStorage.getItem(STORAGE_KEY);
  if (saved) {
    setShowResumeDialog(true);
  }
}, []);

// In JSX:
{showResumeDialog && (
  <div className="resume-dialog" role="dialog" aria-label="Resume saved progress">
    <p>You have a saved draft. Would you like to continue where you left off?</p>
    <button onClick={() => setShowResumeDialog(false)}>Continue</button>
    <button onClick={() => {
      localStorage.removeItem(STORAGE_KEY);
      localStorage.removeItem(STORAGE_KEY + '-step');
      setFormData(defaultFormData);
      setCurrentStep(0);
      setShowResumeDialog(false);
    }}>Start Fresh</button>
  </div>
)}

Complete Example: 4-Step Registration Wizard

Let us bring everything together into a complete, working wizard. This example includes all the patterns we have discussed: shared state, per-step validation, step indicators, navigation, localStorage persistence, and error handling.

// RegistrationWizard.tsx
'use client';

import { useState, useEffect, useRef } from 'react';

// ── Types ──
interface FormData {
  firstName: string;
  lastName: string;
  email: string;
  phone: string;
  street: string;
  city: string;
  state: string;
  zip: string;
  newsletter: boolean;
  contactMethod: 'email' | 'phone' | 'text';
  theme: 'light' | 'dark' | 'system';
}

interface StepProps {
  data: FormData;
  onUpdate: (fields: Partial<FormData>) => void;
  errors: Record<string, string>;
}

const defaultFormData: FormData = {
  firstName: '', lastName: '', email: '', phone: '',
  street: '', city: '', state: '', zip: '',
  newsletter: false, contactMethod: 'email', theme: 'system',
};

// ── Validation ──
function validateStep0(data: FormData) {
  const errors: Record<string, string> = {};
  if (!data.firstName.trim()) errors.firstName = 'First name is required';
  if (!data.lastName.trim()) errors.lastName = 'Last name is required';
  if (!data.email.trim()) errors.email = 'Email is required';
  else if (!/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(data.email))
    errors.email = 'Invalid email format';
  return errors;
}

function validateStep1(data: FormData) {
  const errors: Record<string, string> = {};
  if (!data.street.trim()) errors.street = 'Street is required';
  if (!data.city.trim()) errors.city = 'City is required';
  if (!data.state.trim()) errors.state = 'State is required';
  if (!data.zip.trim()) errors.zip = 'ZIP code is required';
  else if (!/^\d{5}(-\d{4})?$/.test(data.zip))
    errors.zip = 'Invalid ZIP code';
  return errors;
}

function validateStep2() { return {}; }
function validateStep3() { return {}; }

// ── Steps Configuration ──
const STEPS = [
  { label: 'Personal Info', validate: validateStep0 },
  { label: 'Address',       validate: validateStep1 },
  { label: 'Preferences',   validate: validateStep2 },
  { label: 'Review',        validate: validateStep3 },
];

const STORAGE_KEY = 'registration-draft';

// ── Main Wizard Component ──
export default function RegistrationWizard() {
  // Load persisted data
  const [formData, setFormData] = useState<FormData>(() => {
    if (typeof window === 'undefined') return defaultFormData;
    const saved = localStorage.getItem(STORAGE_KEY);
    if (saved) {
      try { return { ...defaultFormData, ...JSON.parse(saved) }; }
      catch { return defaultFormData; }
    }
    return defaultFormData;
  });

  const [currentStep, setCurrentStep] = useState(() => {
    if (typeof window === 'undefined') return 0;
    const saved = localStorage.getItem(STORAGE_KEY + '-step');
    return saved ? parseInt(saved, 10) : 0;
  });

  const [errors, setErrors] = useState<Record<string, string>>({});
  const [isSubmitting, setIsSubmitting] = useState(false);
  const [submitError, setSubmitError] = useState<string | null>(null);

  // Ref for focus management
  const stepRef = useRef<HTMLDivElement>(null);

  // Persist form data
  useEffect(() => {
    localStorage.setItem(STORAGE_KEY, JSON.stringify(formData));
  }, [formData]);

  useEffect(() => {
    localStorage.setItem(STORAGE_KEY + '-step', String(currentStep));
  }, [currentStep]);

  // Focus the step container when step changes (accessibility)
  useEffect(() => {
    stepRef.current?.focus();
  }, [currentStep]);

  // Update function for child steps
  function updateFormData(fields: Partial<FormData>) {
    setFormData(prev => ({ ...prev, ...fields }));
  }

  // Navigation
  function handleNext() {
    const stepErrors = STEPS[currentStep].validate(formData);
    if (Object.keys(stepErrors).length > 0) {
      setErrors(stepErrors);
      return;
    }
    setErrors({});
    setCurrentStep(prev => Math.min(prev + 1, STEPS.length - 1));
  }

  function handleBack() {
    setErrors({});
    setCurrentStep(prev => Math.max(prev - 1, 0));
  }

  async function handleSubmit() {
    // Final validation sweep
    for (let i = 0; i < STEPS.length; i++) {
      const stepErrors = STEPS[i].validate(formData);
      if (Object.keys(stepErrors).length > 0) {
        setCurrentStep(i);
        setErrors(stepErrors);
        return;
      }
    }

    setIsSubmitting(true);
    setSubmitError(null);

    try {
      const response = await fetch('/api/register', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(formData),
      });

      if (!response.ok) throw new Error('Registration failed');

      // Success: clean up and redirect
      localStorage.removeItem(STORAGE_KEY);
      localStorage.removeItem(STORAGE_KEY + '-step');
      window.location.href = '/welcome';
    } catch (err) {
      setSubmitError(err instanceof Error ? err.message : 'Unknown error');
    } finally {
      setIsSubmitting(false);
    }
  }

  const isFirstStep = currentStep === 0;
  const isLastStep = currentStep === STEPS.length - 1;

  return (
    <div className="wizard-container">
      {/* Step Indicator */}
      <StepIndicator steps={STEPS} currentStep={currentStep} />

      {/* Screen reader announcement */}
      <div
        role="status"
        aria-live="polite"
        className="sr-only"
      >
        Step {currentStep + 1} of {STEPS.length}: {STEPS[currentStep].label}
      </div>

      {/* Current Step */}
      <div
        ref={stepRef}
        tabIndex={-1}
        className="wizard-step"
        aria-label={`Step ${currentStep + 1}: ${STEPS[currentStep].label}`}
      >
        <h2>{STEPS[currentStep].label}</h2>

        {currentStep === 0 && <StepPersonalInfo data={formData} onUpdate={updateFormData} errors={errors} />}
        {currentStep === 1 && <StepAddress data={formData} onUpdate={updateFormData} errors={errors} />}
        {currentStep === 2 && <StepPreferences data={formData} onUpdate={updateFormData} errors={errors} />}
        {currentStep === 3 && <StepReview data={formData} onUpdate={updateFormData} errors={errors} />}
      </div>

      {/* Submit Error */}
      {submitError && (
        <div className="submit-error" role="alert">
          <strong>Error:</strong> {submitError}
        </div>
      )}

      {/* Navigation Buttons */}
      <div className="wizard-nav">
        {!isFirstStep && (
          <button type="button" onClick={handleBack}>Back</button>
        )}
        <div style={{ flex: 1 }} />
        {isLastStep ? (
          <button
            type="button"
            onClick={handleSubmit}
            disabled={isSubmitting}
          >
            {isSubmitting ? 'Submitting...' : 'Submit Registration'}
          </button>
        ) : (
          <button type="button" onClick={handleNext}>Next</button>
        )}
      </div>
    </div>
  );
}

This complete example demonstrates every concept from this lesson working together: state management, step navigation, validation, localStorage persistence, error handling, and accessibility features. Each step component receives the same props interface, and the parent wizard orchestrates everything.

Accessibility: Focus Management and Screen Reader Support

Multi-step forms present unique accessibility challenges. When the user clicks "Next" and the step changes, a sighted user sees the new content appear. But a screen reader user hears nothing unless you explicitly manage focus and announcements.

Focus Management Between Steps

When the step changes, move focus to the top of the new step. This ensures keyboard users and screen reader users start at the right place:

// The step container has tabIndex={-1} so it can receive focus
<div
  ref={stepRef}
  tabIndex={-1}
  className="wizard-step"
  aria-label={`Step ${currentStep + 1}: ${STEPS[currentStep].label}`}
>
  {/* Step content */}
</div>

// When step changes, focus the container
useEffect(() => {
  stepRef.current?.focus();
}, [currentStep]);

The tabIndex={-1} attribute makes the element focusable via JavaScript but not via the Tab key. This is exactly what we want: focus moves here when the step changes, but the user's next Tab press goes to the first form field within the step.

Screen Reader Announcements

Use an ARIA live region to announce the step change:

<div
  role="status"
  aria-live="polite"
  className="sr-only"
>
  Step {currentStep + 1} of {STEPS.length}: {STEPS[currentStep].label}
</div>

The sr-only class visually hides this element but keeps it available to screen readers. When its content changes (because currentStep changed), the screen reader announces the new text: "Step 2 of 4: Address."

Additional Accessibility Practices

  • Use aria-invalid="true" on fields with validation errors
  • Use aria-describedby to associate error messages with their fields
  • Use role="alert" on error messages so screen readers announce them immediately
  • Use aria-current="step" on the current step indicator circle
  • Ensure all navigation buttons have visible focus styles
  • Do not use aria-disabled on upcoming step indicators — use the HTML disabled attribute instead
Do Not Auto-Advance Steps Some forms auto-advance to the next step when all fields are filled. This is disorienting for screen reader users because the page changes without any explicit action. Always require the user to click "Next" to advance. The user should be in control of when the context changes.

Hands-On Exercises

  1. Two-step form: Build a simple two-step form (Step 1: Name and Email, Step 2: Review and Submit). Use useState for form data and current step. Add a Back button on step 2 and a Submit button that logs the data to the console.
  2. Step indicator: Add a visual step indicator to the form from Exercise 1. Show numbered circles with the current step highlighted and completed steps showing a checkmark. Make completed steps clickable.
  3. Per-step validation: Add validation to your form. Step 1 should require both name and email, and email must be a valid format. The Next button should not advance if there are errors. Display error messages below the fields.
  4. localStorage persistence: Add localStorage saving to your form. When the user refreshes the page, the form data and current step should be restored. Add a "Clear saved data" button.
  5. Four-step wizard: Expand your form into a four-step wizard: Personal Info, Address, Preferences, and Review. Implement the complete pattern from the lesson including validation, persistence, and a review step that displays all entered data.
  6. Accessibility audit: Tab through your wizard using only the keyboard. Verify that focus moves to the step content when you click Next, that screen readers announce the current step, and that error messages are associated with their fields using aria-describedby.

Key Takeaways

  • Multi-step forms reduce overwhelm by breaking long forms into focused, manageable chunks.
  • Wizard state has two parts: the current step index (which step to show) and the shared form data (all fields across all steps in one object).
  • Each step is its own component that receives data, an update callback, and errors through a consistent interface.
  • Validate each step before allowing the user to advance — catch errors early, not all at the end.
  • A step indicator shows progress and lets users navigate back to completed steps.
  • On final submission, run a validation sweep across all steps and jump the user to any step with errors.
  • Persist form data and current step to localStorage so users do not lose progress if they close the tab.
  • Always clear saved data after successful submission.
  • For accessibility: move focus to the new step content, announce step changes to screen readers, and never auto-advance steps.
