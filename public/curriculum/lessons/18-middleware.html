Middleware & the Request Pipeline

Intercept every request before it reaches your pages or API routes -- the gatekeeper of your application.

What You Will Learn

  • Understand what middleware is and why it runs before every request
  • Create and configure the middleware.ts file
  • Use the matcher config to target specific routes
  • Add security headers to every response
  • Redirect unauthenticated users to the login page
  • Implement role-based route protection
  • Read and set cookies in middleware
  • Visualize the complete request pipeline from browser to response

What Is Middleware?

Middleware is code that runs before a request reaches your page or API route handler. Every incoming request to your application passes through middleware first, giving you the chance to inspect, modify, redirect, or reject it.

Analogy: Middleware is like a security checkpoint at a building entrance. Before anyone reaches their destination floor (your page or API route), they must pass through the checkpoint. The guard can check their ID (authentication), verify they have clearance for that floor (authorization), attach a visitor badge (set headers), redirect them to the right entrance (URL rewriting), or turn them away entirely (block the request).

Common Use Cases for Middleware

  • Authentication: Check if the user is logged in before allowing access to protected pages
  • Authorization: Verify the user has the right role for the requested route
  • Security headers: Add protective HTTP headers to every response
  • Redirects: Send users to different URLs based on conditions
  • Logging: Record information about every request for monitoring
  • URL rewriting: Modify the request URL before it reaches the handler
  • Rate limiting: Block excessive requests from a single source

The middleware.ts File

Next.js middleware lives in a single file at the root of your project (or inside src/ if you use the src directory). The file must be named exactly middleware.ts (or middleware.js):

project-root/
├── src/
│   ├── app/
│   │   └── ...
│   └── middleware.ts       # Middleware file (inside src/)
├── package.json
└── next.config.mjs

The file exports a single default function (named middleware) that receives the incoming request and returns a response:

// src/middleware.ts
import { NextRequest, NextResponse } from 'next/server';

export function middleware(request: NextRequest) {
  // This runs before EVERY matched request
  console.log('Request to:', request.nextUrl.pathname);

  // Continue to the actual page/API route
  return NextResponse.next();
}

NextResponse.next() tells Next.js "let this request continue to its destination." If you do not call this, the request is effectively blocked.

The Matcher Config: Targeting Specific Routes

By default, middleware runs on every request -- including requests for images, fonts, and static files. This is wasteful. The config.matcher export lets you specify exactly which routes should trigger your middleware:

// src/middleware.ts

export function middleware(request: NextRequest) {
  // ... your logic
  return NextResponse.next();
}

// Only run middleware on these routes
export const config = {
  matcher: [
    // Match all routes EXCEPT static files, images, and favicon
    '/((?!_next/static|_next/image|favicon.ico|.*\\.(?:svg|png|jpg|jpeg|gif|webp|ico)$).*)',
  ],
};

The matcher above is a regular expression that excludes:

  • _next/static -- Next.js static file chunks
  • _next/image -- Next.js optimized images
  • favicon.ico -- The browser tab icon
  • Any file ending in common image extensions

Multiple Specific Matchers

You can also list specific route patterns:

export const config = {
  matcher: [
    '/admin/:path*',     // All admin routes
    '/api/:path*',       // All API routes
    '/portal/:path*',    // Customer portal routes
  ],
};
The :path* Syntax: In matcher patterns, :path* matches zero or more path segments. So /admin/:path* matches /admin, /admin/blog, /admin/blog/new, and so on.

Adding Security Headers

One of the most common and important uses of middleware is adding security headers to every response. These headers instruct the browser to enable various security protections:

// src/middleware.ts
import { NextRequest, NextResponse } from 'next/server';

function addSecurityHeaders(response: NextResponse): void {
  // Prevent the page from being loaded in an iframe (clickjacking protection)
  response.headers.set('X-Frame-Options', 'DENY');

  // Prevent the browser from guessing the MIME type (MIME sniffing attacks)
  response.headers.set('X-Content-Type-Options', 'nosniff');

  // Control how much referrer information is sent with requests
  response.headers.set('Referrer-Policy', 'strict-origin-when-cross-origin');

  // Disable browser features you do not use
  response.headers.set(
    'Permissions-Policy',
    'geolocation=(), microphone=(), camera=(), payment=()'
  );

  // Legacy XSS protection for older browsers
  response.headers.set('X-XSS-Protection', '1; mode=block');
}

export function middleware(request: NextRequest) {
  const response = NextResponse.next();

  // Add security headers to every response
  addSecurityHeaders(response);

  return response;
}

export const config = {
  matcher: ['/((?!_next/static|_next/image|favicon.ico|.*\\.(?:svg|png|jpg|jpeg|gif|webp|ico)$).*)'],
};

What Each Header Does

Header Value Protection Against
X-Frame-Options DENY Clickjacking (embedding your site in a malicious iframe)
X-Content-Type-Options nosniff MIME type confusion attacks
Referrer-Policy strict-origin-when-cross-origin Leaking sensitive URL data to third parties
Permissions-Policy geolocation=(), ... Malicious scripts using device features
X-XSS-Protection 1; mode=block Reflected XSS attacks (older browsers)
Strict-Transport-Security max-age=63072000; includeSubDomains HTTP downgrade attacks (forces HTTPS)
CSK Connection CSK's middleware.ts calls an addSecurityHeaders() function on every request. It sets X-Frame-Options to DENY, X-Content-Type-Options to nosniff, Referrer-Policy, Permissions-Policy (disabling geolocation, microphone, camera, and payment APIs), and X-XSS-Protection. Additionally, next.config.mjs adds HSTS (Strict-Transport-Security) and X-DNS-Prefetch-Control headers via the headers() configuration -- a total of 7 security headers protecting every response.

Authentication: Redirecting Unauthenticated Users

The most impactful use of middleware is protecting routes that require authentication. Instead of checking auth in every page component, middleware handles it centrally:

import { NextRequest, NextResponse } from 'next/server';

// Routes that anyone can access without logging in
const PUBLIC_ROUTES = ['/', '/about', '/contact', '/blog', '/services'];
const PUBLIC_PREFIXES = ['/blog/', '/services/', '/api/public', '/_next'];

function isPublicRoute(pathname: string): boolean {
  if (PUBLIC_ROUTES.includes(pathname)) return true;
  return PUBLIC_PREFIXES.some(prefix => pathname.startsWith(prefix));
}

export function middleware(request: NextRequest) {
  const { pathname } = request.nextUrl;
  const response = NextResponse.next();

  // Add security headers to all responses
  addSecurityHeaders(response);

  // Public routes -- allow without auth
  if (isPublicRoute(pathname)) {
    return response;
  }

  // Check for authentication cookie
  const sessionCookie = request.cookies.get('session_token');

  if (!sessionCookie) {
    // Not authenticated -- redirect to login
    const loginUrl = new URL('/login', request.url);

    // Save where they were trying to go so we can redirect back after login
    loginUrl.searchParams.set('returnTo', pathname);

    return NextResponse.redirect(loginUrl);
  }

  // Authenticated -- allow through
  return response;
}

This pattern ensures:

  • Public pages (homepage, blog, services) are always accessible
  • Protected pages (admin, portal) require authentication
  • Unauthenticated users are redirected to login with a returnTo URL
  • After logging in, users are sent back to where they originally wanted to go
Why Check Auth in Middleware? Without middleware, you would need to check authentication in every protected page and API route. That means duplicated code, easy-to-forget spots, and inconsistent behavior. Middleware centralizes the check in one place -- if middleware says "not allowed," the page component never even runs.

Role-Based Route Protection

Authentication asks "are you logged in?" Authorization asks "are you allowed to do this?" Many applications have different user roles with different permissions:

// Define which roles can access which routes
const ROUTE_PERMISSIONS: Record<string, string[]> = {
  '/admin':           ['admin', 'technician', 'receptionist'],
  '/admin/settings':  ['admin'],
  '/admin/users':     ['admin'],
  '/admin/tickets':   ['admin', 'technician', 'receptionist'],
  '/admin/blog':      ['admin', 'technician'],
  '/portal':          ['customer', 'admin', 'technician', 'receptionist'],
};

function canAccessRoute(userRoles: string[], pathname: string): boolean {
  // Check from most specific to least specific
  const routes = Object.keys(ROUTE_PERMISSIONS).sort((a, b) => b.length - a.length);

  for (const route of routes) {
    if (pathname.startsWith(route)) {
      const allowedRoles = ROUTE_PERMISSIONS[route];
      return userRoles.some(role => allowedRoles.includes(role));
    }
  }

  // No specific permission defined -- allow authenticated users
  return true;
}

export async function middleware(request: NextRequest) {
  const { pathname } = request.nextUrl;
  const response = NextResponse.next();

  addSecurityHeaders(response);

  // Skip public routes
  if (isPublicRoute(pathname)) return response;

  // Check authentication
  const sessionCookie = request.cookies.get('session_token');
  if (!sessionCookie) {
    const loginUrl = new URL('/login', request.url);
    loginUrl.searchParams.set('returnTo', pathname);
    return NextResponse.redirect(loginUrl);
  }

  // Get user roles (from cookie or database)
  const userRoles = getUserRolesFromSession(sessionCookie.value);

  // Check authorization
  if (!canAccessRoute(userRoles, pathname)) {
    console.log(`[AUTH] Unauthorized: ${pathname} by roles ${JSON.stringify(userRoles)}`);

    // Redirect to appropriate page with error
    const redirectUrl = new URL('/admin', request.url);
    redirectUrl.searchParams.set('error', 'unauthorized');
    return NextResponse.redirect(redirectUrl);
  }

  return response;
}
CSK Connection CSK's middleware implements a multi-role permission system. All /admin/* routes require authentication and use a canAccessRoute() function from a role-helpers library that checks the user's roles array against route-specific permissions. Unauthenticated users hitting /admin are redirected to /login?returnTo=/admin. Users with insufficient roles are redirected to their appropriate dashboard with an ?error=unauthorized parameter. The system supports roles like owner, lead_developer, technician, receptionist, and customer.

Reading and Setting Cookies

Middleware has full access to cookies on both the request (reading) and response (setting):

Reading Cookies

export function middleware(request: NextRequest) {
  // Read a specific cookie
  const session = request.cookies.get('session_token');
  console.log(session?.value); // The cookie value

  // Check if a cookie exists
  const hasSession = request.cookies.has('session_token');

  // Read all cookies
  const allCookies = request.cookies.getAll();
  // Returns: [{ name: 'session_token', value: '...' }, { name: 'theme', value: 'dark' }]

  return NextResponse.next();
}

Setting Cookies

export function middleware(request: NextRequest) {
  const response = NextResponse.next();

  // Set a cookie on the response
  response.cookies.set('visited', 'true', {
    httpOnly: true,       // Cannot be read by JavaScript (XSS protection)
    secure: true,         // Only sent over HTTPS
    sameSite: 'strict',   // Only sent to your domain (CSRF protection)
    maxAge: 60 * 60 * 24, // Expires in 24 hours (in seconds)
    path: '/',            // Available on all routes
  });

  // Delete a cookie
  response.cookies.delete('old_cookie');

  return response;
}

The Complete Request Pipeline

Understanding the full lifecycle of a request helps you know exactly when and where things happen:

Browser sends request | v [1] MIDDLEWARE (middleware.ts) - Check authentication - Add security headers - Redirect if needed - Rewrite URLs | v [2] LAYOUT RENDERING (layout.tsx) - Root layout wraps everything - Nested layouts render in order | v [3] ROUTE HANDLER | +--- Page Route (page.tsx) | - Server Component renders | - Data fetched | - HTML generated | +--- API Route (route.ts) - Handler function executes - JSON response built | v [4] RESPONSE sent back to browser - Security headers included - Cookies set - HTML or JSON body

What Happens at Each Step

Step What Happens Can Be Modified?
1. Middleware Runs first, can redirect, rewrite, or add headers Yes -- full control over request and response
2. Layout Wraps the page content, renders shared UI Yes -- can add context providers, fetch data
3. Route Handler Renders the page or processes the API request Yes -- your main application logic
4. Response Sent to the browser with all modifications applied No -- already sent

Chaining Multiple Middleware Concerns

Since Next.js only supports one middleware.ts file, you need to handle all concerns within that single function. The best approach is to break each concern into a helper function and call them sequentially:

// src/middleware.ts
import { NextRequest, NextResponse } from 'next/server';

// --- Concern 1: Security Headers ---
function addSecurityHeaders(response: NextResponse): void {
  response.headers.set('X-Frame-Options', 'DENY');
  response.headers.set('X-Content-Type-Options', 'nosniff');
  response.headers.set('Referrer-Policy', 'strict-origin-when-cross-origin');
  response.headers.set('Permissions-Policy', 'geolocation=(), microphone=(), camera=()');
  response.headers.set('X-XSS-Protection', '1; mode=block');
}

// --- Concern 2: Route Classification ---
function isPublicRoute(pathname: string): boolean {
  const publicRoutes = ['/', '/about', '/contact', '/login', '/register'];
  const publicPrefixes = ['/blog', '/services', '/api/public', '/api/health', '/_next'];

  if (publicRoutes.includes(pathname)) return true;
  return publicPrefixes.some(p => pathname.startsWith(p));
}

function isAuthRoute(pathname: string): boolean {
  return ['/login', '/register', '/reset-password'].includes(pathname);
}

// --- Concern 3: Authentication ---
function checkAuth(request: NextRequest): { isAuth: boolean; roles: string[] } {
  const session = request.cookies.get('session_token');
  if (!session?.value) return { isAuth: false, roles: [] };

  // In production, you would validate the session here
  const rolesCookie = request.cookies.get('user_roles');
  let roles: string[] = [];
  if (rolesCookie?.value) {
    try { roles = JSON.parse(rolesCookie.value); } catch { /* ignore */ }
  }

  return { isAuth: true, roles };
}

// --- Concern 4: Authorization ---
function canAccessRoute(roles: string[], pathname: string): boolean {
  if (pathname.startsWith('/admin/settings')) {
    return roles.includes('admin') || roles.includes('owner');
  }
  if (pathname.startsWith('/admin')) {
    return roles.some(r => ['admin', 'owner', 'technician', 'receptionist'].includes(r));
  }
  return true;
}

// --- Main Middleware: Chain All Concerns ---
export function middleware(request: NextRequest) {
  const { pathname } = request.nextUrl;
  const response = NextResponse.next();

  // 1. Always add security headers
  addSecurityHeaders(response);

  // 2. Public routes -- no further checks needed
  if (isPublicRoute(pathname)) {
    return response;
  }

  // 3. Check authentication
  const { isAuth, roles } = checkAuth(request);

  // 4. Auth routes -- redirect away if already logged in
  if (isAuthRoute(pathname) && isAuth) {
    return NextResponse.redirect(new URL('/admin', request.url));
  }

  // 5. Protected routes -- redirect to login if not authenticated
  if (!isAuth) {
    const loginUrl = new URL('/login', request.url);
    loginUrl.searchParams.set('returnTo', pathname);
    return NextResponse.redirect(loginUrl);
  }

  // 6. Authorization -- check role permissions
  if (!canAccessRoute(roles, pathname)) {
    const errorUrl = new URL('/admin', request.url);
    errorUrl.searchParams.set('error', 'unauthorized');
    return NextResponse.redirect(errorUrl);
  }

  // 7. All checks passed -- continue
  return response;
}

export const config = {
  matcher: ['/((?!_next/static|_next/image|favicon.ico|.*\\.(?:svg|png|jpg|jpeg|gif|webp|ico)$).*)'],
};

This pattern keeps each concern isolated in its own function while maintaining a clear, readable flow in the main middleware function.

URL Rewriting and Redirects

Middleware can also rewrite URLs (change the destination without the user seeing it) or redirect (send the user to a different URL):

Redirect (URL Changes in Browser)

// Permanently redirect old URLs to new ones
if (pathname === '/old-page') {
  return NextResponse.redirect(new URL('/new-page', request.url));
}

// Redirect with a specific status code
if (pathname === '/moved-page') {
  return NextResponse.redirect(new URL('/new-location', request.url), 301); // Permanent
}

Rewrite (URL Stays the Same in Browser)

// User visits /blog/my-post, but we serve content from /posts/my-post
if (pathname.startsWith('/blog/')) {
  return NextResponse.rewrite(new URL(pathname.replace('/blog/', '/posts/'), request.url));
}
Performance Note: Middleware runs on every matched request. Keep it fast. Avoid heavy computations, large database queries, or long-running operations in middleware. If you need to do something complex (like fetching a user profile from a database), cache the result or keep the query minimal.

Request Logging

Middleware is a natural place to add request logging for monitoring and debugging:

export function middleware(request: NextRequest) {
  const start = Date.now();
  const { pathname, search } = request.nextUrl;
  const method = request.method;

  // Log the incoming request
  console.log(`[${method}] ${pathname}${search}`);

  const response = NextResponse.next();

  // Log the response time
  const duration = Date.now() - start;
  console.log(`[${method}] ${pathname} - ${duration}ms`);

  return response;
}

Exercises

  1. Create basic middleware: Create a middleware.ts file that logs every request's pathname and method to the console. Add the standard matcher config to exclude static files. Visit several pages and observe the logs in your terminal.
  2. Add security headers: Write an addSecurityHeaders function that sets all five security headers from this lesson. Verify they appear in browser DevTools (Network tab, click a request, look at Response Headers).
  3. Protect admin routes: Create a simple authentication check that looks for a session_token cookie. If a user visits any /admin/* route without the cookie, redirect them to /login?returnTo=.... Test by visiting /admin directly.
  4. Redirect authenticated users: If a logged-in user visits /login, redirect them to /admin instead of showing the login page.
  5. Role-based protection: Extend your middleware to read a user_role cookie. Allow only "admin" users to access /admin/settings, while all employees can access /admin. Test with different cookie values.
  6. Request logging: Add timing information to your middleware. Log the HTTP method, pathname, and response time (in milliseconds) for every request. Visit several pages and review the timing data.

Key Takeaways

  • Middleware is a single middleware.ts file that runs before every matched request -- it is your application's gatekeeper.
  • The config.matcher export controls which routes trigger middleware. Always exclude static files.
  • NextResponse.next() continues to the destination; NextResponse.redirect() sends the user elsewhere.
  • Security headers should be added to every response in middleware -- it is the one place you cannot forget.
  • Centralize authentication checks in middleware instead of duplicating them across pages and API routes.
  • Role-based authorization compares the user's roles against route-specific permission rules.
  • Break middleware concerns into separate helper functions for readability and maintainability.
  • The request pipeline flows: Browser --> Middleware --> Layout --> Route Handler --> Response.
  • Keep middleware fast -- it runs on every request and heavy operations will slow down your entire application.
