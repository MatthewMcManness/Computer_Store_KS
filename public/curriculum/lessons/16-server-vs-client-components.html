Phase 4: Next.js

Server Components vs. Client Components

The single most important concept in modern Next.js -- understanding where your code runs changes everything.

What You Will Learn

  • Understand the fundamental difference between Server and Client Components
  • Know that Server Components are the default in the App Router
  • Learn when and why to use the 'use client' directive
  • Fetch data directly in Server Components without useEffect
  • Build a decision framework for choosing the right component type
  • Compose Server and Client Components together effectively
  • Avoid the most common mistakes developers make

Why This Is THE Most Important Concept

In the previous lesson, you learned how Next.js routes work with the App Router. Now we need to understand something that fundamentally changes how you write React code: not all components run in the browser anymore.

In traditional React (the kind you learned in Lessons 12-14), every component runs in the browser. The server sends a JavaScript bundle to the browser, and React renders everything client-side. This means:

  • Every component's code is downloaded by the user's browser
  • Data fetching requires useEffect + useState + loading states
  • Sensitive logic (database queries, API keys) cannot live in components
  • Large libraries inflate the JavaScript bundle size

Next.js App Router introduces a new model: Server Components. These components run only on the server. The browser never sees their code. This single change solves all four problems above.

Analogy: Think of a restaurant kitchen. The Server Component is the chef in the kitchen -- they have access to all the ingredients (database, file system, API keys), do the heavy work (data processing, formatting), and send the finished dish out. The Client Component is the waiter at the table -- they handle the interactive part (taking orders, refilling drinks). The customer (browser) sees the finished meal, not the kitchen.

Server Components: The Default

In the Next.js App Router, every component is a Server Component by default. You do not need to add any special annotation. Just write a normal component:

// src/app/blog/page.tsx
// This is a Server Component -- no directive needed

import { createClient } from '@supabase/supabase-js';

const supabase = createClient(
  process.env.NEXT_PUBLIC_SUPABASE_URL!,
  process.env.SUPABASE_SERVICE_ROLE_KEY! // Secret! Safe here because it never reaches the browser
);

export default async function BlogPage() {
  // Fetch data directly -- no useEffect, no useState, no loading state
  const { data: posts } = await supabase
    .from('blog_posts')
    .select('id, title, slug, excerpt, published_at')
    .eq('status', 'published')
    .order('published_at', { ascending: false });

  return (
    <main>
      <h1>Our Blog</h1>
      {posts?.map(post => (
        <article key={post.id}>
          <h2>{post.title}</h2>
          <p>{post.excerpt}</p>
          <time>{new Date(post.published_at).toLocaleDateString()}</time>
        </article>
      ))}
    </main>
  );
}

Notice what is different from traditional React:

  • The component is async -- you can use await directly
  • No useEffect or useState needed for data fetching
  • The database service key (SUPABASE_SERVICE_ROLE_KEY) is used safely -- this code never ships to the browser
  • The Supabase library code is not included in the client JavaScript bundle

What Server Components Can Do

Capability Example
Access databases directly Query Supabase, PostgreSQL, MongoDB
Use secret environment variables process.env.API_SECRET_KEY
Read the file system fs.readFile('./data/config.json')
Use server-only libraries Heavy parsing, image processing, AI models
Render to HTML on the server Zero JavaScript sent for static content

What Server Components CANNOT Do

Cannot Do Why
Use useState or useReducer No client-side state exists on the server
Use useEffect or useLayoutEffect No browser lifecycle on the server
Add event handlers (onClick, onChange) No user interaction on the server
Use browser APIs (window, localStorage) No browser environment on the server
Use useRouter() or usePathname() These are client-side hooks

Client Components: The Interactive Parts

When you need interactivity -- buttons that respond to clicks, forms that manage state, animations, or anything that requires the browser -- you use a Client Component. You opt into this by adding the 'use client' directive at the very top of the file:

// src/components/features/ContactForm.tsx
'use client'; // This line makes it a Client Component

import { useState } from 'react';

export default function ContactForm() {
  const [name, setName] = useState('');
  const [email, setEmail] = useState('');
  const [message, setMessage] = useState('');
  const [status, setStatus] = useState<'idle' | 'sending' | 'sent' | 'error'>('idle');

  async function handleSubmit(e: React.FormEvent) {
    e.preventDefault();
    setStatus('sending');

    try {
      const res = await fetch('/api/contact', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ name, email, message }),
      });

      if (res.ok) {
        setStatus('sent');
        setName('');
        setEmail('');
        setMessage('');
      } else {
        setStatus('error');
      }
    } catch {
      setStatus('error');
    }
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        type="text"
        value={name}
        onChange={(e) => setName(e.target.value)}
        placeholder="Your name"
        required
      />
      <input
        type="email"
        value={email}
        onChange={(e) => setEmail(e.target.value)}
        placeholder="Your email"
        required
      />
      <textarea
        value={message}
        onChange={(e) => setMessage(e.target.value)}
        placeholder="Your message"
        required
      />
      <button type="submit" disabled={status === 'sending'}>
        {status === 'sending' ? 'Sending...' : 'Send Message'}
      </button>
      {status === 'sent' && <p>Message sent! We will get back to you soon.</p>}
      {status === 'error' && <p>Something went wrong. Please try again.</p>}
    </form>
  );
}
The 'use client' Directive
  • Must be the very first line in the file (before any imports)
  • Tells Next.js: "This component and everything it imports should be included in the browser JavaScript bundle"
  • Is not the same as saying "this only runs in the browser" -- Client Components still render on the server for the initial HTML, then "hydrate" in the browser

Decision Framework: Which Should I Use?

This is the question you will ask yourself dozens of times per project. Here is a comprehensive decision table:

Scenario Component Type Why
Display a list of blog posts from database Server Data fetching, no interactivity needed
Contact form with validation Client Needs useState, onChange, onSubmit
Navigation bar with active link highlighting Client Needs usePathname() hook
Footer with copyright year Server Static content, no interactivity
Image gallery with lightbox Client Needs onClick handlers for modal
Product detail page Server Fetch product data, render HTML
"Add to Cart" button on product page Client Needs onClick, updates cart state
Admin sidebar navigation Client Needs usePathname for active state, mobile toggle
Blog post content (rendered markdown) Server Rendering markdown is a server task
Search input with live filtering Client Needs useState, onChange, real-time updates
Testimonials carousel Client Needs state for current slide, click handlers
Services listing page Server Static data display

The Golden Rule

Default to Server Components. Only add 'use client' when you need interactivity (state, effects, event handlers, or browser APIs). Keep Client Components as small and focused as possible -- push them down to the leaves of your component tree.

Data Fetching in Server Components

One of the biggest advantages of Server Components is how dramatically they simplify data fetching. Compare the old way with the new way:

The Old Way: Client Component with useEffect

'use client';
import { useState, useEffect } from 'react';

export default function BlogPage() {
  const [posts, setPosts] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    async function fetchPosts() {
      try {
        const res = await fetch('/api/blog');
        if (!res.ok) throw new Error('Failed to fetch');
        const data = await res.json();
        setPosts(data);
      } catch (err) {
        setError(err.message);
      } finally {
        setLoading(false);
      }
    }
    fetchPosts();
  }, []);

  if (loading) return <p>Loading...</p>;
  if (error) return <p>Error: {error}</p>;

  return (
    <div>
      {posts.map(post => <h2 key={post.id}>{post.title}</h2>)}
    </div>
  );
}

The New Way: Server Component (async)

// No 'use client' -- this is a Server Component
import { createClient } from '@supabase/supabase-js';

const supabase = createClient(
  process.env.NEXT_PUBLIC_SUPABASE_URL!,
  process.env.SUPABASE_SERVICE_ROLE_KEY!
);

export default async function BlogPage() {
  const { data: posts, error } = await supabase
    .from('blog_posts')
    .select('*')
    .eq('status', 'published')
    .order('published_at', { ascending: false });

  if (error) {
    throw new Error('Failed to load blog posts');
  }

  return (
    <div>
      {posts.map(post => <h2 key={post.id}>{post.title}</h2>)}
    </div>
  );
}

The Server Component version is:

  • Simpler: No useState, no useEffect, no loading state management
  • Faster: Data is fetched on the server (close to the database), HTML is sent already rendered
  • Safer: The service role key never leaves the server
  • Lighter: The Supabase library code is not sent to the browser

Parallel Data Fetching

When a page needs multiple pieces of data, fetch them in parallel with Promise.all:

export default async function DashboardPage() {
  // Both fetches happen simultaneously -- much faster than sequential
  const [customers, tickets] = await Promise.all([
    supabase.from('rs_customers').select('id, name, email').limit(10),
    supabase.from('rs_tickets').select('id, subject, status').limit(10),
  ]);

  return (
    <div>
      <section>
        <h2>Recent Customers</h2>
        {customers.data?.map(c => <p key={c.id}>{c.name}</p>)}
      </section>
      <section>
        <h2>Recent Tickets</h2>
        {tickets.data?.map(t => <p key={t.id}>{t.subject}</p>)}
      </section>
    </div>
  );
}
CSK Connection The CSK blog listing page is a Server Component that fetches posts directly from Supabase. There is no useEffect or client-side loading spinner -- the HTML arrives fully rendered with all blog post data already embedded. The admin reception dashboard similarly uses parallel fetching to load ticket data and customer information simultaneously.

Passing Server Data to Client Components via Props

The most common pattern is a Server Component that fetches data and passes it to a small Client Component for interactivity:

// src/app/blog/page.tsx -- Server Component (fetches data)
import BlogSearch from '@/components/features/BlogSearch';

export default async function BlogPage() {
  const { data: posts } = await supabase
    .from('blog_posts')
    .select('id, title, slug, excerpt, category')
    .eq('status', 'published');

  // Pass server-fetched data to a Client Component as props
  return (
    <main>
      <h1>Blog</h1>
      <BlogSearch posts={posts ?? []} />
    </main>
  );
}

// src/components/features/BlogSearch.tsx -- Client Component (handles interactivity)
'use client';

import { useState } from 'react';
import Link from 'next/link';

interface Post {
  id: string;
  title: string;
  slug: string;
  excerpt: string;
  category: string;
}

export default function BlogSearch({ posts }: { posts: Post[] }) {
  const [searchTerm, setSearchTerm] = useState('');
  const [selectedCategory, setSelectedCategory] = useState('all');

  const categories = ['all', ...new Set(posts.map(p => p.category))];

  const filtered = posts.filter(post => {
    const matchesSearch = post.title.toLowerCase().includes(searchTerm.toLowerCase());
    const matchesCategory = selectedCategory === 'all' || post.category === selectedCategory;
    return matchesSearch && matchesCategory;
  });

  return (
    <div>
      <input
        type="text"
        placeholder="Search posts..."
        value={searchTerm}
        onChange={(e) => setSearchTerm(e.target.value)}
      />
      <select value={selectedCategory} onChange={(e) => setSelectedCategory(e.target.value)}>
        {categories.map(cat => (
          <option key={cat} value={cat}>{cat}</option>
        ))}
      </select>
      {filtered.map(post => (
        <article key={post.id}>
          <Link href={`/blog/${post.slug}`}>
            <h2>{post.title}</h2>
          </Link>
          <p>{post.excerpt}</p>
        </article>
      ))}
    </div>
  );
}
Data Serialization Rule: Props passed from Server to Client Components must be serializable -- they can only be plain objects, arrays, strings, numbers, booleans, null, or Date objects. You cannot pass functions, class instances, or Symbols. Think of it as: "Could this be converted to JSON?"

Performance Implications

The split between Server and Client Components has a massive impact on performance:

Less JavaScript = Faster Pages

Every Client Component's code gets included in the JavaScript bundle that the browser downloads. Server Components send zero JavaScript -- only the rendered HTML.

Traditional React App (everything is client): Bundle: React + ReactDOM + Router + Supabase + date-fns + all components Size: ~250KB+ JavaScript Next.js with Server Components: Bundle: React + ReactDOM + only 'use client' components Size: ~80KB JavaScript (server-heavy libraries excluded)

For a blog listing page that uses a date formatting library like date-fns, using a Server Component means date-fns (47KB) never gets sent to the browser. The dates are formatted on the server and sent as plain text in the HTML.

Faster Time to Content

With Server Components, the user sees content faster because:

  1. The server fetches data (typically fast -- server is close to the database)
  2. The server renders HTML with that data
  3. The browser receives and displays the HTML immediately
  4. No "loading spinner while fetching" step for the user

Composing Server and Client Components

The key to effective Next.js architecture is composing both types of components together. Here are the rules:

Rule 1: Server Components Can Render Client Components

// Server Component (page.tsx)
import InteractiveButton from '@/components/ui/InteractiveButton'; // Client Component

export default async function ProductPage() {
  const product = await getProduct();

  return (
    <div>
      <h1>{product.name}</h1>
      <p>{product.description}</p>
      <InteractiveButton productId={product.id} />  {/* Client in Server: OK */}
    </div>
  );
}

Rule 2: Client Components CANNOT Import Server Components

// This does NOT work!
'use client';

import ServerOnlyWidget from './ServerOnlyWidget'; // ERROR: Cannot import Server Component

export default function ClientPage() {
  return <ServerOnlyWidget />; // Will not work
}

Rule 3: Client Components CAN Receive Server Components as Children

This is the escape hatch. Instead of importing a Server Component inside a Client Component, pass it as children:

// Server Component -- parent orchestrates the composition
import ClientWrapper from '@/components/ui/ClientWrapper';
import ServerContent from '@/components/ServerContent';

export default function Page() {
  return (
    <ClientWrapper>
      <ServerContent />  {/* Server Component passed as children */}
    </ClientWrapper>
  );
}

// Client Component -- accepts children without knowing their type
'use client';

export default function ClientWrapper({ children }: { children: React.ReactNode }) {
  const [isOpen, setIsOpen] = useState(true);

  return (
    <div>
      <button onClick={() => setIsOpen(!isOpen)}>Toggle</button>
      {isOpen && children}
    </div>
  );
}
Analogy: Think of Server Components as pre-made dishes and Client Components as interactive serving stations. A serving station (Client Component) can display any pre-made dish (Server Component children) -- it just needs to receive them, not make them itself.

Common Mistakes and How to Avoid Them

Mistake 1: Adding 'use client' to Everything

Developers coming from traditional React often add 'use client' to every file out of habit. This defeats the purpose of Server Components and inflates your JavaScript bundle.

// BAD: Unnecessary 'use client'
'use client'; // Why? This component has no interactivity!

export default function Footer() {
  return (
    <footer>
      <p>Copyright 2026</p>
    </footer>
  );
}

// GOOD: No directive needed -- Server Component by default
export default function Footer() {
  return (
    <footer>
      <p>Copyright 2026</p>
    </footer>
  );
}

Mistake 2: Huge Client Component Boundaries

Marking a whole page as 'use client' because one small part needs interactivity.

// BAD: The entire page is a Client Component because of one button
'use client';

export default function ServicesPage() {
  return (
    <main>
      <h1>Our Services</h1>
      {/* 50 lines of static content... */}
      <button onClick={() => alert('Contact us!')}>Get Started</button>
    </main>
  );
}

// GOOD: Only the interactive part is a Client Component
// ServicesPage stays as a Server Component
import GetStartedButton from '@/components/ui/GetStartedButton';

export default function ServicesPage() {
  return (
    <main>
      <h1>Our Services</h1>
      {/* 50 lines of static content -- no JS sent */}
      <GetStartedButton />  {/* Only this sends JS to the browser */}
    </main>
  );
}

Mistake 3: Using useEffect for Data Fetching in Server Components

// BAD: Don't do this in a Server Component
'use client'; // Forced to add this because of useEffect

import { useState, useEffect } from 'react';

export default function UsersPage() {
  const [users, setUsers] = useState([]);
  useEffect(() => {
    fetch('/api/users').then(r => r.json()).then(setUsers);
  }, []);
  return <div>{users.map(u => <p key={u.id}>{u.name}</p>)}</div>;
}

// GOOD: Async Server Component -- much simpler and faster
export default async function UsersPage() {
  const users = await getUsers(); // Direct database/API call
  return <div>{users.map(u => <p key={u.id}>{u.name}</p>)}</div>;
}

Mistake 4: Trying to Use Hooks in Server Components

// BAD: useState does not work in Server Components
export default function Counter() {
  const [count, setCount] = useState(0); // ERROR!
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}

// GOOD: Extract the interactive part into a Client Component
// Counter.tsx
'use client';
import { useState } from 'react';

export default function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}

Mistake 5: Passing Non-Serializable Props

// BAD: Functions cannot be passed from Server to Client
export default function Page() {
  function handleClick() { console.log('clicked'); }

  return <ClientButton onClick={handleClick} />; // ERROR: functions are not serializable
}

// GOOD: Define the handler inside the Client Component
// ClientButton.tsx
'use client';

export default function ClientButton() {
  function handleClick() { console.log('clicked'); }
  return <button onClick={handleClick}>Click me</button>;
}
CSK Connection In Computer Store KS, the architecture follows these patterns precisely. Public pages like the blog listing, services hub, and about page are Server Components that fetch data directly from Supabase. Interactive elements are isolated into small Client Components: the contact form uses 'use client' for form state and submission, the testimonials carousel uses it for slide navigation, the admin ticket filter buttons use it for status filtering, and the gallery editor uses it for image upload and management. The admin sidebar is also a Client Component because it needs usePathname() to highlight the current page.

The Mental Model: A Visual Summary

Your Page Component Tree: ServerPage (async, fetches data) -- Runs on Server ├── ServerHeader -- Runs on Server │ ├── Logo -- Runs on Server │ └── ClientNav ('use client') -- Runs on Client │ └── usePathname() for active link ├── ServerContent (renders markdown) -- Runs on Server │ └── ClientShareButton ('use client') -- Runs on Client │ └── onClick to copy URL └── ServerFooter -- Runs on Server JavaScript sent to browser: ClientNav + ClientShareButton only Everything else: rendered to HTML on the server, zero JS cost

Key Takeaways

  • In the App Router, every component is a Server Component by default. No directive needed.
  • Server Components run only on the server: they can access databases, secrets, and the file system. They send zero JavaScript to the browser.
  • Client Components are activated with 'use client' and are needed for interactivity: state, effects, event handlers, and browser APIs.
  • Server Components can be async -- use await directly for data fetching instead of useEffect.
  • Push 'use client' boundaries as far down the component tree as possible. Keep interactive parts small and isolated.
  • Server Components can render Client Components. Client Components cannot import Server Components, but can accept them as children.
  • Props passed from Server to Client must be serializable (no functions, no class instances).
  • Less JavaScript shipped to the browser means faster pages and better user experience.
