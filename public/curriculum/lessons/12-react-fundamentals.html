What Is React and Why Does It Dominate?

React is a JavaScript library for building user interfaces. Created by Facebook (now Meta) in 2013, it has become the most widely used front-end library in the world. When you visit sites like Facebook, Instagram, Netflix, Airbnb, or Uber, you are looking at React applications.

But why did React become so popular? To understand that, we need to understand the problem it solves.

The Problem: Keeping the UI in Sync with Data

In the previous lessons, you learned to manipulate the DOM with vanilla JavaScript. You selected elements, changed their text, added event listeners, and toggled classes. This works well for simple pages, but imagine building something like a ticket management dashboard where:

  • A list of tickets updates every 30 seconds
  • Clicking a status filter changes which tickets are visible
  • A search box filters tickets in real time
  • Each ticket card shows customer name, status badge, and creation date
  • Clicking a ticket opens a detail panel

With vanilla JavaScript, you would need to manually find every DOM element that needs updating, change its content, add or remove elements from lists, and keep everything in sync. As the application grows, this becomes a tangled mess of document.querySelector calls and innerHTML assignments. One missed update creates a bug where the UI shows stale data.

Analogy: Imagine you are running a restaurant kitchen. Without React, you are the chef AND the waiter — you cook the food AND personally walk each dish to every table, remembering which table ordered what. With React, you just update the menu board (your data), and a team of efficient waiters (React's rendering engine) automatically delivers the right dishes to the right tables. You describe what should be served, not how to deliver it.

React's Solution: Declarative UI

React introduces a fundamentally different approach. Instead of telling the browser how to update the DOM step by step (imperative), you describe what the UI should look like for any given data (declarative). React figures out the most efficient way to update the actual DOM to match.

// Imperative (vanilla JS) - HOW to update
const list = document.querySelector('.ticket-list');
list.innerHTML = '';
tickets.forEach(ticket => {
  const li = document.createElement('li');
  li.textContent = ticket.subject;
  list.appendChild(li);
});

// Declarative (React) - WHAT the UI should be
function TicketList({ tickets }) {
  return (
    <ul className="ticket-list">
      {tickets.map(ticket => (
        <li key={ticket.id}>{ticket.subject}</li>
      ))}
    </ul>
  );
}

The React version says "here is what a ticket list looks like given some data." When the data changes, React automatically re-runs this function and updates only the parts of the DOM that actually changed.

The Virtual DOM

React achieves its efficiency through something called the virtual DOM. Here is how it works:

  1. Render: When your data changes, React calls your component functions and builds a lightweight JavaScript representation of what the DOM should look like. This is the virtual DOM — a plain JavaScript object tree, not actual DOM nodes.
  2. Diff: React compares the new virtual DOM with the previous one to figure out exactly what changed. This comparison is called "reconciliation."
  3. Patch: React applies only the minimal set of changes to the real DOM. If one ticket's status changed out of 50 tickets, React updates just that one element — not all 50.
Virtual DOM Flow: Your Data Changes | v +------------------+ +------------------+ | New Virtual DOM | vs | Old Virtual DOM | | (JS objects) | | (JS objects) | +------------------+ +------------------+ | v Diff / Reconcile | v +------------------+ | Minimal DOM | | Updates Applied | +------------------+

This is much faster than wiping out a section of the DOM and rebuilding it from scratch, which is what many vanilla JavaScript approaches do with innerHTML.

The Component Model

React's other big idea is components. Instead of building a page as one giant HTML file, you break it into small, self-contained pieces. Each piece is a component — a JavaScript function that returns a description of what part of the UI should look like.

A Page Broken Into Components: +-----------------------------------------------+ | <Header /> | | [Logo] [Nav Links] [Search] | +-----------------------------------------------+ | | | +-------------------+ +--------------------+ | | | <Sidebar /> | | <TicketList /> | | | | [Filters] | | <TicketCard /> | | | | [Status Counts] | | <TicketCard /> | | | +-------------------+ | <TicketCard /> | | | +--------------------+ | +-----------------------------------------------+ | <Footer /> | +-----------------------------------------------+

Components are reusable. Build a <TicketCard /> once and render it 50 times with different data. Components are composable. Combine simple components to build complex interfaces. Components are isolated. A bug in the sidebar does not break the ticket list.

The TestimonialsCarousel component is reused wherever customer reviews need to be shown. The gallery page renders a grid of FlipCard components — each one displaying a different computer.

Creating a React Project

The easiest way to start a React project with TypeScript in 2026 is using Vite (pronounced "veet"), a lightning-fast build tool. In a real production project, you would typically use Next.js (which we cover in Lesson 15), but Vite is perfect for learning React fundamentals without the added complexity.

# Create a new React + TypeScript project
npm create vite@latest my-react-app -- --template react-ts

# Move into the project folder
cd my-react-app

# Install dependencies
npm install

# Start the development server
npm run dev

Open your browser to the URL shown (usually http://localhost:5173). You should see a starter page with a Vite + React logo.

Project Structure

Here is what a fresh Vite + React project looks like:

my-react-app/
  public/              # Static files (favicon, images)
  src/
    App.tsx            # Main application component
    App.css            # Styles for App
    main.tsx           # Entry point - renders App into the DOM
    index.css          # Global styles
    vite-env.d.ts      # TypeScript type declarations for Vite
  index.html           # The single HTML page
  package.json         # Dependencies and scripts
  tsconfig.json        # TypeScript configuration
  vite.config.ts       # Vite configuration

The key file is main.tsx. It takes your root <App /> component and renders it into the <div id="root"> element in index.html:

// src/main.tsx
import React from 'react'
import ReactDOM from 'react-dom/client'
import App from './App'
import './index.css'

ReactDOM.createRoot(
  document.getElementById('root')!
).render(
  <React.StrictMode>
    <App />
  </React.StrictMode>
)

React.StrictMode is a development-only wrapper that helps catch common mistakes by running your components twice and warning about unsafe patterns. It does not affect production.

JSX: JavaScript + XML (It Is Not HTML!)

The most striking thing about React code is JSX — that HTML-like syntax sitting inside your JavaScript. JSX stands for JavaScript XML, and it is a syntax extension to JavaScript. It looks like HTML, but it is NOT HTML. It is closer to JavaScript wearing an HTML costume.

// This is JSX - it looks like HTML but compiles to JavaScript
const element = <h1>Hello, world!</h1>;

// Under the hood, the compiler transforms it to this:
const element = React.createElement('h1', null, 'Hello, world!');

The build tool (Vite, in our case) transforms JSX into regular JavaScript function calls before the browser ever sees it. The browser never processes JSX directly.

Key Differences from HTML

Because JSX is JavaScript, not HTML, there are several important differences you must know:

HTML JSX Why
class="btn" className="btn" class is a reserved word in JavaScript
for="email" htmlFor="email" for is a reserved word in JavaScript
style="color: red" style={{ color: 'red' }} Styles are JavaScript objects, not strings
onclick="handleClick()" onClick={handleClick} Event handlers use camelCase and take functions
<img src="..."> <img src="..." /> All tags must be closed (self-closing slash required)
tabindex="0" tabIndex={0} Multi-word attributes use camelCase

Expressions in Curly Braces

The curly braces {} are JSX's escape hatch into JavaScript. Anything inside curly braces is evaluated as a JavaScript expression:

const name = 'Computer Store KS';
const ticketCount = 42;

const element = (
  <div>
    <h1>Welcome to {name}</h1>                     {/* Variable */}
    <p>You have {ticketCount} open tickets</p>        {/* Variable */}
    <p>{ticketCount > 0 ? 'Busy day!' : 'All clear'}</p>  {/* Expression */}
    <p>{new Date().toLocaleDateString()}</p>     {/* Method call */}
    <p>{2 + 2}</p>                                  {/* Math: shows 4 */}
  </div>
);
Important: You can only put expressions inside curly braces — things that produce a value. You cannot put statements like if, for, or let inside curly braces. That is why we use ternary operators and .map() instead (covered later in this lesson).

Style Objects

In JSX, the style attribute takes a JavaScript object, not a CSS string. Property names use camelCase instead of kebab-case:

// In HTML:  style="background-color: blue; font-size: 16px; margin-top: 10px;"
// In JSX:
const myStyles = {
  backgroundColor: 'blue',       // background-color becomes backgroundColor
  fontSize: '16px',              // font-size becomes fontSize
  marginTop: '10px',             // margin-top becomes marginTop
};

<div style={myStyles}>Styled content</div>

// Or inline (note the double curly braces: outer = JSX expression, inner = object literal)
<div style={{ color: 'red', fontWeight: 'bold' }}>Bold red text</div>

In practice, most React projects use CSS classes (via className) or a framework like Tailwind CSS rather than inline styles. Inline styles are useful for dynamic values that depend on data (like setting a progress bar width).

JSX Must Have One Root Element

A JSX expression must return exactly one root element. If you need to return multiple elements side by side, wrap them in a parent <div> or use a Fragment:

// Error! Multiple root elements
return (
  <h1>Title</h1>
  <p>Paragraph</p>
);

// Solution 1: Wrap in a div
return (
  <div>
    <h1>Title</h1>
    <p>Paragraph</p>
  </div>
);

// Solution 2: Use a Fragment (adds no extra DOM node)
return (
  <>
    <h1>Title</h1>
    <p>Paragraph</p>
  </>
);

The <>...</> syntax is shorthand for <React.Fragment>...</React.Fragment>. It groups elements without adding an extra <div> to the DOM.

Components: Functions That Return JSX

A React component is simply a JavaScript function that returns JSX. That is it. The function name must start with a capital letter (this is how React distinguishes components from regular HTML tags).

// A simple component
function Welcome() {
  return <h1>Welcome to our store!</h1>;
}

// Using it (just like an HTML tag, but capitalized)
function App() {
  return (
    <div>
      <Welcome />
      <Welcome />
      <Welcome />
    </div>
  );
}

This renders "Welcome to our store!" three times. The component is reusable — define once, use everywhere.

Naming Convention: Component names must start with an uppercase letter. <welcome /> would be treated as an HTML element (and fail). <Welcome /> is treated as a React component. This is a hard rule, not a style preference.

You can also write components as arrow functions, which is equally common:

// Arrow function component
const Welcome = () => {
  return <h1>Welcome to our store!</h1>;
};

// With implicit return (no curly braces = automatic return)
const Welcome = () => <h1>Welcome to our store!</h1>;

Props: Passing Data to Components

A component that always shows the same thing is not very useful. Props (short for "properties") let you pass data into a component, making it dynamic and reusable.

Analogy: Think of a component as a cookie cutter and props as the dough. The cookie cutter (component) defines the shape, but the dough (props) determines the flavor and color. Same shape, different cookies. 
// Component that accepts props
function Greeting(props) {
  return <h1>Hello, {props.name}! You have {props.ticketCount} tickets.</h1>;
}

// Using it - props are passed like HTML attributes
function App() {
  return (
    <div>
      <Greeting name="Matthew" ticketCount={5} />
      <Greeting name="Sarah" ticketCount={12} />
      <Greeting name="Mike" ticketCount={0} />
    </div>
  );
}

Destructuring Props

Writing props.name and props.ticketCount everywhere gets tedious. JavaScript destructuring lets you pull out the values directly:

// Destructuring in the parameter list (most common pattern)
function Greeting({ name, ticketCount }) {
  return <h1>Hello, {name}! You have {ticketCount} tickets.</h1>;
}

TypeScript Typing for Props

Since we are using TypeScript, we should define the shape of our props. This catches bugs at compile time and gives you autocomplete in your editor:

// Define a type or interface for the props
interface GreetingProps {
  name: string;
  ticketCount: number;
}

// Use the type in the component
function Greeting({ name, ticketCount }: GreetingProps) {
  return <h1>Hello, {name}! You have {ticketCount} tickets.</h1>;
}

// Now TypeScript catches errors:
<Greeting name={42} />          // Error! name must be a string
<Greeting name="Bob" />        // Error! ticketCount is required
<Greeting name="Bob" ticketCount={5} />  // Correct!

Optional Props and Default Values

interface ButtonProps {
  label: string;
  variant?: 'primary' | 'secondary' | 'danger';  // ? makes it optional
  disabled?: boolean;
}

function Button({ label, variant = 'primary', disabled = false }: ButtonProps) {
  return (
    <button
      className={`btn btn-${variant}`}
      disabled={disabled}
    >
      {label}
    </button>
  );
}

// Usage
<Button label="Submit" />                          // variant defaults to 'primary'
<Button label="Cancel" variant="secondary" />          // explicit variant
<Button label="Delete" variant="danger" disabled />   // boolean prop without value = true

The Children Prop

There is a special prop called children that represents whatever you put between a component's opening and closing tags:

interface CardProps {
  title: string;
  children: React.ReactNode;  // ReactNode = any renderable content
}

function Card({ title, children }: CardProps) {
  return (
    <div className="card">
      <h2>{title}</h2>
      <div className="card-body">
        {children}
      </div>
    </div>
  );
}

// Usage - anything between the tags becomes children
<Card title="Customer Info">
  <p>Name: John Smith</p>
  <p>Email: john@example.com</p>
</Card>

<Card title="Ticket Details">
  <TicketForm />
  <TicketHistory />
</Card>

The children prop makes components extremely flexible. The Card component does not need to know what will be inside it. It just provides the wrapper (border, padding, title), and the parent decides the content.

Props Are Read-Only: A component must never modify its own props. Props flow down from parent to child, and the child treats them as read-only data. If you need data that changes, you need state (covered in Lesson 13).

Rendering Lists with .map()

Displaying a list of data is one of the most common things you do in React. Since you cannot use for loops inside JSX (they are statements, not expressions), you use the array .map() method to transform an array of data into an array of JSX elements:

interface Service {
  id: number;
  name: string;
  price: number;
}

const services: Service[] = [
  { id: 1, name: 'Virus Removal', price: 79 },
  { id: 2, name: 'Data Transfer', price: 49 },
  { id: 3, name: 'OS Installation', price: 59 },
];

function ServiceList() {
  return (
    <ul>
      {services.map(service => (
        <li key={service.id}>
          {service.name} — ${service.price}
        </li>
      ))}
    </ul>
  );
}

Let us trace through what happens: .map() takes each item in the services array and returns a <li> element. The result is an array of three <li> elements, which React happily renders inside the <ul>.

Why Keys Matter

Notice the key={service.id} prop on each <li>. The key prop is a requirement when rendering lists in React, and understanding why is crucial.

When your list data changes (an item is added, removed, or reordered), React needs to figure out which DOM elements to update. Without keys, React would have to compare items by position, which leads to incorrect and inefficient updates.

Without keys (comparison by position): Before: [ Virus Removal, Data Transfer, OS Install ] After: [ Data Transfer, OS Install ] React thinks: Position 0: "Virus Removal" changed to "Data Transfer" (UPDATE) Position 1: "Data Transfer" changed to "OS Install" (UPDATE) Position 2: "OS Install" removed (REMOVE) = 3 operations, 2 are wrong! With keys (comparison by identity): Before: [ id:1 Virus Removal, id:2 Data Transfer, id:3 OS Install ] After: [ id:2 Data Transfer, id:3 OS Install ] React thinks: id:1 is gone (REMOVE just that one element) id:2 and id:3 are unchanged (do nothing) = 1 operation, all correct!

Rules for keys:

  • Keys must be unique among siblings (not globally unique)
  • Keys must be stable — the same item should always get the same key
  • Use a database ID, unique identifier, or other stable unique value
  • Never use array index as a key if items can be reordered, added, or removed (the index is not stable in those cases)
  • Keys are not passed as a prop to the component — they are used internally by React
// Good: stable unique IDs
{tickets.map(ticket => <TicketCard key={ticket.id} ticket={ticket} />)}

// Bad: array index as key (items can be reordered)
{tickets.map((ticket, index) => <TicketCard key={index} ticket={ticket} />)}

// Okay: index as key for truly static lists that never change
{menuItems.map((item, index) => <li key={index}>{item}</li>)}
CSK Connection The gallery page on Computer Store KS uses .map() to render a grid of computer cards from the gallery.json data file. Each computer has a unique ID that serves as the key. The admin ticket list maps over fetched ticket data the same way, using RepairShopr's ticket ID as the key.

Conditional Rendering

Often you want to show different UI depending on some condition: a loading spinner while data loads, an error message when something fails, or different content based on user role. React gives you several patterns for this.

Pattern 1: Ternary Operator

The ternary operator (condition ? valueIfTrue : valueIfFalse) is the most versatile because it handles both the true and false cases:

function TicketStatus({ isOpen }: { isOpen: boolean }) {
  return (
    <span className={isOpen ? 'badge-open' : 'badge-closed'}>
      {isOpen ? 'Open' : 'Closed'}
    </span>
  );
}

Pattern 2: Logical AND (&&)

When you only want to show something when a condition is true (and show nothing otherwise), use &&:

function CustomerCard({ name, hasSilverPlan }: { name: string; hasSilverPlan: boolean }) {
  return (
    <div className="customer-card">
      <h3>{name}</h3>
      {hasSilverPlan && <span className="silver-badge">Silver Plan</span>}
    </div>
  );
}

If hasSilverPlan is true, the badge renders. If false, React renders nothing (it skips false, null, and undefined values).

Watch out for zero! The expression {count && <span>Items</span>} will render the number 0 on screen when count is 0, because 0 is falsy but is a valid React node. Use {count > 0 && <span>Items</span>} instead, which evaluates to false (and renders nothing) when count is 0.

Pattern 3: Early Return

For larger conditional blocks, you can return early from the component function:

interface DataDisplayProps {
  isLoading: boolean;
  error: string | null;
  data: string[];
}

function DataDisplay({ isLoading, error, data }: DataDisplayProps) {
  // Early return for loading state
  if (isLoading) {
    return <div className="spinner">Loading...</div>;
  }

  // Early return for error state
  if (error) {
    return <div className="error">Error: {error}</div>;
  }

  // Early return for empty state
  if (data.length === 0) {
    return <div className="empty">No items found.</div>;
  }

  // Happy path - we have data!
  return (
    <ul>
      {data.map((item, i) => <li key={i}>{item}</li>)}
    </ul>
  );
}

Early return is the cleanest pattern when you have multiple conditions, because each case is handled completely before moving on. The final return is always the "happy path" — when everything is normal.

Component Composition: Building Complex UIs

The real power of React emerges when you compose small, focused components into larger ones. Each component handles one concern.

Analogy: Think of React components like LEGO bricks. A single brick is simple and boring. But combine them and you can build a castle, a spaceship, or anything you can imagine. A <Button /> brick, a <Badge /> brick, and a <Card /> brick combine into a <TicketCard />. Multiple <TicketCard /> bricks form a <TicketList />. Add a <SearchBar /> and some <Filter /> bricks and you have a <TicketDashboard />.

Let us build a realistic example step by step: a product card for a computer store.

// Step 1: Small, focused components

interface PriceBadgeProps {
  price: number;
  salePrice?: number;
}

function PriceBadge({ price, salePrice }: PriceBadgeProps) {
  if (salePrice) {
    return (
      <div className="price-badge">
        <span className="price-original">${price}</span>
        <span className="price-sale">${salePrice}</span>
      </div>
    );
  }
  return <div className="price-badge">${price}</div>;
}


interface SpecListProps {
  specs: string[];
}

function SpecList({ specs }: SpecListProps) {
  return (
    <ul className="spec-list">
      {specs.map((spec, index) => (
        <li key={index}>{spec}</li>
      ))}
    </ul>
  );
}


interface CategoryBadgeProps {
  category: 'desktop' | 'laptop';
}

function CategoryBadge({ category }: CategoryBadgeProps) {
  return (
    <span className={`badge badge-${category}`}>
      {category === 'desktop' ? 'Desktop' : 'Laptop'}
    </span>
  );
}
// Step 2: Compose them into a ProductCard

interface Product {
  id: number;
  name: string;
  category: 'desktop' | 'laptop';
  price: number;
  salePrice?: number;
  imageUrl: string;
  specs: string[];
}

function ProductCard({ product }: { product: Product }) {
  return (
    <div className="product-card">
      <img src={product.imageUrl} alt={product.name} />
      <CategoryBadge category={product.category} />
      <h3>{product.name}</h3>
      <SpecList specs={product.specs} />
      <PriceBadge price={product.price} salePrice={product.salePrice} />
    </div>
  );
}
// Step 3: Compose ProductCard into a ProductList

interface ProductListProps {
  products: Product[];
  title: string;
}

function ProductList({ products, title }: ProductListProps) {
  if (products.length === 0) {
    return <p>No products available.</p>;
  }

  return (
    <section>
      <h2>{title} ({products.length} items)</h2>
      <div className="product-grid">
        {products.map(product => (
          <ProductCard key={product.id} product={product} />
        ))}
      </div>
    </section>
  );
}

Look at how each layer only knows about its immediate children: ProductList knows about ProductCard, and ProductCard knows about PriceBadge, SpecList, and CategoryBadge. Nobody needs to know the whole tree. This is the power of composition.

File Organization and Import/Export

As your application grows, putting all components in one file becomes unmanageable. The standard practice is one component per file, with the file named after the component.

Naming Conventions

Convention Example Notes
File name ProductCard.tsx PascalCase, matches component name
Component name ProductCard PascalCase (required by React)
Props interface ProductCardProps Component name + "Props"
File extension .tsx .tsx for JSX + TypeScript, .ts for non-JSX TypeScript

Export Patterns

// ---- src/components/ProductCard.tsx ----

// Named export (you can have multiple per file)
export interface ProductCardProps {
  product: Product;
}

export function ProductCard({ product }: ProductCardProps) {
  return (
    <div className="product-card">
      {/* ... */}
    </div>
  );
}


// ---- src/components/ProductList.tsx ----

// Import the component from its file
import { ProductCard } from './ProductCard';
// Note: .tsx extension is omitted in imports

export function ProductList({ products }: ProductListProps) {
  return (
    <div>
      {products.map(p => <ProductCard key={p.id} product={p} />)}
    </div>
  );
}

Complete Example: Building a Product Catalog

Let us bring everything together into a complete, working example. This is what a real-world component structure looks like.

// ---- types/product.ts ----
export interface Product {
  id: number;
  name: string;
  category: 'desktop' | 'laptop';
  price: number;
  salePrice?: number;
  imageUrl: string;
  specs: string[];
  inStock: boolean;
}
// ---- components/gallery/ProductCard.tsx ----
import type { Product } from '../../types/product';

interface ProductCardProps {
  product: Product;
}

export function ProductCard({ product }: ProductCardProps) {
  const isOnSale = product.salePrice !== undefined;

  return (
    <div className="product-card">
      {/* Image */}
      <div className="product-image">
        <img src={product.imageUrl} alt={product.name} />
        {isOnSale && <span className="sale-badge">SALE</span>}
      </div>

      {/* Info */}
      <div className="product-info">
        <span className={`badge badge-${product.category}`}>
          {product.category}
        </span>
        <h3>{product.name}</h3>

        {/* Specs */}
        <ul className="spec-list">
          {product.specs.map((spec, index) => (
            <li key={index}>{spec}</li>
          ))}
        </ul>

        {/* Price */}
        <div className="price-section">
          {isOnSale ? (
            <>
              <span className="price-original">${product.price}</span>
              <span className="price-sale">${product.salePrice}</span>
            </>
          ) : (
            <span className="price">${product.price}</span>
          )}
        </div>

        {/* Stock status */}
        <p className={product.inStock ? 'in-stock' : 'out-of-stock'}>
          {product.inStock ? 'In Stock' : 'Out of Stock'}
        </p>
      </div>
    </div>
  );
}

import { ProductCard } from './ProductCard';
import type { Product } from '../../types/product';

interface ProductListProps {
  products: Product[];
}

export function ProductList({ products }: ProductListProps) {
  if (products.length === 0) {
    return (
      <div className="empty-state">
        <h3>No computers available</h3>
        <p>Check back soon for new inventory!</p>
      </div>
    );
  }

  return (
    <div className="product-grid">
      {products.map(product => (
        <ProductCard key={product.id} product={product} />
      ))}
    </div>
  );
}

Key Takeaways

  • React is a declarative library: you describe what the UI should look like, and React figures out how to update the DOM efficiently via the virtual DOM.
  • JSX is JavaScript, not HTML. Use className instead of class, style objects instead of strings, camelCase attributes, and curly braces {} for JavaScript expressions.
  • Components are functions that return JSX. Their names must start with an uppercase letter.
  • Props pass data from parent to child. Always type your props with TypeScript interfaces. Props are read-only.
  • The children prop captures whatever is placed between a component's opening and closing tags, making wrapper components possible.
  • Use .map() to render lists. Every mapped element needs a unique, stable key prop so React can efficiently track changes.
  • Conditional rendering uses ternary (? :) for either/or, && for show-or-nothing, and early return for handling multiple exclusive conditions.
  • Compose complex UIs from small, focused components. Each component should do one thing well.
  • Organize files as one component per file, using PascalCase naming, and group related components into feature folders.
