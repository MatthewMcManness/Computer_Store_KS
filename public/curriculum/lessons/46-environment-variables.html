Environment Variables & Configuration

Keep your secrets safe, your environments separate, and your configuration flexible with environment variables.

What You Will Learn

  • Understand what environment variables are and why they exist
  • Distinguish between development, staging, and production environments
  • Use .env files in Next.js: .env.local, .env.development, and .env.production
  • Understand the NEXT_PUBLIC_ prefix and the critical difference between browser-safe and server-only variables
  • Read environment variables with process.env in both server and client code
  • Create an .env.example file to document every required variable without exposing real secrets
  • Manage environment variables in deployment platforms like Render
  • Validate environment variables at startup for type safety
  • Organize variables by service for maintainability
  • Understand the 12-factor app methodology and why configuration belongs in the environment

What Are Environment Variables?

Imagine you are building a house. The house has a mailbox where the postman delivers letters. The address of the house is not built into the walls -- it is something the outside world assigns to it. If the house were picked up and moved to a different street, the house itself would not need to change; only the address would change.

Environment variables work the same way. They are named values that live outside your code but that your code can read at runtime. Instead of hardcoding a database password directly into a file (which would be like engraving your bank PIN on the front door), you store it in an environment variable. Your code says, "Give me whatever value is stored under the name DATABASE_URL," and the environment provides it.

There are three fundamental reasons environment variables exist:

1. Security: Keeping Secrets Secret

Your application needs sensitive information to function: database passwords, API keys, encryption secrets, email service credentials. These values must never appear in your source code, because source code gets committed to Git, pushed to GitHub, and potentially seen by anyone with access to the repository. Even in a private repository, secrets in code create a permanent security risk -- they live in the Git history forever, even if you delete the file later.

Environment variables solve this by keeping secrets outside of the codebase entirely. The code says process.env.RESEND_API_KEY, and the actual key value is provided by the environment -- whether that is a .env file on your laptop or a configuration panel in Render's dashboard.

2. Per-Environment Configuration

Your application runs in different places with different settings. During development on your laptop, you connect to a local or test database. In production, you connect to the real database with real customer data. The code is identical -- only the configuration changes. Environment variables let you swap configuration without changing a single line of code.

3. Flexibility Without Redeployment

Need to change an email address, rotate an API key, or toggle a feature flag? With environment variables, you update the value in your deployment platform and restart the service. No code changes. No new build. No redeployment of the application.

Analogy: Think of environment variables like the settings on a car's dashboard. The engine (your code) does not change when you adjust the thermostat, switch radio stations, or toggle the headlights. The settings are external knobs that control the engine's behavior without modifying the engine itself.

Understanding Different Environments

A "environment" is the complete context in which your application runs: the machine, the operating system, the installed software, and -- crucially -- the configuration values. Most web applications run in at least two environments, and many use three:

Environment Purpose Who Uses It Data
Development Building and testing features locally You, the developer, on your laptop Test data, dummy accounts, fake API keys
Staging Final testing before production QA team, project reviewers Realistic data, near-production configuration
Production The live site that real users access Customers, employees, the public Real data, real API keys, real money

Each environment needs different values for the same variables. For example:

# Development (.env.local on your laptop)
NEXT_PUBLIC_SUPABASE_URL=https://dev-project.supabase.co
RESEND_API_KEY=re_test_key_for_development
NEXT_PUBLIC_APP_URL=http://localhost:3000

# Production (Render dashboard)
NEXT_PUBLIC_SUPABASE_URL=https://production-project.supabase.co
RESEND_API_KEY=re_live_key_for_production
NEXT_PUBLIC_APP_URL=https://computerstoreks.com

The code is the same in both environments. The line process.env.RESEND_API_KEY works identically in development and production. But the value it returns is different because the environment variable was set differently.

Why Separate Databases Matter Never use the same database for development and production. If you accidentally run a destructive query or test script while developing, it could delete real customer data. Always use a separate Supabase project (or at minimum, separate tables) for development.
CSK Connection Computer Store KS has two Render services: CSK-Production (deploys from the Production branch) and CSK-Development (deploys from the Development branch). Each service has its own set of environment variables configured in the Render dashboard, pointing to different resources where appropriate.

.env Files in Next.js

Next.js has built-in support for .env files. When you start your development server with npm run dev or build your application with npm run build, Next.js automatically reads values from specific .env files and makes them available through process.env.

The .env File Hierarchy

Next.js reads .env files in a specific order. Files loaded later override values from files loaded earlier:

File When Loaded Commit to Git? Purpose
.env Always Yes (if no secrets) Default values for all environments
.env.development npm run dev Yes (if no secrets) Development-specific defaults
.env.production npm run build / npm run start Yes (if no secrets) Production-specific defaults
.env.local Always (except test) No -- never commit Local overrides with real secrets

The loading priority (highest wins) is:

.env.local (highest priority -- your personal secrets) | .env.development (or .env.production depending on mode) | .env (lowest priority -- shared defaults)

.env.local: Your Personal Secrets File

The .env.local file is where you put your actual, real secret values during development. This file is automatically added to .gitignore by create-next-app and should never be committed to Git.

# .env.local -- YOUR actual secrets (never commit this file!)

# Supabase
NEXT_PUBLIC_SUPABASE_URL=https://gzcmwpcxnwlgknhjijic.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
SUPABASE_SERVICE_ROLE_KEY=eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

# Resend (email)
RESEND_API_KEY=re_abc123def456

# Session
SESSION_SECRET=a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2

.env.development and .env.production

These files contain non-secret defaults that are safe to commit. They provide sensible values that differ between environments:

# .env.development -- safe to commit (no real secrets)
NEXT_PUBLIC_APP_URL=http://localhost:3000
NODE_ENV=development
NEXT_PUBLIC_ENABLE_ANALYTICS=false

# .env.production -- safe to commit (no real secrets)
NEXT_PUBLIC_APP_URL=https://computerstoreks.com
NEXT_PUBLIC_ENABLE_ANALYTICS=true

When you run npm run dev, Next.js loads .env.development. When you run npm run build, it loads .env.production. In both cases, .env.local overrides any conflicting values.

How It Works Under the Hood Next.js uses the dotenv library to parse .env files. Each line in the format KEY=value is injected into process.env at startup. Lines starting with # are comments. Blank lines are ignored. Values can be quoted with single or double quotes, which is useful for values containing spaces.

The NEXT_PUBLIC_ Prefix: Browser vs. Server

This is one of the most important concepts in Next.js environment variables, and misunderstanding it is one of the most common security mistakes beginners make.

By default, all environment variables are server-only. They are available in API routes, Server Components, and server-side code, but they are completely invisible to the browser. This is a security feature -- it prevents your database passwords and API keys from being sent to users' browsers.

To make an environment variable available in client-side code (React components that run in the browser), you must prefix its name with NEXT_PUBLIC_.

Variable Name Available Server-Side? Available Client-Side? Use For
SUPABASE_SERVICE_ROLE_KEY Yes No Server-only secrets (API keys, passwords)
RESEND_API_KEY Yes No Server-only secrets
SESSION_SECRET Yes No Encryption keys
NEXT_PUBLIC_SUPABASE_URL Yes Yes Public URLs, public keys
NEXT_PUBLIC_APP_URL Yes Yes Public configuration
NEXT_PUBLIC_TURNSTILE_SITE_KEY Yes Yes Keys designed to be public
Critical Security Rule Never add NEXT_PUBLIC_ to a secret value. If you name a variable NEXT_PUBLIC_DATABASE_PASSWORD, that password will be included in the JavaScript bundle sent to every user's browser. Anyone who opens DevTools can see it. The NEXT_PUBLIC_ prefix literally means "send this to every browser that visits the site."

How It Works Technically

During the build process (npm run build), Next.js scans your client-side code for references to process.env.NEXT_PUBLIC_* and performs a string replacement. The variable reference is replaced with the actual value at build time:

// What you write in your code:
const supabaseUrl = process.env.NEXT_PUBLIC_SUPABASE_URL;

// What the browser receives after build:
const supabaseUrl = "https://gzcmwpcxnwlgknhjijic.supabase.co";

This means NEXT_PUBLIC_ values are baked into the build. If you change them, you need to rebuild and redeploy. Non-public variables, by contrast, are read at runtime and can be changed by simply restarting the server.

Analogy: Think of NEXT_PUBLIC_ variables like a store's public phone number printed on the sign outside. Everyone can see it, and that is fine. Server-only variables are like the safe combination in the back office. Only employees with access to the back office (the server) should know it. You would never print the safe combination on the store sign.

Reading Environment Variables with process.env

In Node.js (and by extension, Next.js), you read environment variables using the process.env object. It is a global object available in any server-side code without any imports.

In API Routes (Server-Side)

// src/app/api/contact/route.ts
import { NextRequest, NextResponse } from 'next/server';
import { Resend } from 'resend';

export async function POST(request: NextRequest) {
  // Read a server-only environment variable
  const resend = new Resend(process.env.RESEND_API_KEY);

  const notificationEmail = process.env.NOTIFICATION_EMAIL;

  // Use the values
  await resend.emails.send({
    from: 'Contact Form <noreply@computerstoreks.com>',
    to: notificationEmail!,
    subject: 'New Contact Form Submission',
    html: '<p>Someone reached out!</p>',
  });

  return NextResponse.json({ success: true });
}

In Server Components

// src/app/page.tsx (Server Component by default)
export default function HomePage() {
  // Server Components can read ALL environment variables
  const dbUrl = process.env.NEXT_PUBLIC_SUPABASE_URL;
  const serviceKey = process.env.SUPABASE_SERVICE_ROLE_KEY; // server-only, works here

  return (
    <main>
      <h1>Welcome</h1>
      {/* Never render secret values in HTML! */}
    </main>
  );
}

In Client Components

// src/components/features/analytics.tsx
'use client';

export function Analytics() {
  // Client Components can ONLY read NEXT_PUBLIC_ variables
  const gaId = process.env.NEXT_PUBLIC_GA_ID;

  // This would be undefined in the browser:
  // const secret = process.env.SESSION_SECRET; // undefined!

  if (!gaId) return null;

  return <script src={`https://analytics.example.com/${gaId}`} />;
}

The TypeScript Type Issue

Every value in process.env is typed as string | undefined in TypeScript. This means you will see type errors if you try to use a value without checking if it exists:

// TypeScript error: Type 'string | undefined' is not assignable to type 'string'
const apiKey: string = process.env.RESEND_API_KEY;

// Solution 1: Non-null assertion (when you are sure it exists)
const apiKey = process.env.RESEND_API_KEY!;

// Solution 2: Default value
const apiKey = process.env.RESEND_API_KEY ?? 'missing-key';

// Solution 3: Runtime check (safest)
const apiKey = process.env.RESEND_API_KEY;
if (!apiKey) {
  throw new Error('RESEND_API_KEY environment variable is not set');
}

Creating .env.example: The Documentation File

Your .env.local file is not committed to Git, which means a new developer joining the project would have no idea what environment variables are needed. The solution is to create a .env.example file that documents every required variable with placeholder values and helpful comments. This file is committed to Git.

The Format

# .env.example -- Copy to .env.local and fill in real values
# This file documents all environment variables needed by the application.
# It is committed to Git. The .env.local file is NOT committed.

# ===========================================
# Supabase (Database & Authentication)
# ===========================================
# Dashboard: https://supabase.com/dashboard/project/YOUR_PROJECT

# Supabase project URL (safe for client-side)
NEXT_PUBLIC_SUPABASE_URL=https://your-project.supabase.co

# Supabase anon/public key (safe for client-side)
NEXT_PUBLIC_SUPABASE_ANON_KEY=your_supabase_anon_key_here

# Supabase service role key (SERVER-ONLY -- keep secret!)
SUPABASE_SERVICE_ROLE_KEY=your_supabase_service_role_key_here

# ===========================================
# Email Service - Resend
# ===========================================
# Create API key at: https://resend.com/api-keys

RESEND_API_KEY=re_your_resend_api_key_here
NOTIFICATION_EMAIL=contact@yourdomain.com

# ===========================================
# Session Security
# ===========================================
# Generate with: openssl rand -hex 32
# Must be exactly 64 hex characters

SESSION_SECRET=

Best Practices for .env.example

  • Group by service: Organize variables under clear headings (Supabase, Resend, GitHub, etc.)
  • Explain where to find values: Include links to dashboards and setup pages
  • Include generation commands: For secrets that need to be generated (like openssl rand -hex 32)
  • Use placeholder values: Never put real keys in this file, even for a second
  • Note which are public: Mark NEXT_PUBLIC_ variables as safe for client-side
  • Note which are required: Distinguish between required and optional variables
CSK Connection The Computer Store KS .env.example file documents over 40 environment variables organized into clear groups: Application, GitHub Integration, Authentication, Session Security, RepairShopr Integration, Supabase, Resend Email, Cloudflare Turnstile, Google Business Profile, NinjaOne RMM, ESET Protect Cloud, Cytracom Phone System, and Feature Flags. Every variable includes a comment explaining where to find or generate the value. A new developer can copy this file to .env.local and systematically fill in each value.

Never Committing Real Secrets

This point is critical enough to warrant its own section. If a secret value (API key, password, encryption key) ever ends up in a Git commit, it is compromised. Even if you immediately delete the file and make a new commit, the secret still exists in the Git history and can be recovered.

Defense Layer 1: .gitignore

Your .gitignore file should include every file that might contain secrets:

# .gitignore -- environment files with secrets
.env
.env.local
.env.development.local
.env.production.local
.env.test.local

Notice that .env.example is not in this list. That is the documentation file with placeholder values, and it should be committed.

Defense Layer 2: Pre-Commit Awareness

Before every commit, run git status and git diff to review what you are about to commit. If you see a .env file in the list, stop immediately.

# Always review before committing
$ git status
$ git diff --staged

# If you accidentally staged a .env file:
$ git reset HEAD .env.local

Defense Layer 3: What To Do If a Secret Leaks

  1. Rotate the key immediately. Go to the service dashboard (Supabase, Resend, GitHub) and generate a new key. The old key is now compromised.
  2. Update the new key in your deployment platform (Render) and locally (.env.local).
  3. Clean the Git history if the repository is public (use git filter-branch or the BFG Repo Cleaner tool). For private repos, rotating the key is usually sufficient.
Real-World Consequence In 2023, Toyota exposed customer data because a subcontractor accidentally committed an access key to a public GitHub repository. GitHub itself scans for common secret patterns and will alert you, but by the time the alert arrives, automated bots may have already harvested the key. Prevention is far easier than recovery.

Managing Environment Variables in Deployment Platforms

When your application runs on a hosting platform like Render, there are no .env files. Instead, you configure environment variables through the platform's dashboard or configuration file. The platform injects these values into the running application's environment.

Render Dashboard

In Render, you add environment variables in the service's settings page. Each variable has a key and a value. Render stores values encrypted and injects them when the service starts.

# What you see in Render's Environment tab:
# Key                              Value
# ──────────────────────────────   ─────────────────────────────
# NODE_ENV                         production
# RESEND_API_KEY                   re_abc123def456...
# NEXT_PUBLIC_SUPABASE_URL         https://xxx.supabase.co
# SUPABASE_SERVICE_ROLE_KEY        eyJhbGciOi...
# SESSION_SECRET                   a1b2c3d4e5f6...

render.yaml (Infrastructure as Code)

Render also supports defining environment variables in a render.yaml file. Non-secret values can be set directly. Secret values use sync: false to indicate they must be set manually in the dashboard:

services:
  - type: web
    name: my-app-production
    env: node
    envVars:
      # Non-secret: value is set directly in the file
      - key: NODE_ENV
        value: production
      - key: NEXT_PUBLIC_APP_URL
        value: https://myapp.com

      # Secret: must be set manually in Render dashboard
      - key: RESEND_API_KEY
        sync: false
      - key: SUPABASE_SERVICE_ROLE_KEY
        sync: false
      - key: SESSION_SECRET
        sync: false

The sync: false flag means "this variable exists but its value is managed through the dashboard, not this file." This keeps secrets out of your repository while still documenting that the variable is required.

Other Platforms Work Similarly Vercel, Railway, Fly.io, and AWS all have their own ways to set environment variables, but the concept is the same: you configure key-value pairs through a dashboard or CLI, and the platform injects them at runtime. The principles you learn here apply everywhere.

Type Safety: Validating Environment Variables at Startup

One of the most frustrating deployment failures is pushing your code, waiting for the build, and then discovering the app crashes because an environment variable is missing. You can prevent this by validating all required variables when the application starts.

Simple Validation

// src/lib/env.ts -- validate environment variables at import time

function requireEnv(name: string): string {
  const value = process.env[name];
  if (!value) {
    throw new Error(
      `Missing required environment variable: ${name}\n` +
      `Check your .env.local file or Render dashboard.`
    );
  }
  return value;
}

// Server-only variables (will throw at startup if missing)
export const env = {
  supabaseUrl: requireEnv('NEXT_PUBLIC_SUPABASE_URL'),
  supabaseAnonKey: requireEnv('NEXT_PUBLIC_SUPABASE_ANON_KEY'),
  supabaseServiceKey: requireEnv('SUPABASE_SERVICE_ROLE_KEY'),
  resendApiKey: requireEnv('RESEND_API_KEY'),
  sessionSecret: requireEnv('SESSION_SECRET'),
  notificationEmail: requireEnv('NOTIFICATION_EMAIL'),
} as const;

Zod-Based Validation (Recommended for Larger Projects)

For more robust validation, use the Zod library to define a schema for your environment variables. This gives you type safety, transformation, and clear error messages:

// src/lib/env.ts -- Zod-based environment validation
import { z } from 'zod';

const envSchema = z.object({
  // Required server-only variables
  SUPABASE_SERVICE_ROLE_KEY: z.string().min(1, 'Supabase service key is required'),
  RESEND_API_KEY: z.string().startsWith('re_', 'Must be a valid Resend API key'),
  SESSION_SECRET: z.string().length(64, 'Must be exactly 64 hex characters'),
  NOTIFICATION_EMAIL: z.string().email('Must be a valid email address'),

  // Required public variables
  NEXT_PUBLIC_SUPABASE_URL: z.string().url('Must be a valid URL'),
  NEXT_PUBLIC_SUPABASE_ANON_KEY: z.string().min(1, 'Supabase anon key is required'),

  // Optional variables with defaults
  NODE_ENV: z.enum(['development', 'production', 'test']).default('development'),
  NEXT_PUBLIC_ENABLE_ANALYTICS: z.string().transform(v => v === 'true').default('false'),
});

// Validate and export
export const env = envSchema.parse(process.env);

If any variable is missing or invalid, the application fails immediately with a clear error message instead of crashing mysteriously later when the variable is first used.

Organizing Variables by Service

As your application grows, you may end up with dozens of environment variables. Keeping them organized makes them manageable. Group variables by the service or feature they support, and use clear comment headers.

# ===========================================
# Application
# ===========================================
NEXT_PUBLIC_APP_URL=http://localhost:3000
NODE_ENV=development

# ===========================================
# Supabase (Database & Auth)
# ===========================================
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_ANON_KEY=
SUPABASE_SERVICE_ROLE_KEY=

# ===========================================
# Email Service (Resend)
# ===========================================
RESEND_API_KEY=
NOTIFICATION_EMAIL=

# ===========================================
# Authentication
# ===========================================
AUTH_MODE=repairshopr
SESSION_SECRET=
REPAIRSHOPR_SUBDOMAIN=

# ===========================================
# GitHub Integration (Gallery Images)
# ===========================================
GITHUB_TOKEN=
GITHUB_OWNER=
GITHUB_REPO=
GITHUB_BRANCH=

# ===========================================

# ===========================================

This organizational pattern makes it easy to find the variable you need, understand what each service requires, and onboard new developers quickly.

The 12-Factor App: Configuration in the Environment

The 12-factor app methodology is a set of best practices for building modern web applications, originally published by developers at Heroku. Factor number three states:

"Store config in the environment. An app's config is everything that is likely to vary between deploys (staging, production, developer environments). Config should be strictly separated from code."

This principle drives everything we have learned in this lesson. The idea is simple but powerful: the same code should run in any environment without modification. The only things that change between environments are the environment variables.

This matters because:

  • No code changes for deployment: The code deployed to production is identical to the code tested in development. Only the configuration differs.
  • No secrets in code: Credentials never touch the codebase.
  • Easy scaling: Spinning up a new instance just means setting the same environment variables.
  • Easy rotation: API keys can be rotated by updating the environment variable and restarting, with zero code changes.
The Other 11 Factors The 12-factor methodology also covers codebase management, dependencies, backing services, build/release/run stages, processes, port binding, concurrency, disposability, dev/prod parity, logs, and admin processes. You will encounter many of these principles throughout this phase of the curriculum.

Key Takeaways

  • Environment variables store configuration and secrets outside your code, keeping them secure and flexible across environments.
  • Next.js loads .env files automatically: .env.local for your secrets (never committed), .env.development and .env.production for safe defaults (committed).
  • The NEXT_PUBLIC_ prefix makes a variable available in the browser. Never prefix secret values with NEXT_PUBLIC_.
  • Use process.env.VARIABLE_NAME to read environment variables in your code.
  • Create a .env.example file that documents every variable with placeholder values, organized by service. Commit this file to Git.
  • Validate environment variables at startup to catch missing values immediately instead of discovering them at runtime.
  • Deployment platforms like Render manage environment variables through dashboards or config files. Use sync: false in render.yaml for secrets.
  • The 12-factor app methodology teaches us to strictly separate configuration from code, storing it in the environment.
  • If a secret is ever committed to Git, rotate the key immediately -- deleting the commit is not enough.
