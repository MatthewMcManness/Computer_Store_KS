1. Executive Summary

Computer Store KS is already a Next.js 14.2 App Router project. This migration is an upgrade + restructuring, not a framework change. The plan combines three objectives:

  1. Upgrade to Next.js 15 with React 19 for modern features and performance
  2. Strip the employee portal down to only In-Store Manager and Gallery Manager, removing ~60% of admin code
  3. Restructure the remaining codebase for optimal Server Component usage, eliminating unnecessary client-side JavaScript

3. Migration Improvements

Performance Gains

Before (Next.js 14, Current)

  • 0 statically generated pages (all force-dynamic)
  • TTFB 200-500ms for static content pages
  • Homepage: 146 kB First Load JS
  • Gallery: 152 kB First Load JS
  • 89 client component files shipping to browser
  • All pages SSR'd on every request

After (Next.js 15, Optimized)

  • 15-18 statically generated pages (CDN-cached)
  • TTFB <50ms for static pages via CDN
  • Homepage: ~65 kB First Load JS
  • Gallery: ~80 kB First Load JS
  • ~15 client component files (only interactive parts)
  • Static pages pre-built, dynamic pages stream via Suspense

Key Next.js 15 Features to Leverage

FeaturePartial Prerendering (PPR)

Static shell renders instantly while dynamic parts stream in. The gallery page can have its layout statically prerendered while the photo grid loads from Supabase.

FeatureServer Actions

Replace API route handlers with inline 'use server' functions for mutations. Type-safe, no separate API routes needed for CRUD operations.

FeatureTurbopack (Stable)

10x faster dev server builds. Run next dev --turbopack for near-instant hot reloads during development.

FeatureEnhanced Streaming

Replace manual isLoading + useState patterns with <Suspense fallback={<Skeleton/>}> boundaries for cleaner async UI.

FeatureDynamic Sitemap/Robots

app/sitemap.ts and app/robots.ts auto-generate from your routes and data, keeping SEO artifacts always in sync.

FeatureReact 19 Improvements

Improved error handling, use() hook for promises, simplified ref forwarding (no more forwardRef), better hydration error messages.

Critical Blockers to Address Before Starting

1. No Test Framework There is no Jest, Vitest, or any test runner in package.json. The 7 test files are dead code. Install Vitest and write smoke tests for all kept features BEFORE making any changes.
2. TypeScript Errors Suppressed next.config.mjs has typescript.ignoreBuildErrors: true. React 19 type changes will be silently ignored during build, shipping broken code. Set this to false and fix all type errors before upgrading.
3. Monolithic supabase.ts (2,522 lines) This single file contains database functions for ALL features. When removing admin features, carefully verify which functions are still needed by kept features and the public site before deleting anything.

Specific Breaking Changes

Async params/searchParams (Next.js 15)

In Next.js 15, params and searchParams in pages and route handlers become Promises. The codebase is in a mixed state:

Pages using useSearchParams() without a <Suspense> boundary will crash. Affected pages:

  • src/app/(public)/in-store-pcs/page.tsx

  • src/app/admin/in-store/page.tsx (being kept)

10. Deployment & Rollback Plan

Deployment Strategy

Blue-Green via Render: Render performs zero-downtime deployments. If the build succeeds but health check fails, the old version stays live. This provides natural rollback protection.

  1. All work on Development branch
  2. Deploy to Render Development service for testing
  3. After full verification, merge to Production
  4. Render auto-deploys and health-checks
  5. If health check fails, old version remains live

Rollback Plan

If Production deployment fails:

# Render will auto-rollback if health check fails
# If manual rollback needed:
git revert HEAD
git push origin Production
# Render will rebuild from the reverted state

If issues discovered after deployment:

# Option 1: Quick revert
git revert HEAD
git push origin Production

# Option 2: Redeploy previous commit via Render dashboard
# Go to Render → Service → Deploys → Redeploy previous

Expected Downtime

Expected: Zero downtime Render's zero-downtime deployment means the old version serves traffic until the new version is built, deployed, and health-checked. Users should never see an error page during the migration.
