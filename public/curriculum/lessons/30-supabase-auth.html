Supabase Auth: Built-In Authentication

Supabase provides a complete authentication system out of the box. Instead of building login, signup, password reset, and email verification from scratch, Supabase handles all of this for you. You just need to configure it and call the right functions.

What Supabase Auth Provides

  • Email/password signup and signin -- with automatic password hashing
  • Email verification -- confirmation emails sent automatically
  • Password reset -- "forgot password" flow built in
  • OAuth providers -- Google, GitHub, Facebook, etc.
  • Magic links -- passwordless login via email
  • Session management -- JWT-based sessions with automatic refresh
  • Row-Level Security integration -- auth.uid() in RLS policies

Setting Up Auth in the Supabase Dashboard

Before writing any code, you need to configure auth settings in your Supabase project dashboard:

  1. Go to your Supabase project dashboard and click Authentication in the sidebar.
  2. Under Providers, enable Email (it is usually on by default).
  3. Configure email settings:
    • Enable or disable "Confirm email" (recommended: enable for production)
    • Set minimum password length (recommended: 12 characters)
    • Customize email templates for confirmation, password reset, and magic links
  4. Under URL Configuration, set your site URL and redirect URLs:
    • Site URL: https://yourdomain.com
    • Redirect URLs: https://yourdomain.com/auth/callback
  5. For OAuth (e.g., Google): click the provider, enter your Client ID and Client Secret from Google Cloud Console, and add your redirect URI.

The Auth Flow: Signup to Session

1. Signup

Creating a new user account with Supabase Auth:

import { createClient } from '@supabase/supabase-js';

const supabase = createClient(
  process.env.NEXT_PUBLIC_SUPABASE_URL!,
  process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!
);

// Sign up a new user
const { data, error } = await supabase.auth.signUp({
  email: 'user@example.com',
  password: 'securePassword123!',
  options: {
    data: {
      full_name: 'Jane Smith',  // Custom metadata stored with the user
    },
    emailRedirectTo: 'https://yourdomain.com/auth/callback',
  },
});

if (error) {
  console.error('Signup failed:', error.message);
} else {
  console.log('Check your email for verification link!');
  // data.user contains the new user object
  // data.session may be null until email is verified
}

After calling signUp(), Supabase sends a confirmation email. The user clicks the link, which redirects them to your emailRedirectTo URL with a verification token.

2. Email Verification

When the user clicks the verification link in their email, Supabase handles the verification automatically. Your /auth/callback route just needs to exchange the token for a session:

// app/auth/callback/route.ts
import { NextResponse } from 'next/server';
import { createServerClient } from '@supabase/ssr';
import { cookies } from 'next/headers';

export async function GET(request: Request) {
  const { searchParams } = new URL(request.url);
  const code = searchParams.get('code');

  if (code) {
    const cookieStore = await cookies();
    const supabase = createServerClient(
      process.env.NEXT_PUBLIC_SUPABASE_URL!,
      process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
      {
        cookies: {
          getAll() { return cookieStore.getAll(); },
          setAll(cookiesToSet) {
            cookiesToSet.forEach(({ name, value, options }) => {
              cookieStore.set(name, value, options);
            });
          },
        },
      }
    );

    // Exchange the code for a session
    await supabase.auth.exchangeCodeForSession(code);
  }

  return NextResponse.redirect(new URL('/dashboard', request.url));
}

3. Sign In

// Sign in an existing user
const { data, error } = await supabase.auth.signInWithPassword({
  email: 'user@example.com',
  password: 'securePassword123!',
});

if (error) {
  console.error('Login failed:', error.message);
  // Common errors:
  // "Invalid login credentials" - wrong email or password
  // "Email not confirmed" - user hasn't verified their email
} else {
  console.log('Logged in as:', data.user.email);
  // data.session contains the JWT access token and refresh token
}

4. Getting the Current User

// Get the currently authenticated user (server-side)
const { data: { user }, error } = await supabase.auth.getUser();

if (user) {
  console.log('Current user:', user.id, user.email);
  console.log('Metadata:', user.user_metadata);  // { full_name: 'Jane Smith' }
} else {
  console.log('No user logged in');
}
getUser() vs getSession(): Always use getUser() on the server side. It verifies the JWT with Supabase's servers. getSession() reads the JWT from the cookie without verification, which means a tampered token could pass. For security, trust getUser().

5. Sign Out

// Sign out the current user
const { error } = await supabase.auth.signOut();
// This clears the session cookies

Server-Side Auth with @supabase/ssr

In a Next.js App Router application, authentication needs to work on the server -- in Server Components, API routes, and middleware. The @supabase/ssr library manages Supabase sessions using cookies, which are accessible on both the client and server.

Creating a Server-Side Supabase Client

// lib/supabase-server.ts
import { createServerClient } from '@supabase/ssr';
import { cookies } from 'next/headers';

export async function createSupabaseServerClient() {
  const cookieStore = await cookies();

  return createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      cookies: {
        getAll() {
          return cookieStore.getAll();
        },
        setAll(cookiesToSet) {
          try {
            cookiesToSet.forEach(({ name, value, options }) => {
              cookieStore.set(name, value, options);
            });
          } catch {
            // Ignore errors in Server Components (read-only context)
          }
        },
      },
    }
  );
}

This client reads and writes Supabase session cookies. The @supabase/ssr library handles cookie splitting for large JWTs (Supabase tokens can exceed the 4KB cookie size limit, so the library splits them across multiple cookies).

Why cookies instead of localStorage? localStorage is only accessible from JavaScript in the browser. Server Components and middleware cannot read localStorage. Cookies, on the other hand, are automatically sent with every HTTP request, making them accessible everywhere -- browser, server components, API routes, and middleware.

Password Hashing with bcryptjs

While Supabase Auth handles password hashing internally for users in its auth system, you sometimes need to hash passwords yourself -- for example, when building a custom authentication system alongside Supabase, or when migrating users from a legacy system.

Installing bcryptjs

npm install bcryptjs
npm install --save-dev @types/bcryptjs  # TypeScript types

We use bcryptjs (a pure JavaScript implementation) rather than bcrypt (a native C++ addon) because it works in all environments without compilation, including serverless platforms like Render.

Hashing a Password

import bcrypt from 'bcryptjs';

// When user creates an account or changes their password:
const plainPassword = 'mySecurePassword123';
const saltRounds = 12;  // 2^12 = 4096 iterations (good balance of speed/security)

const hashedPassword = await bcrypt.hash(plainPassword, saltRounds);
// Result: "$2a$12$LJ3m5ZWcXY9bN7v1wKsL2.ABC123XYZ..."
// Format: $algorithm$cost$salt+hash

// Store hashedPassword in your database (NEVER the plain password)

Verifying a Password

// When user tries to log in:
const inputPassword = 'mySecurePassword123';  // What user typed
const storedHash = '$2a$12$LJ3m5ZWcXY9bN7v1wKsL2.ABC123XYZ...';  // From database

const isValid = await bcrypt.compare(inputPassword, storedHash);
// Returns true if password matches, false otherwise

if (isValid) {
  // Create session, redirect to dashboard
} else {
  // Show "Invalid credentials" error
}

Notice that bcrypt.compare() extracts the salt from the stored hash automatically. You do not need to store the salt separately -- it is embedded in the hash string itself.

CSK Connection CSK uses bcryptjs for hashing passwords when creating customer portal accounts. The auth.ts file contains legacy password handling alongside the newer Supabase Auth integration. This dual system exists because CSK migrated from RepairShopr authentication to Supabase Auth, and some legacy code paths still use bcrypt directly.

AES-256-GCM: Encrypting Session Data

Sometimes you need more than what Supabase Auth provides. You might need to store additional session data (roles, user type, location) in a cookie, and you want that data to be encrypted so that users cannot read or tamper with it.

What is AES-256-GCM?

AES (Advanced Encryption Standard) is a symmetric encryption algorithm, meaning the same key is used for both encryption and decryption. It is the most widely used encryption algorithm in the world -- your HTTPS connections, your phone's disk encryption, and government classified communications all use AES.

  • 256 -- the key size in bits (32 bytes). Larger keys are more secure.
  • GCM (Galois/Counter Mode) -- a mode that provides both encryption AND authentication. It ensures the data was not tampered with.
Analogy: AES-256-GCM is like a sealed envelope with a tamper-evident seal. The encryption (AES) is the envelope -- only someone with the key can read the contents. The authentication (GCM) is the tamper-evident seal -- if anyone opens and modifies the contents, you will know because the seal will be broken.

Key Concepts

Concept What It Is Size
Key The secret used to encrypt and decrypt 32 bytes (256 bits)
IV (Initialization Vector) A random value that ensures the same data encrypts differently each time 12 bytes for GCM
Auth Tag A checksum that proves the data was not tampered with 16 bytes
Ciphertext The encrypted data Same size as input

Node.js crypto Module

Node.js includes a built-in crypto module for encryption. No external packages needed.

import { randomBytes, createCipheriv, createDecipheriv } from 'crypto';

const ALGORITHM = 'aes-256-gcm';
const IV_LENGTH = 12;        // 12 bytes for GCM mode
const AUTH_TAG_LENGTH = 16;  // 16 bytes authentication tag

Encrypt Function

function encryptSession(sessionData: SessionData): string {
  // 1. Get the 32-byte secret key from environment variable
  const secret = Buffer.from(process.env.SESSION_SECRET!, 'hex');
  // SESSION_SECRET must be exactly 64 hex characters (= 32 bytes)

  // 2. Generate a random Initialization Vector (unique per encryption)
  const iv = randomBytes(IV_LENGTH);  // 12 random bytes

  // 3. Create the cipher (encryption tool)
  const cipher = createCipheriv(ALGORITHM, secret, iv, {
    authTagLength: AUTH_TAG_LENGTH,
  });

  // 4. Encrypt the session data
  const sessionJson = JSON.stringify(sessionData);
  const encrypted = Buffer.concat([
    cipher.update(sessionJson, 'utf-8'),
    cipher.final(),
  ]);

  // 5. Get the authentication tag (tamper-detection checksum)
  const authTag = cipher.getAuthTag();

  // 6. Combine: IV + Auth Tag + Encrypted Data
  const combined = Buffer.concat([iv, authTag, encrypted]);

  // 7. Return as base64 string (safe for cookies)
  return combined.toString('base64');
}

The result is a base64 string that you can safely store in a cookie. It contains the IV, auth tag, and encrypted data packed together.

Decrypt Function

function decryptSession(encryptedString: string): SessionData | null {
  try {
    // 1. Decode from base64 back to a Buffer
    const combined = Buffer.from(encryptedString, 'base64');

    // 2. Extract the three parts
    const iv = combined.subarray(0, IV_LENGTH);                         // First 12 bytes
    const authTag = combined.subarray(IV_LENGTH, IV_LENGTH + AUTH_TAG_LENGTH);  // Next 16 bytes
    const encrypted = combined.subarray(IV_LENGTH + AUTH_TAG_LENGTH);   // The rest

    // 3. Get the same secret key
    const secret = Buffer.from(process.env.SESSION_SECRET!, 'hex');

    // 4. Create the decipher (decryption tool)
    const decipher = createDecipheriv(ALGORITHM, secret, iv, {
      authTagLength: AUTH_TAG_LENGTH,
    });
    decipher.setAuthTag(authTag);  // Set the expected auth tag

    // 5. Decrypt
    const decrypted = Buffer.concat([
      decipher.update(encrypted),
      decipher.final(),  // This THROWS if auth tag doesn't match (tampered!)
    ]);

    // 6. Parse JSON back to session data
    const session = JSON.parse(decrypted.toString('utf-8'));

    // 7. Check expiration
    if (session.expiresAt < Date.now()) {
      return null;  // Session expired
    }

    return session;
  } catch {
    // Decryption failed -- cookie was tampered with or corrupted
    return null;
  }
}
The IV must be unique for every encryption. Never reuse an IV with the same key. That is why we call randomBytes(12) every time we encrypt. Reusing an IV breaks the security of GCM mode and can leak your key.
CSK Connection This is exactly how CSK's session-cookie.ts works. The session data includes userId, supabaseUserId, email, name, role, roles[], userType, location_id, and timestamps. The SESSION_SECRET environment variable must be a 64-character hex string (32 bytes). Sessions expire after 8 hours for employees and 30 days for customers.

Setting Encrypted Session Cookies

Now let us combine encryption with cookie management. After a user authenticates successfully, we create session data, encrypt it, and store it in a cookie:

import { cookies } from 'next/headers';

const SESSION_COOKIE_NAME = 'admin_session';
const SESSION_MAX_AGE = 8 * 60 * 60;  // 8 hours in seconds

async function createUserSession(user: AuthenticatedUser): Promise<void> {
  // 1. Build the session data object
  const sessionData: SessionData = {
    userId: user.id,
    supabaseUserId: user.supabaseId,
    email: user.email,
    name: user.name,
    role: user.role,
    roles: user.roles,          // ['technician', 'social_media']
    userType: user.userType,    // 'employee' or 'customer'
    apiToken: '',               // Deprecated field, kept for compatibility
    createdAt: Date.now(),
    expiresAt: Date.now() + (SESSION_MAX_AGE * 1000),
  };

  // 2. Encrypt the entire session object
  const encryptedSession = encryptSession(sessionData);

  // 3. Store in an httpOnly cookie
  const cookieStore = await cookies();
  cookieStore.set(SESSION_COOKIE_NAME, encryptedSession, {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'lax',
    maxAge: SESSION_MAX_AGE,
    path: '/',
  });
}

The encrypted session is a single string stored in one cookie. When the middleware needs to check who the user is, it reads the cookie, decrypts it, and has access to the full session data without any database query.

Reading Sessions in Middleware

Next.js middleware runs before every request. It is the perfect place to check authentication and authorization:

// middleware.ts
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

export async function middleware(request: NextRequest) {
  const { pathname } = request.nextUrl;

  // 1. Skip auth check for public routes
  if (isPublicRoute(pathname)) {
    return NextResponse.next();
  }

  // 2. Read the session cookie
  const sessionCookie = request.cookies.get('admin_session');
  if (!sessionCookie?.value) {
    // No session -- redirect to login
    const loginUrl = new URL('/login', request.url);
    loginUrl.searchParams.set('returnTo', pathname);
    return NextResponse.redirect(loginUrl);
  }

  // 3. Decrypt and validate the session
  const session = decryptSession(sessionCookie.value);
  if (!session) {
    // Invalid or expired session -- redirect to login
    return NextResponse.redirect(new URL('/login', request.url));
  }

  // 4. Check authorization (does this user have permission?)
  if (!canAccessRoute(session.roles, pathname)) {
    // Authenticated but not authorized -- redirect to their dashboard
    return NextResponse.redirect(new URL('/unauthorized', request.url));
  }

  // 5. User is authenticated and authorized -- let the request through
  return NextResponse.next();
}
Why check auth in middleware? Middleware runs at the edge (before your page code). This means unauthorized users are redirected before any page data is fetched or rendered. It is the most efficient and secure place to enforce authentication because the protected page code never executes for unauthorized users.

Login and Logout API Routes

Login Route

// app/api/auth/login/route.ts
import { NextRequest, NextResponse } from 'next/server';
import { cookies } from 'next/headers';

export async function POST(request: NextRequest) {
  try {
    const { email, password } = await request.json();

    // 1. Validate input
    if (!email || !password) {
      return NextResponse.json(
        { error: 'Email and password are required' },
        { status: 400 }
      );
    }

    // 2. Authenticate with Supabase
    const supabase = createFreshClient();
    const { data: authData, error: authError } =
      await supabase.auth.signInWithPassword({
        email: email.toLowerCase(),
        password,
      });

    if (authError || !authData.user) {
      return NextResponse.json(
        { error: 'Invalid email or password' },
        { status: 401 }
      );
    }

    // 3. Get user profile (roles, location, etc.)
    const { data: profile } = await supabase
      .from('user_profiles')
      .select('*')
      .eq('id', authData.user.id)
      .single();

    // 4. Build session data
    const roles = profile?.roles || ['customer'];
    const sessionData = createSessionData({
      userId: profile?.repairshopr_user_id || 0,
      supabaseUserId: authData.user.id,
      email: authData.user.email || email,
      name: profile?.full_name || email.split('@')[0],
      role: mapRolesToSessionRole(roles),
      roles: roles,
      userType: isEmployeeRole(roles) ? 'employee' : 'customer',
    });

    // 5. Encrypt and set cookie
    const encrypted = encryptSession(sessionData);
    const cookieStore = await cookies();
    cookieStore.set('admin_session', encrypted, {
      httpOnly: true,
      secure: process.env.NODE_ENV === 'production',
      sameSite: 'lax',
      maxAge: 8 * 60 * 60,
      path: '/',
    });

    // 6. Return success
    return NextResponse.json({
      success: true,
      user: { email: sessionData.email, name: sessionData.name, roles },
    });
  } catch (error) {
    console.error('Login error:', error);
    return NextResponse.json(
      { error: 'Authentication failed' },
      { status: 500 }
    );
  }
}

Logout Route

// app/api/auth/logout/route.ts
import { NextResponse } from 'next/server';
import { cookies } from 'next/headers';

export async function POST() {
  const cookieStore = await cookies();

  // 1. Delete all session cookies
  cookieStore.delete('admin_session');
  cookieStore.delete('user_role');
  cookieStore.delete('user_roles');

  // 2. Sign out of Supabase (clears Supabase session cookies too)
  try {
    const supabase = createFreshClient();
    await supabase.auth.signOut();
  } catch {
    // Continue even if Supabase signout fails
  }

  // 3. Return success
  return NextResponse.json({ success: true });
}

Protected Page Pattern

For server-rendered pages that require authentication, you check the session and redirect if the user is not logged in:

// app/admin/dashboard/page.tsx
import { redirect } from 'next/navigation';
import { getCurrentUser } from '@/lib/auth';

export default async function AdminDashboard() {
  // 1. Get the current user from the session cookie
  const user = await getCurrentUser();

  // 2. If no user, redirect to login
  if (!user) {
    redirect('/login?returnTo=/admin/dashboard');
  }

  // 3. User is authenticated -- render the page
  return (
    <div>
      <h1>Welcome, {user.name}</h1>
      <p>Role: {user.roles.join(', ')}</p>
      {/* Dashboard content */}
    </div>
  );
}

This pattern provides defense in depth: the middleware checks auth first (blocking the request before the page loads), and the page checks auth again as a safety net in case the middleware is bypassed or misconfigured.

CSK Connection CSK implements all of these patterns. supabase-auth.ts handles Supabase Auth operations (signup, signin, signout, password reset, Google OAuth, magic links). session-cookie.ts uses AES-256-GCM via Node.js crypto for custom session encryption. auth.ts uses bcryptjs for legacy password verification. Login routes in /api/auth/login authenticate via Supabase, create encrypted session cookies, and set separate role cookies for the middleware. The middleware at middleware.ts reads these cookies and enforces permission-based access control.

Key Takeaways

  • Supabase Auth provides signup, signin, signout, email verification, password reset, and OAuth out of the box.
  • Use @supabase/ssr for server-side auth in Next.js -- it manages sessions via cookies.
  • Always use getUser() (not getSession()) on the server for security -- it verifies the JWT.
  • Use bcryptjs with salt rounds of 12 for password hashing. The salt is stored inside the hash string automatically.
  • AES-256-GCM provides both encryption (confidentiality) and authentication (tamper detection) for session data.
  • Never reuse an IV -- generate a new random IV for every encryption operation.
  • The SESSION_SECRET must be a 32-byte (64 hex character) cryptographically random key.
  • Login routes: validate input, authenticate, create session, set encrypted cookie. Logout routes: delete cookies, sign out of Supabase.
  • Check auth in middleware (first line of defense) AND in page components (defense in depth).
