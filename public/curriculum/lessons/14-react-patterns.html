The Prop Drilling Problem

In Lesson 13, you learned to "lift state up" when sibling components need to share data. That works well for shallow component trees, but what happens when data needs to travel through many layers?

Prop Drilling Problem: <App> [theme = "dark"] <Layout> passes theme down... <Sidebar> passes theme down... <Navigation> passes theme down... <NavItem> FINALLY uses theme! Every intermediate component must accept and pass a "theme" prop it doesn't even use.

This is called prop drilling — passing data through multiple layers of components that do not need it, just so a deeply nested component can access it. Prop drilling makes code harder to maintain: if you rename the prop or change its type, you have to update every component in the chain.

Context API: Sharing Data Without Prop Drilling

React's Context API lets you create a "broadcast channel" that any component in the tree can tune into, regardless of how deeply nested it is. No more passing props through intermediaries.

Step 1: Create a Context

// contexts/ThemeContext.tsx
import { createContext, useContext, useState } from 'react';

// Define the shape of the context value
interface ThemeContextType {
  theme: 'light' | 'dark';
  toggleTheme: () => void;
}

// Create the context with a default value
const ThemeContext = createContext<ThemeContextType | undefined>(undefined);

Step 2: Create a Provider

The Provider is a component that wraps part of your tree and makes data available to all descendants:

// Still in contexts/ThemeContext.tsx
export function ThemeProvider({ children }: { children: React.ReactNode }) {
  const [theme, setTheme] = useState<'light' | 'dark'>('light');

  function toggleTheme() {
    setTheme(prev => prev === 'light' ? 'dark' : 'light');
  }

  return (
    <ThemeContext.Provider value={{ theme, toggleTheme }}>
      {children}
    </ThemeContext.Provider>
  );
}

Step 3: Create a Custom Hook to Consume

// Still in contexts/ThemeContext.tsx
export function useTheme() {
  const context = useContext(ThemeContext);
  if (context === undefined) {
    throw new Error('useTheme must be used within a ThemeProvider');
  }
  return context;
}

The error check is important. If someone accidentally uses useTheme() outside of a <ThemeProvider>, they get a clear error message instead of a mysterious undefined.

Step 4: Wire It Together

// App.tsx - Wrap the tree in the Provider
import { ThemeProvider } from './contexts/ThemeContext';

function App() {
  return (
    <ThemeProvider>
      <Layout>
        <Sidebar />
        <MainContent />
      </Layout>
    </ThemeProvider>
  );
}


// Any deeply nested component - just use the hook!
import { useTheme } from '../contexts/ThemeContext';

function NavItem({ label }: { label: string }) {
  const { theme, toggleTheme } = useTheme();

  return (
    <div className={`nav-item ${theme}`}>
      {label}
      <button onClick={toggleTheme}>Toggle Theme</button>
    </div>
  );
}

// NavItem didn't need Layout, Sidebar, or Navigation to pass theme down!
With Context: <ThemeProvider> [provides theme + toggleTheme] <App> <Layout> (does NOT need theme prop) <Sidebar> (does NOT need theme prop) <Navigation> (does NOT need theme prop) <NavItem> useTheme() -- reads directly!

When to Use Context (and When Not To)

Use Context For Do NOT Use Context For
Theme (light/dark) Data that only one or two components need
Current authenticated user Props that only go 1-2 levels deep
Locale/language preferences Frequently changing data (causes many re-renders)
Feature flags Form data (keep it local to the form)
App-wide configuration Replacing all prop passing (props are good!)
Performance note: When a Context value changes, every component that uses that context re-renders. For frequently changing values (like a search input's text), this can cause performance problems. In those cases, keep the state local or use state management libraries. Context works best for values that change infrequently.

Custom Hooks: Extracting Reusable Logic

Custom hooks are one of React's most powerful patterns. A custom hook is simply a function whose name starts with use that calls other hooks. It lets you extract component logic into reusable functions.

Analogy: If components are like kitchen appliances (toaster, blender, oven), custom hooks are like recipes. A recipe describes a sequence of steps that can be followed by any chef in any kitchen. A useDebounce hook describes a sequence of React operations that can be used by any component.

Custom Hook: useLocalStorage

This hook works like useState, but automatically persists the value to localStorage:

import { useState, useEffect } from 'react';

function useLocalStorage<T>(key: string, initialValue: T): [T, (value: T) => void] {
  // Initialize state from localStorage or use the initial value
  const [storedValue, setStoredValue] = useState<T>(() => {
    try {
      const item = localStorage.getItem(key);
      return item ? JSON.parse(item) : initialValue;
    } catch {
      return initialValue;
    }
  });

  // Sync to localStorage whenever the value changes
  useEffect(() => {
    localStorage.setItem(key, JSON.stringify(storedValue));
  }, [key, storedValue]);

  return [storedValue, setStoredValue];
}

// Usage - works just like useState, but persists across page refreshes
function Settings() {
  const [fontSize, setFontSize] = useLocalStorage('fontSize', 16);

  return (
    <div style={{ fontSize: `${fontSize}px` }}>
      <button onClick={() => setFontSize(fontSize + 2)}>Bigger</button>
      <button onClick={() => setFontSize(fontSize - 2)}>Smaller</button>
      <p>Current size: {fontSize}px</p>
    </div>
  );
}

Custom Hook: useDebounce

Debouncing delays an action until the user stops performing it for a specified time. This is essential for search inputs — you do not want to fire an API request on every single keystroke:

import { useState, useEffect } from 'react';

function useDebounce<T>(value: T, delayMs: number): T {
  const [debouncedValue, setDebouncedValue] = useState(value);

  useEffect(() => {
    // Set a timer to update the debounced value after the delay
    const timer = setTimeout(() => {
      setDebouncedValue(value);
    }, delayMs);

    // Cleanup: if value changes before the delay, cancel the previous timer
    return () => clearTimeout(timer);
  }, [value, delayMs]);

  return debouncedValue;
}

// Usage
function TicketSearch() {
  const [searchTerm, setSearchTerm] = useState('');
  const debouncedSearch = useDebounce(searchTerm, 300); // Wait 300ms after typing stops
  const [results, setResults] = useState<Ticket[]>([]);

  // This effect runs with the DEBOUNCED value, not every keystroke
  useEffect(() => {
    if (debouncedSearch.length < 2) return;

    fetch(`/api/tickets?q=${debouncedSearch}`)
      .then(r => r.json())
      .then(setResults);
  }, [debouncedSearch]);

  return (
    <div>
      <input
        value={searchTerm}
        onChange={e => setSearchTerm(e.target.value)}
        placeholder="Search tickets..."
      />
      {results.map(t => <div key={t.id}>{t.subject}</div>)}
    </div>
  );
}

Custom Hook: useMediaQuery

This hook detects whether a CSS media query matches, useful for responsive behavior in JavaScript:

function useMediaQuery(query: string): boolean {
  const [matches, setMatches] = useState(false);

  useEffect(() => {
    const media = window.matchMedia(query);
    setMatches(media.matches);

    function handleChange(e: MediaQueryListEvent) {
      setMatches(e.matches);
    }

    media.addEventListener('change', handleChange);
    return () => media.removeEventListener('change', handleChange);
  }, [query]);

  return matches;
}

// Usage
function TicketFilters() {
  const isMobile = useMediaQuery('(max-width: 768px)');

  return isMobile
    ? <CollapsibleFilterGrid />   // Mobile: collapsible grid
    : <HorizontalFilterBar />;    // Desktop: horizontal buttons
}

Custom Hook Naming Convention

All custom hooks must start with the word use. This is not just a convention — the React linter uses this to enforce the rules of hooks inside your custom hook.

Hook Name Purpose Returns
useLocalStorage State synced to localStorage [value, setValue]
useDebounce Delayed value after typing stops The debounced value
useMediaQuery CSS media query match boolean
useFetch Generic data fetching { data, error, isLoading }
useBotProtection Spam detection for forms { honeypotProps, validate }
useInteractionTracking Track user mouse/keyboard events { interactionCount }
CSK Connection The Computer Store KS codebase uses custom hooks for bot protection (useBotProtection) and interaction tracking (useInteractionTracking). These hooks encapsulate complex logic — honeypot fields, timing analysis, mouse/keyboard event tracking — behind a simple API that any form component can use with one line of code.

Performance: useCallback and useMemo

Every time a component re-renders, all functions defined inside it are recreated, and all expressions are re-evaluated. Usually this is fine and has no noticeable impact. But in certain situations, you need to optimize.

useCallback: Memoizing Functions

useCallback returns a memoized version of a function that only changes if its dependencies change:

import { useCallback, useState } from 'react';

function ParentComponent() {
  const [count, setCount] = useState(0);
  const [name, setName] = useState('');

  // Without useCallback: a new function is created every render
  // This means ChildComponent re-renders even when only 'name' changed
  const handleClick = () => setCount(c => c + 1);

  // With useCallback: same function reference unless dependencies change
  const handleClickMemoized = useCallback(() => {
    setCount(c => c + 1);
  }, []); // No dependencies - function never changes

  return (
    <div>
      <input value={name} onChange={e => setName(e.target.value)} />
      <ExpensiveChild onClick={handleClickMemoized} />
    </div>
  );
}

useMemo: Memoizing Computed Values

useMemo caches the result of an expensive computation, only recalculating when dependencies change:

import { useMemo, useState } from 'react';

function TicketDashboard({ tickets }: { tickets: Ticket[] }) {
  const [statusFilter, setStatusFilter] = useState<string>('all');

  // Without useMemo: filtering runs on every render
  // With useMemo: only recalculates when tickets or statusFilter change
  const filteredTickets = useMemo(() => {
    console.log('Filtering tickets...'); // Only logs when it actually runs
    if (statusFilter === 'all') return tickets;
    return tickets.filter(t => t.status === statusFilter);
  }, [tickets, statusFilter]);

  // Expensive stats calculation - only recalculate when tickets change
  const stats = useMemo(() => ({
    total: tickets.length,
    open: tickets.filter(t => t.status !== 'completed').length,
    urgent: tickets.filter(t => t.priority === 'high').length,
  }), [tickets]);

  return (
    <div>
      <p>{stats.total} tickets, {stats.open} open, {stats.urgent} urgent</p>
      {/* filter buttons and list */}
    </div>
  );
}
Do not over-optimize! Both useCallback and useMemo add complexity and have their own cost (memory for caching, comparison checks). Only use them when you have a measurable performance problem:
  • A child component re-renders unnecessarily because a function prop changes identity
  • An expensive computation runs on every render when it should not
  • A list of 1,000+ items needs filtered/sorted on every render
For most components, the default behavior (recreate everything each render) is fast enough.

Component Patterns

Container / Presentational Pattern

Separate components into two categories:

  • Container components handle data, state, and side effects (fetching, submitting)
  • Presentational components handle what things look like (pure JSX + props, no side effects)
// Container: handles data logic
function TicketListContainer() {
  const [tickets, setTickets] = useState<Ticket[]>([]);
  const [isLoading, setIsLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    fetch('/api/tickets')
      .then(r => r.json())
      .then(setTickets)
      .catch(e => setError(e.message))
      .finally(() => setIsLoading(false));
  }, []);

  // Delegates rendering to the presentational component
  return (
    <TicketListView
      tickets={tickets}
      isLoading={isLoading}
      error={error}
    />
  );
}


// Presentational: handles display only (no state, no effects)
interface TicketListViewProps {
  tickets: Ticket[];
  isLoading: boolean;
  error: string | null;
}

function TicketListView({ tickets, isLoading, error }: TicketListViewProps) {
  if (isLoading) return <LoadingSpinner />;
  if (error) return <ErrorMessage message={error} />;
  if (tickets.length === 0) return <EmptyState message="No tickets found" />;

  return (
    <ul className="ticket-list">
      {tickets.map(ticket => (
        <TicketCard key={ticket.id} ticket={ticket} />
      ))}
    </ul>
  );
}

The presentational component is easier to test (just pass props and check output) and easier to reuse (it does not care where the data comes from).

Complete Data-Fetching Component Pattern

This pattern combines everything: loading, error, empty, and success states in a single reusable structure:

interface AsyncDataProps<T> {
  isLoading: boolean;
  error: string | null;
  data: T | null;
  renderData: (data: T) => React.ReactNode;
  renderEmpty?: () => React.ReactNode;
}

function AsyncData<T>({ isLoading, error, data, renderData, renderEmpty }: AsyncDataProps<T>) {
  if (isLoading) {
    return <div className="loading">Loading...</div>;
  }
  if (error) {
    return <div className="error">Error: {error}</div>;
  }
  if (!data) {
    return renderEmpty ? renderEmpty() : <div>No data</div>;
  }
  return <>{renderData(data)}</>;
}

// Usage
<AsyncData
  isLoading={isLoading}
  error={error}
  data={tickets}
  renderData={(data) => (
    <ul>{data.map(t => <li key={t.id}>{t.subject}</li>)}</ul>
  )}
  renderEmpty={() => <p>No tickets yet. Create your first ticket!</p>}
/>

Advanced Form Patterns

Form with Validation Feedback

interface FormErrors {
  name?: string;
  email?: string;
  message?: string;
}

function ValidatedContactForm() {
  const [formData, setFormData] = useState({ name: '', email: '', message: '' });
  const [errors, setErrors] = useState<FormErrors>({});
  const [touched, setTouched] = useState<Set<string>>(new Set());

  function validate(data: typeof formData): FormErrors {
    const errs: FormErrors = {};
    if (!data.name.trim()) errs.name = 'Name is required';
    if (!data.email.includes('@')) errs.email = 'Valid email required';
    if (data.message.length < 10) errs.message = 'Message must be at least 10 characters';
    return errs;
  }

  function handleChange(e: React.ChangeEvent<HTMLInputElement | HTMLTextAreaElement>) {
    const { name, value } = e.target;
    const newData = { ...formData, [name]: value };
    setFormData(newData);
    setErrors(validate(newData));
  }

  function handleBlur(e: React.FocusEvent<HTMLInputElement | HTMLTextAreaElement>) {
    setTouched(prev => new Set(prev).add(e.target.name));
  }

  // Only show error if user has interacted with (blurred) the field
  function showError(field: keyof FormErrors): string | undefined {
    return touched.has(field) ? errors[field] : undefined;
  }

  return (
    <form onSubmit={handleSubmit}>
      <div>
        <input
          name="name"
          value={formData.name}
          onChange={handleChange}
          onBlur={handleBlur}
          className={showError('name') ? 'input-error' : ''}
        />
        {showError('name') && <span className="error-text">{showError('name')}</span>}
      </div>
      {/* ... similar for email and message ... */}
    </form>
  );
}

The touched state tracks which fields the user has interacted with. We only show validation errors after the user has left a field (on onBlur), not while they are still typing. This is a much better user experience than showing "Email is required!" before the user even starts typing.

Form Libraries: For complex forms in production, libraries like React Hook Form or Formik handle validation, touched state, dirty tracking, and submission automatically. They are worth learning once you understand the manual patterns shown here.

Preview: The 'use client' Directive

Starting in Lesson 15, you will learn Next.js, which introduces a significant concept: Server Components and Client Components. Here is a preview so the concept is not entirely new when you encounter it.

In Next.js (with the App Router), components are Server Components by default. They run on the server, have no access to browser APIs, and cannot use hooks like useState or useEffect. This is great for performance — the server does the work and sends pre-rendered HTML to the browser.

But some components need interactivity: click handlers, form inputs, browser APIs. These components need the 'use client' directive at the top of their file:

'use client'  // This tells Next.js: "this component runs in the browser"

import { useState } from 'react';

export function SearchBar() {
  const [query, setQuery] = useState('');  // Hooks need 'use client'

  return (
    <input
      value={query}
      onChange={e => setQuery(e.target.value)}  // onClick/onChange need 'use client'
      placeholder="Search..."
    />
  );
}

When do you need 'use client'? When a component uses:

  • Any React hook (useState, useEffect, useRef, custom hooks)
  • Event handlers (onClick, onChange, onSubmit)
  • Browser APIs (window, document, localStorage)

We will explore this in depth in Lesson 16. For now, just know that the hooks and patterns you learned in this lesson and the previous one all require 'use client' in Next.js.

Hands-On Exercises

  1. Build a Theme Context: Create a complete theme system with createContext, a ThemeProvider, and a useTheme hook. Build a toggle button and at least two components that consume the theme. Apply different class names based on the theme.
  2. Build useLocalStorage: Implement the useLocalStorage hook from the lesson. Use it in a settings component that persists the user's preferred font size and color scheme. Verify it survives a page refresh.
  3. Build useDebounce: Implement useDebounce and use it with a search input. Log each API call (or use console.log) to verify that typing "hello" quickly only triggers one search (for "hello"), not five separate searches (for "h", "he", "hel", "hell", "hello").
  4. Container/Presentational split: Take a component that fetches and displays data. Refactor it into a container component (handles data) and a presentational component (handles display). The presentational component should handle loading, error, and empty states via props.
  5. Form with validation: Build a user registration form with name (required), email (must contain @), password (min 8 characters), and confirm password (must match). Show errors only after the user blurs each field. Disable the submit button until all fields are valid.
  6. Feature folder organization: Create a new Vite project and organize it by feature. Build a "Tickets" feature with: TicketCard.tsx, TicketList.tsx, TicketFilter.tsx, and a useTickets.ts custom hook. Put them all in a components/tickets/ folder with an index.ts barrel file that re-exports everything.

Key Takeaways

  • The Context API solves prop drilling by broadcasting data to any descendant component. Create a context, wrap your tree in a Provider, and consume with useContext (or a custom hook). Use Context for infrequently changing global data like theme, auth, and locale.
  • Custom hooks extract reusable logic into functions prefixed with use. They can call other hooks and return any values. Common examples: useLocalStorage, useDebounce, useMediaQuery.
  • useCallback memoizes functions and useMemo memoizes computed values. Only use them when you have a measurable performance problem — premature optimization adds complexity for no benefit.
  • The container/presentational pattern separates data logic from display logic, making components easier to test and reuse.
  • Forms should track touched state and only show validation errors after the user has interacted with each field. For complex forms, consider libraries like React Hook Form.
  • The 'use client' directive in Next.js marks components that need browser interactivity (hooks, event handlers, browser APIs). Server Components are the default and run on the server.
  • Organize components by feature (gallery/, admin/, forms/) rather than by type (components/, hooks/, contexts/) for easier navigation in growing codebases.
